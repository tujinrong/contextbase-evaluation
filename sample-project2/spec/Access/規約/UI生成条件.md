# Access UI生成条件

版1.1／2026-10-29。通常遷移時の初期viewportとタブ見出しの可視性を具体化する。

## 適用と確定前提

2026-10-29の利用者指示「Accessのクラシック風・フォント条件をAgentのルールに明確化」「共通の適合検査を他方式にも横展開」「両方式を再生成し最終成果物でテスト」「その言語の最適な実現方法」を本方式へ適用する。DQA-UI01に対応する確定した生成条件であり、実装済み・受入済みの証拠とは区別する。既存F01～F06、5表48列、業務文字数、認証・権限、初期データと明示保存境界は維持する。

確定した共通の品質条件と、題材固有の業務値を分ける。別方式の画面・認証・DB構成を流用せず、このspecRootの詳細・共通・QAから具体値を固定する。既存の未決・既知設計残件をこのUI改訂で解決済みにしない。

## 方式別の実現

Access生成チェック（AG-BUILD-ACCESS-QUALITY 1.2）のクラシック既定を採用する。Accessの標準未連結単票フォーム、標準入力部品、タブ、標準のメッセージ・確認機能で構成する。画面背景・標準ボタンは落ち着いた灰色、入力面は白、文字は黒を基調とし、Officeテーマ・グラデーション・丸い装飾に見た目を依存させない。標準部品の押下・無効・フォーカスの識別を保つ。検査エラー欄など既存詳細で定める色は意味を保つ例外として記録し、色だけで成否を伝えない。

本文・ラベル・一覧と一覧ヘッダー・ボタン・タブ見出しはYu Gothic UIの11ptを採用する。フォントを持つ実部品と付随ラベルを全件測定し、タブだけを既定フォントへ残さない。標準ダイアログはOS管理範囲として別に記録し、独自部品の検査から黙って除外しない。

基準96DPIのTwips/ptと、各詳細の部品寸法を守る。社員登録の氏名3900twip、カナ4950twip、日付2250twip等は項目ごとの採用値として扱い、同幅へ無断統一しない。収まらない場合は配置・余白・スクロール・タブを工夫し、フォントを縮小して解決しない。外枠・Ribbonと本文の寸法を分け、画面下端の操作まで到達できることを検査する。

初期フォーカス・選択タブ・初期viewportを一組で定義する。通常のメニュー→検索→新規/既存編集・コード画面の開始時は標準フォームの表示原点を上端/左端とし、社員登録は基本情報タブを選び、タブ見出しと指定入力先を表示する。初期化中や処理中の一時フォーカス移動による不要なスクロールを残さない。処理後は操作前の意図した表示位置とフォーカスを保ち、仕様で保持する検索一覧位置は別に扱う。下端操作・取消/保存・両タブ切替後の通常再表示でも確認し、測定直前の強制スクロールで補正した画像だけを合格根拠にしない。

社員番号は先頭ゼロを含む6桁文字列で、新規は実入力可能、編集は選択コピー可能な読取専用とする。標準のInputMask・Format・イベントを適切に組み合わせ、過長貼付を黙って切り詰めず、表示・raw・保存の契約を独立して検査する。入力マスクの採用だけで保存サービスの検査を省略しない。

## 適合と最終成果物

UI適合検査（DOC-UI-CONFORMANCE 1.0）に従い、期待値は根拠文書ID・版・SHAとともに実測より先に固定する。測定結果を期待値へ転記して合格を作らない。規則ID、適用部品、生成設定、最終成果物の実測、試験結果を一対一に追跡し、未観測・未知部品・欠落・旧版の証拠を合格としない。

5画面と社員登録の両タブ・必要な状態を対象とし、フォント・外観・項目寸法・文字切れ・重なり・フォーカス・Tab順・操作到達・新規保存再読込を検査する。Accessは実ACCDBの複製、Webは最終publishの専用fixture hostを使用する。最終成果物と入力manifest、期待値、測定器・テストソースのSHAを記録し、再生成した場合は前版の合格を失効させる。

今回の固定結果はsourceRoot/build/test-results/とbuild/generation/、中間・失敗試行・専用DB/画面コピーはsourceRoot/.tmp/へ置く。利用者の既存ファイル・DB・Office instanceを接収・初期化・終了しない。Office/ブラウザー/DPI/viewport・実施範囲を記録し、未実施のIME・他DPI・製品受入・正式採点は別に残す。
