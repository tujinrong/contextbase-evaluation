# ACE 物理DB定義の詳細設計

版1.0／2026-10-28。sample-project2／Access／detail-design。SQL・DAO記述は設計例であり、ACCDB作成・DDL実行・接続・投入は未実施。

## 対象と型

単一ACCDBのACEテーブルだけを対象にし、基本設計の5表48項目・fieldIds・業務長・NULL・既定値の意味を維持する。物理型だけを実ACE型へ具体化する。SQLServerのschema名・rowversion型・新しい制御表／履歴表は採用しない。[共通実装仕様](../../共通/方式別/01_共通実装仕様.md)のゲートとDAO private Workspaceを使い、同一端末・同一実ファイルの協調する2プロセスを検査対象にする。

文字はACE Unicode。ASCII固定値はTEXT(業務長)、一般Unicodeは最大2 UTF-16単位/scalarに備えTEXT(業務長×2)を確保し、255を超える容量又は長文にはLONGTEXTを使う。業務scalar上限は別検査で、物理容量まで緩和しない。Short Textの物理Sizeで補助文字の業務上限を保証しない。`AllowZeroLength=False`、Long Textは`TextFormat=PlainText`相当・`AppendOnly=False`、文字圧縮を使っても原値を変えない。照合はAccess日本語General相当の配布DBプロファイルを明示し、ASCIIキーは書込前に形式／大文字を検査する。氏名検索のNFKC照合はVBA側で行いDBのlocale順に依存しない。

COUNTERはDAO dbLong＋dbAutoIncrFieldで正のLong範囲、FKはLONG。更新版もLONGで1～2147483647、人数／順序はSHORT、失敗回数はBYTE、YESNOはBoolean（True=-1、False=0）。DATETIMEはDAO dbDateで、join_dateと年月は時刻0、年月は日1、updated_atとlocked_untilはUTCの時点とする。DateTime Extended／大きい数は使わない。UTC属性はACEにtimezone型を追加せずDAO境界で一意に扱う。

## 制約と索引

分冊のPK／NOT NULLをDAO.TableDef／Index／Relation設計へ対応する。Required=TrueとAllowZeroLength=Falseを分ける。任意文字列はNull、任意終了年月・ロック期限はNullとし、空文字や0日付を代入しない。初期値の「有効」はDefaultValue=True、「1」「0」と固定分類は原定義にあるものだけを設定する。自動採番は列属性でDEFAULT値ではない。更新日時／主体はサービスが実値を設定し、固定の過去日時をDB既定にしない。

| 制約ID | 定義・期待 |
| --- | --- |
| PK/UK | PK_T01(user_id)、UK_T01_login(login_id)、PK_T02(employee_id)、UK_T02_no(employee_no)、PK_T03(career_id)、PK_T04(category_id)、PK_T05(category_id,code)。キー更新／連鎖更新を禁止 |

ACEでCHECK句の実行経路差に依存しないため、本版はDAO Field/TableDef.ValidationRuleとRelation／Indexの作成仕様を正本とする。SQL DDL例を読むだけで検査が適用済みとしない。固定在籍3値の名称・順序・有効もF06入口と保存時に拒否する。DB直接編集をDEMO認可の保護対象へ拡張しない。

## DAOパラメータ

SELECT/UPDATE/DELETEは一時QueryDefの明示Parametersを使う。`Long`はDAO.dbLong、`Short`はdbInteger、`Byte`はdbByte、`YesNo`はdbBoolean、`DateTime`はdbDate、ShortTextはdbTextと物理Size、LongTextはDAO Field.Type=dbMemoの実表へdynaset.Fields.Valueで代入する。必須値はNullを渡す前に拒否し、任意値はVariant/Nullをそのまま渡す。文字列の引用符や年月リテラルを連結しない。

```sql
PARAMETERS pId Long;
SELECT * FROM m_employee
WHERE employee_id=pId;
```

参照はpIdだけを渡す。版照合は取得したrevisionと保存要求のExpectedRevisionをサービスで比較し、更新例は次の条件を使う。

```sql
PARAMETERS pId Long, pExpected Long, pName Text(80),
 pAt DateTime, pActor Text(40), pNext Long;
UPDATE m_employee
SET employee_name=pName, updated_at=pAt,
 updated_by=pActor, revision=pNext
WHERE employee_id=pId AND revision=pExpected;
```

上例は氏名だけを変える場合の差分説明で、F04全項目の更新定義を代替しない。`q.Execute dbFailOnError`直後の`q.RecordsAffected=1`だけを期待成功とする。0件は対象再照会で不存在／版不一致を分け、2件以上はMSG-020。新規社員／経歴のCOUNTERはdynaset AddNew/Update/LastModifiedで同じRecordsetから取得する。社員番号・分類コードにMAX+1や数値採番を適用しない。

LongTextを含むF04親子と初期検証情報は、キーだけを明示Parametersで渡したSELECTからdbOpenDynasetを開き、Edit/AddNew後Fields.Valueへ値を代入してUpdateする。DAOのAccess WorkspaceではParameter.Typeは読取専用であり、後付けdbMemo指定を行わない。Nullを保持して255字のTEXTへ変換せず、更新対象Recordsetの0/1件を検査し、同じゲート／Workspace／親版を全操作の前後で照合する。実1000scalarの往復はDQA-A03の未実施検証とする。

## 保存と初期化

社員全体の親版比較→コード／所有／上限→差分→親1→既存子の明示除去／差分更新→新規子→最終件数→Commitを同じWorkspace／ゲートで行う。親のカスケード削除・全子削除再挿入・独立子Commitをしない。親番号／ID・既存子ID／親ID・固定分類・作成済み他行を変更しない。

初期化は[共通実装仕様](../../共通/方式別/01_共通実装仕様.md)と[初期確認データ](../../共通/06_初期確認用データ.md)の新規staging専用。3分類→9コード→2利用者→3社員→3経歴を同じ確定単位へ置き、全検査後のみ配布候補へする。利用者IDはSP2ADMIN/SP2STAFF、監査実行主体とUTCを実投入時に設定する。投入済みmanifestはDB外の配布記録で、6表目や業務列を増やさない。暗号情報・実秘密をmanifestへ載せない。

今回の物理設計は未適用である。参照整合・ValidationRule・Unicode補助文字・dbMemo・採番・Rollback・同時確定・Commit結果不明・5表／48項目の読戻しは実装工程の検証対象とする。
