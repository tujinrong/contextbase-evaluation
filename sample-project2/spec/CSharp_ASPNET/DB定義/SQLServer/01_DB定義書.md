## 型・制約・索引

Unicode文章と利用者ID/更新者はnvarchar、容量は論理スカラー上限の2倍UTF-16単位とする。nvarchar(80)の氏名を80スカラーへ拡張せず、アプリのRuneLength=40を正本とする。DBはLatin1_General_100_BIN2で原値を保持し、幅/空白を推測統合しない。ログインIDだけASCII varchar(20)・Latin1_General_100_CI_ASで英字大小無視一意。番号/コードはchar(6)/char(2)、分類はvarchar(24)、内部IDはbigint、版はint、チーム人数/並び順はsmallint、真偽bit、年月/入社日date、UTC時点datetime2(7)。以下のSQLパラメーター略記で末尾?はDBNull許可、nvarchar(n)/varchar(n)/char(n)のnはSqlParameter.Size（nvarcharはUTF-16単位）を表す。?のない値は非NULL、数値/日付のSizeは指定しない。型・Size・NULLは各TABLEと当索引で照合する。SQL文字列リテラルはnvarcharにはNを付ける。C# SqlParameterは型とSizeを明示し、AddWithValueを使わない。

一意制約UQ_app_user_login(login_id)、UQ_employee_no(employee_no)。FK_career_employee(employee_id)、FK_code_category(category_id)、FK_employee_department(department_category,department_code)、FK_employee_employment(employment_category,employment_status)、FK_career_role(role_category,role_code)。すべてON UPDATE NO ACTION/ON DELETE NO ACTION。監査updated_byは当時の主体ID記録で、初期マスタ→利用者投入順と履歴保存を維持するためFKを追加しない。利用者・社員・分類・コードの物理DELETE権限をWebサービス主体へ与えず、経歴DELETEだけ親保存トランザクションで許可する。

CHECKは社員番号6桁、コード01～99、固定分類列の値、ADMIN/STAFF、failed_count 0～5、版1～2147483647、人数/並び順1～999、年月DAY=1、開始≦終了、入社日/開始月≧1900年、NULL/必須を対象とする。現在業務日/参照有効性/社員200人/経歴20行/完全重複は保存時サービスの同一ゲート内再検査で保証し、GETDATE依存CHECKや推定一意索引へ置換しない。固定在籍3値の名称/順序/有効はサービスで変更拒否し、固定3値の照合を起動時とF06読取時に行う。管理用直接更新も同じゲート/制約契約に従い、契約外直接改変は検知してMSG-020にする。

索引はPK/UQに加えIX_employee_department_status(department_category,department_code,employment_category,employment_status,employee_no)、IX_career_employee_month(employee_id,start_month DESC,career_id DESC)。検索氏名は保存列を増やさず.NETで照合するため専用氏名キー索引を設けない。小規模200人/4000経歴で過剰索引を増やさず、採否の性能は実装時に計測する。

## 接続と確定境界

Microsoft.Data.SqlClientを採用。接続先は明示設定だけ、Integrated Security/Encrypt=True/TrustServerCertificate=False、DB名は許可リストでSampleProject2_Careerへ固定する。接続秘密はサーバーのサービス主体/秘密管理に限定。Web側主体は5表の必要SELECT、社員/経歴/コード及び認証制御の必要DMLだけ、スキーマ変更/管理者権限なし。DB所有者/DDL/初期設定主体を分離する。未指定の既存DBを探索・自動初期化しない。

全業務保存、コード保守、認証失敗/成功更新、利用者停止/役割/検証情報の管理更新は同一DBのsp_getapplock resource=N'SP2.Career.WriteGate'、DbPrincipal=public、LockOwner=Transaction、LockMode=Exclusive、LockTimeout=10000を使う。帳票/検索/一括編集読取は同じ資源をShared＋Serializableで短時間保持する。同一プロセスのSemaphoreだけへ依存しない。lockの順は画面状態→DB applock→利用者→社員番号順→経歴ID順→コードキー順とし逆順を作らない。

```sql
SET XACT_ABORT ON;
SET LOCK_TIMEOUT 10000;
SET TRANSACTION ISOLATION LEVEL SERIALIZABLE;
BEGIN TRANSACTION;
DECLARE @gate int;
EXEC @gate=sys.sp_getapplock
 @Resource=N'SP2.Career.WriteGate', @LockMode=@lockMode,
 @LockOwner='Transaction', @LockTimeout=10000, @DbPrincipal='public';
-- @lockMode varchar(32): write=Exclusive / read=Shared、呼出元固定値
-- @gate < 0ならDB操作を開始せずROLLBACK。0/1は取得成功。
-- 現在認可・対象版・参照・件数・差分→必要なDMLと期待件数照合。
-- 全成功時だけ呼出元UnitOfWorkがCOMMIT。失敗はROLLBACK。
```

トランザクションはサービスだけが所有し、Repositoryはcommitしない。CommandTimeout=30秒、applock/DBロック待ち10秒。-1/1222の未確定確認済み待ち超過MSG-027、-2は要求取消、-3/1205は全取消確認後MSG-017、-999は構成異常。SQL2601/2627は制約名で社員番号MSG-006/コードMSG-022へ変換。547は入力参照ならMSG-016、既存データ異常ならMSG-020、その他は取消確認時MSG-017。CommitAsync送信後の通信例外はMSG-034/成否不明を優先し、自動再送しない。commit応答喪失時にrollback要求成功と見えても確定成否を断定しない。

Snapshot isolation設定は変更せず、上記のShared/Exclusiveゲート＋Serializableで同じ読取時点を固定する。読取完了でcommit/接続解放し、ClosedXML生成中は保持しない。受渡前再認可は新しい短いShared読取として利用者1件だけを現在値で確認する。

## 読取りSQL

SQL-AUTH（F01/F02/全保護操作）:

```sql
SELECT user_id,login_id,display_name,password_verifier,role_id,is_enabled,
 failed_count,locked_until
FROM dbo.m_app_user WHERE login_id=@loginId;
-- @loginId varchar(20)、0/1件。保護操作はuser_id=@actor nvarchar(40)を使用。
```

F01はExclusiveゲート下で現在失敗回数/ロックUTCを照合し、同一現在行に対しfailed_count/locked_untilだけを更新する。SuccessRehashNeededでも認証成功として扱うだけでpassword_verifierは更新しない。利用者に存在しない業務revisionを追加しない。ロック中は更新0。不存在は外部MSG-001。DB異常/失敗制御属性異常は内部Outcome/受付番号記録でIntegrity/DB障害/成否不明を区別するが、F01のController境界では照会/確定/制御異常も外向きMSG-001へ統一し、MSG-020/017等の内部原因やID存在を外へ出さない。認証Cookieは発行しない。

SQL-SEARCH（F03）:

```sql
SELECT e.employee_id,e.employee_no,e.employee_name,e.employee_kana,
 e.department_category,e.department_code,e.employment_category,
 e.employment_status,e.join_date,d.code_name AS department_name,
 s.code_name AS employment_name
FROM dbo.m_employee e
LEFT JOIN dbo.m_code d ON d.category_id=e.department_category
 AND d.code=e.department_code
LEFT JOIN dbo.m_code s ON s.category_id=e.employment_category
 AND s.code=e.employment_status
WHERE (@employeeNo IS NULL OR e.employee_no=@employeeNo)
 AND (@department IS NULL OR e.department_code=@department)
 AND (@status IS NULL OR e.employment_status=@status)
ORDER BY e.employee_no;
```

@employeeNo char(6)?、@department/@status char(2)?。先に固定分類・候補存在を確認する。氏名/カナは全候補行を同じ読取単位で.NETのNFKC/空白除去/大小無視へ正規化してNameKeyのOrdinal部分一致を適用し、最終一致の201件目でMSG-010/結果0とする。名前条件適用前のTOP(201)で切ると正しい一致を失うため付けない。200人という設計不変条件と異常fixtureを分ける。参照名称のNULL/複数一致/別分類はMSG-020、停止コードのis_enabledでJOINを削らない。未検索/クリアはSQLを呼ばない。

SQL-EMPLOYEE/CAREERS（F04/F05、同じTx内）:

```sql
SELECT employee_id,employee_no,employee_name,employee_kana,
 department_category,department_code,employment_category,employment_status,
 join_date,career_summary,skills,qualifications,self_pr,
 updated_at,updated_by,revision
FROM dbo.m_employee WHERE employee_id=@employeeId;
SELECT career_id,employee_id,start_month,end_month,company_name,project_name,
 description,duties,achievements,technologies,role_category,role_code,
 team_size,phases FROM dbo.t_career WHERE employee_id=@employeeId
ORDER BY start_month DESC,career_id DESC;
SELECT category_id,code,code_name,sort_order,is_enabled
FROM dbo.m_code WHERE category_id IN
 ('DEPARTMENT','EMPLOYMENT_STATUS','PROJECT_ROLE');
```

@employeeId bigint正数、社員期待1、経歴0～20（F05は1～20）、名称辞書は必要複合キーそれぞれ1。全経歴生行数をJOIN前に数え、結合で欠落行を消さない。F04読込集合と親版をScreenStateへ固定する。F05は名前/役割の現在有効性で既存行を落とさず、全量/所有/年月/完全重複/必須を検査する。F06分類候補はm_code_categoryの固定3行、一覧はm_code WHERE category_id=@category ORDER BY sort_order,code（停止含む）、保守1行は(category_id,code)で0/1件。

## 保存SQLとパラメーター

SQL-EMPLOYEE-WRITE（F04-E03）:

```sql
-- 新規：同じExclusive TxでCOUNT社員<200と番号未使用を確認。
INSERT dbo.m_employee(employee_no,employee_name,employee_kana,
 department_category,department_code,employment_category,employment_status,
 join_date,career_summary,skills,qualifications,self_pr,updated_at,updated_by,revision)
OUTPUT INSERTED.employee_id,INSERTED.revision
VALUES(@no,@name,@kana,'DEPARTMENT',@dep,'EMPLOYMENT_STATUS',@status,
 @join,@summary,@skills,@qualifications,@selfPr,@utc,@actor,1);
-- 既存実変更：存在/現在版を先に検査し、無変更の場合は実行しない。
UPDATE dbo.m_employee SET employee_name=@name,employee_kana=@kana,
 department_code=@dep,employment_status=@status,join_date=@join,
 career_summary=@summary,skills=@skills,qualifications=@qualifications,
 self_pr=@selfPr,updated_at=@utc,updated_by=@actor,revision=revision+1
OUTPUT INSERTED.revision
WHERE employee_id=@id AND revision=@expected AND revision<2147483647;
```

パラメーター: @no char6、@name nvarchar80（業務40）、@kana nvarchar160（業務80）、@dep/@status char2、@join date、@summary/@skills/@qualifications/@selfPr nvarchar2000?（各業務1000）、@utc datetime2(7)UTC、@actor nvarchar40（業務20）、@id bigint、@expected int。全期待1件、0は対象消失MSG-019/版MSG-008/上限MSG-039へ再分類。社員番号/管理ID/固定分類は既存更新しない。子だけの変更でもこの親更新を1回行う。無変更はDML0、版/日時/更新者据置。

SQL-CAREER-WRITE（同じTx）:

```sql
DELETE dbo.t_career WHERE employee_id=@parent AND career_id=@career;
UPDATE dbo.t_career SET start_month=@start,end_month=@end,
 company_name=@company,project_name=@project,description=@description,
 duties=@duties,achievements=@achievements,technologies=@technologies,
 role_code=@role,team_size=@team,phases=@phases
WHERE employee_id=@parent AND career_id=@career;
INSERT dbo.t_career(employee_id,start_month,end_month,company_name,project_name,
 description,duties,achievements,technologies,role_category,role_code,team_size,phases)
OUTPUT INSERTED.career_id
VALUES(@parent,@start,@end,@company,@project,@description,@duties,
 @achievements,@technologies,'PROJECT_ROLE',@role,@team,@phases);
```

@parent/@career bigint、@start/@end date（月初・end?）、@company/@project nvarchar200、@description/@duties/@achievements nvarchar2000（成果?）、@technologies nvarchar1000?、@phases nvarchar400?、@role char2、@team smallint。各DML期待1件、同値保持行は0操作、明示除去IDだけDELETE、読込IDと保持/除去集合の過不足を先に検査。子版列を追加しない。件数/所有不正はMSG-025、期待件数異常はMSG-020で親子全rollback。

SQL-CODE-WRITE（F06-E02）:

```sql
INSERT dbo.m_code(category_id,code,code_name,sort_order,is_enabled,
 updated_at,updated_by,revision)
VALUES(@category,@code,@name,@sort,@enabled,@utc,@actor,1);
UPDATE dbo.m_code SET code_name=@name,sort_order=@sort,is_enabled=@enabled,
 updated_at=@utc,updated_by=@actor,revision=revision+1
OUTPUT INSERTED.revision
WHERE category_id=@category AND code=@code AND revision=@expected
 AND revision<2147483647;
```

@category varchar24（DEPARTMENT/PROJECT_ROLEのみ保存可）、@code char2 01～99、@name nvarchar80（40スカラー）、@sort smallint1～999、@enabled bit、@utc datetime2、@actor nvarchar40、@expected int。ADMIN現在認可/固定在籍拒否/複合キー不変/分類99件/現版を同じExclusive Txで検査して各1件。停止はis_enabled変更、参照社員/経歴を更新/削除しない。無変更0件/版競合0件を別結果にする。

## 初期化と検査

物理DDLと投入の実装は次工程。[共通06](../../共通/06_初期確認用データ.md)のSP2-DEMO-01/1.0のキー・値・件数を保持し、元manifestの内容・所有と対象DBが一致する新規隔離資源へだけ初回投入する。実行ユーザーの明示許可なくDB名の類似/0件を所有証明にしない。3分類→9コード→2利用者→3社員→3経歴を同じTxへ投入。IDはOUTPUTで解決、初期秘密は対話設定でHashPassword、日時は実投入UTC。再投入は全一致ならスキップ、編集/不足/他所有衝突は無変更停止。Web起動にDDL/再投入/全削除を組み込まない。

検査設計: schema/table/列48件、PK/FK/UQ/CHECK/索引と型容量、0/200/201社員、0/20/21経歴、0/99/100コード、先頭ゼロ/補助文字、2接続の番号/上限/停止/版競合、経歴の所有/送信集合、ロック10秒/取消/commit成否不明、同一時点の帳票取得を対象にする。SQL文の記載はこれらの実行合格を意味しない。正式採点null。
