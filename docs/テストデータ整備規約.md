# テストデータ整備規約（全方式共通）

版1.1／2026-10-28。要件・設計・実装の担当分離に合わせ、基本設計と詳細設計のデータ契約、実装側の投入資源の責務を明確化する。今回は規約の更新のみで、データ投入やアプリ実行は行わない。

## 適用と責務

生成するサンプルシステムは、起動後に利用者が検索・新規登録・編集・参照を確認できる初期確認用データと手順を備える。データ整備はソース生成の完了条件に含める。特定の題材、件数、採用DB、学校年度、認証方式を全体規則へ固定しない。basic-design-agentは基本設計に必要なデータ条件を定め、detail-design-agentはその条件に基づく初期化・投入・検査の詳細契約を選択specRootに記す。build-agentは同方式sourceRootに独立した投入資源・検査・操作手順を作成する。他方式の仕様・生成器・fixtureの共用を前提にしない。

新しい利用者指示と旧仕様の初期件数が異なる場合は、その差分を明示して対象版の仕様へ反映する。実装改善だけの工程で仕様正本を変更しない指定がある場合は、利用者の新しい指示、旧仕様の文書ID/版/ハッシュ、適用差分を今回の記録へ残し、次回の仕様工程へ引き継ぐ。投入用データや自動検査結果を業務要件・正式採点の代わりにしない。

## データの区分

| 区分 | 目的と扱い |
| --- | --- |
| スキーマ・制約・制御行 | 表・列・主外部キー・一意性・固定制御行等。DB定義を正本とし、構造作成と業務データ投入を分ける |
| 必須の参照マスタ | 起動・選択・保存に必要なコード、分類、採用プロファイルの固定値。件数、版、保護値、再投入時の差分方針を独立に記録する |
| 初期確認用の業務データ | 完全に架空のマスタ・業務行。通常検索、選択、参照、編集、新規保存を確認できる少数の正常データとし、配布サンプルへ含める内容を明示する |
| 自動試験のfixture | 境界・異常・権限差・競合・大量件数・障害注入等。正式な試験コード/入力は保持し、実行コピーと試験後の破壊状態は.tmpへ隔離する |
| 利用者の既存データ | 実データまたは利用者が編集したサンプル。確認用データの再投入やビルドを理由に上書き・全削除・権限変更しない |

## 内容と再現性

氏名・住所・連絡先・識別番号は完全に架空とする。実在人物の転用、秘密情報、実運用資格情報、他環境から抽出した個人情報を含めない。メールは予約済みの例示用ドメインを使い、実在する連絡先への通知・自動アクセスを実行しない。架空データであることを操作手順とmanifestへ記す。

初期確認用データは採用仕様の必須、一意、FK、分類、日付関係、定員、有効期間、条件付き必須、削除状態を満たす。候補だけを作り業務行が保存できない、所属候補が全て停止/期限切れ、定員が全て満員、初期検索に1件も一致しない等の状態にしない。未選択からの新規操作に使える候補と余席を残し、登録用の未使用業務キーを手順へ示す。異常データは正常な配布サンプルへ混ぜず、各試験の隔離fixtureで作る。

同じ入力版と基準日から同じ論理データを生成できるよう、データセットID/版、固定業務キー、値、並び順、疑似乱数を使う場合のseed、日付の算定規則を明示する。DB自動採番の値に依存する場合は投入結果の対応表を検査し、MAX+1で採番しない。実投入日時・実行主体などの監査値は固定架空値で偽装せず、決定的な業務データと別属性として記録する。

日付依存の候補・在籍等は基準業務日と適用可能期間を持たせる。実行日を使う場合はその日付をmanifestへ固定し、月末・年度境界・閏日・翌年でも成立する算定と、期限外時の明確な案内を検査する。試験用の時計固定が本番コードへ漏れないようにする。

認証・認可は選択方式の確定前提に従う。確認用データのためにログインを無効化したり、全員へ管理権限を付けたり、他方式の認証なしサンプル設定を持ち込まない。評価用主体が必要なら取得元・役割の作成範囲・許可対象・配布時の扱いを明記し、秘密を埋め込まない。

## 投入と既存データ保護

新しく生成した空の確認用環境には、必要マスタと初期確認用データを投入する。投入先は選択方式の許可されたサンプル資源に固定し、外部DBの発見・既存運用DBへの接続・管理者権限の変更を暗黙に行わない。接続先が未確定なら投入資源とdry-run/事前確認を作成し、実投入の未実施を記録する。起動のたびに自動再投入しない。

投入は依存順を守り、全体を単一トランザクションで確定/取消するか、隔離した新規stagingへ全データを作成して全検査成功後だけ最終配布物へ置換する。後者はビルド専用の明示フラグと所有範囲で新規staging/試験fixtureに限定し、配布物では追加許可を無効化する。途中の失敗・一部commitがあっても未完成stagingを公開せず、前の最終配布物を変更しない。既存利用者環境のデータ補充へstaging用フラグを転用しない。

再実行は冪等とし、同一データが既にあれば追加しない。データセット専用識別子や投入manifestで管理範囲を確認する。自分の投入済み行を利用者が編集/論理削除していた場合は、既存値を保持してスキップするか無変更で停止する方針を先に定義し、その対象と理由を報告する。別の所有者/データセットによる既存行と予約キーが衝突した場合は、投入前に検出し無変更で停止する。staging方式の完成配布物で不足キーが見つかった場合も、挿入を始めず対象と理由を報告して停止する。単に件数0か・名前が似ているかを削除許可として使わず、異なる値の強制上書きや削除行の自動復活を行わない。

リセットが必要な試験は、隔離した実行コピーに対象を限定する。削除・初期化の前に実パス/DB名と所有範囲を確認する。配布物の再ビルドと、既存利用者ファイルへの移行を分ける。Access等の単体ファイルでも、利用者が操作中のACCDBを上書きして初期化しない。

## 操作確認と検査

投入後は表ごとの実件数、FK/一意/必須、業務制約、選択候補と余席、初期検索結果を確認する。再投入して件数が増えず、既存値が変わらず、競合時には無変更で停止することも検査する。データ作成の検査とアプリ操作の検査を別々に記録する。

利用者向け手順には起動、必要な認証/権限、検索キーと期待結果、選択する候補、新規登録に使う未使用キー、更新・取消・再検索、保存値の確認方法を含める。DB直接編集を通常の画面確認手段にしない。画面入力を想定する試験は実部品へのキー入力・選択・貼付を使い、モデルやValueプロパティへの代入だけで入力可能を証明しない。データが少数でも文字切れ・先頭ゼロ・マスクと保存値・新規/既存の入力状態を確認する。

最低限、正常な検索→選択→参照/編集→取消、新規入力→保存→再検索の経路を選択方式で検査する。削除・競合・境界・権限差・大量件数・障害注入は専用fixtureで行い、試験後の状態を最終配布物へ戻さない。試験の未実施や制約を記録し、fixture合格を実利用環境の受入や正式採点へ転記しない。

## 配置と記録

データ定義・投入処理・正式なfixture/試験コードはsourceRoot内の正本へ置く。確認用データが製品ビルドに必要ならsource-only配布へ含め、原仕様や異常系期待値は逆生成パッケージへ含めない。初期確認用の正式データ定義と使い捨て実行コピーを混同しない。

最終配布物、初期データmanifest、検査結果、確認手順はsourceRoot/build/の固定パスへ更新する。manifestにはproject/方式、データセットID/版、今回の入力版/ハッシュ、データ定義/投入処理のハッシュ、投入先の種類、基準業務日、表別件数、業務キーと用途、架空データ宣言、再実行方針、認証範囲、検査範囲と未実施を残す。実利用者IDや連絡先等の不要な個人情報は記録しない。

作成途中、コンパイル、fixture実行コピー、破壊試験結果、失敗試行はsourceRoot/.tmp/へ隔離しGit除外する。日付・runId別のデータ履歴やbackupを累積せずGitを使う。正式な入力・QA・fixtureを中間物として削除しない。
