# Access画面の設計・生成・検証に共通する品質規約

版1.2／2026-10-30。Accessの要件定義・基本設計・詳細設計・プログラム作成を、利用者の作業と実画面の品質で接続する。工程固有の文書形式・処理手順は各Agentのrules/・workflows/、製品検査の共通形式は[UI適合検査](UI適合検査.md)を正本とする。

今回の改訂ではAUI-05a～05cを追加し、タイトル階層、文字と入力高の組合せ、日本語CP932とUnicodeの境界を全工程で確認する。規約の反映と既存製品の改修・実機合格は別に記録する。

## 適用と根拠

**AUI-01［必須］** 利用者指定の外部レビュー `references/access-review.md`「AI向け業務画面作成・修正ルール」v1.0（2026-10-29、SHA-256 `f55df1f0edfa800710ae9fad2cd7f234e6d5018e82d27ec61f03ae219bd6034b`）を、Accessの工程横断規約として採用する。原文は参照資料として保持し、業務仕様や実行する設定ファイルにしない。次回生成では本規約をAccessの凍結入力へ含め、原文の変更を本規約の無記録な変更として扱わない。原文を再採用する際は差分・版・SHA・適用判断を更新する。

本規約の「必須」は今回採用した範囲の条件、「標準」は理由付きで調整できる初期値、「条件付き」は該当する機能に限定した条件である。利用者の明示指示・確定済み業務要件・採用済み規約/QAと照合し、矛盾は根拠と影響を記録して解消する。画面寸法や例示値を業務上限、公的規格、全環境対応の保証へ置き換えない。他方式へAccessの数値・プロパティ・外観を横展開しない。

**AUI-02［必須］** 新規/修正、目的、変更範囲、対象環境、確認済み/仮定/未確認を区分する。既存画面の変更範囲が未指定なら`layout_only`とし、保存方式・DB・検索条件の意味・認証/権限・削除範囲を変えない。ラベルを変えて実際にはない取消や保存結果を約束しない。保存方式が未決なら`undecided`として該当部分を未完了にし、確定済み回答は継承する。認証を設けない採用済み方式へログインを追加しない。

## 利用者の作業と画面タイプ

**AUI-03［必須］** 「開始→対象を探す/識別する→入力/確認する→確定する→戻る」の利用者タスクを先に定義する。各画面に主タイプを一つ、必要な補助領域と特性だけを対応させる。以下は構成の標準であり、すべての画面へ一覧・タブ・フッター・保存ボタンを付ける指示ではない。

| screenType | 標準構成と設計する結果 |
| --- | --- |
| AUTH | サービス識別→入力と主操作を近接した小領域→終了等。採用済み認証がある場合だけ作る |
| HOME | 業務目的/利用頻度に沿った入口→補助情報→終了。利用可否の理由を統一する |
| SEARCH_LIST | 条件と検索/条件クリア→件数/状態/一覧→選択対象の操作。出力対象の範囲も示す |
| DETAIL | 対象識別→読取り専用情報→関連操作。長文/識別子を確認・コピーできる |
| EDIT_FORM | 新規/編集モードと対象→業務別入力群→保存と離脱。入力失敗も設計する |
| MASTER_DETAIL | 親対象識別→一覧と選択明細→明細操作と全体操作。選択切替と保存単位を明示する |
| WIZARD | 全体と現在の手順→入力→戻る/次へ/最終確定。手順間の入力保持を定める |
| DASHBOARD_REPORT | 条件/期間/単位/基準時点→集計→出力。未取得・ゼロ・失敗を区別する |
| SETTINGS | 個人/共有等の適用範囲→設定→反映タイミングと保存。初期化と破棄を区別する |
| DIALOG | 一つの目的と対象/影響→選択肢。初期フォーカス/既定操作/復帰先を定める |
| CUSTOM | purposeに独自の目的を記録し、領域・主操作・離脱と既存タイプで表せない理由を示す |

**AUI-04［必須］** 画面・状態別に次の4観点を、観測可能な合格条件へ落とす。「バランスがよい」「readable=true」一つで代用しない。

| 観点 | 利用者の判断 | 合格条件にする例 |
| --- | --- | --- |
| 合理性 | 作業順に対象を選び、必要な情報で判断できるか | 識別列を読んで対象を選べる。条件/明細/全体に作用する操作が該当領域にある |
| 統一性 | 同じ役割を同じ見せ方・名称・操作で理解できるか | 同じ役割のトークン・ラベル配置・操作位置と戻り方が揃い、例外に理由がある |
| 見やすさ | 現在の画面・対象・状態と重要な内容を判読できるか | 対象識別がタブ切替でも残り、見出し/列/文字が欠けず、長い値の全文へ到達できる |
| 操作性 | 次の操作とその結果を予測し、入力を失わず進めるか | 選択と表示対象が一致し、保存/取消/離脱/エラー復帰とキー操作が契約どおりに動く |

## 寸法と情報の配分

**AUI-05［標準］** 以下を方式内の共通トークンへ一度定義する。既存の正式な採用値を引き継ぎ、変更した値・理由・対象を方式内へ記録する。通常/compact/touch等の密度は画面単位で揃える。

| 役割 | 新規設計のAccess推奨初期値 |
| --- | --- |
| 基本間隔U | 0.1 cm |
| 外周余白/異なるグループ間 | 6U |
| ラベルと入力/同一操作群のボタン間 | 2U |
| 入力行間 | 3U |
| 一行入力高/通常ボタン高 | 採用フォントの実行高＋上下余白＋境界から算定。8U / 9Uは未計測時の配置候補で、フォントと無関係な固定高にしない |
| 本文・通常ラベル・一覧・入力・ボタン・Tab | Yu Gothic UI 11 pt |
| 画面タイトル | Yu Gothic UI 18 pt太字を標準、16 pt以上かつ本文より4 pt以上大きくする。既存の明示採用値を調整するときは理由と実画面検査を残す |
| ボタン幅 | 通常/長い名称用等の役割別共通幅。文字幅と内側余白から算定する |

設計cmと実装Twipsの換算（1 cm = 1440/2.54 Twips）・丸め方を共通化する。pt、論理px、物理pxを同値として扱わない。本文11ptをタイトル等の全役割へ一律強制せず、同じ役割での字体・寸法を統一する。クラシック外観等のAccess標準は[Access生成チェック](../agents/builds/build-agent/docs/Access生成チェック.md)に従う。

### タイトルと文字・入力高の組合せ

**AUI-05a［必須］** 画面タイトル、領域見出し、本文、補足を別の役割として定義し、タイトルを本文と同じ11ptにして太字だけで済ませない。Form.CaptionのOS文字と、アプリ管理のタイトルLabelを区別する。画面内タイトルは全Form・両Tab・新規/編集/参照で同じトークンを使い、Label高とHeader高も同時に確保する。タイトルを18ptへ変えて旧330twipのLabel高を残すなど、文字だけの変更を禁止する。小さいタイトルという利用者指摘がある既存11ptを「採用済み」の一言で継承しない。

**AUI-05b［必須］** fontFamily/fontSize/fontWeight、実行高、TextBoxのTopMargin/BottomMargin、境界、Control.Height、隣接行間を一組で仕様化する。1pt=20twipを使い、採用フォント・基準DPIで測った一行の文字領域に上下余白と境界を加え、丸め単位も記録する。日本語の上下・濁点、英数字のg/j/p/q/y、全角/半角、選択中・入力中のcaretが欠けず、余白が片側へ偏らないことを実Formで確認する。Label/TextBox/ComboBox/Buttonは同じ高さへ機械的にそろえず、同じ役割の行で基準線と高さをそろえる。複数行は必要な可視行数・行間・スクロールバーを含める。フォント変更時は入力高、付属Label、Tab、見出し、Header/Footer、ダイアログを横断して再検査する。未計測の「ちょうどよい高さ」を合格値へ固定しない。

### 日本語文字コードと表示の境界

**AUI-05c［必須］** 日本語Access向けのVBAテキスト（.bas/.cls等）はWindows-31J/CP932（Windows版Shift-JIS）を明示採用し、読取り・書込み・配布・再取込みで同じ契約を使う。MD/JSON/Python等のUTF-8、AccessネイティブForm/ReportエクスポートのBOM付きUnicode、VBA実行時StringとDBのUnicodeは別の境界であり、一括Shift-JIS変換しない。実ファイルのBOM・厳密復号・往復一致とOfficeの実入出力を確認する。変換不能・非往復文字をerrors=replace/ignoreや暗黙の文字正規化で失わない。必要なリテラルはChrWとsurrogate対で正確に構築するか、対象を明示して停止する。

Officeの表示言語とWindowsの実ANSIコードページを別々に記録する。日本語UIでもACP=932とは推定しない。936等のホストで932の生byteをそのまま取り込まず、検証済みのUnicode/ASCIIリテラル輸送を使い、再読取り・実行結果・実表示を独立Unicode期待値で照合する。代替経路が未検証なら生成を止める。OS言語設定の変更を自動回避策にしない。タイトル、付属Label、候補、MSG、長文、Excel帳票、再起動後を横断し、エディターだけ・静的HTMLだけの正常表示で製品全体の文字化け解消としない。

**AUI-06［必須］** 共通の列境界/行基準、領域内のラベル位置、同種部品高を定める。番号・年月・数量の幅は必要桁と矢印等から算定し、名称・案件名・長文へ幅を優先配分する。用途を無視した全項目の一律同幅、全画面中央寄せ、一覧:詳細の固定比率、空白を埋めるためだけの引伸ばしを禁止する。AUTH等の単一目的は横中央を標準とし、多項目画面は左揃えのグリッドを使える。項目とボタンが一つの作業群として追える距離に置く。

**AUI-06a［必須］** [UIパターン規約](UIパターン規約.md)のUIP-03aをAccessの標準部品で具体化する。ログインIDとパスワードは同じ親/Sectionの座標系でWidth/Heightを共通トークンへ対応させる。縦配置はLeftと右端、横配置はTopと下端を揃え、ラベル位置と行/欄間も統一する。縦配置のTopや横配置のLeftまで同値にはしない。表示幅の差を入力許容文字数の差で正当化しない。同じ書式の開始/終了等、既存の同型ペアと同じfactory/定義を使うFormも点検する。標準TextBoxのPasswordマスクや補助面への切替、再表示で既定幅へ戻らないことを保存属性と実画面で確認する。数値のTwips一致、字体と高さ、描画上の整列を別に検査し、既存の認証/入力上限を変更しない。

**AUI-07［必須］** 日本語/英数字/最大長付近/複数行を用いて字幅と内側余白を確認する。見出しとデータは同じ列幅定義を使う。重要な識別列が切れる場合は幅や構成を再配分し、全文表示・欄内移動・別詳細等の到達手段を用意する。ホバーのみへ依存しない。固定行数を超える一覧はスクロール等で対応し、0件/少件数で一覧や主要ボタンの位置を不必要に変えない。表示幅を入力上限にせず、文字の縮小を最初の解決策にしない。

**AUI-08［必須］** 最小client領域を、物理解像度・Windows倍率・Access枠/リボンを除いた有効領域と区別して定める。未指定なら1280×720論理px相当を暫定設計基準とし、100/125/150%は確認候補に留める。採用条件・実測した条件・未実施条件を別記する。Form幅、各Section高、表示方式、ScrollBars、Popup/Modal等の方針、Anchor/レイアウトによる伸縮、Subform/Tab/Page内部を設計する。広い領域は一覧と長文へ配分し、狭い領域では縦配置・領域分割・縦スクロールを使う。全体の横スクロールは原則不要とし、多列表の局所スクロールには理由を記す。保存・戻るへ到達でき、固定領域が入力を隠さないことを確認する。

## 対象と操作の識別

**AUI-09［必須］** 画面名/目的、現在の対象の識別番号と名称、新規/編集/参照モードを必要な領域で表示する。タブ/明細切替でも親対象を判別できる共通領域を設ける。画面名が親枠で明確なら同じ大見出しを重複させない。一覧の選択状態と詳細・編集・出力の対象を一致させ、必要なら「選択中」等を併記する。未選択時の対象操作は無効化等で制限する。

**AUI-10［必須］** 条件・結果・選択明細・画面全体の操作を領域と近接で分ける。操作名は対象と結果を示し、条件クリア/初期化/変更破棄/検索へ戻るを混同しない。主操作は同一操作群で原則一つとし、保存・戻る・削除の違いを位置/文言でも伝える。削除を既定Enterにしない。色だけで必須/選択/エラーを表現せず、ネイティブのフォーカスや選択/ハイコントラストを保つ。

形式、単位、空欄=継続中等の意味が自明でない項目には補足を付け、必須/初期値/権限は確定業務仕様から採用する。値なし/ゼロ/不明/未設定を混同せず、先頭ゼロを保持する。入力エラーは項目・理由・直し方を示し、入力を保持して復帰可能にする。出力や一括操作は対象範囲と成功/失敗を表示する。採用済み権限をUI非表示だけで代替せず、通常画面へ秘密や不要な内部情報を出さない。

## 保存と状態の契約

**AUI-11［必須］** 保存方式（none/explicit/automatic/per_item/undecided）、保存単位、確定契機、追加/変更/削除の未保存範囲、取消可能範囲、失敗時/部分成功/競合時の動作を定める。明示保存と中間の「明細へ反映」を使う場合は各段階の対象・バッファ・DB確定を分ける。入力中/未反映の明細を最終保存で取り込む・確認する・明確に拒否するいずれかを仕様化し、黙って欠落させない。明細切替で別対象へ誤反映したり値を消したりしない。自動保存では保存中/済み/失敗と実際の取消限界を示す。

**AUI-12［必須］** 未保存の内容を失う戻る/対象切替/タブ移動/ウィンドウ終了等の経路を列挙する。明示保存の標準は「保存して移動」「破棄して移動」「編集を続ける」とし、実装可能で契約に合う選択肢だけを示す。保存失敗では離脱せず入力を保持する。変更なし/保持される移動に不要な確認を繰り返さない。削除/上書きは対象・影響と確定時期を示し、必要な確認または復元手段を定める。標準MsgBox等でボタン名を変えられない場合は本文へ対象/実行結果を明記し、安全な既定操作と例外理由を残す。

**AUI-13［必須］** 連結/非連結・親子/単一の方式を明示し、Dirty、BeforeUpdate、Undo、レコード移動、Refresh/Requery、フォーム終了等の該当経路が保存契約と一致するか実機で検査する。親子全体の取消をボタン名や単一のUndo呼出だけで保証したとしない。必要な編集バッファ/作業領域/トランザクションの責務と寿命を詳細設計へ渡す。RecordSelectors、NavigationButtons、標準メニュー、Default/Cancelキー等を残す場合も独自操作を迂回しないか確認し、隠す場合は必要な代替操作を用意する。

**AUI-14［必須］** 初期/未検索/0件/未選択/通常/編集中/処理中/入力エラー/保存失敗/権限不足等の適用状態を設計する。Tab順、初期フォーカス、Enter/Esc/ショートカット、複数行の改行、ダイアログ後の復帰を定義する。Escで無警告の破棄を行わず、処理中の二重実行・終了を契約どおり制御する。読み取り専用の確認/コピーを妨げず、停止できない処理を取消可能に見せない。処理の割合や残時間を捏造しない。

## 工程間の引継ぎ

**AUI-15［必須］** 工程ごとの責務と出力を次のように分け、後工程を依頼なしに開始しない。

| 担当 | 今回の工程で残す内容 |
| --- | --- |
| requirement-agent | 利用者タスク/頻度/対象、環境/変更範囲/保存単位、4観点の受入条件、確定/仮定/QA |
| basic-design-agent | 画面タイプ/領域と状態、対象識別、役割別トークン/幅配分、静的HTML、操作の意味と利用者レビュー |
| detail-design-agent | Form/Page/Controlと座標/単位/列定義、状態・キー・イベントとバッファ/DB境界、個別合格条件/根拠と検査方法 |
| build-agent | 根拠から独立した期待値を先に固定→標準部品を実装→最終ACCDBの属性/描画/実操作/データ再読込→問題修正と回帰 |

共通トークン、対象画面/状態、採用/対象外と理由、合格条件、要求/項目/イベントID、根拠文書ID・版・SHAを同じ選択specRoot内で引き継ぐ。業務値をこの共通規約へ持ち込まない。工程固有の正本を共通docsや別Agentへ複製しない。

## 検査契約と証拠

**AUI-16［必須］** [UI適合検査](UI適合検査.md)のschemaVersion=1を使い、本規約が今回inputs.jsonへ凍結されたAccessのUI契約に`accessScreenChecks`配列を追加する。これは品質条件の定義漏れを検出する補助であり、宣言があるだけで目視・保存結果を自動証明しない。

各要素は`target`（components内の画面ID）、`screenType`、`checks`を持つ。CUSTOMは空でない`purpose`も必要。componentsのkindがForm/Page/TabPage/Dialog/Surface（大文字小文字を区別しない）のすべてを列挙し、最低一画面を登録する。タブの各Pageや確認/エラーダイアログを外側のFormだけで代替しない。親と共有する対象識別等は実際の共通部品のruleへ対応させる。

checksは次の9キーを省略せず持つ。各値は`{"applicable":true,"ruleIds":["個別ruleのID"]}`、または`{"applicable":false,"reason":"機能/状態に基づく理由","ruleIds":[]}`である。適用条件を満たすカテゴリを対象外にできない。該当する追加特性（一覧内編集/出力/一括等）は下表の最低条件へ追加し、意味レビューで確認する。

カテゴリの適用は機能追加を指示しない。読み取り専用の親子表示や保存のない手順画面でも、保存方式none・変更不可等の現行契約が実操作と一致することを該当カテゴリで検査し、保存ボタンやDB更新を新設しない。

| キー | 最低の適用条件 | 参照するrulesの最低kind | 検査対象 |
| --- | --- | --- | --- |
| identity | 全画面 | render | 画面・対象・モード/状態の識別 |
| layout | 全画面 | dimensions | トークン、列/行、領域と操作の近接 |
| content | 全画面 | render | 文字切れ、長い値の全文到達、見出しと列 |
| selection | SEARCH_LIST/MASTER_DETAIL。その他は適用判断を記録 | interaction | 未選択/対象切替、一覧と詳細/出力の対象一致 |
| saveCancel | EDIT_FORM/MASTER_DETAIL/WIZARD/SETTINGS。その他は適用判断を記録 | interaction | 未反映入力、保存/破棄範囲と失敗/再読込 |
| navigation | 全画面 | interaction | 戻る/閉じる/離脱と入力保持・フォーカス復帰 |
| keyboard | 全画面 | interaction | Tab、Enter、Esc、主要操作と複数行入力 |
| states | 全画面 | render | 正常/空/失敗等の該当状態の表示 |
| viewport | 全画面 | dimensionsとrender | 最小有効領域、対象倍率、Tab内部/主要操作への到達 |

参照先は存在する必須ruleとし、根拠は同方式specRootの採用仕様へ結ぶ。異なるカテゴリ間で同じ万能rule IDを流用しない。同じカテゴリ内で複数画面に共通する実部品/動作を参照できるが、別の画面/状態を観測した扱いにしない。9カテゴリは最低の網羅性であり、すべての状態・列・保存経路は複数の個別ruleに分ける。kindだけを満たす無関係な属性、理由のない対象外、実値の期待値への転記を独立レビューで拒否する。

**AUI-17［必須］** 本規約を凍結したAccessのinteractionにも非空evidenceを要求する。クリック/キー、開始状態、対象識別、入力値、画面遷移と期待結果、保存/取消に該当する場合はDB再読込を追跡できる操作記録を方式内build/test-results/へ残し、file/SHAで参照する。秘密情報は記録しない。renderには今回画面/計測記録が必要で、プロパティ値の代入や単なる`statePreserved=true`を操作結果にしない。

**AUI-18［必須］** 未検索/0/1/表示行数超過、未選択、長い名称/長文、追加/編集/削除、明細未反映で保存/別対象選択、エラー/保存失敗、変更なし/ありの離脱、破棄後/保存後の再読込、Tab切替、実キーボードを、業務仕様に該当する範囲で確認する。確定環境ごとに最小client領域・Office版/bit・DPI/倍率・実測領域を記録する。ui-observations.jsonのenvironmentは一条件の観測であり、全倍率の実施証明に使わない。追加条件の記録と対象条件ごとのrule/証拠を残し、未実施環境を対応済みとしない。

問題は「ルールID/画面・状態・箇所/事実/利用者の支障/修正内容/合格条件/検証方法・結果」で記録する。各条件を適合/不適合/未検証/対象外（理由付き）に区分し、未検証・重大な未解決を適合へ集計しない。静的仕様/HTML描画、コード生成、コンパイル、実ACCDBの描画、実操作、データ再読込、正式受入を分け、formalScoreは正式評価がなければnullとする。今回の最終検査記録だけを固定build/へ置き、中間物は.tmp/、履歴はGitを使う。
