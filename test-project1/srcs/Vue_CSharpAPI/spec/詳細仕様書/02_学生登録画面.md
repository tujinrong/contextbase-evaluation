#### 表示状態・モード別制御

[共通UI状態](../共通/04_共通UI部品設計.md)に従う。参照権限では全業務項目読取専用・保存不可。編集でも学籍番号・管理項目は変更不可。新規の生年月日・入学日は空。元号・年・月・日の原入力と正規化後日付を分け、エラー時に原入力を失わない。


#### 学生編集の配置と確認状態

通常画面は基本情報を上段へ横並びにし、下段を住所・本人連絡先／在籍・所属／緊急連絡先と備考・理由の3列にまとめる。管理番号と更新日時・更新者を短い管理行へ置き、操作バーは入力と説明の後の通常フロー末尾へ置く。固定配置で入力欄を覆わない。

REG-001～034の意味とID、保存19入力＋2生成値・通常更新18入力＋2生成値、必須・条件付き必須、rawと正規化後の上限、権限・同時更新・監査・確定境界を保持する。和暦の元号・年・月・日は独立した4原入力を保ち、新規では空。年度・学年は編集の所属選択補助として残す。短い入力欄の幅を保存上限に読み替えず、住所45・メール60・備考120・各理由60を全文確認・編集できる。

1366×650と1280×650 CSS px、100%の通常編集では全入力・所属人数・更新情報・主要操作を1画面へ収める。文字12px以上、入力・操作34px以上。長い管理値は折返し、テキスト入力はカーソル移動、備考・理由は内部スクロールとリサイズで全文へ到達する。エラー一覧・長文説明・狭幅・拡大では縦スクロールを許し、入力保持と操作の到達を優先する。

通常編集、重複候補確認（REG-032/033/034）、論理削除確認（REG-026）、変更破棄・再読込確認を別の表示状態にする。確認を通常画面の下へ常時並べない。重複確認は全候補数と最大20行を専用スクロール領域で示し、理由入力を関連付ける。削除理由は削除確認でのみ必須。取消を初期フォーカスにし、背景へ操作を通さず、取消後は元の入力と起点へ戻す。確認待ちは保存単位を終了し、続行で既存の再検査を行う。

## イベント仕様

### EV-REG-001 新規画面表示

#### 処理概要

作成権限のある利用者が新規モードを開く。

#### 処理手順

1. 共通01・02・03で権限と業務日時を確定。OP-CODE・OP-CLASSで候補と初期値の存在を確認する。
2. 性別0、在籍01、年度は当年度。他の値、特に生年月日・入学日を未入力にする。学生管理番号・版は未採番。

### ネイティブイベント・通信の対応

#### 登録APIと結果

| API | 契約 |
| --- | --- |
| GET /api/students/new | Create権限、性別0・在籍01・当年度・入学日空、候補 |
| GET /api/students/{id} | Read権限、非削除、最新全項目・rowVersion・permissions |
| POST /api/students | 新規、StudentSaveRequestの平坦JSON（formというラッパーは送信しない） |
| PUT /api/students/{id} | 同じ平坦StudentSaveRequest＋expectedVersion必須。ルートIDを対象の正本とする |
| POST /api/students/{id}/soft-delete | expectedVersion、reason、confirmed、returnContextIdのみ |

保存順は認証・CSRF→raw検査・正規化→DBゲート→最新対象版・マスタ・状態・定員→変更なし→全候補確認→変更＋監査→確定。409 confirmationRequiredの場合はTx終了後にダイアログ、別人確認と理由付き再送でもAPIで全検査。変更された入力・候補集合・期限切れは再警告。

```json
{
  "outcome":"confirmationRequired",
  "messageId":"W-STU-101",
  "message":"同一人物の候補があります。確認してください。",
  "duplicateToken":"<server-issued-token>",
  "candidateCount":1,
  "candidates":[{"studentId":"1001","studentNo":"S2026-0001",
  "studentName":"見本 太郎","birthDate":"2008-05-15","classLabel":"Aクラス"}]
}
```

例のmessageは説明用で、実文言は共通メッセージ正本から生成する。候補に住所・電話・メールを返さない。成功新規は201、更新・削除は200、noChangeは200。savedの確定応答を受けたときだけdirty解除して検索へ復帰しresumeで再検索。

### 業務判断の決定表

#### 主要な業務チェック

| チェック | 判定 | 結果 |
| --- | --- | --- |
| 学籍番号重複 | 削除済みを含む全学生で使用済み | 保存不可。番号の再利用も不可 |
| 同一人物候補 | 非削除の他学生と生年月日が同じ、氏名またはカナの照合値が同じ | 別人確認・理由付きなら保存可 |
| コード存在 | 正しい分類内に値がある | 不存在は保存不可 |
| コード利用可否 | 新規・変更する値が有効・期間内 | 不可値は保存不可。既存の同値保持は可 |
| クラス存在 | 選択クラスが実在し年度・学年が一致 | 不存在・不一致は保存不可 |
| 日付 | 生年月日≦入学日≦本日、終了日も本日以前 | 不整合は保存不可 |
| 連絡手段 | 本人電話・メール・緊急電話の1つ以上 | 不足は保存不可 |
| 緊急連絡先 | 氏名・続柄・電話を全部空または全部入力 | 一部だけは保存不可 |
| 他者の更新 | 画面読込後に別操作が更新済み | 上書きせずエラー。入力を保持 |
| 理由 | 必要な操作で空白でない60文字以内 | 不足は保存不可 |

#### クラス選択・定員の決定表

| 保存後の状態・変更 | クラス要否・利用規則 | 定員 |
| --- | --- | --- |
| 新規の在学・休学、別クラスへの異動、卒業等から在学へ訂正 | 必須。利用可かつ本日が利用期間内 | 自分を除いた在学・休学人数＋1が定員以下 |
| 在学・休学のまま同じクラスを保持 | 存在必須。期間外等でも住所などの変更は可、見直し警告 | 席が増えないため既存の超過だけでは拒否しない |
| 新規の卒業・退学 | 任意。指定するならクラス利用期間と入学～終了日の期間が重なる | 席を消費しない |
| 卒業・退学の最終所属・在籍日付・区分を変更 | 停止・過去クラスも可。指定した期間の重なりを確認 | 席を消費しない |
| 卒業・退学の最終所属・在籍日付・区分を変えず住所等だけ変更 | 既存値を保持できる | 席を消費しない |
| 論理削除 | 元のクラス情報を保持 | 削除後は人数に含めない |

休学も1席を使用する。定員未設定は制限なし。定員40人に対し39人在籍で同時に2人を登録した場合は片方だけ保存でき、超過させない。期間の重なりは1日以上あればよく、卒業日がクラス利用期間内に入ることまでは必須にしない。

#### 在籍区分の状態遷移

| 変更前 | 変更後 | 実行者・条件 |
| --- | --- | --- |
| 在学・休学 | 在学・休学・卒業・退学 | 担当者または管理者。変更後の日付・クラス規則を満たす |

### 制約・正本

本書は1機能を対象とし、複数クラス・API・パネルはその内部実装である。マスタ保守、共通UI、物理テーブル、ビルド・配備は[方式別共通仕様](../共通/方式別/01_共通実装仕様.md)を参照する。

### 試験観点

[共通T-01～28](../共通/06_要件対応・設計判断.md)と[DATE-T01～20](../共通/07_日付・和暦仕様.md)の該当項目を実装工程で実施する。入力→処理値→DB→再表示を往復確認し、Unicode最大長、日付境界、停止候補、最終席競合、旧版、履歴失敗、保存結果不明を含める。

レビュー結果。文書検査と実装試験合格を区別する。

### 開発入力と責務

本機能を実装する直接入力は、本書、[方式別共通仕様](../共通/方式別/01_共通実装仕様.md)、[DB定義](../DB定義/SQLServer/01_DB定義書.md)、[方式別開発規約](../規約/Vue_CSharpAPI.md)、[共通開発規約](../規約/開発規約.md)である。基本設計は背景理解・承認確認に用いる。項目の必須・長さ・初期値は本書に再掲し、[共通項目制約](../共通/09_項目制約定義.md)と一致させる。

raw入力は表示用に保持し、正規化成功後の値だけを型付き命令に移す。型変換エラーをNULLと扱わない。生年月日は和暦4入力、変換後のみbirth_dateとして保存する。氏名・カナの照合値は保存側が再生成する。操作イベントごとの引数・結果分岐は本書イベント仕様に従い、共通呼出しの成功を業務保存の成功と混同しない。

本書の構成要素IDは親項目の細分化であり、新たな業務要件を追加するものではない。内部名が前版で未指定だった表示用変数は本版の実装設計名。ソースが実在するという主張ではない。

### 更新表の補足

EV-REG-004・006から呼び出す。新規19入力、通常更新18入力（学籍番号以外）、生成照合値2の対応を固定する。更新・削除は対象ID＋期待版＋非削除で1件を要求し、0件の場合は不在／競合を区別する。

### 長さと物理領域の解釈

項目一覧の「言語型」は検証途中のモデルを含む。DateOnly?等の未設定状態を許容しても、保存時の必須検査を省略しない。Raw入力と正規化値を別領域へ保持する。対応DB型・NULL可否は採用DB定義と同じ値を再掲している。

Unicode入力はスカラー値で業務長を判定し、UTF-16のMaxLength／HTML maxlengthが同じ数字だから正しいとは判断しない。画面部品の物理入力上限は必要に応じ2Nコード単位以上を確保し、共通検査でNスカラー値を厳守する。描画モックのdata-business-maxlengthが業務上限であり、HTMLの物理ガード値は業務上限を拡張する指定ではない。

### SQL Serverとの接続

Microsoft.Data.SqlClientの型付きパラメーターを使用する。[DB定義](../DB定義/SQLServer/01_DB定義書.md)と[方式別共通](../共通/方式別/01_共通実装仕様.md)のSNAPSHOT検索、書込ゲート・負戻り値、OUTPUT後の確定確認を適用。表示用の和暦値ではなく内部dateを保存・比較する。文字数は業務スカラー値で検査し、nvarchar容量は別に確保する。

### 続柄分類の派生・全消去

続柄コードがnullなら分類もnull。分類をJSON業務入力へ追加せず、C# APIの保存側で算定してDBへ渡す。

分類は新たな画面入力ではない。全消去時は氏名・分類・続柄値・電話を同時にNULL化する。原入力保持・読込時スナップショット・論理削除の更新範囲は変えない。生成物の旧固定分類代入は修正対象であり、本仕様変更だけで更新済みと扱わない。
