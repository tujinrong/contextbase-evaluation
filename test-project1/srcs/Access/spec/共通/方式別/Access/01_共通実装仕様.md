## DAO検索・ページング

全要求で専用Workspaceとそこから開いたDatabaseを用い、QueryDef.ParametersでクラスID・在籍集合をバインドする。学生の非削除は固定。氏名照合値の部分一致と学籍番号前方一致は返却行の正規化値をVBAのInStr／StrComp、vbBinaryCompareでリテラル比較する。4条件AND・在籍内ORだけを実装し、カナ・年度・学年・未所属・住所・電話・期間条件を受け付けない。clsSearchCriteriaはStudentNoPrefix As String、NameKey As String、ClassId As Variant(Null/Long)、StatusSelected(1 To 4) As Booleanの4業務プロパティだけ。

```sql
PARAMETERS pClassId LONG, pS1 TEXT(4), pS2 TEXT(4), pS3 TEXT(4), pS4 TEXT(4);
SELECT s.student_id, s.student_no, s.student_name, s.student_name_kana,
       s.name_key, s.birth_date, s.class_id, s.enrollment_status_code,
       s.admission_date, s.updated_at
FROM m_student AS s
WHERE s.is_deleted=False
  AND (pClassId Is Null OR s.class_id=pClassId)
  AND ((pS1 Is Null AND pS2 Is Null AND pS3 Is Null AND pS4 Is Null)
       OR s.enrollment_status_code IN (pS1,pS2,pS3,pS4));
```

動的値は型付きパラメーター。name_keyは検索照合、admission_date・updated_atはソート内部値としてだけ保持し、一覧DTOは8論理項目（7列相当）＋学生IDへ投影する。クラス・学年・在籍の名称は分類＋値／IDの読取辞書で結合し、停止・名称欠落で学生行を消さない。住所・電話・更新日時を表示DTOへ返さない。

1要求内の件数・一覧を揃えるため、t_write_guardのゲート取得後にマスタと学生を読み、全検索条件に一致した行だけを最大10,001件まで数える。10,000件以内なら必要なDTOをメモリーに保持し、許可順序で全体をソートしてから指定ページを抽出する。名前KeyがLONGTEXTでも、先に10001原始行だけを選んでから条件をかける誤実装を禁止する。

ソートはstudentNo／nameKey／admissionDateIso／updatedAtUtcの4種類、同順位StudentId。文字はバイナリー順、日付はISO順、時点はDate値。DB製品を跨いだすべてのUnicode文字の同じ並び順まで保証するものではない。全件一致が多い・選択度が低い検索の走査負荷は実測する。

lstStudents.RowSourceType="StudentListCallback"、ColumnCount=8、BoundColumn=1、先頭ID列幅0。残る7列は学籍番号／氏名とカナの合成文字列／和暦生年月日／年度と学年／クラスコードと名称／在籍／操作案内。行操作案内は文字でありクリック可能なセル内ボタンではない。既存cmdOpenSelectedかダブルクリックから非表示IDを解決する。コールバックはフォームインスタンス別メモリー配列の初期化・行数・列数・値・終了を返し、その中でSQLを実行しない。[A-01]

ListBoxはセル内改行を前提としない。長い合成文字列・クラスは選択行全文欄で確認する。取得20／50／100の範囲内はListBoxの縦スクロール、DBの前後ページは外部ページ操作とする。フォームの面積条件と入力欄は検索／編集詳細の省スペース契約を適用する。

## 保存・排他・原子性

補助`t_write_guard`を単体成果内に追加する。`guard_id LONG PRIMARY KEY`、`lock_bit YESNO NOT NULL`、固定行(1,False)を投入。業務5表には含めない。全学生変更・削除・マスタ保守と、件数・一覧を揃える検索が同じ制御行を使用する。

```vb
'保存単位の骨格。検証・業務書込み・監査の実装は省略している。
Dim ws As DAO.Workspace, db As DAO.Database
Dim inTx As Boolean
On Error GoTo Failed
Set ws = DBEngine.CreateWorkspace("StudentTx", "Admin", "", dbUseJet)
Set db = ws.OpenDatabase(CurrentProject.FullName)
If Not db.Transactions Then Err.Raise vbObjectError + 100, , "Transactions required"
ws.BeginTrans
inTx = True
db.Execute "UPDATE t_write_guard SET lock_bit=Not lock_bit WHERE guard_id=1", dbFailOnError
If db.RecordsAffected <> 1 Then Err.Raise vbObjectError + 101, , "Guard missing"
'この後に最新版・全検査・業務書込み・監査を同じdb/wsで実行する。
ws.CommitTrans dbForceOSFlush
inTx = False
GoTo Cleanup
Failed:
'最初のErr/DAO.Errorsを退避する。Rollback自体の失敗も別記録する。
If inTx Then
    On Error Resume Next
    ws.Rollback
    On Error GoTo 0
End If
'確定不明を含め共通エラーへ変換。ここで成功通知を設定しない。
Cleanup:
'Recordset、QueryDef、Database、Workspaceを確実にClose/解放する。
```

AdminはDAO Workspace生成のための指定であり、業務上の管理者権限を意味しない。処理のUserId・役割はmodSecurityの認証情報から取得する。複数の独立した保存単位を既定Workspaceへ混在させない。DAOのトランザクションはWorkspace範囲なので、業務と履歴を別Workspaceへ分けない。[A-02]

検索はゲート取得後に必要結果をメモリーへコピーし、Rollbackでゲート変更を取消・解放してからUI表示。保存はゲート取得後の別読込みで最新対象の存在・版を照合、マスタ・在籍・定員・全重複候補を検査する。確認待ちや変更なしはRollbackして終了。ダイアログ表示、DoEvents、外部対話をTx中に行わない。

### 業務レコードの書込み

更新の正本方式は、パラメーター付きQueryDefで`student_id=pId AND row_version=pVersion AND is_deleted=False`を条件に**単一表の更新可能dynaset**を開き、対象が1件であることを確認して`Edit`→許可列の`Fields(...).Value`設定→`Update`を行う。文字値はSQLへ連結しない。対象はゲート取得後に読み、全更新経路が同じゲートを守るため、対象検査からUpdateまで別の協調書込みが割り込まない。ゲートに従わない直接ファイル編集は本構成の保証対象外。

通常更新は学籍番号以外の18入力＋生成NameKey/KanaKey＋条件付き続柄分類＋更新者日時＋版加算。LongTextもRecordset.Fieldsへの値代入で保存し、TEXT(255)へ変換しない。新規はAddNewで19入力＋照合値2＋必須３分類・条件付き続柄分類＋作成更新＋版1を設定し、Update直後に`Bookmark=LastModified`で採番StudentIdを取得する。MAX+1は禁止。[A-03]

論理削除は同じ対象・版検査後に削除状態・日時・者・理由と更新情報・版だけを変更。t_operation_logは同じdbの別dynasetへAddNewし、学生とまとめてCommitする。監査失敗は両方Rollback。監査だけ別CurrentDbで実行しない。

補助的な固定短文列の更新例は次のとおり。Execute方式を採用する場合はRecordsAffected=1も必須。

```sql
PARAMETERS pName TEXT(16), pAt DATETIME, pBy TEXT(64), pId LONG, pVersion LONG;
UPDATE m_student SET student_name=pName, updated_at=pAt, updated_by=pBy,
 row_version=row_version+1
WHERE student_id=pId AND row_version=pVersion AND is_deleted=False;
```

これは版付き更新構文の例であり、氏名変更時のNameKey等を省略して本番に用いてよいという意味ではない。全業務更新は前段の許可列定義に従う。

## 状態・例外・画面部品

clsSearchContextは認証者・ログイン状態・Formインスタンス・AppliedCriteria・CriteriaFormatVersion=2・Revision・ページ・ソート・最終利用時点を保持、30分で失効。clsConfirmationは10分、対象・旧版・全正規化業務値・全候補IDと版を対応付け、再保存時に再取得・比較する。表示候補20件だけで一致を判定しない。確認情報はメモリー、フォーム終了・認証変更で破棄。汎用の確認済Booleanだけで警告を迂回させない。

フォームのmBusy、mDirty、mInitializingを分ける。DAOは同期呼出を基準とし、VBAに存在しないTask/Awaitを仮定しない。処理中操作不可、Tx外でも不用意なDoEventsの再入を防ぐ。エラーはラベルと項目別表示、最初の入力不備へSetFocus。DB保存済み状態をフォームのDirtyプロパティだけで判断しない。

DAO3022は制約・対象の再確認によって学籍／マスタ重複へ分類。ロック／競合系の3188・3197・3218・3260はDAO.Errorsも確認し、全Rollback後に再確認を案内する。対象なし・版不一致はE-STU-103/105、その他はE-COM-004＋受付番号。ロック競合時に処理途中から自動再実行しない。Commitの応答を失った場合は検索確認、保存失敗と断定しない。

### 保守入口・方式固有の適合条件

#### マスタ保守・制約・試験

`modMasterMaintenance`の管理者向け入口から承認済みデータを検査して投入する。通常の画面にマスタ保守機能を増やさない。初期5分類70値、再投入が同値なら無変更、差分なら停止して確認。クラス年度＋コード一意、参照学生がいる学年変更、在籍人数未満の定員、在学・休学がいる利用停止、保護コード変更を拒否し、履歴と一括確定する。

ACCDBの画面・VBAによる権限制御は、共有ファイルを直接変更できる利用者に対する強いDBアクセス境界にはならない。本案は信頼された職員向け評価構成。本番で厳密な閲覧者／担当者／管理者の分離が必要ならサーバーDBまたはAPI方式への変更承認を稼働条件とする。ACCDE化・ナビゲーション非表示をセキュリティ保証と説明しない。

共通T-01～28に加え、非連結フォーム移動で保存されないこと、保存中のDoEvents再入がないこと、Nullと空文字、LongとIntegerの違い、長い住所・備考、Unicode補助文字、ListBoxの区切り文字を含む表示、2つのAccessプロセスの最終席競合、履歴失敗のRollback、共有フォルダー切断、Office32/64bitでのAPI宣言を試験する。

### 派生分類と監査の共通実装

新規／通常更新は[共通データアクセス](../../08_データアクセス仕様.md)の緊急４保存項目一式を適用する。続柄分類を常にRELATIONSHIPへ設定する処理は禁止し、続柄値未設定時は分類もNULLへバインドする。コード値を更新する際は分類も同時更新し、変更列監査へ含める。必須３分類は固定のまま。

マスタ監査は[共通モジュール](../../03_共通モジュール設計.md)の状態遷移表に従い、停止中の名称変更はUPDATE、状態が実際に停止へ変わる時だけDISABLEとする。認証不成立はE-COM-001、認証済み利用者の認可拒否はE-COM-002を使用し、実装の誤った番号を仕様値として採用しない。
