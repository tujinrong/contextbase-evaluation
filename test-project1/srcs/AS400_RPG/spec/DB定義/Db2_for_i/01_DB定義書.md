# Db2_for_i DB定義書（索引・共通規則）

版8.0／2026-10-12。report指摘による設計改訂。本改訂の実DB・アプリ再検証は未実施。

## 概要

本書はテーブル別仕様への索引と共通の保存・制約規則。各テーブルは「テーブルヘッダー＋項目詳細」の１ファイルで定義し、Excelでは同一シートに配置する。索引・共通規則はテーブルシートへ繰返し展開しない。

業務5表の全89列をテーブル別に省略せず示す。業務的な長さ・必須は[論理テーブル仕様](../../基本設計書/03_テーブル仕様書.md)と一致させる。実装の直接入力は本書。生年月日は内部日付、画面は和暦。その他は西暦。日付下限・元号・動的範囲は[共通日付](../../共通/07_日付・和暦仕様.md)。

DB既定値が空欄の列は保存入口で値を明示する。画面初期値とDB DEFAULTは別物。NOT NULLと空白禁止、NULL可と条件付き必須を分ける。業務5表と認証・競合・確認の技術補助表を区別する。サーバー業務日による検査は変動するため固定CHECKへ埋めない。

Unicode文字列の物理領域を確保しても業務上限は元のNスカラー値のまま。ID・版は正の64bit BIGINTを使用する。

各分冊の明細は９列。NOT NULLは〇/空欄、DB確定時のタイプは実DB型、長さは業務上限。初期値なしは空欄とする。型容量・業務上限を維持。続柄分類のNULL条件は本改訂の保存契約に従う。

## 補足説明

t_write_guardの固定行を初期投入し、欠落時は処理を止める。業務表の追加ではない。全書込みと同一読取り結果が必要な検索が同じゲートを守る前提と、直接編集の制約を方式別開発規約に残す。

### AS400／RPG：Db2 for i：物理全89列

DBスキーマSTUDAPP、SQL名は下記、システム名は順にM_STUDENT、M_CLASS、MCAT、M_CODE、T_OPLOGとする。長いSQL表名は作成時にFOR SYSTEM NAMEを明示。RPGのDB入出力は明示SQLホスト変数で行い、自動生成の短いフィールド名に依存しない。

記号ID＝BIGINT GENERATED ALWAYS AS IDENTITY、L＝BIGINT、I＝INTEGER、S＝SMALLINT、D＝DATE、T＝TIMESTAMP(6)、Vn＝ASCII用途VARCHAR(n)、Un＝業務Unicode N scalarを収めるVARGRAPHIC(2*N) CCSID 1200。?はNULL可、他はNOT NULL。A＝created_at T、created_by V64、updated_at T、updated_by V64、row_version L DEFAULT 1。

業務5表の全物理列・型・業務上限は本書のテーブル一覧から参照する５つの分冊に列挙する。以下の責務・参照整合の追加条件と併せて実装する。

Unは物理2N UTF-16コード単位の領域であり、業務上限を2N文字へ増やす意味ではない。STUNICODEでscalar上限Nを検証する。changed_columnsは物理列名だけのJSON配列、生成器で妥当性を検査する。UTC時点はTZなしTIMESTAMPへUTC変換済みで保存する。

PK＝各ID、category_id、(category_id,code_value)。UQ＝student_no全行、クラス(school_year,class_code)。FK＝学生クラス、学生4分類組→コード、クラス学年組→コード、コード→種別、RESTRICT。コード固定分類CHECKとすべての真偽0/1 CHECKを設ける。版正数、日付順、状態01/02の終了日NULLとクラス必須、03/04の終了日必須、連絡先1つ・緊急一式、削除属性一式、年度1900～9998と年度内期間、定員NULLまたは1～9999、コード期間順を保護する。現在日・有効性・分類桁・集計は保存処理で再検証。

業務5表の全物理列・型・業務上限は本書のテーブル一覧から参照する５つの分冊に列挙する。以下の責務・参照整合の追加条件と併せて実装する。

### 技術制御行の固定制約

`guard_id=1`の行を初期投入し、主キーと`guard_id=1`の固定制約を設ける。lock_bitはSMALLINTの0/1。削除・複数制御行の生成を運用権限で禁止する。制御行欠落は共通設定エラーで処理中止。

### 続柄の任意参照と行内制約（7.4）

`m_student.relationship_category`と`relationship_code`は共にNULL可。前者はコード選択時だけ`RELATIONSHIP`を保存入口が設定する。緊急連絡先４保存列の許可状態を、C-010の既存「連絡手段が１つ以上」の条件とAND結合する。次の述語は各列のNULL状態を明示し、CHECKのUNKNOWNを利用して部分入力が通る実装を防ぐ。

```sql
(
  (emergency_contact_name IS NULL
   AND relationship_category IS NULL AND relationship_code IS NULL
   AND emergency_phone_number IS NULL)
  OR
  (emergency_contact_name IS NOT NULL
   AND relationship_category IS NOT NULL AND relationship_code IS NOT NULL
   AND emergency_phone_number IS NOT NULL
   AND relationship_category = 'RELATIONSHIP')
)
```

C-008の旧「学生４分類は常に固定」を、必須３分類の固定と、上記の条件付き続柄分類へ置換する。既存の複合FK `(relationship_category, relationship_code) → m_code(category_id, code_value)` は有効のまま維持し、親コードの参照中削除・キー更新を拒否する。新規および通常UPDATEのSET対象へ派生分類を含める。分類の固定DEFAULTは作らない。空文字・空白だけは共通正規化でNULLとして扱い、コードの既存値保持・有効性・一式必須も保存入口で検査する。

[SQL Server CHECKのNULL判定](https://learn.microsoft.com/en-us/sql/relational-databases/tables/unique-constraints-and-check-constraints?view=sql-server-ver17)は固定制約の記述根拠であり、当該構成の実機合格証拠ではない。

これは仕様の修正であってDBへ適用済みのDDLではない。導入時は旧データを事前検査し、既知の旧表現（緊急３項目全NULLかつ分類だけRELATIONSHIP）のみ承認済み移行で全NULLへ変換する。他の不整合を自動修正しない。制約・列変更の製品別DDL、移行前後件数・監査・バックアップ・戻し手順は移行工程で検証する。
