# 本方式の独立プロジェクト構成

版8.3／2026-10-25。設計・評価基準。アプリ実装・実機試験・逆生成採点は未実施。

## 概要

仕様作成Agent、順生成Agent、逆生成Agentを複数の独立したテストプロジェクトへ適用する。本書は配置規則を定め、実装・実行の状態は今回の最終記録で区別する。docsは全体の規則、agentsは役割・入出力契約、test-project1は最初の評価題材。test-project2は将来の追加予定で、今回の業務要件をコピーして未承認の第二プロジェクトを作らない。

## 配置一覧

| 領域 | 目的 | 書込み範囲 |
| --- | --- | --- |
| docs/ | 全プロジェクト共通の仕様作成、MD/Excel、開発、評価方針 | 共通ルールの変更のみ。特定業務の桁数やDB採用は置かない |
| agents/ | Agentの役割・入力許可・出力契約 | Agent定義。特定プロジェクトの正解仕様を内蔵しない |
| test-project1/ | 題材の要求・仕様・開発プロファイル・最終成果 | 選択されたプロジェクト内 |
| test-project1/spec/README.md | 方式別仕様の配置索引 | 配置情報のみ。横断した業務仕様は持たない |
| test-project1/spec/方式ID/ | 選択方式の独立した原仕様正本（specRoot） | 指定方式の仕様工程と、順生成で許可された局所修正 |

| test-project2/（将来） | 独立した次の題材 | 明示的作成指示後。他プロジェクトの入力を混ぜない |

## 識別と変更

projectId/仕様セット版/方式ID/文書ID/機能ID/項目IDを識別子として保持する。プロジェクトを跨いだ同じ項目IDは別物。移動では相対リンク・メタ情報path・評価根拠・画像参照も更新する。同一IDの意味を変更した場合は仕様版を更新する。評価旧版はGit履歴で保持する。共通ルールを変えても、既存プロジェクトの承認済み範囲へ無断適用しない。

### 独立方式の仕様配置

独立方式の仕様正本はproject/spec/方式ID/とし、このパスをspecRootとする。ソース正本sourceRoot=project/srcs/方式ID/とは別に扱う。方式内で閉じるとは、業務仕様と仕様間の依存が選択方式のspecRoot内で完結することであり、ソースフォルダ内に仕様を置くことではない。spec/README.mdは配置索引に限定し、他方式の仕様を共用入力にしない。順生成は詳細・共通・DB定義・開発規約をspecRootから読み、実装をsourceRootへ出力する。specRootがない場合に旧srcs/方式ID/specへ戻ったり、旧仕様を自動複製したりしない。

方式が既に確定しているため、詳細仕様書と方式別共通の下へ同じ方式IDのフォルダを重ねない。詳細文書はspecRoot/詳細仕様書/直下、方式固有の共通実装仕様はspecRoot/共通/方式別/直下へ置く。

DB定義の採用DB名は方式名とは異なる分類である。DB定義/Access、DB定義/SQLServer、DB定義/Db2_for_i等のプロファイル階層は保持する。フォルダ整理ではファイル名・文書ID・機能/項目/イベントIDと業務定義を維持し、相対リンク・spec-meta.path・索引・現在の検査manifestを新しい配置へ合わせる。過去生成時の入力パスとハッシュを現在の生成結果へ偽装しない。

## テーブル文書の配置

選択したspecRoot（独立方式はproject/spec/方式ID）内の基本設計書/テーブル/およびDB定義/＜プロファイル＞/テーブル/へ１テーブル１文書を置く。全体の[記述規約](テーブル仕様書記述規約.md)を使用する。具体的な業務項目・長さ・DB採用は全体docsへ転記しない。

## Git管理とローカル実行記録

ソース、正式な試験コード・fixture、設定例、Agent定義、仕様・評価基準、QA、ContextBaseの解析正本（identities.jsonを含む）、正式なoutputとspec-analysisはGit管理を継続する。拡張子だけでJSON・画像・HTML・Excel等を一括除外しない。

全方式で仕様はspecRoot、ソースはsourceRootの正本を更新し、最終配布物・今回の最終検査結果・入出力manifestはsrcs/方式ID/build/の固定パスへ更新する。これらの最終結果をGitで管理する。日付、run-id、attempt、backup、archive別の過去生成結果を残す義務はなく、累積させない。run-idは最終記録の属性として保持できるが、出力先の世代分けには使わない。Accessもbuild/内の最終accdb1個に従う。

中間生成、失敗試行、取得処理系、依存・コンパイルキャッシュ、テストfixtureの実行用コピー、隔離展開は各方式の.tmp/内で処理し、Gitから除外する。方式に属さない共通工程は担当Agentまたは選択projectの.tmp/を使い、その最終結果は同じ所有範囲のbuild/へ固定名で更新する。既存のreport/・test-report/・test-evidence/を新たな履歴置場にしない。正式な試験コード・入力fixture・QA・ContextBase正本と、実行中の一時コピーを区別する。

逆生成へは選択方式のsource-onlyパッケージだけを渡し、移動後のproject/spec/全体・spec-eval・他方式を取得と独立検証の両方から除外する。

対象パターンは.gitignoreで管理する。.tmp/はすべて除外し、build/の最終結果は追跡対象とする。以前の最終結果はGit履歴から確認し、作業ツリーへ別名複製しない。検査は今回の入力・出力版と範囲・未実施を記録し、旧PASSを現在の結果へ流用しない。不要な過去生成物を整理する際も、入力・QA・正式なfixtureを削除しない。秘密情報と実行時ロックファイルは最終成果へ含めない。
