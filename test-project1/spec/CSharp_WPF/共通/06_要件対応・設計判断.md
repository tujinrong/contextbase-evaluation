# 要件対応・設計判断・適合試験

版：8.5／2026-10-28。文書ID：COM-STU-006。

## 改訂の要点

ユーザーの追加指定により、基本設計と共通の業務契約を言語非依存にし、詳細を7方式へ分割する。前段で作成していた単一のC#／ASP.NET Core向け詳細案を本方式共通の仕様として扱わない。現在のリポジトリに実装ソースが存在するという意味ではない。

| 方式 | 今回採用する実装前提（選定案） | 独自に定義する内容 |
| --- | --- | --- |
| VB.NET / WinForms | .NET 10、Windows Forms、SQL Server 2022 | Form、イベント、BindingSource、ErrorProvider、VB型・例外 |
| C# / WPF | .NET 10、WPF、SQL Server 2022 | XAML、MVVM、Command、通知・検証、Dispatcher |
| C# / ASP.NET | ASP.NET Core MVC／Razor、.NET 10、SQL Server 2022 | サーバー描画、ModelState、POST/Redirect/GET、認証・CSRF |
| Vue / C# API | Vue 3／TypeScript、ASP.NET Core Web API、SQL Server 2022 | SFC、Composition API、JSON契約、画面とAPIの分離 |
| AS400 / RPG | IBM i 7.5、ILE RPG全自由形式、DDS 5250、Db2 for i | DSPF・サブファイル・プロシージャー・CCSID・コミットメント制御 |

採用処理系・DB製品・バージョンは上記の設計基準に従う。画面設計はWEB系（WPFを含む）・WinForms系・Text系の三分類とし、本方式はWEB系である。WPF/XAMLと既存バインドは維持する。COBOLはText端末アダプターへ仕様を改訂し、端末製品は未選定とする。AS400_RPGはIBM iのILE RPG/DDSによるText系とする。各方式の具体的な制約はその方式内で閉じ、各方式は別配備・別DBを原則とする。

## 範囲と制約

業務5表・89論理項目、5分類70コード、検索・登録の2画面、成績対象外を継承する。保持期間・学校種別・実クラス・認証基盤製品は未指定。画面パネル分割や補助技術表を追加しても業務機能の追加とは区別する。

本版の方式別評価設計は、小規模校向けに保存を短時間直列化する方法を許容する。DBの同時保存制御を利用し、プロセス内だけのフラグでは代用しない。細粒度化は性能測定後の変更とし、定員・同一人物候補・マスタ変更の競合試験を維持する。確認待ちにロックを保持しない。

AccessのACCDB単体では利用者別の強いDB権限境界を提供できない。共有ファイルを直接改変できる利用者に対し、VBA画面の権限制御を完全な保護と説明しない。信頼された職員だけの評価構成とし、本番で厳格な閲覧者／担当者分離が必要ならサーバーDBまたはAPIを介する別構成の承認を条件とする。[S-09]

Text系の端末表示は保存可能なUnicode文字集合と一致するとは限らない。表示セル数、固定長領域のバイト数、業務文字数を分け、変換不能文字を上書きせず保持し、全文補助入力と端末実機の確認を方式ごとに定義する。COBOLもText系とし、内部UTF-8データの保持をWeb画面の採用理由へ読み替えない。

## 検索と編集の最適化判断

小規模の学生管理という利用者指定を設計前提とし、件数・頻度の実測値とは扱わない。対象発見には学籍番号の前方一致（SRC-001）、氏名照合キーの部分一致（SRC-002）、クラスIDの完全一致（SRC-006）、在籍区分の複数OR（SRC-008）を使用する。4条件間はAND、未指定の条件は追加しない。初期在籍は在学・休学、全解除で全区分。論理削除済みは常に除外する。

SRC-003/004/005/007/009/010/011/012は廃止しIDを再利用しない。氏名カナ、年度・学年、未所属専用、都道府県、電話、入学期間による詳細絞込みは設けない。年度・学年はクラス候補と結果の識別情報へ集約する。候補は全年度・停止・期間外を含み、年度／学年／クラスコード／名称で区別する。候補なしは「すべて」を残し、停止値を理由に検索を拒否しない。

一覧は学籍番号、氏名＋カナ、生年月日（和暦）、年度＋学年、クラス、在籍区分、操作の7列・8論理項目（SRC-020/021/022/023/024/025/026/030）。SRC-027/028/029は一覧DTOから廃止し、住所・本人電話・更新情報は既存の学生編集／参照画面で確認する。検索の更新日時ソートは維持するが、更新日時を一覧DTOへ返す理由にしない。20/50/100件・既定20、許可4ソートと方向、1万件上限、非削除・認可・所有者・期限・Revision契約は維持する。

検索形式版は `student-search-compact-1` とする。既存のフォーム／Window別SearchContextの読出し時に形式版を照合する。旧版・形式版欠落は8条件だけ捨てて自動復元せず、検索状態全体を未検索・初期4条件・20件・学籍番号昇順へ再初期化し、旧形式のため初期化した旨を通知する。現行形式へ廃止／未知条件が渡された場合はCHK-024／E-COM-003で拒否し、黙って無視しない。形式版はRevisionと別に検査し、状態ID・期待Revision・所有者・画面インスタンス・30分期限の照合を省略しない。新しいHTTPエンドポイントは追加せず、ネイティブの型付き呼出しと状態ストアの境界へ適用する。

通常編集は基本情報6項目を上段の3列×2行へ置き、下段を「住所・本人連絡先」「在籍・所属」「緊急連絡先・備考・理由」の3列にする。更新情報と操作バーは通常フローの末尾に置き、入力・エラー・説明へ重ねない。REG-001～034と全保存項目、和暦4入力、原入力／保存文字数、条件付き必須、保存19入力／更新18入力＋生成照合値2は維持する。

通常表示の設計確認サイズは1366×650および1280×650 CSS px・100%。入力高さ34px、文字12px以上を基本とする。長い1行入力は標準部品内でカーソル移動して全文を編集でき、備考・理由は複数行で全文へ到達できる。狭幅、200%相当、項目エラー展開時は縦スクロールを許可する。通常編集に確認例を縦積みせず、重複・削除・未保存破棄は排他的な別ダイアログとする。埋め込みHTMLから作業用に抽出した同じ断片のdata-stateをduplicate/delete/discardへ切り替え、排他的な確認状態を検査する。取消を既定とし、確認待ちにDBロックを保持しない。

### 2026-10-28 基本設計の書式・追跡性適用

学生検索/登録の19列を11列へ整理し、項目ID・グループ・論理項目・raw/保存上限・条件付き必須・初期値・未設定・候補/N/CHK/イベント・DB連携を移送した。DB2列は方式内TABLE正本の論理名を使い、検索日時など永続起源のない一時情報に架空列を作らない。4以上の手順を階層化し、既存CHKと日本語MSG、OPと項目更新仕様、検索ERのキー/分類を追跡できるよう明示した。

これは既存設計の書式と説明の適用であり、新機能・業務値・認証・DBプロファイルの変更ではない。詳細仕様・TABLE9列・既存HTMLを保全する。初期確認用データ/QA/採用プロファイルを再設定しない。今回の文書静的確認と、アプリ生成・DB実行・受入・正式採点を区別し、未採点はformalScore=null。
