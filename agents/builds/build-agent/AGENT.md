# 仕様からシステム生成Agent 契約

版7.14／2026-10-30。固定build/・方式内.tmp/・Git履歴とAccess品質gateを維持し、WEB/WinForms/Textの配置familyと描画技術を、独立期待値・実製品の検査へ接続する。

## 概要

AG-BUILD。Codexが本契約を読み、選択projectの仕様から各方式のソースを生成する。対象projectIdと工程を明示した実行で使用する。[実行指示](PROMPT.md)を入口とし、[事前検査スクリプト](scripts/preflight.mjs)で入力版・SHA-256・構造検査結果を保存する。スクリプトは文書検査であり、コード生成器や業務実装の合格判定ではない。

UIP-03aの認証入力群・同型ペアを、[UIパターン生成チェック](docs/UIパターン生成チェック.md)に従って共通の幅/配置定義へ実装する。AccessはAUI-06aと専用チェックを併用し、入力上限とは別に、各状態の実部品と描画の整列を検査する。Agent改善だけの依頼では既存仕様・アプリを再生成しない。

## 入出力

| 区分 | 内容 |
| --- | --- |
| 入力 | docsの全体規則、agentsの役割定義、選択方式のspecRoot内の詳細/共通/DB定義/開発規約・プロファイル。要件と基本設計は同じspecRoot内で理解・矛盾確認用 |
| 実行ルート | specRoot=対象project/spec/方式ID/、sourceRoot=対象project/srcs/方式ID/を別々に固定する。旧sourceRoot/specへのfallbackや他方式の入力共用は行わない |
| 出力 | 対象project/srcs/方式ID/のソース正本・DDL・画面・手順を更新し、build/へ最終配布物、build/generation/へ入力・出力manifestと構造/中断報告、build/test-results/へ今回の最終検査結果を固定名で更新。中間結果は方式内.tmp/ |
| 書込み範囲 | agents/builds/build-agent/と実行要求で指定したprojectのみ。project外の問題は報告だけ。ユーザーが範囲を狭めた場合はその指定を優先 |
| 除外入力 | spec-eval、別project、選択外方式のspecRoot/ソース、過去レポートの合格判定。評価期待値から実装を作らない |
| 禁止事項 | 上限/必須/権限/DB/方式の無断変更、未決事項の承認扱い、構造問題の推測補完、未生成の方式を実装済みとすること |

## 実行手順

1. 全体docsとagentsの役割定義を読み、projectId、工程、方式一覧、specRootとsourceRoot、出力先、許可/除外パス、実行IDを確定する。存在しないprojectを自動作成しない。
2. `node agents/builds/build-agent/scripts/preflight.mjs --project <projectId> --run-id <実行ID> --profile <方式ID>` をリポジトリから実行する。build/generation/の固定inputs.json・structure.json・structure.mdを今回の値へ更新し、前回のoutputs.jsonを失効させる。実行IDは属性であり履歴フォルダーを作らない。終了コード2は構造問題による中断、1は検査自体の失敗、0は機械的構造検査の通過だけを意味する。配置確認だけの工程では同じコマンドへ`--inspect-only true`を加える。検査専用ではinputs/structureを標準出力のJSONへ返し、build/・.tmp/を書き換えず、旧outputs.jsonやsource.zipも失効させない。この結果から実装生成のmanifestを確定せず、生成工程は通常のpreflightで入力を凍結する。
3. 自動検査とは別に、各方式の詳細・共通・DB・規約の入出力、型、状態、認証、正規化、保存/取消境界の整合性を確認する。初回に読んだ仕様のハッシュを固定し、他Agentが入力を変更した場合は旧版と混在させず再検査する。

   [UIパターン規約](../../../docs/UIパターン規約.md)と[UIパターン生成チェック](docs/UIパターン生成チェック.md)を全方式で読み、WEB=CSharp_ASPNET/Vue_CSharpAPI/CSharp_WPF、WINFORMS=VB.NET_WinForms/Access、TEXT=COBOL/AS400_RPGの配置分類を保つ。該当する[WEB](../../../docs/WEB画面品質規約.md)/[WinForms](../../../docs/WinForms画面品質規約.md)/[Text](../../../docs/Text画面品質規約.md)規約だけを方式別に凍結する。新profileは選択specRootの規約/UIパターン.jsonでfamily/rendererを明示し、未確定のUIを完成扱いにしない。既知分類の無断変更、CLIの画面化、source側profile.jsonからの入力分類推測を禁止する。
4. 局所バグは下記基準に従って仕様と必要な関連資料を修正し、変更前後の版/ハッシュ・理由をbuild/generation/へ記録して再検査する。構造問題は修正せず、同固定先へ根拠を記録して生成を中断する。
5. 構造問題がなくなった入力セットから、各方式の規約どおりのプロジェクト・実ソース・DDL・設定例・画面資源をsrcs/方式ID/へ生成する。別方式のUIで代替せず、既存成果物を無断で削除しない。入力仕様IDと実装ファイル/シンボルの対応を保存する。

   MDの文章・項目/イベントと埋込み静的HTMLを正本として、採用パターン・共通トークン・状態/保存契約を同方式内の標準部品へ実装する。外部の単独HTML/JSデモや架空の保存・件数を本番処理へ転用せず、設計との差分を記録する。ブラウザー方式は共通サイト枠、行の対象操作、サーバー側検索/安定順序/ページング、URL/履歴・復帰・未保存保護を実装する。20/50/100件やCSS寸法は採用候補であり既存契約や他familyへ強制しない。CSharp_WPFはWEB配置をXAML/DIP/実部品で実現し、DOM/CSS/URL/ブラウザー履歴を必須化しない。WinFormsはFormのclient領域/DPI/伸縮/実入力と保存境界、Textは採用端末の行列/セル/保護属性/キーとページ・入力保持を検査する。具体手順は生成チェックに従う。

   採用方式の標準部品と入力機能を使い、新規/編集/参照の入力属性、業務キー/自動採番ID、raw/表示/正規化/保存の桁、フォント・グループ見出しの可読性を具体化する。Accessは[Access生成チェック](docs/Access生成チェック.md)を実施する。値の直接代入やHTMLモックの表示だけでキーボード入力・マスク・実画面が合格したとしない。

   全方式で[UI適合検査](../../../docs/UI適合検査.md)を適用し、実装前にtests/ui-contract.jsonの具体的期待値と根拠版/SHAを固定する。profile.jsonのuiConformance.required/contractを宣言し、最終製品から独立取得したui-observations.jsonで全対象部品・必須rule/property、字体・寸法・描画/可読性・実操作を照合する。AccessはTab/付属ラベルを含め標準のクラシック外観と本文11pt等の役割別トークンを具体化し、タイトル等の採用済み例外を保つ。Web等は同方式仕様の単位/部品/最適な実現を使う。未観測・未指定部品・旧製品・期待値欠落は失敗とし、生成実値の転記や定義の自己比較でPASSを作らない。

   Accessは[Access画面品質規約](../../../docs/Access画面品質規約.md)を凍結入力へ含め、画面タイプ・各Form/Page/Dialog・状態ごとに合理性/統一性/見やすさ/操作性を確認する。既存改修の範囲未指定はlayout_onlyとし、対象の常時識別、列幅/全文到達、操作の近接、選択一致を保存/認証/DBの無断変更と切り離す。仕様からaccessScreenChecksの9カテゴリと個別ruleを先に定義し、対象外理由を記す。保存方式/単位、入力中/未反映の明細、別対象への移動/離脱、保存失敗後の保持は実キー/クリックとデータ再読込で検査し、interactionにも証拠を残す。

AUI-05a～05cにより、タイトルの本文フォントへの上書き、TextBox高と文字領域の不整合、CP932/Unicode境界の文字化けを全Form/Page/Dialogへ横断検査する。VBAの厳密往復と実行/実表示を別々に記録し、非日本語ACPでの暗黙変換や過去のPASSで補わない。

   [テストデータ整備規約](../../../docs/テストデータ整備規約.md)に従い、必要マスタと架空の初期確認用業務データ・投入処理・操作手順を作成する。初回の空の確認用環境へ投入し、既存利用者データを自動リセットせず、再実行の冪等性・参照整合・通常の検索/新規保存経路を検査する。データ定義・正式fixtureはsourceRootの正本、実行コピーは.tmp、今回のデータmanifest/検査/手順はbuildの固定先へ置く。データ整備は全方式の次回生成に適用し、別方式を今回の実行範囲へ追加する根拠にしない。

各方式は独立したテスト材料とする。仕様は `project/spec/方式ID/` のspecRoot内で独立して完結し、コード・DB資源・生成器・ビルド・試験は `project/srcs/方式ID/` のsourceRoot内で完結する。方式内閉包はこの対応する2つの領域を意味し、仕様をソース内へ戻す条件ではない。specRootの不足は構造問題として記録し、旧sourceRoot/specや横断共有仕様から補わない。他方式の仕様・ライブラリー・ソースを引用しない。共通ファイル、外部ProjectReference、リンクによる共用は使用しない。方式に適した言語・構成で作成する。逆生成へ渡すsource-onlyパッケージから原仕様を除外し、逆生成のallowedPathsへproject/spec/全体・spec-eval・他方式を含めない。DB共有・Access単体/サーバーDB・成果物名は選択project/方式の採用プロファイルで固定する。特定題材の過去指示を全projectへ強制しない。共有プロファイルが明示採用された場合だけ同方式内の共有契約を使い、独立ACCDBを採用する方式を暗黙にSQLフロントエンドへ変更しない。成果物名やsolution名も題材固定とせず、方式の実装配置契約・配布設定を参照する。
6. 利用可能な処理系でコンパイル/単体検査を行う。実行要求の品質水準と改善回数を記録し、品質「高」では正常系・境界/複合/権限/競合/障害・独立テスト・実UI・配布再現の必要範囲を検査する。改善回数Nは検査→指摘修正→回帰確認のサイクルをN回行い、固定build/test-results/quality-cycles.jsonの配列へ入力/コード版・検査・指摘・修正・再検証・未実施を記録する。変更不要の回も根拠を残し、不具合や修正を捏造しない。コンパイル途中、fixture実行コピー、試行・失敗ログ、処理系・キャッシュは方式内.tmp/に置く。最終配布物だけbuild/、今回の最終検査結果・実行コマンド・処理系・終了値・検査範囲・未実施はbuild/test-results/の固定ファイルへ更新する。日付・実行ID・attempt別成果やbackupを累積しない。DB実行・実機試験は利用者の指示と環境に従い、専用fixtureと配備初期DBを分ける。秘密情報や本番データを成果物へ含めない。
7. 生成・ビルド・単体・結合・実機・逆生成・採点を別状態で報告する。最後に同じproject・profile・実行IDでmanifest.mjsを実行し、入力ハッシュを再照合してbuild/generation/outputs.jsonを更新する。入力変更・失敗を以前のPASSで補わない。全方式指定の共通集約だけproject/build/、共通中間物だけproject/.tmp/を使う。履歴はGitで管理する。manifestは実装や正式受入の合格を意味しない。

   UI方式は先にui-conformance.mjsで今回のgate記録を確定する。manifestは必須宣言・契約・実測・原根拠・validator・最終artifactのSHAを再照合し、削除/未検査/旧観測ならoutputsを確定しない。非UI例外はrequired:false、理由、同方式の凍結根拠sourceFilesを明示する。今回の規則を凍結した生成で宣言を省略しない。source-only ZIPからUI試験期待値とprofileの試験参照を除外する。

source-onlyの再構築・通常初期設定に必要なhelperはsourceRoot/profile.jsonのproductionHelpersへ、方式内POSIX相対ファイルの完全一致配列で明示する。toolsは宣言ファイルと必要ancestorだけを含め、題材固有helperを無条件で許可しない。絶対/外部/リンク/重複/不在/ディレクトリ、tests・.tmp・仕様/評価・バイナリを拒否する。正常初期データ資源と正式ライセンスはproductionの必要資源として保持し、独立試験の期待値を混ぜない。梱包後は原仕様も未宣言toolsもない別展開から、実ビルド入口と初期設定CLIの閉包を検証する。

## 問題の分類と中断

局所バグは、同じ入力セットから正しい値が一意に確定する誤字・単独の誤記・参照先の誤記等。修正が業務判断、共有契約、仕様階層や複数方式の再設計を要求しないことを確認する。正本が衝突している場合に片方を恣意的に採用しない。

構造問題は、章/メタ情報/表構造の不一致、必要な定義や入出力契約の欠落、詳細・共通・DB間で両立しない型/状態/責務、実装入力だけでは閉じない参照等。reportに問題ID、現行版、ファイル/行、相反する記載、影響方式、再開条件を記録し、中断する。別Agentによる修正を待つ。中断中に仮のアプリや動作しない骨組みを完成品として生成しない。今回の依頼でAgent改善が許可されていれば、Agentの処理/固定値/入力境界の不備は先に修正して回帰検査し再開する。仕様の別工程に属する問題は担当契約と根拠/影響/採用判断/残件を記録して引き継ぐ。利用者がroot等の報告先を明示した場合は、その指定ファイルを報告の書込み許可範囲に含める。

稼働前の運用留保や処理系の未導入だけを構造問題にしない。範囲外の問題はbuild/generation/へ報告する。再開時は新しい入力版・ハッシュで事前検査と必要な再検証を行い、固定の最終記録を更新する。旧状態はGitで参照し、過去の結果を新版へ流用しない。入力・QA・正式fixtureは履歴整理の対象にしない。

## 完了条件

指定された資料から追跡可能な成果物を作り、未確認・未決・矛盾を報告する。形式合格を実装/ビルド/試験/採点の合格とみなさない。所属プロジェクト外を書き換えず、版と根拠を記録する。全体規則は../../../docs、プロジェクト固有の長さ・DB・受入条件は選択方式のspecRootの入力セットに従う。仕様の移動だけを理由に業務UI・DB・権限・既存アプリを再設計しない。

初期確認用データの件数/版/基準日/用途、投入と再投入の結果、利用者向け確認手順を残す。Accessは今回生成したACCDBで、新規キーの実入力、マスク対象の桁/貼付/保存再読込、編集/参照の保護、フォント/見出し/一覧/ダイアログを検査する。実機の版・bit・DPI・サイズ・範囲を明示し、未導入の環境や未実施を過去のPASSで補わない。

Accessでは4観点レビューの各指摘を画面/状態・利用者の支障・修正・個別合格条件・再検証へ対応させる。全画面のaccessScreenChecks・操作証拠の欠落をUI gateとmanifestで拒否し、用途を無視した全欄の一律同幅・余白削減・文字縮小だけを品質達成にしない。通常表示以外の長文/未選択/空/失敗/未保存離脱と対象環境の実施範囲を示す。仕様HTMLの描画、構造検査、実ACCDBの見やすさ、実操作/再読込、利用者受入は別状態で報告する。

各familyで設計ID→実装/部品→UI契約の個別rule→最終製品の属性/描画/操作証拠を追跡できることを完了条件にする。描画技術に合う単位・方法を使い、WPFのHTMLモック、Textのstdout整列、参考パッケージの過去PASSを製品UI合格にしない。既知/明示family規約の削除・更新ではpreflight/manifestを失効させ、非該当familyの規約を方式固有入力に混ぜない。構造・ビルド・実UI・DB/API再読込・正式受入と未実施を分ける。
