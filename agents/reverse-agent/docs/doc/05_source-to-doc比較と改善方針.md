# 5. source-to-docとの比較と改善方針

## 5.1 比較対象を確定した

今回案内された`D:\開発\source-to-doc`のGitHub上の対象は、**`tujinrong/source-to-doc`の`main`**として確認した。対象読取版は`d9e6033ae9cf5de95ffbd814c7dfc0edd6d892c5`。ローカルの未push変更との一致は確認していない。

本プロジェクトの比較版は`c348187912164218aac0d9df2bc1b5b7c9aafe8b`。今回の目的は構造と改善方針の説明であり、旧プロジェクトを変更・起動したり、出力品質や性能を同条件で測定したりしていない。

## 5.2 旧プロジェクトにも良い分離が既にある

[AGENTS.md](https://github.com/tujinrong/source-to-doc/blob/d9e6033ae9cf5de95ffbd814c7dfc0edd6d892c5/AGENTS.md)とルート構成には、以下が記載されている。すべてを今回の小さなプロジェクトへ移し替える必要はない。

| 旧プロジェクトの資産 | 役割 | 維持・再利用する価値 |
| --- | --- | --- |
| source-analysis1～4 | デスクトップ、Java Web、Web/API、Access等の方式別解析 | 既に蓄積された方式対応・抽出ルール |
| source-to-spec | 案件に依存しない仕様化 | 抽出と文章化の分離 |
| spec-contracts | schema、共通計画、モジュール契約 | 中間データの正本・登録台帳 |
| analysis-validator | 固定評価器、方式別・案件別ルール | 生成器だけで判断しないための資産 |
| projects/{id} | 案件のinput、analysis、spec、output等 | 案件単位の所有境界・履歴 |
| spec-pipeline | プロジェクト解決、ロック、受渡し、実行制御 | 入口・ロック管理の一本化 |
| 各種manual／video／doc-analysis／db-sync | 仕様以外の納品物や別ワークフロー | 必要業務では残す。ソース解析だけとの単純規模比較は不適切 |

[analysis_module_router.py](https://github.com/tujinrong/source-to-doc/blob/d9e6033ae9cf5de95ffbd814c7dfc0edd6d892c5/spec-pipeline/analysis_module_router.py)は実際に入力構造を調べ、Access、VB6、Java Web、Web/API、JavaFX、WPF、WinForms等の候補を選ぶ。方式別の分離は文書だけでなく実装にも存在する。ただし、形式を選べることと、その全方式が同品質で完全解析できることは別である。

## 5.3 実際に確認できた集中・注意点

### A. 中心ファイルの責務が広い

GitHubツリーのサイズは、`spec-pipeline/orchestrator.py`が447,620バイト、`analysis_pilot.py`が137,481バイト。統括処理の先頭では案件解決、ロック、工程実行、Pilot、復旧、納品形式等の依存が確認できる。

これは保守対象を確認する手掛かりであって、サイズだけで悪い設計や不具合と断定しない。詳細な関数依存を調べる前の推奨は、中心処理から業務解釈を増やさず、「登録台帳に従って子処理を起動し、結果契約を確認する」責務へ寄せること。

根拠：[orchestrator.py](https://github.com/tujinrong/source-to-doc/blob/d9e6033ae9cf5de95ffbd814c7dfc0edd6d892c5/spec-pipeline/orchestrator.py#L1-L110)、[Pilot制御](https://github.com/tujinrong/source-to-doc/blob/d9e6033ae9cf5de95ffbd814c7dfc0edd6d892c5/spec-pipeline/analysis_pilot.py#L1-L140)。

### B. 案件IDと方式の対応が中心コードにある

`PROJECT_PREFIX_ANALYSIS_MODULES`に001～004の接頭辞と方式別解析器の対応がある一方、入力証拠による判定も存在する。推奨は、案件IDを業務上の識別として保ち、能力・構造判定・明示設定による選択を主にすること。混在案件や未知方式を既定のデスクトップ解析器へ渡すときも、その後の方式検査で必ず未対応を明示する。

### C. 指示書の大きさと読込規則を確認する

ルート`AGENTS.md`は34,243バイトで、公式に示されるCodexの標準的なプロジェクト指示読込上限32KiB（32,768バイト）を単独で超える。**既定設定で自動読込する場合に末尾や下位文書が取り込まれないリスクがある**。利用環境の設定変更や独自のプロンプト添付がある可能性は未確認で、実際に欠落したと断定しない。

また旧AGENTSの「root優先」という独自規則は、Codex公式の階層読込では下位の記述が後に連結される仕組みと同じではない。独自ランナーがどの順で何を添付するか、Codex起動ディレクトリ、適用された指示を明示的に検査する。下位への保護ルールの伝達を文章の優先宣言だけに頼らず、CIの変更範囲検査で守る。

推奨は長い説明を削除することではなく、短い入口に安全条件・コマンド・資料への導線を残し、詳細を必要時に読むこと。[Codexの指示読込規則](https://developers.openai.com/codex/guides/agents-md)

## 5.4 今回のプロジェクトも同じ問題になり得る

| 項目 | contextbase-chatgptの現状 | 残る課題 |
| --- | --- | --- |
| 案件分離 | srcとsrc-dynamicを分けている | フォルダ名だけでは汎用性を保証しない |
| 案件選択 | 原本アンカーのハッシュ照合 | 小さな変更でも不一致。未知案件は限定出力へ移る |
| 文章の品質 | 社員Pilotの詳細資産と原本照合 | 社員専用の固定文章・経路表への依存がある |
| 画面復元 | 中立ツリーと状態別描画 | 対応するVue条件・部品が限定され、UI寸法も既定値を持つ |
| DB追跡 | 社員用経路の詳しい照合 | 未知のDBラッパーを自動的に完全解釈するものではない |
| 評価 | 原本・文書・図・変更保護 | 同じ資産を生成と期待値へ使う箇所は意味の独立評価にならない |
| 再生成 | 検証後公開とファイルキャッシュ | 全面的な影響差分実行・自動適応ループは未完成 |

したがって「こちらへ移れば汎用性が解決する」とはまだ言えない。**今回のプロジェクトは、小さい範囲で共通契約と高品質なPilotを固める実験基盤として有効**である。旧プロジェクトの幅広い対応と比較するなら、同じ対象・同じ評価基準で測る必要がある。

## 5.5 推奨する進め方

| 段階 | 変更内容 | 成功の条件 |
| --- | --- | --- |
| 1. 現状固定 | 社員の承認済み画面・事実・未確認事項・試験を固定 | 現状品質が測定可能。期待値を無断変更しない |
| 2. 契約の整理 | 既存spec-contractsも参照し、最小の共通データ形式を決める | 同じ概念を案件別に異なる意味で使わない |
| 3. 例外のデータ化 | 名前・表・部品・API対応・補足文章を宣言データへ移す | 新しい同方式案件で共通Pythonに案件名分岐を足さない |
| 4. 限定的な適応 | 不足する方式だけ小さなアダプターをAI支援で追加 | 原本の正解標本・既存回帰・未対応検出に通る |
| 5. 独立評価 | 未使用の別構造で評価し、失敗を分類 | 調整済み案件だけの合格を汎用成功と呼ばない |
| 6. 必要資産を移植 | 実測で有効な部分だけ旧新の間で共有 | 二つの統括基盤へ同じ責務を二重実装しない |

全面書換え、全機能の一括移行、毎案件の一式コピー、さらに大きな統括フレームワーク追加を先に行わない。まず「新案件一つを追加するために共通コード何箇所を変更したか」と「確認済み業務仕様がどれだけ保持されたか」を測る。

## 5.6 調査の限界

比較先の全ソースを網羅監査していないため、重複率、循環依存、未使用コード、テストの実効網羅率、どちらが速いかは結論を出していない。今回確認した構造からの提案と、実測で確定した不具合を区別する。比較先のソース・設定は今回変更しない。
