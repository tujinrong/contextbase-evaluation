# 3. Codexと目標駆動開発

調査日：2026-10-06。製品機能は公式資料を確認した。以下の本案件への適用評価は設計上の判断であり、今回Codexとの比較実験を実施した結果ではない。

## 3.1 同じ品質で実現できるか

**Codexで同等品質を目標に実装・修正・検証することは可能。ただし、製品名だけで同じ結果になる保証はない。** 公式には、コードの理解、複数箇所の変更、テスト実行、レビュー、文書作成等の開発支援が示されている。[公式の利用例](https://openai.com/business/guides-and-resources/how-openai-uses-codex/)

| 何を「同じ」と呼ぶか | 判断 | 確認方法 |
| --- | --- | --- |
| 確定済みPythonで既存社員仕様を再生成 | 入力、コード、依存、設定が同じなら再現を検査できる | 文書内容、構造データ、レイアウト断片のハッシュ。描画環境差を別扱い |
| Codexが別途書いた実装で同等の仕様を作る | 達成を目指せるが未実測 | 同じ原本、同じ受入基準、固定テスト、第三者レビューで比較 |
| 未知案件を社員Pilotと同じ深さで自動解析 | 現状未実装・未実証 | 新しい構造の案件を学習・調整用と評価用に分けて検証 |
| 稼働アプリと完全に同じ挙動を再実装 | 現状の静的合格だけでは判断不可 | UI/API/DBの実行、外部依存、競合・失敗経路を含む比較 |

現在の社員品質は、汎用Pythonだけで得られたものではない。原本調査、業務解釈、個別の文章、固定経路表、レイアウト・不変範囲、検査資産を組み合わせた結果である。Codexへはこの資産一式と未確認事項を渡す必要がある。[社員DB生成の実装](../../src-dynamic/mcterp/mcterpgen/employee_db.py)

## 3.2 手順指定より目標駆動にできるか

できる。利用者が毎回「次にこのファイルを読む、次にこの関数を作る」と指定する代わりに、**達成する状態・変更禁止範囲・証明方法・許可資源・停止条件**を定め、AIに調査と実装の手順を選ばせる。

Codexには持続する目標を扱うGoalsの公式説明がある。対応ビルドでは`/goal`で目標を設定でき、予算・中断・依存情報不足等による停止を伴う。利用中の版と利用可能なコマンドは確認が必要であり、無制限の自律稼働や成功保証を意味しない。[Using Goals in Codex](https://developers.openai.com/cookbook/examples/codex/using_goals_in_codex)

```text
弱い目標：社員マスタをもっと詳しくする。

検証可能な目標：
社員マスタの検索・登録について、画面入力からAPI・共通処理・DB結果まで
途切れなく説明する。抽出条件、空値、並び順、関連情報の反映順を明示する。
承認済みレイアウトと他機能は変更しない。
各説明を原本の位置と対応付け、独立したチェックで欠落を確認する。
未取得のライブラリ内部は確定せず、境界と不足を記録する。
```

この例の調査手順はAIが変えてよい。しかし「原本を変更しない」「不足を合格に変えない」「証拠なしに結合を創作しない」という条件は変えてはいけない。

### 目標駆動と固定パイプラインは併用する

```text
AIの適応ループ：目標 → 調査 → 不足の特定 → 修正案 → 検証 → 次の行動
                         ↓ 承認済みの解析器・定義
固定の生成処理：原本 → 抽出JSON → 関係付け → 文書 → 決定的な検査 → 公開
```

毎回の文書再生成までAIに自由に書き直させる必要はない。初回適応・不足箇所・変更の意味の判定にはAIを使い、確認済みの抽出・変換・公開は小さな固定プログラムで再現する。これが、目標駆動と保守性を両立させる本案件向けの提案である。

## 3.3 どこまで任せるか

| 作業 | 任せる範囲 | 固定する条件 |
| --- | --- | --- |
| 未知コードの調査 | 関係ファイルの探索、仮説、不足一覧 | 推測を事実として記録しない |
| 解析器の改修 | 小さな差分、テスト、最小再現例 | 評価器・期待値の無断緩和禁止 |
| 仕様の文章化 | 根拠付き事実を自然な日本語へ編集 | 個別の意味・空値・順序を落とさない |
| UI復元 | 定義・状態・画像を用いた比較補助 | 承認済み範囲・実測と近似を区別 |
| DB追跡 | 呼出、引数、条件、ルーチン、参照関係の調査 | 実際のJOINと名称補完、FKと論理関係を分ける |
| 最適化 | ボトルネックの調査と比較実験 | 品質を満たした候補同士で総時間比較 |
| 業務承認 | 不整合と選択肢の提示まで | 業務上どれが正しいかを利用者が承認 |
| 本番DBや外部サービス | 明示許可と専用環境がある範囲のみ | 実データ変更、秘密情報、料金発生を無断実行しない |

OpenAIの実践報告も、巨大な一枚の指示書より、短い入口と必要時に読む資料、機械的に確認できる境界・試験を重視する。この方式を参考に、ゴールだけでなく検証できる開発環境を整える。[Harness engineering](https://openai.com/index/harness-engineering/)

## 3.4 同品質を判定する基準案

同品質とは文章が同じ長さになることではない。次の基準を社員Pilotと評価用案件で共通に固定する。

| 軸 | 基準例 |
| --- | --- |
| 範囲 | 全入力の扱いを列挙し、解析済み・除外・未対応の合計を一致させる |
| 項目 | 名称・順序・役割・必須・長さ・単位・DB対応を原本と照合 |
| イベント | 入力、状態条件、処理順、反映先、正常・失敗・取消、出力例を確認 |
| DB | 対象列、キー、条件、呼出先、更新境界、明示SQL結合と後段補完を区別 |
| 根拠 | 重要な記述に原本位置・版を持たせ、未解決と競合を残す |
| 保護 | 原本不変、他機能不変、承認済み画面不変 |
| 実装比較 | 実行したケース・条件の範囲と、未実行の範囲を明記 |
| 再利用 | 評価用の別案件で、共通エンジン修正なしに受入基準へ適合するか |

生成器自身が作った文章と同じ文章を期待値にする検査は、欠落防止には役立つが、意味の正しさの独立評価ではない。原本を別に列挙する試験、固定した正解標本、意図的な誤りの検出、実行比較を組み合わせる。

## 3.5 Codexへ情報を渡す方法

短い`AGENTS.md`を入口にし、この`docs/doc`や対象別仕様・固定テストへ誘導する。命名・所有範囲・実行コマンドは固定し、調査の順序まで大量の例外ルールで縛らない。公式の指示ファイルは階層と読込上限を持つため、巨大な一枚に集約しない。[AGENTS.md公式](https://developers.openai.com/codex/guides/agents-md)

非対話実行には`codex exec`があり、`--json`のイベント記録と`--output-schema`の最終構造化出力を使用できる。ただしJSON Schemaに合うことは、内容が事実であることの保証ではない。[非対話実行](https://developers.openai.com/codex/noninteractive)

WindowsのローカルCLI等でも利用でき、PowerShell向けの権限制限機構がある。ただし、本案件の入力配置・外部ツール・社内ポリシーに合わせた許可設定が必要。ローカルでコマンドが動くことを「モデルへ機密情報が一切送られない」と同一視せず、コード・ログの扱いを事前に確認する。[Windowsの実行環境](https://developers.openai.com/codex/windows)

## 3.6 今回の判定

Codexでの開発は有力な選択肢であり、目標駆動にもできる。ただし本案件ではCodex対ChatGPTの同条件品質比較をまだ行っていない。社員Pilotを評価の入口とし、評価用の別機能・別構造を追加することで、製品名ではなく実測で判断する。
