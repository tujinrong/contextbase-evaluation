# ContextBaseによる２段階解析・仕様書生成方式【修正案】

## 1. 目的

ソースコードから仕様書を生成する際の解析精度、案件ごとの汎用性、再生成の安定性を改善するため、次の処理を明確に分離する。

1. システム全体、機能骨子、テーブル情報を整理する「基盤解析」
2. 基盤情報と関連ソースから動作を詳しく理解する「詳細解析」
3. 詳細解析結果を仕様書へ展開する「文書生成」
4. MDをHTML・PDF・Excelへ変換する「形式変換」

**解析は２段階とし、文書生成・形式変換は解析とは別工程とする。**

各工程は独立したプログラムとして実装する。１つの大きなプログラムの中で、ソース解析、業務判断、文章作成、Excel書式設定を混在させない。

本書に記載するフォルダ構成・プログラム名・コマンドは改修設計案であり、既存実装は可能な限り再利用する。

---

## 2. 全体方式

### 2.1 採用する構成

**ContextBase1を作成した後、ContextBase1とソースコードを使って詳細解析を行い、ContextBase2を作成する。仕様書はContextBase2から生成する。**

```text
input/
  ソースコード、画面定義、DB定義、既存資料、設定など
          │
          ▼
P1：基盤解析プログラム
  システム構造、一覧、機能骨子、テーブル定義、
  共通処理の構造、原本索引、関連先を整理
          │
          ▼
ContextBase1
  「何があり、どこを詳しく調べるべきか」
          │
          ├──────────── input/の関連ソース
          │                         │
          ▼                         ▼
P2：詳細解析プログラム
  条件、処理順序、分岐、項目の意味、DB操作、
  正常・異常時の動作、状態変化を解析
          │
          ▼
ContextBase2
  「どの条件で、何を、どの順番で行うか」
          │
          ▼
P3：仕様書生成プログラム
  解析済み情報を章・文章・表・図へ展開
          │
          ▼
output/md/
          │
          ▼
P4：形式変換プログラム
          │
          ├─ output/html/
          ├─ output/PDF/
          └─ output/Excel/

QA/      質問、仮定、回答、採用判断
report/  未完成事項、矛盾、解析範囲、検証結果
```

### 2.2 基本原則

- ContextBase1の要約を文章として膨らませるだけで、ContextBase2を作成しない。第２段階では関連ソースを詳しく解析する。
- 詳細解析で分かった内容を仕様書だけに直接追加しない。ContextBase2へ保存してから文書へ反映する。
- 文書生成時に解析不足を発見した場合は、詳細解析へ戻す。文書生成プログラムが独自に業務仕様を推測しない。

２段階解析は、同じ処理を２回実行することではない。第１段階で取得した構文情報・索引・キャッシュを利用し、第２段階では機能を横断した動作とデータの意味を解析する。

## 3. プログラムの分離

### 3.1 独立した４つのプログラム

| プログラム | 主な入力 | 主な出力 | 責任 |
|---|---|---|---|
| P1：基盤解析 | ソース、DB定義、関連資料、案件設定 | ContextBase1 | 全体構造、骨子、テーブル基礎定義、原本索引の作成 |
| P2：詳細解析 | ContextBase1、関連ソース、案件固有ルール、採用済みQA回答 | ContextBase2 | 機能・共通処理の詳細動作、データ関連、業務説明の確定 |
| P3：仕様書生成 | ContextBase2の公開用確定データ、文書構成ルール | MD、図・画面などの文書用素材 | 解析済み情報の文書化 |
| P4：形式変換 | MD、文書用素材、出力テンプレート | HTML、PDF、Excel | 内容を変えずに表示形式を変換 |

全体を一括実行する統括プログラムは別に設ける。ただし、統括プログラムは工程の実行、再開、検証、公開を管理するだけとし、解析や書式設定の本体を持たない。

### 3.2 分離の条件

各プログラムは、単独で実行・テスト・再実行できること。

工程間の受渡しは、版管理されたJSON・MD・素材ファイルと明示的なAPIで行う。前工程のメモリー上の状態や、他工程の内部変数に依存させない。

各工程は入力世代、処理状態、出力先、検証結果を記録し、後工程は必要な条件を満たした入力だけを使用する。

### 3.3 処理境界

| 工程 | 行ってよいこと | 行わないこと |
|---|---|---|
| 基盤解析 | 構造抽出、定義照合、基礎情報の推定、関連先の特定 | 詳細を確認せずに完成仕様と断定すること |
| 詳細解析 | 関連ソースの追跡、業務判断、条件・順序・状態の解析 | 原本へ戻らず、骨子だけから詳細動作を創作すること |
| 仕様書生成 | 確定済み説明の配置、表・図・章構成への展開 | ソースを独自解析して業務仕様を追加すること |
| 形式変換 | レイアウト、画像埋込み、罫線、改ページ、リンク変換 | 必須条件、DB対応、処理順序などの意味を変更すること |

## 4. 第１段階：ContextBase1の作成

### 4.1 役割

ContextBase1は、詳細解析のための土台とする。

単なる要約やファイル一覧ではなく、**機能骨子・テーブル基礎定義・共通構造・原本への対応を十分に整備する。**

### 4.2 保存する情報

| 分類 | 保存内容 |
|---|---|
| システム全体 | システム名、目的、業務範囲、利用者、開発言語、フレームワーク、構成、DB、外部接続 |
| 各種一覧 | 業務機能、画面、帳票、バッチ、API、ファイル、テーブル、DBオブジェクト、共通処理、共通UI、コード、メッセージ |
| 機能骨子 | 機能ID、名称、種類、入口、関連ファイル、入出力の概要、関連機能、処理単位 |
| テーブル基礎定義 | 論理名、物理名、列、型、長さ、精度、NULL、初期値、キー、制約、インデックス |
| 画面・帳票構造 | 部品、ラベル、定義順、領域、繰り返し、宣言上の属性、表示条件の記述位置 |
| イベント構造 | イベント入口、対応する処理、呼出先、未解決の呼出候補 |
| 共通構造 | 共通処理の入口、入出力、利用箇所、共通部品の構成 |
| 業務用語辞書 | 論理名、物理名、別名、略称、用語候補、名称の対応 |
| 関連索引 | 呼出関係、参照関係、SQL・マッピング・設定への接続 |
| 解析根拠 | ファイル、シンボル、行範囲、資料位置、ハッシュ、対象リビジョン |
| 未解決情報 | 未確定の定義、資料とソースの矛盾、追加確認先、QA参照 |

一覧は実装ファイル数ではなく、業務上の機能境界を考慮して作成する。画面とその処理クラスは関連付け、ファイルが分かれているだけで別機能として数えない。

### 4.3 テーブル情報の整備

テーブル情報は、第１段階の重点対象とする。

#### 定義資料がある場合

テーブル定義書、CREATE TABLE、ALTER TABLE、マイグレーション、ビュー定義、マッピングを照合する。

対象環境、リリース、適用順序を確認し、プログラムの参照・更新内容と整合する基礎定義を作成する。

資料間または資料とソースに矛盾がある場合は、両方の根拠と採用判断を保持する。

#### 定義資料がない場合

SQL、マッピング、代入処理、検索条件、保存処理、画面・帳票の利用箇所から推定する。

ただし、次の情報を区別する。

- 原本に明示された定義
- 複数の利用箇所から導出した定義
- 根拠が不足するため仮定した定義

画面の入力桁数を、そのままDB列の桁数と断定しない。検索・更新条件に使われる列を、根拠なく主キーと扱わない。

推定DDLを生成する場合は「推定DDL」として保存し、実DBから取得した定義と混同しない。

### 4.4 第２段階へ進む条件

対象機能について、次が確認できれば詳細解析へ進める。

| 条件 | 内容 |
|---|---|
| 対象の識別 | 機能の入口、関連ソース、共通処理が識別できる |
| データの識別 | 必要な表・列・保持先が識別され、未確定部分が明示されている |
| 根拠への接続 | 骨子から該当する原本へ戻れる |
| 構造の整合 | ID重複、必須情報欠落、不正な参照などが整理されている |

全システムのテーブル情報が100％完成するまで、すべての詳細解析を停止する方式にはしない。機能単位で準備状態を判定する。

## 5. 第２段階：ContextBase2の作成

### 5.1 役割

ContextBase2は、機能別・共通処理別の詳細解析結果の正本とする。

**ContextBase1と関連ソースを使用して、実際の条件、処理順序、データ操作、状態変化を解析する。**

### 5.2 詳細解析の対象

| 分類 | 解析内容 |
|---|---|
| 機能仕様 | 目的、利用者、開始条件、終了条件、前提、入出力、他機能との関係 |
| 項目詳細 | 意味、初期値、必須条件、形式、長さ単位、編集条件、候補取得、設定元、保存先 |
| イベント詳細 | 発生契機、実行条件、チェック順、処理手順、分岐、繰り返し、正常・異常時の結果 |
| データ操作 | 検索条件、結合条件、設定値、加工、更新条件、削除条件、更新順序 |
| 状態変化 | 入力保持、入力消去、セッション変更、画面状態、処理結果、遷移先 |
| 共通仕様 | 業務上の意味、利用条件、副作用、例外、共通UIの動作 |
| トランザクション・排他 | 更新単位、確定・取消条件、ロールバック、同時更新時の扱い |
| 外部連携 | API・ファイルの受渡し、認証、エラー、再試行、タイムアウト |
| メッセージ | 表示条件、表示先、内容、後続処理への影響 |
| レイアウト詳細 | 項目の表示・非表示、状態別レイアウト、一覧・帳票の出力条件 |
| 検証シナリオ | 正常系、異常系、境界値、取消・クリア、保存・削除の期待結果 |

画面内の処理だけで終了せず、必要に応じてサービス、共通処理、データアクセス、DB内処理まで追跡する。

追跡範囲を制限した場合や接続を解決できない場合は、その範囲を記録する。「解析できなかった」と「処理が存在しない」を区別する。

### 5.3 項目・イベント・データを接続する

次の関係を同じID体系で保持する。

```text
画面項目
  → 入力チェック
  → 加工・変換
  → 保存処理
  → DB項目

候補取得処理
  → 参照データ
  → 絞込条件・並び順
  → 選択部品

検索条件
  → 検索処理
  → 表・ビュー・結合
  → 表示項目
```

DB連携項目と候補取得元を混同しない。画面状態、セッション、DB、ファイル、外部APIの保持先も区別する。

### 5.4 詳細情報の保存方法

構造化情報と説明文を併用する。

条件、順序、分岐、DB操作、入出力、状態変化はJSONなどで構造化する。業務説明や補足は、対応するIDと根拠を付けてMDへ保存してよい。

完成した仕様書の文章だけを保存し、解析結果の代わりにしない。

### 5.5 ContextBase1への訂正

詳細解析で基礎定義の誤りを発見した場合は、次の手順で修正する。

```text
詳細解析で差異を発見
  → 根拠付きの修正提案を記録
  → ContextBase1の採用判断を更新
  → 影響するContextBase2を再評価
  → 関連する仕様書を再生成
```

P2は共有テーブル定義を無条件に上書きしない。複数機能からの矛盾を整理してから、基礎定義を更新する。

## 6. ContextBase1とContextBase2の管理境界

### 6.1 二重管理の防止

| 情報 | 管理主体 |
|---|---|
| システム構造、安定ID、テーブル基礎定義、原本索引 | ContextBase1 |
| 機能固有の条件、処理順序、項目詳細、DB利用仕様、業務説明 | ContextBase2 |
| 質問・回答・回答の採用状態 | QA |
| Excelの列幅、罫線、印刷設定など | 文書出力テンプレート |

テーブルの型・桁数などを、ContextBase1と全機能のContextBase2で別々に編集しない。

ContextBase2は使用したContextBase1の版と対象IDを参照する。

### 6.2 ContextBase2からの文書生成

P2の完了時に、文書生成に必要な共通定義・テーブル定義・説明・素材参照を解決した「公開用確定データ」を用意する。

P3はその確定データだけを使用し、ソースや更新途中のContextBase1を直接参照しない。

必要な定義をContextBase2へ複製する場合は、編集可能な第二の正本ではなく、自動生成された読取り専用スナップショットとして扱う。

### 6.3 根拠と確認状態

事実・推定・未確定の状態は、必要に応じて属性単位で管理する。

| 属性 | 内容 |
|---|---|
| 値 | 抽出・採用した内容 |
| 根拠種別 | 原本明示、導出、仮定、未確定、該当なし |
| 出典 | ソース位置、資料のシート・セル、関連する定義ID |
| 対象世代 | 案件ID、ソースハッシュ、コミット、設定条件 |
| 確認状態 | 未レビュー、照合済み、矛盾あり、再確認 |
| QA参照 | 関連する質問・回答・採用判断 |

推定の信頼度を記録する場合は理由を付ける。根拠のない数値スコアだけで、確認済みとは判定しない。

## 7. ContextBaseのフォルダ構成案

```text
ContextBase/
├─ manifest.json
│   対象案件、ソース世代、スキーマ・解析器の版、各層の参照関係
│
├─ 01-foundation/                  ContextBase1
│  ├─ system/                     システム全体情報
│  ├─ catalogs/                   各種一覧
│  ├─ glossary/                   用語・論理名辞書
│  ├─ database/                   テーブル・DBオブジェクト基礎定義
│  ├─ feature-skeletons/          機能骨子
│  ├─ common-index/               共通処理・共通UIの索引
│  ├─ relations/                  呼出・参照関係
│  └─ source-index/               原本索引・根拠
│
├─ 02-detailed/                    ContextBase2
│  ├─ functions/
│  │  └─ 機能ID/
│  │     ├─ feature.json
│  │     ├─ items.json
│  │     ├─ layout.json
│  │     ├─ events.json
│  │     ├─ data-relations.json
│  │     ├─ scenarios.json
│  │     └─ explanation.md
│  ├─ common/                     共通処理の詳細
│  ├─ table-usage/                テーブルの利用仕様
│  ├─ interfaces/                 外部連携の詳細
│  ├─ messages/                   メッセージの利用条件
│  ├─ decisions/                  採用判断・仮定・QA参照
│  └─ resolved/                   文書生成用の確定データ
│
└─ schemas/                       各情報の形式定義
```

機能・テーブル・共通処理単位に分割し、巨大なJSONを一括更新する構成を避ける。

`layout.json`は解析対象の画面・帳票構造を表す。仕様書Excelのレイアウト・罫線とは別に管理する。

## 8. srcとsrc-dynamicの役割

### 8.1 src：再利用可能な固定プログラム

`src/`には、案件を変えても再利用するプログラムを配置する。

| 分類 | 役割 |
|---|---|
| 基盤解析 | ContextBase1の構築、索引、定義照合、関連付け |
| 詳細解析 | ContextBase2の構築、処理・データ・状態の追跡 |
| 言語別解析器 | VB6、Access、Java、C#、Vueなどの一般的な構文・定義の抽出 |
| 共通情報モデル | スキーマ、ID、根拠、状態、参照関係、版管理 |
| 差分・再開管理 | ハッシュ、依存関係、キャッシュ、再解析範囲、途中再開 |
| 独立評価 | 原本照合、解析漏れ、整合性、文書内容・書式検査 |
| 仕様書生成 | ContextBase2からのMD・図・素材生成 |
| 形式変換 | MDからHTML・PDF・Excelへの変換 |
| 実行統括 | 各工程の起動、検証、段階保存、成果物の入替え |

**言語依存の解析器であっても、複数案件に共通して使えるものはsrcへ置く。**

「C#用だからsrc-dynamic」「Vue用だからsrc-dynamic」とは分類しない。

### 8.2 src-dynamic：案件固有の解析補助

`src-dynamic/`には、特定案件の構造・共通基盤・業務知識に依存する補助を配置する。

| 分類 | 例 |
|---|---|
| 案件固有の名称辞書 | 物理名と論理名、略称、独自コードの対応 |
| 独自フレームワーク対応 | 標準解析器で解決できない画面生成・API呼出・DBアクセス規約 |
| 案件固有の解析ルール | 特定の命名規則、特殊なSQL組立、共通関数の業務上の解釈 |
| 追加解析アダプター | 独自設定、特殊な画面・帳票定義、独自メタデータの読取り |
| Pilot・レビュー材料 | 根拠付きの期待仕様、確認済みの対応、回帰テスト |
| 対象識別 | 案件ID、適用条件、対象ソース、互換性、版、レビュー状態 |

できるだけJSON・YAML・辞書・設定で表現し、コードが必要な場合だけ案件固有PYを追加する。

**src-dynamicは、生成済み仕様書の貼付け場所でも、自由に実行する一時コード置場でもない。**

### 8.3 依存関係

```text
srcの解析基盤
   │
   ├─ 共通の言語別解析器
   │
   └─ 公開された拡張インターフェース
          │
          └─ src-dynamicの案件別アダプター
                     │
                     ▼
              共通形式の解析結果
                     │
                     ▼
             ContextBase1 / 2
```

案件別アダプターは、共通形式の事実・関連・根拠・仮定を返す。納品用のExcelやPDFを直接作成しない。

仕様書生成・形式変換は、特定案件の`src-dynamic`を直接呼ばず、ContextBase2の確定データを使用する。

### 8.4 安全性・汎用性

案件別コードは適用条件とレビュー状態を確認して読み込む。入力ソースをPythonの実行パスへ追加したり、解析対象コードを実行したりしない。

AIが作成・変更した案件別PYも、自動的には実行しない。テスト、差分確認、適用条件の確認を行う。

複数案件で有効と確認できた処理は、共通化と回帰テストを行って`src/`へ移す。ただし、案件固有の名称・業務値は残さない。

### 8.5 プログラム配置の論理構成案

```text
src/
├─ contextbase/
│  ├─ foundation/                P1：基盤解析
│  ├─ detail/                    P2：詳細解析
│  ├─ specification/             P3：仕様書生成
│  ├─ orchestration/             工程統括・公開
│  ├─ shared/                    共通スキーマ・根拠・ID
│  └─ validation/                独立評価
│
├─ specgen/
│  └─ adapters/                  再利用可能な言語別解析器
│
└─ docsite/                      P4：既存のHTML・PDF・Excel変換
   └─ v2/                        V2様式・書式ルール

src-dynamic/
└─ 案件ID/
   ├─ manifest.json              適用条件・版・レビュー状態
   ├─ terminology/               案件固有辞書
   ├─ rules/                     案件固有の解析規則
   ├─ adapters/                  必要な追加PY
   ├─ reviewed/                  根拠付きの確認済み情報
   └─ tests/                     案件別回帰テスト
```

既存の`specgen`、`docsite`、案件別アダプターを再利用し、責任分離のために必要な範囲で整理する。

## 9. 仕様書生成・形式変換

### 9.1 仕様書生成

ContextBase2から、機能一覧、基本設計書、詳細仕様書、共通仕様書、テーブル定義書、DBオブジェクト一覧、CRUD図、関連図、メッセージ一覧、コード一覧などを生成する。

基本設計書は外部仕様として、利用者の操作、入出力、処理順、画面状態、データの関係を記載する。

内部の関数名・クラス構造・言語固有の実装方法は、根拠または詳細仕様へ分離する。

文章の補完が必要な場合は詳細解析側で行い、採用した説明をContextBase2へ保存する。生成のたびにAIが業務説明を書き直す構成にはしない。

### 9.2 項目一覧

出力の項目一覧は、既存のV2形式を維持する。

```text
No｜グループ｜項目名｜種類｜入出力｜
DB連携項目｜候補取得元｜必須｜形式・桁｜説明
```

ContextBase2はこの10列より詳しい情報を保持し、文書生成時に必要な内容を列へ展開する。

### 9.3 Excel様式

表紙・通常・一覧の３パターンを分離して維持する。

| パターン | 書式 |
|---|---|
| 表紙 | 各ブロックの枠を設定し、右端はAU列。余白に罫線を付けない |
| 通常 | A1からBJ列の最終行までを黒の太線で囲む。空白行・画像行でも外枠を連続させる |
| 一覧 | タイトルを囲まず、項目表の範囲に必要な罫線を設定する |

全パターンで、外枠・対象範囲の外には罫線を一切付けない。標準書式、行・列の既定書式、結合継続セルも検査する。

この書式処理に業務解析の判断を持ち込まない。

### 9.4 正本の関係

| 情報 | 位置付け |
|---|---|
| ContextBase1 | 基礎構造・基礎定義の正本 |
| ContextBase2 | 詳細仕様・業務解釈の正本 |
| output/md | 文書としての正本、派生形式の変換元 |
| HTML・PDF・Excel | MDから作る派生成果物 |

MDの手修正をクリーン再生成でも保持する場合は、ContextBase2または管理された文書修正情報へ戻す。MDの編集内容を、無条件でソース由来の事実へ昇格させない。

## 10. 検証と品質判定

### 10.1 工程別に評価する

| 対象 | 主な確認内容 |
|---|---|
| ContextBase1 | 機能境界、一覧漏れ、テーブル定義、原本接続、ID・参照の整合 |
| ContextBase2 | 条件、処理順、項目意味、DB操作、共通処理、正常・異常時の状態、根拠 |
| 仕様書 | ContextBase2の情報が文章・表・図へ欠落なく反映されているか |
| 派生成果物 | MDとの内容一致、画像、リンク、文字切れ、印刷、罫線 |

ファイル数・項目数の一致だけで、解析精度が十分とは判定しない。

### 10.2 独立評価

期待値を生成結果からそのまま作らない。原本からの別抽出、レビュー済みの期待仕様、独立した確認シナリオを用いる。

構造検証、意味の検証、文書変換の検証を別の結果として記録する。

保存処理、削除処理、権限、状態の消去、例外時の扱いは重点的に確認する。

### 10.3 公開条件

情報不足や未確定事項は、根拠付きの仮定として成果物へ出力できる。

一方、形式破損、世代混在、ID不整合、安全境界違反などは仮定で通過させず、該当更新を停止して正常な成果物を保護する。

---

## 11. 差分解析・途中再開・再生成

入力、設定、解析器、スキーマ、案件固有ルールの版を記録し、変更の影響範囲だけを再解析する。

```text
入力・定義・解析ルールの変更
  → 影響するContextBase1を更新
  → 依存するContextBase2を再解析
  → 関連MDを再生成
  → HTML・PDF・Excelを更新
```

完了済みの解析は、ハッシュと依存情報が有効な場合だけ再利用する。同じファイル名という理由だけで再利用しない。

機能・テーブル・共通処理単位で途中結果を保存し、失敗後は未完了・無効化された範囲から再開できるようにする。

ContextBaseは解析正本、`.specgen-state/`などは再作成可能な作業キャッシュとして分ける。

**outputの削除・再生成と、ContextBaseの再解析・再構築は別操作にする。**

旧outputは新規作業領域で生成・検証した後に入れ替える。input、ContextBaseの必要な履歴、QA回答、人が記録したreportを削除しない。

### コマンド設計案

```shell
# 第１段階：骨子・テーブル等を整備
python -m contextbase.foundation --root .

# 第２段階：基盤情報とソースから詳細解析
python -m contextbase.detail --root . --feature 100008

# ContextBase2からMD仕様書を生成
python -m contextbase.specification --root . --feature 100008

# 生成済みMDをHTML・PDF・Excelへ変換
python -m contextbase build --pdf --excel
```

統括CLIから全工程を呼び出す場合も、これらの独立プログラムを利用する。単独実行と一括実行で別の解析ロジックを持たない。

---

## 12. QA・report・変更範囲

| 保存先 | 内容 |
|---|---|
| output/ | 仕様書。情報不足でも合理的な仮定を明示して結果を出力する |
| QA/ | 質問、暫定採用値、根拠、影響、回答、採用状態 |
| report/ | 未完成・未検証事項、矛盾、解析制限、失敗、検証結果 |

仮定は該当する仕様・項目へQA番号とともに表示する。推測を確定事実として扱わない。

QA回答は再生成でも保持する。回答の採用時は原本との関係を確認し、意図された仕様と実装上の動作が異なる場合は区別する。

変更できるのは本リポジトリのみとする。V2リポジトリは参照専用、inputは非変更・非実行とする。

本方式、プログラムの責任分離、srcとsrc-dynamicの役割、QA・report・outputの運用をAGENTS.mdへ記録する。

## 13. Pilotによる段階導入

最初のPilotは職員番号入力とする。

完成したMDをContextBase2へ移すだけではなく、その根拠となる項目、条件、処理、状態変化、データ関連を構造化する。

| 段階 | Pilotで確認すること |
|---|---|
| ContextBase1 | 画面、項目、イベント入口、関連ソース、共通処理、保持先を識別できるか |
| ContextBase2 | 初期表示、照合成功、照合失敗、クリアの条件・順序・保持・消去を説明できるか |
| 文書生成 | 解析済みの内容を欠落させず、既存V2様式へ出力できるか |
| 差分更新 | ソース変更時に古い解析・説明が無条件で再利用されないか |

次に、検索と複数テーブル更新を含む機能へ適用し、テーブル定義、保存処理、トランザクション、共通処理の詳細解析を検証する。

Pilotで発見した不足は、共通スキーマ・解析器・評価ルールへ戻す。案件固有の完成文章や分岐を増やすだけの改善にしない。

---

## 14. 最終方針

**骨子・テーブルを整備する解析と、機能の動作を理解する詳細解析を分ける。さらに、詳細解析結果からの文書生成と、出力形式への変換も別プログラムにする。**

- ContextBase1：全体構造、機能骨子、テーブル基礎定義、原本索引
- ContextBase2：関連ソースを再確認して得た、条件・処理・データ・状態の詳細仕様
- src：案件を越えて再利用する解析・生成・検証プログラム
- src-dynamic：案件固有の辞書・規則・追加解析アダプター
- output：成果物
- QA：質問と採用判断
- report：未完成事項と検証結果

**案件固有の知識は解析側へ集約し、文書生成・Excel/PDF変換へ業務判断を持ち込まない。**
