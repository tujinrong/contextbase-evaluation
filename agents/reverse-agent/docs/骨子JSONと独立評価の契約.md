# 骨子JSON・索引・独立評価の契約

版：1.0／2026-10-02。状態：方式・データ契約の設計。JSON Schema、汎用解析器、評価器の実装・適合試験の完了宣言ではない。

関連：[ソーススキャン最適化設計](%E3%82%BD%E3%83%BC%E3%82%B9%E3%82%B9%E3%82%AD%E3%83%A3%E3%83%B3%E6%9C%80%E9%81%A9%E5%8C%96%E8%A8%AD%E8%A8%88.md)。JSON例：[feature-skeleton.sample.json](examples/feature-skeleton.sample.json)。例は架空の顧客検索であり、TKLから抽出した業務仕様ではない。

## 1. 目的

文章を書く前に「何を仕様書へ記載する必要があり、何が未解決か」を確定する。骨子を構文解析器と文書生成器の間の共通契約とし、画面・帳票・バッチ・混在・共通を同じ形式で管理する。

骨子だけで文書の全内容を確定しない。骨子から関連原本・共通処理を追加解析して詳細JSONを作り、条件、計算、対象範囲、異常終了等を埋める。文章化は最後に行う。

## 2. JSONの構成

| キー | 内容 | 契約 |
| --- | --- | --- |
| schema_version | データ契約の版 | メジャー変更は移行または再抽出。黙って旧データを読まない |
| data_origin | 原本抽出／手動承認／説明用例 | 説明用例を実ソースの証拠として利用しない |
| system_id・snapshot_id | 案件と原本の世代 | 公開候補では未指定を許可しない |
| feature | 安定ID、名称、種別、業務区分、目的 | 表示順とIDを分ける。名称・配置変更でIDを振り直さない |
| analysis_status | skeleton／enriched／ready_for_review等 | 完成・評価済み・公開済みを混同しない |
| source_enumeration | 原本の列挙範囲と状態 | 全体が不明ならexpected件数をnullとし、0件にしない |
| items | 入力・検索・表示・操作・内部・出力・受渡し | 各役割に必要な属性だけを持たせる |
| events | 契機、前提、入力、条件、結果、取消・異常 | 操作からDB・ファイル・外部処理への対応を持つ |
| data_operations | 対象、操作、列、キー、条件、値の由来、境界 | CRUDだけでなく取込・全件消去・関数呼出等を別属性で表す |
| data_objects | オブジェクトIDと定義の参照 | 詳細なDB定義本体は共有レジストリーへ分離可能 |
| messages | 定義、文面、置換値、表示場所、回答後の処理 | 同じ文面でも発生条件の異なる箇所を失わない |
| io・transitions | 本機能の入出力と遷移 | 読取／書込方向、受渡し、戻り条件を明示 |
| common_refs | 適用共通ID、版、条件、例外 | 共通規則の文面を全機能へ複製しない |
| dependencies | 利用側、提供側、関係種別、条件、解決状態 | 正引き・逆引き両方を作る。未解決依存も保持 |
| evidence | 原本・資料の位置と内容ID | 証拠の重複掲載はID参照にする。全文コードを各機能へ埋め込まない |
| coverage | 抽出済み・未解決・独立基準との対応 | 文書上の項目件数と原本の件数を別に数える |
| open_questions | 不足、矛盾、依存未取得、承認待ち | 解消理由・証拠なしに削除しない |

識別子の参照は、同じJSON内または版付き共有レジストリーのどちらかで解決できること。外部参照が未解決なら、その状態を明示する。IDだけ存在して定義がないものを対応済みに数えない。

## 3. 項目属性を役割に合わせる

### 3.1 必須条件と長さ

入力項目は「入力必須」と「保存先のNOT NULL」を別属性にする。値の省略が認められても、既定値や計算結果が保存される場合がある。表示専用項目の入力必須は対象外だが、表示元・書式・表示上限は必要である。

長さは次を別々に管理する。

| 属性 | 例 |
| --- | --- |
| input_length | 6文字、50バイト、整数部8桁・小数部2桁 |
| input_encoding | バイト長であればShift_JIS等の判定文字コード |
| normalization | 前後空白除去、カナ変換、改行除去の有無と適用順 |
| display_format | 年月日、3桁区切り、先頭ゼロ、非表示、マスク |
| storage_length | DDLで確認した長さ／未確認 |
| state_condition | 新規のみ入力可、請求済みは表示専用等 |

ボタンは操作入力であり値入力ではない。入力必須・入力最大長・ボタン自身のDB列は対象外とする。DB更新や取得は対応するイベントへ持たせる。

### 3.2 多対一・状態別・順番

郵便番号が2欄、業務項目が1、DB列が2の場合はそれぞれ別の数として管理する。グリッドの列定義と、表示された行数を混ぜない。ラベルや装飾枠をデータ項目に数えない。ボタン数は操作項目として別集計にする。

orderは `scope_id / ordinal / basis / state` を持つ。basisは画面の視覚順、フォーカス順、帳票列順、ファイル列位置等を区別する。ソース行順はfallbackとして明示し、画面順を検証した扱いにしない。

編集可能な一覧セルや状態に応じて入力可否が変わる項目は、状態別に役割を明記する。初期状態1種類だけの照合で機能全体を適合としない。

## 4. 事実・推定・未確認の管理

値ごとに以下の状態を保持する。

- declared：原本の宣言・式・操作として確認した値。実環境での動作確認や顧客承認を意味しない。
- inferred：観測値から導いた候補。推定の理由と代替候補を持つ。
- approved：承認者・承認日・対象版を記録した仕様。
- unknown：未取得または未解決。値をnullにして理由を残す。
- conflicting：原本・資料・文書に食い違いがある。両方の証拠を保持する。
- not_applicable：役割・範囲上の対象外。理由を持つ。
- example：説明用。検証済み事実として利用しない。

DBの主キー、NULL、長さ、外部キー、索引、トリガー内部等は属性ごとに状態を持つ。オブジェクト名が分かっただけで定義全体をdeclaredにしない。

## 5. 根拠の持ち方と省容量化

根拠はスナップショット、相対パス、blob／内容ハッシュ、開始・終了行、要素位置、抽出方式の版を持つ。行番号だけでは改行追加で変わるため、シンボルまたは要素IDと本文内容の指紋も補助的に持つ。位置とハッシュが現行世代に一致しない場合はstaleとして再取得する。

各機能JSONは必要な根拠IDを参照し、共通ソース全文や共通モデル全体を毎回複製しない。原本断片の取得時は周辺の制御条件まで含め、固定文字数の切り出しで条件やSQLを途中切断しない。長い処理は小分けにするが、未処理の範囲を台帳に残す。

実データ、接続文字列、秘密鍵、パスワードは骨子や索引に保存しない。メッセージの動的置換はパラメーターの意味を保存し、実際の顧客値は保存しない。

## 6. 文書生成への割当

| 骨子・詳細情報 | 生成する文書の箇所 |
| --- | --- |
| feature、layout、io、transitions | 個別概要仕様書 第1章 |
| items、DB対応、入力・表示の制約 | 第2章：項目名／タイプ／DB関連／必須／長さ／概要説明 |
| events、rules、data_operations、messages、examples | 第3章：文章、箇条書き、Mermaid、データ例 |
| common_refs、notes、open_questions | 第4章：共通、注意事項、その他 |
| 共通レジストリー | 別ファイルの共通概要仕様書 |
| messageレジストリーと使用箇所 | メッセージ一覧 |
| イベントとDB操作・依存 | CRUD表・図 |
| DB定義の確認値と推定属性 | DB定義書、DBオブジェクト一覧 |

文書の1章を直すだけなら、その章に必要なJSONと参照共通仕様だけを入力にする。ただし共通の用語・項目・条件が変わった場合は他章・集約文書も再評価する。

機能別の根拠に基づく事実は同じ正本JSONを参照し、文章・図・表を別々に推測して作らない。独立評価では、この正本を無条件の正解にはしない。

## 7. 独立評価の三系統

### A. 原本との一致

評価器自身の棚卸し・抽出から基準集合を作る。生成器の骨子を分母にしない。定義だけでなく、イベントから共通・DB・ファイル・外部まで辿り、保存先・参照先・メッセージ・状態条件を照合する。

### B. 文書だけで実装できるか

原本を渡さず、個別仕様書＋版を固定した共通仕様＋DB定義＋外部契約から、別の評価者に次を再構成させる。

1. 項目の型・必須・長さ・初期値・変換・配置。
2. 操作ごとの前提・正常系・取消・異常系と判定表。
3. 検索条件・取得元・並び順・対象なし時の動作。
4. 登録・更新・削除の対象、列、キー、範囲、順番、トランザクション、結果。
5. 計算式・丸め・課税・年度境界・符号・上限下限。
6. 帳票・ファイルの列順と形式、バッチの開始・重複・再実行・終了結果。

書かれていない条件を評価者が常識で補った場合は「実装可能」にしない。概要仕様書単独で不足しても、明示した参照文書に仕様が揃っていればよい。参照文書が未作成・未取得なら不足とする。

### C. 文書内・文書間整合性

公開するMD本文・表・Mermaid・データ例を読み直す。JSON上にあるがMDへ落ちていない情報は記載漏れである。Mermaidの構文確認と、図のノード・矢印が意味上正しいかの確認は別に行う。件数、ID集合、役割、順序、値の単位、分岐条件、CRUD方向、共通参照を照合する。

## 8. 具体的な評価ルール

| ID | 検査 | 代表的な指摘 |
| --- | --- | --- |
| E-FLD-01 | 項目ID集合 | 件数は同じだが顧客名がなく、不要な別項目が増えている |
| E-FLD-02 | 役割 | 表示専用項目を入力必須としている／ボタンに入力長とDB列を設定している |
| E-FLD-03 | 長さ・単位 | 50バイトを50文字と記載／DB桁数を画面制限から断定 |
| E-FLD-04 | 状態と順番 | 請求済みの編集禁止を欠落／画面順と項目一覧順が不一致 |
| E-DB-01 | 保存の更新範囲 | 本体の登録はあるが履歴・明細がない |
| E-DB-02 | 検索と関連図 | 検索対象DBが関連図にない／図の読取方向が逆 |
| E-DB-03 | DB推定 | ソースの列参照だけでPK・FK・NULLを断定 |
| E-EVT-01 | 状態分岐 | 「保存」と「確定」を同じDB更新として説明 |
| E-EVT-02 | 失敗・取消 | エラー後にも更新するのに「更新しない」と記載、または結果自体が未記載 |
| E-MSG-01 | 表示と回答 | 定数文面はあるが表示箇所・置換値・はい／いいえの後続がない |
| E-IO-01 | 出力 | CSV列順、文字コード、桁あふれ、再実行時の扱いがない |
| E-COM-01 | 共通 | 適用ID・版・条件がなく、どの共通規則を使うか不明 |
| E-IMP-01 | 実装可能性 | 書かれた資料だけでは更新キー、計算式、境界値を決められない |
| E-CACHE-01 | 差分一致 | 同じ入力の全量実行と差分実行で事実集合が異なる |

指摘は機能・仕様ID、該当箇所、期待値、実際値、根拠、重要度、判定状態、修正案、再評価結果を持つ。合格／不合格／要確認／対象外を区別する。自動検査未実施や原本不足は合格にしない。

## 9. 最適化の受入ケース

初回、変更なし再実行、単一機能変更、共通変更、DB変更、メッセージ変更、文書テンプレート変更、評価ルール変更、追加・削除・移動、定義の新規追加、途中停止、破損キャッシュ、未コミット変更、異言語、DB資料なしを比較する。

最適化候補は、全量との事実集合一致・独立標本での欠落なし・既知欠陥の検出を満たした後で、工程別時間、API回数、読取量、AIトークン、キャッシュ容量、再評価・再修正時間を比較する。ソース調査や評価を省略して得た短縮は改善として採用しない。

## 10. 状態と公開

骨子の候補を先に保存して途中再開できるようにするが、候補を完成仕様書と表示しない。メッセージ一覧・CRUD・DB・共通仕様が同じ原本世代に対応し、重大な不整合が解消されて初めて公開候補とする。

評価を通したMDを変更した場合は評価を失効させる。全文書を毎回文章生成し直す必要はないが、変更した共通契約や項目が参照先に与える影響は必ず再検査する。
