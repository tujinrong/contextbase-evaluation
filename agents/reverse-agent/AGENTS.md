# Repository operating rules

## Scope

- 書込み・削除・コミットできるのは `tujinrong/contextbase-chatgpt` のみ。更新先は `main`。
- `tujinrong/source-to-doc-v2` は仕様・様式を参照するだけの読取り専用リポジトリ。変更、Issue作成、workflow追加は行わない。
- `input/` は解析原本として読み取り、変更・削除・コード実行をしない。既存の案件別 `src-dynamic/` を無関係な変更で壊さない。

## Delivery, QA and report

- `output/` は成果物置場。情報が不足していても合理的な仮定を置いてMD・HTML・PDF・Excelの結果を出力する。未完成という理由だけで空欄の仕様書や失敗報告だけを出して終了しない。
- 推測は事実として偽装しない。該当する仕様・項目には `（仮定）` とQA番号を付け、ソースで確定した仕様と区別する。根拠のないDB物理名、テスト成功、顧客承認を捏造しない。
- 質問はリポジトリ直下の `QA/` に保存する。`QA/questions.json` を機械可読台帳、`QA/仕様確認.md` を閲覧用とし、質問、暫定採用値、根拠、影響、回答、状態を残す。ユーザーへの質問待ちだけで生成を停止しない。
- 再生成時もQAの既存回答・人が記入した状態を保持する。ソース変更や回答との矛盾は新しい確認事項にする。回答から自動で業務仕様を確定せず、根拠と照合して採用する。
- 未完成箇所、解析制限、変換未対応、実行失敗、未検証範囲、検証結果は `report/` に出力する。未完成報告書を `output/` の納品仕様書へ混ぜない。
- 納品形式は `output/md/`、`output/html/`、`output/PDF/`、`output/Excel/`。MDを正本とし、派生文書の名称・章・項目順・内容を対応させる。

## Regeneration and validation

- 変更実装とテスト完了後、`python -m contextbase rebuild --replace-output --pdf --excel` を実行する。
- 原本から新しい作業領域へ生成し、検証後に旧 `output/` 配下を全て除去して新しい成果物一式へ入れ替える。古い成果物・キャッシュ・確認事項文書を新しいoutputへ引き継がない。入替失敗時だけ旧outputへロールバックする。
- 削除対象を `output/` に限定し、`input/`・`QA/`・人が記録した `report/` は削除しない。symlinkや領域外パスへの書込みを禁止する。
- 項目一覧はv2の10列：No、グループ、項目名、種類、入出力、DB連携項目、候補取得元、必須、形式・桁、説明。入出力は `I`、`O`、`I／O`、`‐`。
- Excelは表紙と章別シートを持つ編集可能な `.xlsx`。日本語、改行、先頭ゼロ、数式に見える文字列を保持する。MD由来の文字列を計算式・マクロとして実行しない。
- 自動テスト、入力不変、MD/Excelセル照合、HTML/PDF検査を実行する。構造検証と業務意味の完全性を区別する。
- 成果物と修正をmainへ保存する。force pushをせず、反映直前のmain SHAを照合する。GitHub Actionsの成功・保存コミット・成果物の存在を確認してから完了を報告する。

## V2様式とPilot

- Excel様式はユーザー添付V2（職員番号入力）を基準とする。表紙O6:AU36、本文A:BJの62列格子、項目一覧A:Jの10列。画像はURL文字列だけで代用せずExcelへ埋め込む。
- `src/docsite/v2/PROVENANCE.json` に参照元PY、リビジョン、移植・依存分離の範囲を残す。全量コピーと移植版を混同しない。
- 職員番号入力Pilotは `src-dynamic/jsbrms-pilot/` のレビュー済み本文を11ソースのハッシュ一致時だけ採用する。原本変更時はQAとreportへ記録して汎用出力に戻し、古い業務説明を黙って流用しない。
- V2添付の内容より現行inputを優先し、画面に存在しない操作、DB参照、遷移を転記しない。初期・正常・異常・クリア時の入力、出力、状態保持を区別する。

## Excel罫線の品質条件

- 標準セル書式（cellXfsの0番）はGeneral・塗りつぶしなし・罫線なし。未記載セルや行／列の既定書式で、シート全体に罫線を付けない。
- 表紙の各枠の右端はAU列。AV列以降、O6:AU36の外、および枠の間の余白へ罫線を延長しない。
- 全シートで仕様書範囲外は罫線なし。本文と項目表の必要な罫線は残し、結合範囲の継続セルには外周側の罫線だけを設定する。
- 生成後のXLSXから、標準書式、範囲外セル、結合枠の右辺・下辺・内部を再検査する。内容・画像・結合範囲・印刷範囲を罫線修正で変更しない。


## Excel外枠の３パターン（添付V2原本を基準）
- 書式パターンを表紙・通常・一覧に分離する。印刷範囲の存在だけを理由に全シートへ同じ外枠を追加しない。
- 表紙：O6:AU9のタイトルは二重線、情報欄と承認欄は各結合ブロックの細線。会社名帯O36:AU36は上側の細線のみ。枠間の余白は無罫線。右端はAU列で止める。
- 通常：A1:BJ最終行を黒の太線で囲む。添付のExcel罫線種別はmedium。空白行・画像行でも左右の外枠を連続させ、下端は生成した最終行へ追従する。ヘッダー直下は二重線、内側の表と見出しは必要な罫線だけを付ける。
- 一覧：タイトルを囲まず、項目表のA:Jだけに罫線。見出しの上・左右はmedium、明細はthin。説明行・余白行・K列以降は無罫線。通常パターンの太い全体外枠を一覧へ適用しない。
- 枠外は一切無罫線。未使用セル・行/列の既定書式・結合継続セルも対象に含める。標準書式は必ず罫線なしとし、四隅、全周、直外のセル、結合内部、空白行をXLSXから再読込して検証する。

## ２段階解析と独立プログラム（v5）

- 現行generic経路の再生成はP1基盤解析→P2詳細解析→P3文書生成→既存P4形式変換の順とする。工程名だけを分けず、JSONとハッシュ検証済みの永続ファイルで受け渡す。
- P1は `python -m contextbase.foundation`。`ContextBase/01-foundation` に骨子・テーブル基礎情報・原本索引を保存する。画面とPageModelを１機能として結び付ける。DTOやメモリー上のデータ構造を物理DB表と断定しない。
- P2は `python -m contextbase.detail`。P1の世代・解析器・inputハッシュを照合し、関連ソースから条件、分岐、順序、状態操作を再解析して `ContextBase/02-detailed` に保存する。
- P3は `python -m contextbase.specification`。P2の `resolved` と素材だけを使用する。input・src-dynamic・P1を読んだり業務仕様を追加推測したりしない。ソース非依存の再実行を独立プロセスで検証する。
- P4は既存 `docsite`。Excel/PDFの業務判断を増やさず、V2３パターンと枠外無罫線を維持する。
- `src/specgen/adapters` は案件横断の言語別解析、`src/contextbase/{foundation,detail,specification,shared,validation}` は固定の共通プログラム。`src-dynamic` は案件固有辞書・レビュー情報・ハッシュ照合済みアダプター。案件固有の画面再構成コードは `src-dynamic/jsbrms-pilot/adapters` で管理する。
- 案件別追加PYはextension.jsonの承認状態・コードハッシュ・原本ハッシュを検査してからP2だけで使用する。P3から直接利用しない。旧 `contextbase.pilot` / generic の入口は過去テスト互換用とし、本再生成の完成MD差替えには使わない。
- QA自由記述を自動採用しない。型付きadoptionのapprovedと依存ソースハッシュを確認し、判断として保存する。原本明示の事実とは区別する。
- ContextBaseは解析正本、`.specgen-state`は再作成可能なキャッシュ。output再生成でContextBase・QA回答を消さない。全体rebuildは新しい領域でクリーン解析し、検証後にContextBaseとoutputを同時に入れ替える。
- 現行input以外の旧MCTERP/TKL専用経路は互換維持とし、２段階移行済み・同精度とは報告しない。未対応の資料読取・型解決・実行同等性はreport/incompleteへ記録する。

## 汎用画面・データ関連の品質条件

- P2は画面のHTML・CSSを非実行の静的表示へ投影し、レイアウト画像と部品位置をContextBase2へ保存する。P3は封印済み素材を掲載し、ソースや案件別PYを読まない。条件付き表示・共通CSSの近似はQAへ記録する。
- 基本設計書の汎用経路にも画面レイアウト、操作対象データ、データ操作関連図、入力検査、保存値の設定規則を掲載する。レビュー済みPilotだけに限定しない。
- 呼出は条件式内も対象とし、受信変数の型・登録された実装・引数数を照合する。同名関数だけで別クラスへ接続しない。解決できない候補はreportへ残す。
- ソースの文字列リテラル内の全角・半角空白を解析途中に正規化しない。比較・変換規則の意味を保つ。
- メモリー保持、ORM実体、物理DB、セッションを区別する。SQL未検出を理由にメモリー上のCRUDを省略せず、逆にメモリー上の一覧を物理テーブルと偽装しない。
- 公開仕様書IDは画面SCR-001形式、共通処理COM-001形式とし、既存の明示ID（100008等）は保持する。ContextBase/identities.jsonで採番を永続化し、追加・削除で既存番号を振り直さない。旧ハッシュIDはaliasとして引き続き指定可能にする。
- ２段階の独立検査に、画面画像の掲載、保存先とCRUD操作の掲載、根拠、読みやすいID、旧IDからの解決を加える。内容・画像の検査とExcel３パターン罫線の検査を混同しない。

## 独立品質ゲート（2026-10-09追加）

- `src/contextbase/validation/quality.py` は生成器のSQL・画面・フロー抽出を呼ばず、inputを別の字句走査で検査する。P1/P2から項目を消しても原本由来の義務を隠せないこと。
- 原本の画面に対応する基本設計書、画面レイアウトの本文掲載、実画像ファイルを必須にする。欠落・破損・微小・単色の代用画像はERROR。原本を実行した画面と静的再構成を区別する。
- DB使用があればDB仕様書を必須にする。個別の表定義書とDDLの各列を照合し、一つのDB概要ファイルだけで全表を説明済みにしない。ローカルDDLと本番DDLのスキーマ・世代は混同しない。
- 機能・項目・テーブル・列の論理名は日本語を必須とする。ContextBaseと公開MDの双方を検査し、英語の物理名・IDは論理名とは別欄で保持する。「未確認」等の埋草だけで合格させない。
- 挿入・更新・削除・MERGEの各原本処理には、対象テーブル、処理説明、設定項目（挿入・更新）、対象条件、確定・取消、原本根拠を必要とする。JDBC呼出や文字列SQLの存在だけ、CRUD記号だけでは合格にしない。機能別仕様にも関連するDB説明を掲載する。
- 同じ表を更新する別メソッドは別に照合する。物理DBとメモリー保存を混同せず、メモリー保持を存在しないDBに置換しない。
- 上記の欠落は警告でなくERROR、検証プロセスは非0終了。レポートはreport/qualityへ出す。エラーを無視して検証済み成果物として公開するオプションを設けない。安全な作業領域の途中成果物とQAは保持し、修正後に再評価する。
- 期待値は生成結果のコピーにせず、手書きの正常例・欠落を埋め込む負例で検査する。画面・表・列・論理名・操作説明を削除／改変した場合にエラーとなる回帰テストを維持する。
- 大きな中間JSONは字下げの省略で損失なく保存する。上限を超える場合は分割を要求し、属性・処理の切捨てで合格にしない。

## 統合DB定義・項目バインド・イベント説明

- テーブル定義書は全表を1個のMDと1冊のExcelへ統合する。表ごとの詳細見出し・安定IDと列欠落検査を保持する。旧個別テーブル定義ファイルをoutputへ残さない。
- 項目一覧のDB連携項目は、その項目が表示・保存するDB列であり、Model名・パラメーター名・候補取得元で代用しない。要求値、Modelのsetter/getter、SQL別名、JDBCバインド順序を原本から追跡する。
- 複数表、コード変換、履歴、算出値は項目別DB連携備考へ記載する。未解決を類似名で確定しない。表示経路と書込経路を区別する。
- イベント仕様は処理概要、番号付き手順、条件分岐付きフロー、結果を記載する。SQLがある場合は対象表・項目・結合条件をER図でも示し、条件・設定値・確定取消は別に説明する。
- JOINを根拠にFKや多重度を捏造しない。単一表は単独エンティティを示す。推定・未確定は明記する。
- 共通テンプレートはsrc/contextbase/templatesに置き、根拠はdocs/doc/仕様書テンプレートの根拠.mdに記録する。外部資料を案件の動作仕様として転記しない。
- P2が説明・図・バインド根拠を保存し、P3/P4は新しい業務判断を行わない。既存の独立品質検査・Excel外枠3パターンを維持する。
