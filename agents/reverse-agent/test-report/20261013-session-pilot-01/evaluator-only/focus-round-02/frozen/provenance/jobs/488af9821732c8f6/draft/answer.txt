機能と実装の責務\n\n学生検索画面は、条件に一致する非削除学生を検索し、保存された学生情報と所属・コードの名称を一覧に表示する。利用者は条件を入力し、必要に応じて候補を更新してから検索する。検索後は最後に成功した条件を使って表示件数、並び順、ページを変更できる。新規登録と行の編集・参照は登録画面へ移る操作であり、検索処理自体は学生情報を書き換えない。根拠: `sources/Views/Students/Search.cshtml:4-8`、`sources/Web/Controllers/StudentsController.cs:8-25`、`sources/Core/SqlServerStudentService.cs:103-170`。\n\n接続されたHTTP入口は `GET /students`、`POST /students/search`、`POST /students/options`、`POST /students/page`、`POST /students/clear` である。Resumeは独立ルートではなく、状態ID付きの `GET /students` から呼ぶ。各経路はSearchビューによる画面全体のHTMLを返す。`GET /` は `/students` へ転送する。根拠: `sources/Program.cs:6-7`、`sources/Web/Controllers/StudentsController.cs:8-22`。\n\nControllerはフォーム検査、状態取得、画面モデル作成を担当する。Coordinatorは検索状態の排他内でサービスを呼び、成功結果を状態へ移す。起動登録では `IStudentService` を `SqlServerStudentService` に解決し、接続設定名 `StudentDb` を使う。利用者情報、Coordinator、サービスはScoped、検索・編集・通知の各ストアはSingletonである。根拠: `sources/Infrastructure/WebHostSetup.cs:13-19`、`sources/Infrastructure/WebStudentCoordinator.cs:7-21`。\n\n`StudentSearchPageModel.Data:JsonElement` はRazorへ渡す内部表示材料である。候補用の `OptionsRequest`、Coordinatorの `Options`、`WebPresentation.Lookups` は宣言されているが、実際の候補更新ルートはこれらを呼ばず、`StudentSearchInput` を受けてControllerとRazorで候補を処理する。本画面の公開JSON検索・候補APIとしては扱わない。根拠: `sources/Web/Inputs/StudentSearchInput.cs:31-31`、`sources/Web/Models/StudentSearchPageModel.cs:10-15`、`sources/Infrastructure/WebStudentCoordinator.cs:16-16`、`sources/Infrastructure/WebPresentation.cs:8-18`、`sources/Web/Controllers/StudentsController.cs:22-22,39-39`。\n\n### 入力、検索条件、表示結果の分離\n\n条件値は、HTTPフォームの文字列、MVCがバインドした `StudentSearchInput`、サービスへ渡す `SearchCriteria`、サービス内の正規化値の順に移る。年度はDTOの時点で `int?`、未所属は `bool`、在籍区分は `string[]` である。クラスIDはDTOでは `string?` で、`ToCriteria` が正の `long?` へ解析する。氏名とカナはそれぞれ `Name→StudentName`、`Kana→StudentNameKana` に対応する。根拠: `sources/Web/Controllers/StudentsController.cs:13-22`、`sources/Web/Inputs/StudentSearchInput.cs:7-29`、`sources/Core/Contracts.cs:31-48`。\n\n本書でいうNormalizerのraw上限は、バインドと移送を経てNormalizerに渡された文字列に対する上限である。空白だけのHTTP値がバインド後も保持されるか、nullへ変換されるかは、提示されたアプリケーション側設定だけでは確定しない。サービス単体の空値分岐を、ブラウザー原入力への保証に読み替えない。Controllerの再表示材料も、バインド後inputとModelStateであり、原文字列を別途完全保存する実装ではない。根拠: `sources/Infrastructure/WebHostSetup.cs:16-16`、`sources/Web/Controllers/StudentsController.cs:13-16`、`sources/Core/SqlServerStudentService.cs:113-122`。\n\n入力中の条件はブラウザー、要求のinput、応答モデルの `Criteria` にある。検索Entryには入力中条件専用の領域がなく、最後に成功した条件を `Applied:SearchCriteria?`、その結果を `LastResult:SearchResult?` に保持する。SearchとPageは成功後に条件を深く複製してAppliedへ置き換える。Optionsは今回入力とLastResultを表示に使い、PageはAppliedから検索する。Resumeは元Appliedで再検索するがApplied自体を置き換えない。根拠: `sources/Infrastructure/SearchContextStore.cs:9-15`、`sources/Infrastructure/WebStudentCoordinator.cs:7-15`、`sources/Web/Controllers/StudentsController.cs:22-22`、`sources/Web/Models/StudentSearchPageModel.cs:6-10`。\n\nサービスは学籍番号、氏名キー、カナキー、電話、コード、日付のSQL用ローカル値を作る。成功条件の文字列をこれらの正規化値へ書き換える処理はない。検索入力は学生の保存列へ書き込まれない。根拠: `sources/Core/SqlServerStudentService.cs:113-150`、`sources/Infrastructure/WebStudentCoordinator.cs:8-9`。\n\n```mermaid\nflowchart LR\n  H[HTTPフォーム値] --> B[MVCバインド]\n  B --> I[StudentSearchInput]\n  I
