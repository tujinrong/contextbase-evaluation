属 性 定 義 ・ 条 件
論理名・物理名 論理名はコード分類マスター、物理名は dbo.m_code_category。分類IDによってコードの用途を識別し、分類名称、コード桁数、通常追加
可否、有効状態、備考、作成・更新情報、版を保持する。全11列であり、個々のコード値・表示名称・有効期間は dbo.m_code が保持す
る。根拠：database/001_schema.sql:90-134。
主キー・採番 pk_m_code_category は category_id の単一列主キー。IDENTITY列はなく、初期投入では分類IDを文字列として明示する。根拠：
database/001_schema.sql:90-102、database/002_seed.sql:8-13、database/002_seed.sql:88-89。
索引 分類IDの主キー定義がある。当表に対する別の一意制約および明示的な追加索引の宣言はない。根拠：database/001_schema.sql:90-110、
database/001_schema.sql:187-212。
文字列の容量・照合順序 分類IDは Latin1_General_100_BIN2、名称・備考・作成者・更新者は Latin1_General_100_CS_AS_SC。長さ欄の varchar はバイト数、
nvarchar はUTF-16コード単位の保存容量を示す。名称12、備考120、作成者・更新者各64というUnicodeスカラー上限は別のCHECK制約であ
る。各式は nvarchar(max) へ変換してSC照合順序を適用し、末尾に N'#' を付けたLENから1を引くため、末尾空白も計数する。空文字を
拒否するCHECKはない。根拠：database/001_schema.sql:91-108。
NULL・日時・版の制約 NULLを許す列は remarks だけである。CHECK中の IS NULL は列定義のNOT NULLを解除しない。作成・更新日時はオフセット0、版は正の
bigint、コード桁数は1〜10とする。日時の前後関係を比較するCHECKはない。根拠：database/001_schema.sql:91-109、
database/001_schema.sql:202-202。
分類集合と桁数検査の境界 DDLは分類を5件に限定しない。初期投入は下記5分類を定義し、宣言された SaveCodeAsync はその5個の分類IDだけを受け付ける。配備検
証SQLには分類行数が5であることの検査がある。コード表のCHECKは数字形式等を検査するが、code_value の長さと分類の code_length
を照合しない。分類別桁数の照合はコード保守サービスが行う。根拠：database/001_schema.sql:90-110、database/001_schema.sql:202-
203、database/002_seed.sql:8-13、Core/MasterMaintenanceService.cs:81-96、database/004_verify_deployment.sql:97-99。
外部キー・利用側との関係 fk_code_category は dbo.m_code.category_id → dbo.m_code_category.category_id の参照を定義する。コード表の主キーは分類IDとコ
ード値の組合せである。学生の性別・都道府県・在籍区分・続柄、クラスの学年はコード表への複合FKであり、当表への直接FKではない。
FKは参照先の存在を保証する制約であり、有効状態・有効期間・分類別桁数の検査や候補取得のJOINとは役割が異なる。根拠：
database/001_schema.sql:113-127、database/001_schema.sql:189-199。

属 性 定 義 ・ 条 件
初期分類 GENDER：性別、コード桁数1、通常追加不可（0）。
ENROLLMENT_STATUS：在籍区分、コード桁数2、通常追加不可（0）。
PREFECTURE：都道府県、コード桁数2、通常追加不可（0）。
RELATIONSHIP：緊急連絡先続柄、コード桁数2、通常追加可（1）。
GRADE：学年、コード桁数2、通常追加可（1）。
通常追加可否は分類内に新しいコード値を追加できるかを表し、分類自体の追加権限を表さない。根拠：database/002_seed.sql:8-13、
Core/MasterMaintenanceService.cs:102-104。
初期投入の処理順序・排他 1. XACT_ABORT ON としてトランザクションを開始する。
2. test-project1:student-write のExclusiveアプリケーションロックを、所有者Transaction、待機上限5000ms、DbPrincipal public で
取得する。結果が負ならROLLBACKしてSQL例外51001を送出する。
3. 初期分類・初期コードを定義し、既存値との差分を検査する。差分があればROLLBACKして51002を送出する。
4. 分類IDが存在しない分類だけを追加し、続いて分類ID・コード値が存在しないコードだけを追加する。
5. COMMITする。既存行の上書き、版加算、初期値以外の分類の削除は行わない。学生保存・宣言されたマスター保守と同じロック資源を
使う。根拠：database/002_seed.sql:2-14、database/002_seed.sql:85-92、Core/SqlServerStudentService.cs:92-101。
初期投入の差分拒否条件 同じ分類IDを持つ既存行について、分類名称、コード桁数、通常追加可否をSQLの比較条件で照合し、有効状態が1であることも確認する。
備考・作成更新情報・分類版は比較対象に含まれない。同じ処理で初期コードの名称、表示順、保護状態、有効状態1、開始日1900-01-
01、終了日NULLも照合するため、コード側の差分でも分類追加へ進まず中断する。初期値の不足と既存値の差分は別の扱いである。根拠：
database/002_seed.sql:85-91。
初期投入が設定する値 不足分類のINSERTは有効状態1、備考NULL、作成日時・更新日時 @now、作成者・更新者 @actor、版1を明示設定する。@now は
SYSUTCDATETIME() をオフセット +00:00 にした datetimeoffset(7)、@actor は ORIGINAL_LOGIN() を保持する nvarchar(128) である。
DDLのDEFAULTは有効状態と版だけに存在するが、このINSERTは両方とも明示設定する。既存分類行の作成更新情報や版は変更しない。根
拠：database/001_schema.sql:95-101、database/002_seed.sql:7-7、database/002_seed.sql:88-89。
コード保守での分類照会 CodeChange.CategoryId は string。5分類との一致を接続前に検査し、TrimやNFKC変換をせず raw.CategoryId を @category
（SqlDbType.VarChar、Size=24）へ渡す。DB接続の管理者確認、ReadCommittedトランザクション開始、共通ロック取得後、WHERE
category_id=@category で code_length,allow_add を照会する。主キーにより該当は0または1行で、ページング・ORDER BYはない。行が
なければ ArgumentException（E-MST-001）を送出する。分類名称・備考・分類版・有効状態はこの照会の取得対象ではなく、分類停止を
この保守の拒否条件にはしていない。根拠：Core/MasterMaintenanceService.cs:10-10、Core/MasterMaintenanceService.cs:17-28、
Core/MasterMaintenanceService.cs:79-96。
コード桁数の使われ方 code_length を GetInt16 で short width に読み、StudentNormalizer.Code へ渡す。原入力をwidthスカラー以内で検査してから制御文
字検査とTrimを行い、Trim後も同じ上限で検査する。NULLは空文字へ補完され、必須の空値はE-STU-001、長さ・制御文字違反はE-STU-002
となる。次にNFKC変換し、UTF-16のLengthがwidthと一致するASCII数字列かを検査し、不一致はE-STU-009となる。これらは
InputValidationException、不正なサロゲートは ArgumentException である。ゼロ埋めや数値化は行わず、先頭ゼロを含む文字列がコー
ド表のキーになる。コード表の保存容量および @value のSize=10とは別の制約である。根拠：Core/MasterMaintenanceService.cs:91-
99、Core/StudentNormalizer.cs:37-57、Core/StudentNormalizer.cs:113-117、Core/StudentNormalizer.cs:168-168、
database/001_schema.sql:114-114。

属 性 定 義 ・ 条 件
通常追加可否の判断順序 分類照会とコード値正規化の後、分類ID・コード値でコード表を読む。対象なしで比較版が指定されていればNotFound、対象ありで版が比
較版と一致しなければConflictを返す。新規要求の比較版NULLに対して既存行がある場合もConflictとなる。その後、対象なしで
allow_add=false の場合にだけ ArgumentException（E-MST-003）で通常追加を拒否する。比較版の一致した既存コード更新は、通常追加
不可だけを理由に拒否しない。判定に使う bool allow は GetBoolean で取得する。根拠：Core/MasterMaintenanceService.cs:91-104。
分類照会後の保守結果・確定境界 分類の検査を通過しても、保護コードの停止・期間短縮や版上限の検査が続く。無変更はROLLBACKしてNoChangeを返す。書込み先はコード
表で、新規は版1、更新は分類ID・コード値・比較版をWHEREに持ち版を加算する。更新件数が1でなければ DBConcurrencyException。同じ
トランザクションで操作履歴を追加し、COMMIT完了後にSavedを返す。当表の更新情報・版は変更しない。保守のtry内例外はrollbackを試
みて再throwし、rollback helperの成否からUnknown等の結果を作る処理はない。接続・BeginTransaction・接続前の前処理はそのcatchの
外である。根拠：Core/MasterMaintenanceService.cs:79-121、Core/MasterMaintenanceService.cs:132-135、
Core/SqlServerStudentService.cs:329-329。
学生画面への候補取得 LookupAsync は利用者確認と接続後、SNAPSHOTトランザクションでコード表と当表を分類IDによりINNER JOINする。コード候補のSQLには
WHERE、TOP、ページングがなく、停止・期間外のコードも取得し、分類ID・表示順・コード値の昇順で並べる。返却する
CodeEntry.IsActive は両表の有効状態が1の場合だけ真となり、有効期間はこの算出には含めない。読取り後のCOMMITを経て LookupSet
を返す。各非同期DB呼出しには取消トークンを渡す。根拠：Core/SqlServerStudentService.cs:196-216。
分類名称と候補の表示名称 候補の CodeEntry は分類ID、コード値、コード名称、表示順、合成有効状態、開始日、NULL可能な終了日、保護状態を持つ。分類名称、
分類備考、桁数、通常追加可否、分類の作成更新情報・版は含まない。選択肢の表示名称は m_code.code_name であり、category_name で
はない。表示元のコード名称はNOT NULLの nvarchar(24)、DDLおよび宣言された保存サービスの上限は12スカラー、保存パラメータは
NVarChar(24) である。名称の上限が同じでも、コード名称の保存契約は分類名称の保存契約ではない。根拠：Core/Contracts.cs:61-65、
Core/SqlServerStudentService.cs:203-212、database/001_schema.sql:115-128、Core/MasterMaintenanceService.cs:82-83、
Core/MasterMaintenanceService.cs:113-115。
分類の選択・保存先 学生画面では GENDER がREG-006／Input.GenderCode（string）から学生表の gender_code、PREFECTURE がREG-008／
Input.PrefectureCode（string）から prefecture_code、ENROLLMENT_STATUS がREG-014／Input.EnrollmentStatusCode（string）から
enrollment_status_code、RELATIONSHIP がREG-021／Input.RelationshipCode（string?）からNULL可能な relationship_code へ対応す
る。前3列はDBでもNOT NULLである。すべてselectで、選択コードを StudentDraft に移送する。学生新規INSERTは前3分類IDを固定設定
し、続柄分類は正規化した続柄コードがNULLならNULL、それ以外なら RELATIONSHIP を導出する。GRADE はREG-017／Input.GradeCode
（string?）から SaveRequest.GradeCode へ渡す補助・整合確認値で、学生表への学年コード保存項目ではない。分類表を編集する入力項
目はない。根拠：Views/Students/Edit.cshtml:8-13、Web/Inputs/StudentSaveInput.cs:13-42、database/001_schema.sql:15-31、
Core/StudentNormalizer.cs:147-147、Core/SqlServerStudentService.cs:294-301、Core/SqlServerStudentService.cs:371-371。
初期選択・停止値の保持 新規学生の性別0・在籍区分01は入力モデルと StudentDraft の初期値であり、分類表のDEFAULTではない。性別・都道府県・在籍区分・続
柄の選択肢は、合成有効状態が真で当日が開始日以降かつ終了日以前（終了日NULLは終端なし）の場合、または読込済み学生の保存コード
と同じ場合に選択可能となる。学年selectにはこの有効状態・期間によるdisabled条件がない。根拠：Core/Contracts.cs:15-27、
Web/Inputs/StudentSaveInput.cs:13-29、Web/Inputs/StudentSaveInput.cs:44-54、Views/Students/Edit.cshtml:8-13。

学生保存時の再確認 学生保存の桁数は当表から動的取得せず、性別1桁、都道府県・在籍区分・続柄2桁、学年補助値2桁を処理で指定する。学生への保存パラ
メータも性別 VarChar(1)、他の保存コード VarChar(2) である。入力正規化、ReadCommittedトランザクションと共通ロック、既存学生・
比較版等の確認後、性別・都道府県・在籍区分・続柄をコード表と当表のJOINで再照会する。述語は c.category_id=@category AND
c.code_value=@value、パラメータは VarChar(24) と VarChar(10)。正規化値がstringでない項目は照会しない。行なしはE-STU-009。新
規学生または変更したコードだけ、両表の有効状態とコードの有効期間を検査し、不適合はE-STU-011。既存の同じコードも存在確認は行
うが、停止・期間外だけを理由に拒否しない。判定日は保存冒頭のUTC時刻を+09:00の日付へ変換した値で、DB待機後に取り直さない。根
拠：Core/StudentNormalizer.cs:128-147、Core/SqlServerStudentService.cs:33-37、Core/SqlServerStudentService.cs:44-45、
Core/SqlServerStudentService.cs:227-260、Core/SqlServerStudentService.cs:347-355。
利用不可時の結果 学生保存のコード検査は項目エラーを集め、InputValidationException として送出する。専用catchはrollback後にValidationFailedを返
し、この経路では学生書込みへ進まない。Web保存はその結果を通常HTTP 422とし、候補を再取得して再表示する。再取得等で例外が起き
れば、同じ422画面の返却は確定せず、応答未開始の場合は接続されたmiddlewareが例外を扱う。DTOの非nullable注釈やselectのrequired
だけでは受信NULLの排除を保証しない。根拠：Core/SqlServerStudentService.cs:260-260、Core/SqlServerStudentService.cs:316-323、
Core/SqlServerStudentService.cs:383-383、Web/Controllers/StudentsController.cs:26-33、Infrastructure/WebPresentation.cs:23-
23、Infrastructure/WebHostSetup.cs:16-16、Infrastructure/WebHostSetup.cs:22-24。
学年分類の利用 学年コードの保存元はクラス表の grade_code（varchar(2)、NOT NULL）であり、分類列は GRADE に固定される。宣言された
SaveClassAsync は GRADE と @grade（VarChar(2)）でコード表と当表をJOINし、行なしをE-STU-009、新規クラスまたは学年変更時の停
止・期間外をE-STU-011の ArgumentException で拒否する。既存の同じ学年では有効状態・期間検査を省略する。学生保存側の学年補助値
は指定クラスの学年との一致確認に使い、前述の4分類と同じ有効状態再検査の対象にはしない。根拠：database/001_schema.sql:65-66、
database/001_schema.sql:190-197、Core/MasterMaintenanceService.cs:34-40、Core/MasterMaintenanceService.cs:59-64、
Core/SqlServerStudentService.cs:347-355、Core/SqlServerStudentService.cs:371-371。
分類更新と保守入口の境界 MasterMaintenanceService の保存処理はクラス保存とコード保存であり、分類表を保存するメソッドはない。共通Save helperの呼出先は
クラス表、コード保存の書込先はコード表と操作履歴である。Web登録は IStudentService → SqlServerStudentService で、確認できる
学生コントローラーには分類・コード保守のアクションがない。コード・クラス保守は宣言されたサービス契約として位置付ける。分類名
称・備考・有効状態等の列が存在することから、通常画面による分類編集機能や分類編集履歴を補わない。根拠：
Core/MasterMaintenanceService.cs:30-121、Core/MasterMaintenanceService.cs:124-135、Core/Contracts.cs:71-79、
Infrastructure/WebHostSetup.cs:12-19、Web/Controllers/StudentsController.cs:5-42、Program.cs:2-6。
Web用DB権限 権限SQLは student_viewer に当表のSELECTをGRANTし、student_staff をviewerのメンバー、student_admin をstaffのメンバーにして読
取り権限を継承させる。一方、当表のINSERT・UPDATE・DELETEはadminにも明示的にDENYする。adminへのクラス表・コード表のINSERT・
UPDATE許可は当表の変更許可ではない。根拠：database/003_web_permissions.sql:8-22。
要確認の運用事項 seed以外で分類設定を変更する入口・運用、および変更時の分類版比較・加算、更新情報設定、操作履歴記録の規約は要確認。確認できる
保存契約に分類更新がないため、項目詳細の更新情報・版を通常Web保守で更新する項目とは位置付けない。根拠：
database/002_seed.sql:85-92、Core/MasterMaintenanceService.cs:30-135、database/003_web_permissions.sql:22-22。
