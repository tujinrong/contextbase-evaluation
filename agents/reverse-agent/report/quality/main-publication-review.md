## 強化した検査

src/contextbase/validation/quality.pyで原本を別走査する。生成用SQL・画面・フロー抽出器は呼び出さない。P1/P2から対象を削除しても原本由来の必要文書を隠せない。検証失敗はERROR、プロセスは非0終了し、検証済み公開を停止する。エラーを無視するオプションは設けていない。

| 規則 | エラーとなる条件 |
| --- | --- |
| UI-001 / UI-002 | 原本の画面に対応する機能・基本設計書がない |
| UI-003 / UI-004 | レイアウト情報がない、またはMD本文に実画像を掲載していない |
| UI-005 | 掲載画像の欠落・破損・許可領域外・微小・単色 |
| DB-001 | DB使用根拠があるがDB仕様書がない |
| DB-002 | 原本で識別した個別表の定義書がない |
| DB-003 | 原本DDLの列が定義表から欠落。文章で触れるだけでは不可 |
| NAME-001～004 | 機能・項目・表・列の論理名が日本語でない |
| NAME-005 | 公開MDの論理名が日本語でない。物理名とIDは別扱い |
| DML-001 | 挿入・更新・削除・MERGEの各原本処理に対応する対象付き説明がない |
| DML-002 | 処理説明・設定項目・対象条件・確定取消の記述が不足 |

同じ表を更新する別メソッド・オーバーロードも区別する。SQL未検出のメモリー保存を物理DBと扱わない。画面検査とDB検査は個別文書へ適用し、１冊の概要文書や１枚の画像だけで全体を合格にしない。

## 新しい原本と生成側の補強

inputはJava/JSPのnenkinとn2frameworkに変更されている。旧JSBRMSのメモリー実装や完成済みPilot仕様は流用していない。JDBC・DDL・SQLからDB情報を作成する。

Javaの定数結合、StringBuilder/StringBuffer、限定されたSQL組立補助、直接実行引数、全角アンダースコアを含む識別子の解析を追加した。FOR UPDATE WAITとUPDATE文、TRIMのFROMと表参照を区別する。共通のSQL組立補助による値追加も解析し、後続値の列対応がずれないようにした。

テーブル定義はDDLと参照推定を分離する。DB2、SQL Server、ローカル確認用H2、システムメタデータの定義を、一つの本番DBの表数とは扱わない。初期データのパスワード・個人データ値は納品文書へ転記しない。

再利用可能な解析・検証はsrc、案件固有の日本語名称辞書はsrc-dynamic/nenkinへ分離した。適用原本のルートを検査する。AGENTS.mdとdocs/doc/独立品質評価.mdに規則を記録した。P1、P2、P3、P4の工程分離と、P3のソース非依存性を維持している。

## 残る範囲

評価の合格は全業務の実行同等性保証ではない。Javaの全型解決・動的SQL・全呼出経路、実DB接続・実データ、全画面の動的表示条件は未検証。JSPからの静的画像には動的な値やラベルが空になる部分があり、実アプリのスクリーンショットではない。論理名の日本語判定は文字種条件であり、訳語の業務承認ではない。項目とDB列の完全な対応・入力必須条件に仮定が残る。

原本にDDLがない表は、プログラムから確認できた列・参照と仮定を記載する。実DBから型や制約を取得したとは扱わない。他言語の既存抽出は維持しているが、今回と同じ深さのSQL組立・業務意味解析が全言語に対応したとは扱わない。既存MCTERP/TKL専用経路の２段階移行は今回の対象外。

QAはQA/、未完成事項はreport/incomplete/、納品成果物はoutput/へ分離した。全体の意味解析判定はverified_structure_onlyで、強化した欠落条件はpassである。
