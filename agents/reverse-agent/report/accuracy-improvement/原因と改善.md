# 新規・変更・削除画面の欠落原因と汎用改善

対象旧ID：F-4DCE8CF540。新公開ID：SCR-005。原本：JSBRMS.Web/Pages/Pensions/Edit.cshtml と関連するPageModel・サービス・モデル・共通処理。

## 原因

1. 基本設計の汎用文書モデルにレイアウト画像の生成・掲載経路がなく、画像はStaff Pilotの個別処理だけだった。
2. 基本設計はP2のデータ関連を掲載せず、詳細仕様側に限定していた。
3. フロー抽出が条件式内の呼出を拾わず、if内のDeleteや入力検証メソッドへの接続が欠落していた。受信型・DI実装・引数による呼出解決も不足していた。
4. SQLがない場合のメモリー上のCRUDを、具体的な保持先・項目・実行条件へ対応付けていなかった。
5. 表示用にソースの空白をまとめる処理がリテラル内部にも及び、全角空白→半角空白等の文字列規則を失っていた。
6. 件数・形式の検証はあったが、基本設計の画像・CRUD掲載を必須検査にしていなかった。

## 改善

srcに静的レイアウト投影、C#の受信型とDI登録の照合、条件式を含む呼出、保持先へのCRUD、項目保存先、入力条件とメッセージ、照合キーの正規化、保存値加工の汎用処理を追加した。案件固有部分は名称辞書だけで、対象画面専用の完成仕様書差替えは追加していない。

操作対象は現行ソースではメモリー上の年金予約データであり、物理DB表とは別である。保存は照合した既存レコードを置換し、なければ追加する。照合にはフリガナの前後空白除去・全角空白の半角化・大文字小文字を区別しない比較と、電話番号の数字抽出を使用する。削除もこのキーで照合する。保存時に店舗名、年金種別、更新日を設定する。サンプル実装のロックはDBトランザクションとして記載しない。

画面IDはSCR、共通処理IDはCOMの連番へ移行した。既存の明示ID100008は維持する。旧IDはaliasとしてP2/P3で解決できる。採番はContextBase/identities.jsonへ保存し、クリーン再生成時も保持する。

## 独立評価

合成C#のテストで、別クラス同名関数、DI多重登録、条件式内の削除、引数スコープ、保存変数の名称違い、局所コレクション除外、再帰制限、文字列内の空白保持を確認する。IDの挿入・削除・移動、旧IDの解決、HTML/CSSの非実行化を別の期待値で検査する。

既存PilotとExcelの表紙・通常・一覧の３パターンは別に回帰検査する。P3はP2の封印済み情報だけから再生成し、原本・P1・src-dynamicへのアクセスを拒否して出力を照合する。

## 未検証・限界

静的画面は実アプリケーションの実行キャプチャではない。動的ダイアログ、実値、全表示分岐、外部CSS・画像は未実行または近似する。C#は対応構文内の静的解析であり、完全な型解決・動的呼出・例外伝播・全経路の実行同等性を保証しない。追跡できない呼出候補はreportに保存する。画面側JavaScriptはコールバック内の条件・確認・メッセージの限定抽出である。ほかの言語を同精度で改善したとは扱わない。

質問はQA、成果物はoutput、未完成事項と検証はreportへ分離する。
