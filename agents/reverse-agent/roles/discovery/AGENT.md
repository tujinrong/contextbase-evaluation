# discovery — 取得・目録化

版1.4／2026-10-26。v2の3抽出層の実装契約。step --stage discoveryで抽出し、verifyが別task・文脈で独立検証する。

共通条件の正本は [AGENT.md](../../AGENT.md)、論理手順は [PROMPT.md](../../PROMPT.md)。入力権限、原文保持、版、配置、独立検証、採用、取消・再開は共通契約を使い、本書へ機構を複製しない。

物理requestはcontextbase-analysis/2。今回の義務id／question／stage／scope／requiresをホストが割り当て、検証済みの同scope前提だけを利用する。出力recordには唯一のownerRequirementと依存keyを記録し、ホストが依存の内容版を固定する。未知の関連先・阻害先・範囲理由を分け、非阻害も独立検証へ渡す。

## 入力と担当範囲

元目標と当該領域の必要義務、許可入力・封印snapshot、基準ContextBase版、検証条件、作業領域を受け取る。初回入力は共通基盤で封印してから解釈する。既存目録の補査依頼では対象と不足理由を確認する。

システム概要、業務タスクとしての機能、技術的入口、テーブル／データ、共通処理の候補と被覆を整理する。固定ツールの構造抽出とAIの業務上の帰属を区別する。

## 手順と引渡し条件

1. 対象ファイル一覧、取得状況、解析能力・制約を確認する。除外、未対応、失敗、未調査が理由付きで追跡できる状態にする。
2. 共有アダプターとSourceAccessで構造・根拠を取得し、各候補を原文位置と結ぶ。機能と入口、物理定義と参照だけのデータ、DTO等を区別する。
3. 暫定概要と対象目録、候補間の帰属、領域被覆、未知を作る。推定を観測事実へ変換せず、名称だけで同一対象や共通性を決めない。
4. 各必要義務に候補・根拠付き除外・未解決のいずれかを対応させ、独立検証を依頼する。担当作業の引渡しは検証済みや元目標達成の自己宣言ではない。

## 出力・上流修正・権限

候補差分、原文根拠、分類と根拠状態、被覆、未解決、追加調査要求を指定作業領域へ提出する。関係構築や動作深化から新対象・分類矛盾が戻った場合は該当目録を補査し、変更影響をホストへ示す。

関係構築へ進めるのは、その領域の目録が共通の独立検証を受け、ホストに採用された範囲だけ。目録で要求を満たせば後続層を起動しない。役割は正本・受入状態を直接更新せず、独立検証者にもならない。

修訂時はホストがreviseで採用済み義務と依存下流を撤回し、必要に応じstep --feedbackで原文を再調査する。runが未定義の補査やscope拡大を自動実行するとは扱わない。旧v1や旧役割値は自動変換しない。
