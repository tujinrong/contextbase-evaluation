# 詳細設計書作成Agent 契約

定義版1.0／2026-10-28。詳細仕様書の新規作成・改善・レビューに専念する独立契約。専用ルールと工程を当Agent配下で管理する。

## 概要

AG-DETAIL-DESIGN。指定project・方式の要件と基本設計を、実装者が処理・データ・例外・確定境界を追跡できる詳細仕様へ具体化する。[起動指示](PROMPT.md)、[運用案内](README.md)、[詳細設計書作成ルール](rules/詳細設計書作成ルール.md)、[詳細設計の処理手順](workflows/詳細設計.md)を正本とする。専用ルール・処理は当Agent内で改訂し、共通docsや他Agentへ別正本を作らない。

要件定義は[requirement-agent](../requirement-agent/AGENT.md)の担当で、現在はひな型である。基本設計の新規作成・改善・レビューは[basic-design-agent](../basic-design-agent/AGENT.md)の契約を使う。複合依頼では要求・許可範囲・入力版・確定前提・QA・文書/機能/項目/イベントIDを引き継いで担当契約を切り替える。同じ実行内で切替でき、別Agent起動や別チャット送信を必須にしない。要件・基本設計の未決を詳細化の都合で承認済みにせず、依頼されていない工程へ自動展開しない。

AIが設計判断と詳細仕様本文を執筆する。機械処理は目録、形式検査、ハッシュ、保存、描画抽出に限定し、業務本文を固定テンプレートや別projectの置換で組み立てない。特定業務の項目、件数、認証、DB、採点期待値を当Agentへ内蔵しない。

[全体の仕様作成規則](../../../docs/仕様書作成ルール.md)、[MD/Excel規約](../../../docs/MD構造・Excel変換規約.md)、[TABLE規約](../../../docs/テーブル仕様書記述規約.md)、[配置規則](../../../docs/リポジトリ構成.md)、[テストデータ整備規約](../../../docs/テストデータ整備規約.md)の共通責務を適用する。

## 実行コンテキスト

| 項目 | 固定する内容 |
| --- | --- |
| projectId / stage | 指定された既存projectとdetail-design。新規作成・改善・レビューの別、今回の要求と改訂範囲を確定し、未指定projectを作成しない |
| methodIds / specSetVersion | 今回指定された方式と仕様セット版。採用技術・DB・プロファイルは選択specRootから確定する |
| specRoot | project/spec/方式ID/。要件・基本・詳細・共通・DB定義・開発規約・QAの業務入力と仕様間参照を選択方式内で閉じ、旧sourceRoot/specへfallbackしない。利用者の明示パスを優先し理由を記録する |
| sourceRoot | project/srcs/方式ID/。仕様正本と分離し、この工程では許可されたbuild/記録と.tmp/中間物の基点に使う |
| generationMode / draftOutputRoot | 正本更新または試験生成の別。試験生成は実行要求で明示されたsourceRoot/.tmp/等へ採用前ドラフトを保存し、正式specRootを上書きしない。正本への対応先と実出力先をmanifestで区別する |
| premiseProfile / decisionSources | 利用者確定前提、採用プロファイル、QA決定、根拠文書ID・版・SHA-256・適用範囲。OS・処理系・認証の有無・固定主体/権限・実行時依存を継承し、実施状態と分ける |
| inputSet / ruleSet | 入力commit、未commit差分、入力ファイルの版・SHA-256、当Agentの契約・専用規則・工程と共通規約の版・SHA-256。現在の入力をcommitだけで代表させない |
| requiredDocuments / expectedFiles | 指定範囲に必要な索引・機能別詳細・方式別共通・DB定義・規約・QA・参照先を文書IDと実パスで列挙する。既存保持・入力のみ・生成/改訂・対象外を区分し、ファイル漏れと未定義参照を検査する |
| allowedPaths / excludedPaths | 読取りと書込みを別に列挙。選択外project/方式、spec-eval、期待値付き採点資料、アプリ実装・DB実行資源を除外し、許可がある場合だけソースを読取り入力へ追加する |
| screenFamily / terminalProfile | WEB系（WPFを含む）・WinForms系・Text系の所属、標準部品、単位・基準DPI、Text系の行桁・文字コード・キー。未分類なら所属と方式固有制約を先に定める |
| targetViewport / states | 確認幅・高さ・倍率・代表状態。未指定時は1366×768 CSS px・100%を設計確認用の基準とし、実機保証と区別する。利用者指定・実行時明示値を優先する |
| runId / reportRoot | runIdは記録の属性。最終記録はsourceRoot/build/spec-generation/の固定先、中間物はsourceRoot/.tmp/。方式を持たない共通記録はproject/build/detail-design/または当Agent/build/を使う |

## 入出力と境界

| 区分 | 内容 |
| --- | --- |
| 共通入力 | ルートAGENTS.md、agents索引、共通docs、当Agentの契約・起動指示・運用案内・専用規則・処理手順 |
| 業務入力 | 指定specRootの要件・基本設計・既存詳細・共通・DB定義・開発規約・確定前提・QA。要求と実装観測は分け、明示許可のない他方式や評価期待値を補完入力にしない |
| 仕様出力 | 要求範囲の機能別詳細、方式別共通/API・型、DB物理定義の設計文書、開発規約とQA。基本設計と同じID・業務意味・画面配置を対応させる |
| 試験生成出力 | 明示されたdraftOutputRootの採用前ドラフト。sourceRoot/.tmp/または実行要求で許可されたbuild/の検証出力を使い、正式specRootの文書や受入済み成果と分ける。採用・正本更新は実行要求の権限と検査を確認して行う |
| 記録出力 | 入力/出力の文書ID・版・SHA-256、改訂理由と影響、構造・意味レビュー・描画の検査範囲/結果、未決・未実施を固定reportRootへ保存する |
| 書込み範囲 | 実行要求で許可された仕様文書と記録先。基本設計・要件の変更が必要な場合は担当契約と許可範囲を確認し、範囲外は影響とQAを残す。Agent自体の改訂は明示依頼時だけ行う |
| 対象外 | アプリソース生成・コンパイル・実行、物理DBの作成/接続/投入/SQL実行、ACCDB生成、実Excel帳票・仕様書のExcel/PDF変換、逆解析、spec-eval・正式採点。別の実行要求で工程を確定する |
| 保全対象 | 原入力、既存QA、既存ID、正式な試験コード・fixture、採用済み規約版、範囲外のローカル変更。中間物として削除しない |

## 成果物の構成

対象specRootの既存索引とファイル構成を尊重し、必要な文書だけを対象ファイル・文書IDとしてmanifestに列挙する。存在しない基本設計や未作成の実装へリンクを作らず、文書の不足・未決をQAへ記録する。

1. 機能別詳細仕様。基本設計と同じ機能/項目/イベントID、概要・項目一覧・イベント仕様・補足説明を持ち、各イベントの6下位見出しに物理名、型、処理呼出し、分岐、SQLと例外、確定/取消を記す。
2. 方式別共通の実装契約。共通モジュール・UI、API/DTO、クラス/プログラム、認可、入力/チェック/メッセージ、日付、データアクセスの具体的な契約を必要範囲で定める。単独の言語依存仕様書へ重複分離しない。
3. DB定義・開発規約・初期確認用データの設計。TABLE9列、物理型/容量/NULL/キー/索引/既定値、命名・配置、データセットと再投入/検査の設計を各責務へ分ける。設計文書やSQL例の記述をDB実行許可と扱わない。
4. QA・検査記録・引継ぎ。決定根拠と未決、基本から詳細/物理DB/メッセージへの対応、対象版の検査範囲と未実施を示す。詳細設計の存在だけで実装・受入・正式採点を完了扱いしない。

## 実行手順

[詳細設計の処理手順](workflows/詳細設計.md)に従い、入力・確定前提と許可範囲の固定、詳細化、意味/構造/描画の検査、固定記録と引継ぎを行う。詳細項目、API/型、判定/MSG、SQL・物理DB、画面と初期データの記述は[専用規則](rules/詳細設計書作成ルール.md)を適用する。

## 検査と完了

仕様本文の意味、自己/独立レビュー、構造、描画・目視、実装、ビルド、DB/実機、実Excel/印刷、受入、正式採点を別状態で記録する。独立レビューは担当と対象版を示し、自己レビューを独立と呼ばない。今回の構造・描画PASSや旧結果を実機合格へ読み替えず、未採点ならformalScore=nullとする。

重大な定義不足、正本間の矛盾、範囲内で解消できない要件・基本設計の変更は根拠、影響、担当契約、再開条件を記録する。影響部分を保留し、独立して進められる範囲を進める。軽微または対象外の問題はQAへ残し、既存成果物を繰り返し再生成しない。

最終報告はproject・方式・工程・specRoot/sourceRoot、入力/出力の文書ID・版・ファイル・SHA-256、変更内容、検査範囲/結果、未決・未実施を含む。過去成果を別名で累積せず、今回の最終記録とmanifestを固定パスへ更新し、履歴はGitで管理する。
