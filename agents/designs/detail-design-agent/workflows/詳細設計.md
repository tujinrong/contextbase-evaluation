# 詳細設計の処理手順

定義版1.4／2026-10-30。詳細仕様の執筆・検査・描画・記録の工程正本。3系統の画面品質を方式別の実装可能な条件と下流検査へ接続する。

## 適用と入力

[Agent契約](../AGENT.md)と[詳細設計書作成ルール](../rules/詳細設計書作成ルール.md)を読み、利用者が指定したproject・方式の詳細設計の新規作成・改善・レビューを実行する。要件定義・基本設計・実装を無条件に一括生成する工程ではない。

UI工程間の共通条件は[UIパターン規約](../../../../docs/UIパターン規約.md)と[WEB](../../../../docs/WEB画面品質規約.md)・[WinForms](../../../../docs/WinForms画面品質規約.md)・[Text](../../../../docs/Text画面品質規約.md)の該当規約を読む。詳細化の手順は当Agent内に保持し、参考パッケージの成果物形式やJavaScript試作を実行契約として採用しない。

Accessは詳細化前にAUI-05a～05cの採用を確認し、全タイトル/入力/付属Label/Tab/ダイアログの役割トークンと文字領域・部品高の組合せを列挙する。VBA CP932と他ファイル/DBのUnicodeの境界、ホストACPの実取得、変換不能/非往復文字の扱い、独立した日本語期待値と実再取込み/表示の必要証拠を引き継ぐ。日本語版Officeという名称だけでACP932や文字化け解消を確定しない。

## 詳細設計の工程

1. **入力と改訂範囲の固定**

   1. 共通規約と当契約を読み、project・detail-design・方式・specRoot/sourceRoot・読書きの許可・除外、正本更新または試験生成の別を固定する。試験生成では明示されたsourceRoot/.tmp/等のドラフト出力先と正式specRootへの対応先を分け、正本を上書きしない。未指定projectを作成せず、旧sourceRoot/specや他方式・spec-evalを代替入力にしない。実装ソースの読取りは明示許可がある場合だけ追加する。
   2. 選択specRootのプロジェクト情報・採用プロファイル・方式別共通・QAから利用者確定前提を先に読む。OS、処理系、認証の有無、固定主体/操作権限、実行時依存、DB/入力/版/監査を根拠ID・版・SHA-256・適用範囲とともに固定し、変更指示や新たな矛盾がなければ継承する。既回答の再質問や旧案/未選定への復帰、他方式への展開をしない。
   3. 要件・基本設計・既存詳細と関連する共通/DB/規約を読み、対象ファイル・文書版・SHA-256と未commit差分を保存する。requiredDocuments/expectedFilesに指定範囲の索引、機能別詳細、方式別共通、DB定義・テーブル分冊、規約、QAと必要参照先を文書ID・実パスで列挙し、既存保持・入力のみ・生成/改訂・対象外を区分する。変更要求を機能/項目/イベントIDへ対応付け、既存制約と今回の設計判断を分ける。作業中に入力が変わった場合は影響を確認し、版を混在させない。
   4. 要件・基本設計の不足や変更が必要なら、根拠・影響・未決・担当契約を特定する。許可範囲なら同じ実行内で担当契約へ切り替え、要件Agentがひな型の部分は未整備/QAを明記する。範囲外は無断編集せず、独立して詳細化できる部分を進める。
   5. UIパターン規約と方式別品質規約の採用版/ハッシュをruleSetへ含め、family=WEB/WINFORMS/TEXTとrenderer=BROWSER/WPF/WINFORMS/ACCESS/TERMINALの対応を確定する。既知方式の分類を維持し、追加方式は必要に応じspecRoot/規約/UIパターン.json（schemaVersion=1、family、renderer）を採用根拠と共通UI/QAへ対応付ける。未分類UIを完了にせず、理由・根拠付き非UI例外と分ける。screen_typeと主/補助用途パターンを別々に選び、24候補の全作成をしない。
   6. Accessでは[Access画面品質規約](../../../../docs/Access画面品質規約.md)と[UI適合検査](../../../../docs/UI適合検査.md)の採用版/ハッシュを含める。全UI方式で利用者タスク・traits・選択方式・変更範囲、最小有効領域/倍率又は端末行桁、保存方式/単位/確定/未反映入力/取消/失敗の契約を選択specRootから引き継ぐ。確認済み・仮定・未確認を分け、変更範囲が未指定の既存UI修正はlayout_onlyとして扱う。操作仕様の変更案を配置修正へ混ぜず、画像だけから保存動作を確定しない。

2. **詳細仕様の作成・改善**

   1. AIが機能別詳細・方式別共通・DB定義の設計文書・開発規約・QAの必要範囲を執筆する。物理部品/バインド/変数/言語型、API/DTO/引数戻り値、各判定/例外、SQL/パラメーター/物理列と確定境界を基本設計IDへ結び付ける。業務本文を機械の固定値で組み立てない。
   2. 変更した条件を画面・項目・要求/応答・入力検証・SQL・状態/復帰・メッセージへ同期する。検索条件の削減を登録項目や保存制約・権限/論理削除制約の削除と混同せず、不要な条件・多段検索・ページングを勝手に追加しない。
   3. 基本と同じ画面・状態の静的HTML/CSSをMD概要GRIDにコードフェンス外で埋め込み、画面/項目/操作IDを実部品/バインド/端末領域へ対応付ける。採用分類・標準部品・単位・Text行桁/文字幅/キーを維持し、参考パッケージの単独HTML主成果物指示は採用しない。独自の別画面や仕様PNG・単独HTMLを併置せず、デモJavaScriptの保存/検索や過去の同梱検査を実機合格にしない。
   4. 項目移送/更新、raw/保存長・NULL、認可、候補/停止保持、更新直前の再判定、期待件数、親子/監査の確定・取消、保存結果不明、MSG実文言と復帰、初期確認用データと再投入/保護を具体化する。SQL・物理DB定義は設計文書として記し、アプリ実装や実DB操作を開始しない。
   5. **採用系統のUI契約を具体化する**
      1. ブラウザーWebは共通shell/ナビゲーション/現在位置/独立見出し、リンクとボタン/行操作、入力中・適用済み条件/ページ・安定順/出力範囲を、実装部品・URL/DTO/SQL・状態表へ結ぶ。フォーム保存/未保存離脱/直接URL・履歴・再読込、意味HTML/CSSトークン、キーボード/状態と最終publishのDOM/描画/実操作検査を定義する。
      2. WPFはWEB系の構成目的をXAMLのWindow/Page/Control、DIP/Style・バインド/Command・検証/確定、ネイティブ遷移・キー/フォーカスへ具体化する。URL/DOM/CSS/browserを必須にせず、実Windowの属性/描画/操作とデータ再読込を必要検査にする。
      3. VB.NET WinFormsはForm/Control/TabPage、基準DPI/AutoScale・Anchor/Dock/スクロール、列とフォント/余白、Tab/既定取消キー、連結/非連結モデルの検証・確定/保存/取消・終了を記す。Accessは下記の専用条件を維持し、他方式へ字体や固有APIを強制しない。
      4. Textは固定行桁/原点/半角全角セル・保護/入力属性、入出力レコード/フィールド、CCSID・DBCS/文字数/バイト長、カーソル/機能キー・メッセージ/ページ・長文継続と保存/取消を対応付ける。実端末/エミュレーターで確認するセル・キー・変換・ホスト入出力の期待結果を定義する。
   6. Accessの全Form/Section/Page/Control・付属ラベル・一覧見出しをIDと親子関係で列挙し、共通トークン、位置/寸法とcm/twip・pt、役割別字体、ColumnWidthsと見出しの同一定義、Tab/サブフォーム内部、状態別入力/表示属性を仕様へ具体化する。識別列の代表長と最大長付近の値、全文確認・編集経路から一覧/詳細の必要幅を決め、固定比率・用途を無視した全欄の一律同幅・文字縮小で収めない。全タブの対象識別を維持する。
   7. 連結/非連結・編集バッファ・親子DB確定責務を定め、未反映入力から最終保存、編集中の対象切替、追加/変更/削除後の保存/破棄、戻る/閉じる、保存失敗をイベントIDと状態遷移へ展開する。AccessではDirty/BeforeUpdate/Undo/Refresh/Requery等の採用イベント/APIの責務と呼出し順、Tab/Enter/Esc/初期・復帰フォーカスを対応付ける。現行契約の変更が必要なら根拠と許可範囲を確認し、レイアウト限定の変更へ混ぜない。
   8. 各UI合格条件に規約/用途パターン・根拠ID/版、画面/項目/操作ID、部品/状態、期待する属性/値・単位・許容範囲、検証方法・必要証拠を付ける。共通規約を今回凍結するAccessではaccessScreenChecksの全画面とidentity/layout/content/selection/saveCancel/navigation/keyboard/states/viewportへ対応する適用・対象外理由と独立した期待条件を設計する。実装工程が既存のtests/ui-contract.json/rulesへ落とせる引継ぎを作り、新しい製品検査スキーマを増やさない。製品JSONや実測結果を設計工程で捏造しない。

3. **対応とレビュー**

   1. 変更範囲の要件・基本・詳細・共通・DB・規約・QAを照合し、同じ条件の矛盾や未定義参照、廃止ID/旧取得契約を残さない。基本設計は専用契約の範囲で同期し、範囲外の残件は影響と次の確認条件を記録する。
   2. 番号付き手順と判定ID、成立/不成立/確認不能、API/DBの入出力・型・件数、確定/取消・結果不明、MSGと保持/フォーカス/再操作を追跡する。必要な正常・境界・複合・競合・障害ケースの期待結果を設計し、試験実施と分ける。
   3. 自己レビューと独立レビューの担当・対象版・結果を分ける。重大な契約矛盾や定義不足を承認済み・完成版とせず、根拠・影響・再開条件を示す。軽微・範囲外の問題はQAに記録し、過去成果を繰り返し生成しない。
   4. Accessは利用者が対象を探す/選ぶ→入力する→確定/取消→再表示する流れで、合理性・統一性・見やすさ・操作性を別々にレビューする。対象の常時識別、一覧からの判別性、選択と詳細の一致、操作名と作用範囲、未反映入力・保存失敗・未保存離脱を重点とする。指摘を条件ID/事実/影響/修正/合格条件/検証方法へ分解し、「余白が多い」「同じ幅でない」だけで不適合にしない。
   5. 全UI方式はfamily/renderer・用途パターンと採用理由、規約/画面/項目/操作から個別期待条件への対応、方式固有の実部品/端末制約と下流検証をレビューする。WebのURL・履歴・ページ/出力整合、WPFのバインド/ネイティブ遷移、WinFormsのDPI/保存境界、Textの行桁/キー/入出力を混同せず、参照CSS/HTML/JSの単純移植で完成扱いしない。

## 検証と記録

UIP-03aは基本設計の整列群/トークンから対象部品の具体値へ追跡し、認証入力と既存の同型ペア、同じ共通部品を使う画面を横断レビューする。専用規則に従い、表示幅と入力上限、座標系/単位、補助部品・エラー/再表示時の条件、実装前の期待値と製品観測を分ける。幅の相違をmaxlengthの相違で正当化したり、上限を削って表示を揃えたりしていないことを確認し、対象版と未解決条件を引き継ぐ。

1. **構造・参照の確認**

   1. requiredDocuments/expectedFilesと実入力・実出力の全ファイルを照合し、索引や分冊を含む指定範囲の漏れ、余分な対象、重複ID、未定義参照を確認する。spec-meta.path、H2/sheets、LIST矩形/列/キー、TABLE9列/fieldIds、文書/機能/項目/イベントID、相対リンク・方式内依存を検査する。採用前ドラフトも実出力先から相対リンクを解決し、正式specRootの存在だけで出力一式の完全性を判定しない。欠落・対象外・未生成の理由をmanifestに明記し、専用規則の意味レビューを形式検査だけで代替しない。
   2. 変更した項目から物理部品・型/長さ/NULL、API/DTO、SQL/DB列、CHK/MSG、復帰への対応を確認する。関連する定義・候補・取得条件・ページ・更新条件/期待件数/確定境界と初期データの再現条件を照合する。
   3. AccessのUI部品一覧と全画面/Tab/Page/ダイアログの必要状態を照合し、各部品・属性・カテゴリから仕様の独立期待条件へ到達できることを確認する。保存/取消/選択/遷移/キー操作は実装後の実キー操作と再読込の証拠を必要とする条件にし、renderの目視条件やdimensionsの寸法条件で代替しない。対象外には理由を付け、必要条件の欠落・未決をQAへ残す。
   4. 全UI方式で規約ID・用途パターンと画面/項目/操作・実装部品/入出力レコードの対応、単位/トークン・状態・個別期待条件・必要証拠を照合する。追加方式のUIパターン.jsonが必要な場合は分類と採用根拠・具体仕様の整合も確認し、型宣言だけでUI定義を充足しない。

2. **画面・図の確認**

   1. MD内の図の構文と必要なER/フローを確認し、物理名・キー・JOIN・分類条件・多重度を本文と照合する。図の存在や描画成功だけで処理を正しいと判定しない。
   2. 埋込みHTML/CSSの同じ断片を方式内.tmp/へ抽出し、対象サイズ・倍率・必要状態で描画・目視する。MD/断片のSHA-256、抽出方法、ブラウザー版、計測値・閲覧状態・指摘と修正を記録する。文字切れ、重なり、余白、スクロール、Text行桁/全角セル幅・操作の到達を確認する。
   3. MDビューアーのCSS/フォーム制限、ブラウザーの配置確認、TextのCCSID/DBCS・端末キー・IME、実アプリ/実Excel/印刷を別状態で記録する。一時HTML/画像のパスを恒久的な最終証跡リンクにせず、静的モックを実機試験と呼ばない。
   4. Accessは採用した最小有効領域/倍率と必要状態で、対象識別、重要列の見切れ、長文の全文到達、選択表示、Tab内の見出し、主要操作への到達をモックで確認する。Officeの実Form/Controlの属性・アンカー・日本語入力・キー動作・保存/破棄後の再読込は実装工程の検査として明示する。未確認の100/125/150%候補やモックの画面寸法を、実機確認済みへ読み替えない。
   5. Webの採用幅/文字拡大・状態とCSSスコープ、WPF/WinFormsの実部品制約と単位、Textの行桁/全角セル/保護域・カーソル/キー表記をモックで点検する。製品の最終publish/Window/Form/端末の実測・キー/保存後再読込は下流で未検証とし、ブラウザー描画を全rendererの実機試験にしない。

3. **固定記録の更新**

   1. 修正後の対象版で必要な検査を行い、現在の入力/出力の文書ID・版・ファイル・SHA-256、改訂理由・影響、検査範囲/結果、未決・未実施を固定reportRootへ更新する。Agent契約・専用規則・工程と採用規約の版/ハッシュも記録する。
   2. manifestの出力ハッシュを実ファイルへ照合し、構造・意味/独立レビュー・描画/目視・実装・ビルド・DB/実機・実Excel・受入・正式採点の状態を分ける。正式採点をしていなければformalScore=nullとし、過去のPASSを転記しない。

## 保存先と引継ぎ

専用ルールはrules/、執筆・検査・描画・記録の工程はworkflows/を正本とする。再利用可能な詳細設計専用の機械処理を追加する場合は当Agentのscripts/へ置き、project名、業務値、方式数、旧baselineに固定しない。project固有の一回用処理は所有範囲の.tmp/へ置き、規則・処理の別正本を共通docsや他Agentへ保存しない。

業務仕様と採用済み規約版・QAは対象specRoot、方式別の最終検査と入出力manifestはsourceRoot/build/spec-generation/、中間物はsourceRoot/.tmp/を使用する。方式を持たない共通工程だけproject/build/detail-design/とproject/.tmp/、または当Agent/build/と当Agent/.tmp/へ置く。日付・runId・attempt別の履歴を累積せず、Gitで履歴を管理する。原入力・QA・正式試験コード/fixtureと範囲外ローカル変更を保全する。

試験生成は実行要求で許可されたsourceRoot/.tmp/またはbuild/の検証出力へ採用前ドラフトを保存できる。manifestは入力の正式specRoot、正本への対応先、実出力先、ドラフトの版・SHA-256、生成・検査・採用状態を分ける。試験生成の成功だけで正本の更新・採用・実装・受入を完了扱いしない。

次工程へ文書ID・版・SHA-256、機能/項目/イベントID、確定前提・QA決定、未決・未実施、実装上の契約を引き継ぐ。Agentの規則更新だけでprojectの仕様一式を自動再生成しない。詳細設計の完了をアプリ/DB生成、DB接続、変換・印刷・受入・正式採点の開始許可とせず、次の実行要求で工程と対象を確定する。

Accessでは画面タイプ/対象・部品一覧/トークンと寸法・列幅/状態遷移/保存・取消範囲/キーとフォーカス/根拠付き合格条件/必要証拠を、実装Agentへの引継ぎに含める。UI契約のidentity/layout/content/selection/saveCancel/navigation/keyboard/states/viewportへの対応を示し、仕様条件の設計済み、モックで確認済み、製品実測は未検証を分ける。重大な欠落がある範囲は詳細設計完了とせず、解消条件と担当を残す。

全UI方式の引継ぎにはfamily/renderer、主/補助の用途パターンと採用理由、規約/画面/項目/操作ID、実部品/端末入出力レコード、根拠付き個別期待値・状態・検証方法と証拠、確定/仮定/QA・未実施を含める。最終publishのDOM/実操作、WPF/WinFormsの実Window/Form、Textの実端末/CCSID・DBCS/機能キーという対象ごとの実機検証を計画し、設計段階では実行しない。Agent改訂だけでsample-project等の既存仕様・製品を更新しない。
