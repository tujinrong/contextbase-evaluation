# 基本設計書作成ルール

版1.1／2026-10-29。基本設計に固有の記述規則を維持し、Accessの画面品質を利用者タスク・モック・状態/操作と設計レビューへ具体化する。

## 適用範囲と正本

この文書は基本設計専用Agent（AG-BASIC-DESIGN）が作成・改善する基本設計の専用ルール正本である。[Agent契約](../AGENT.md)と[実行指示](../PROMPT.md)から参照し、基本設計固有のルール・処理の更新は当Agentフォルダへ保存する。共通docsへ同じ専用本文を重複管理しない。

[仕様書作成ルール](../../../../docs/仕様書作成ルール.md)、[MD構造・Excel変換規約](../../../../docs/MD構造・Excel変換規約.md)、[テーブル仕様書記述規約](../../../../docs/テーブル仕様書記述規約.md)の共通契約を引き継ぐ。主章・イベント6下位見出し・一般LIST・TABLE9列・メタ情報・画面HTML・変換・入力隔離・保全等の共通規則は維持し、基本設計の項目一覧・検索ER等の専用条件は本書を適用する。詳細仕様・実装・DB実行・逆解析・実Excel出力の処理は別工程とする。

利用者が指定したproject・方式と改訂範囲に適用し、確定前提・採用プロファイル・QA決定を継承する。採用済みのproject内規約はその版・入力ハッシュの証拠として保持し、新規則を未指定projectへ一括適用しない。特定題材の業務項目、件数、文字長、採用DBや期待値を汎用Agentに固定しない。

## 項目一覧

項目一覧は一章一矩形表だけ。基本設計の列は「項目ID・項目グループ・項目名・コントロール・必須・入力制限・フォーマット・初期値・DBテーブル名・DB項目名・備考」の11列とする。項目グループは基本情報・職務・経歴などの意味単位を示し、同じグループも各行に明記する。コントロールは採用方式の標準部品名で示す。AccessはTextBox・ComboBox・ListBox・CommandButton等、WebはTextBox(input)・Select(select)・Button等を用い、読取専用・パスワード・複数行の区別も記載する。帳票だけの項目は帳票セルなど実際の表現を記し、画面部品を持つように見せない。

全欄を文章で埋める必要はない。必須列は〇＝必須、空欄＝任意、半角「-」＝判定対象外、「条件付」＝条件付き必須、「一部」＝複合項目の一部必須とする。この凡例は共通仕様に一度だけ記し、行の備考には成立条件・対象内訳を残す。条件付・一部を単純な真偽値へ置き換えない。チェックボックス等の初期値・有効状態を含む真偽値は〇＝true、空欄＝falseとする。

入力制限には固有の許容文字・長さ・数値範囲・編集制限、フォーマットには意味のある表示・入力書式だけを短く記す。初期値は実値だけを記し、実際に空ならセルも空欄とする。新規・初回と編集・生成時で固有の差がある場合だけ区別する。属性自体が非該当なら半角「-」、未確定ならQA-IDを記す。空欄を非該当や未確定、前行の継承として使わない。空文字列・Null・未選択等の入力状態、真偽値false、DB保存上のNULLの対応は共通仕様で区別する。

DBテーブル名とDB項目名はそれぞれ独立列へ論理名を明記し、入力値の保存先、検索条件の照合先、表示値の参照元、候補取得元を追跡できるようにする。複数参照は番号や組の表記をそろえる。DB非関連の操作・表示と時計・固定値だけの算出は両DB列を半角「-」とする。DB由来の算出値や認証時キャッシュは元のテーブル・項目を示し、再読取り・更新の有無を備考で区別する。物理名だけで論理名を代用しない。

raw上限・正規化/保存上限・単位の独立列は増やさない。入力前と正規化・保存後で上限が異なる場合は入力制限の中で区別し、長さの数値と単位を同じ句に記す。文字数の計測方法と受理範囲は対象projectの共通仕様に一度定義し、各列名や値に「（Unicodeスカラー値）」等を繰り返さない。DB欄も論理名を使う原則を共通に定め、列名や各値に「（論理名）」を繰り返さない。表記の簡略化でUnicode文字の受理範囲や正規化・保存後の検査を変えない。

共通前提は共通仕様へまとめ、各行には固有の条件だけを残す。「文字列」「入力可」「表示のみ」「利用者入力なし」「初回・新規は空、編集は保存値」等の埋草を繰り返さない。未設定時の特別な扱い、候補の抽出・並び・停止既存保持、条件付き必須、操作・保存条件など、専用列以外の固有情報は備考へまとめる。簡略化で必須・上限・候補・参照・保存条件を削除せず、項目IDを維持する。項目一覧の半角「-」規則は、TABLE形式9列の既存の〇・空欄規則を変更しない。

Excel変換でも11列の区分、部品種別、DB参照の対応と元値を保持する。空セルを文字列「空欄」「非該当」や数値0で補わず、元の記号・空値と意味を保持する。条件付・一部を真偽値や空欄へ変換しない。この項目一覧の例外を、一般LISTやTABLE形式9列へ展開しない。

## 検索とDB更新

基本設計の検索処理は、単一表の場合も対象表と主キーを含むER図を必須とし、[共通の仕様書作成ルール](../../../../docs/仕様書作成ルール.md)の単一表によるER省略規則より本規則を優先する。複数表では論理テーブル名・論理項目名、結合キー、参照マスタの分類条件、関係の多重度を示す。永続DBの外部キー制約と検索時のJOINを区別し、表示名取得・候補取得だけの結合も説明する。図の存在だけで検索仕様を代替せず、条件未指定、検索一致方式、並び順、件数・上限を対応させる。

基本設計のDB更新は、対象テーブルと追加/更新/削除の別、対象キーとWHERE相当の論理条件、項目別の入力元・設定値・変換、変更しない項目、期待更新件数を記す。存在・重複・コード有効性・同時更新版を確認する時点、親子更新の確定単位、無変更時の扱い、確定/取消、失敗・競合・件数不一致の結果も具体化する。SQL構文、DDL、API、実装コードと実DB実行は詳細・実装工程へ分け、基本設計では論理名と業務意味を維持する。

## 処理手順と整合性チェック

処理手順が4項目以上になる場合は、意味のまとまりごとに大項目と小項目の入れ子番号リストへ階層化する。同じ階層は2～4項目を目安とし、必要な場合だけ3階層まで使う。3項目以下の短い手順は一段のままでよい。大項目は「受付・入力確認」「DB処理」「結果・復帰」等の短い目的を示し、小項目に具体的な動作・判定・分岐を置く。元の実行順・条件・判定ID・メッセージ・DB確定境界を維持し、項目数を減らすために処理を省かない。各階層の番号は1から連番とし、本文・チェック表・DB説明から参照する場合は「手順2.1」のように大項目からの経路で特定する。判定順や操作IDを手順番号と混同しない。

処理手順は番号付きで、入力・保持状態の取得から結果表示までを追えるようにする。該当する単項目入力、項目間整合、保存済みデータ、編集/選択/処理中等の状態、認可、版、件数を判定し、更新直前に再判定する条件と時点を示す。各判定へ一意の判定IDを付け、対象項目、前提、成立/不成立の条件、次の手順または終了先、MSG-IDを対応付ける。「検査する」「共通処理を呼ぶ」だけで分岐を省略しない。

複数違反時の優先順位、途中で止めるかまとめて表示するか、未保存入力を保持するかを定める。事前に取得した候補・版と確定直前の現在値を区別し、画面の無効化だけを認可・整合性の保証にしない。共通の判定定義を参照する場合も、そのイベントの引数・対象・適用条件・結果分岐を具体化する。必要のない検査まで全イベントへ列挙して埋草を増やさない。

DB操作は判定と手順に対応させ、項目別設定、対象条件、期待件数、トランザクション範囲、確定/取消後の状態を追跡する。正常な無変更0件と競合・消失による0件を区別する。確定前の失敗と、確定応答を受け取れず保存結果が不明な状態も分ける。結果不明を成功・全取消済みと断定せず、成立確認の方法、確認できない場合の停止/照会、二重保存を避ける再操作可否を設計する。

## メッセージと復帰

各エラー・警告・確認・成功・保存結果不明をMSG-IDと実際の日本語文言へ対応付ける。差込値の取得元と表示方法、画面上の表示位置、保持/破棄する入力・選択、戻すフォーカス、再操作・再読込・取消の可否を明記する。共通メッセージを使う場合もイベント側で適用条件と差込値を特定し、「入力エラー」「共通エラーを表示」だけで済ませない。認証失効や未保存破棄の扱いは既存の確定前提に従う。

## Pilotと品質確認

Pilot用の検証設計は、正常・境界・複合条件・競合・障害から対象業務に必要な代表シナリオを選ぶ。シナリオID、初期DB/画面状態、利用者・権限、操作入力、成立させる判定IDの組合せ、期待する分岐・MSG-IDと文言、DBの確定/取消/無変更、保持・フォーカス・再操作を示す。項目表を長くする代わりに、既存のイベント仕様と検証設計で処理の深さを表す。

複合条件は既存スコープに必然性のある組合せだけを採用し、訓練のためだけの新機能・制約や、単なる複雑化を促さない。設計者の新判断はQAへ採用理由と未承認の状態を記録する。保存と出力の条件を分ける前提や重複許容等の既存契約を、シナリオ作成の都合で変更しない。

品質確認では、4項目以上の階層化・各階層の連番・階層番号参照、判定IDと番号付き手順・分岐先、チェックと保存直前の再判定、DB項目別設定/期待件数/確定境界、MSG-ID・実文言・復帰、代表シナリオの対応を照合する。設計したシナリオと実行済みの試験を分け、実施結果は対象版と証拠で示す。未実施・未評価を合格や正式得点へ置き換えない。

## Access画面の基本設計

段階横断UI品質の正本は[Access画面品質規約](../../../../docs/Access画面品質規約.md)とし、本節は基本設計で具体化する情報と確認方法を定める。規約の数値例や外観を無条件の業務要件にせず、選択specRootの確定前提・採用規約・QAを先に適用する。画像から動作を断定せず、確認済み・仮定・未確認を分ける。

画面設計の前に、利用者タスクと要求IDに対応する主画面タイプ、必要な補助タイプ・特性を決める。方式分類のWinForms系と、SEARCH_LIST/EDIT_FORM/MASTER_DETAIL等の目的別タイプを区別する。対象Form、タブの各Page、確認/エラー等のDialogを列挙し、画面名・対象・モードを親枠又は画面内のどこで識別できるかを示す。既存の認証なしの範囲へAUTH画面を復活させない。

共通UI設計には、採用する字体と役割別サイズ、外周/項目/グループ/ボタンの間隔、部品高、ラベル配置、ボタンの通常/長ラベル幅等をトークンとして一度定義する。各値に単位、採用根拠、正式条件/暫定仮定、適用部品と例外理由を対応付ける。AccessのTwips・pt、モックのCSS px、Windowsの倍率、有効表示領域を区別し、変換や確認条件を記録する。未確定の寸法・倍率は仮定又はQAとし、正式条件・対応保証へ自動昇格しない。

配置は利用者の作業順、対象識別と実際に想定する値の長さを基に設計する。短い番号・年月・数量、名称、複数行長文を分け、必要な文字幅・余白・選択矢印・スクロールを見込む。一覧の見出しと行の列幅定義を共有し、識別に必要な一覧幅と入力に必要な詳細幅を両立させる。省略する値にはキーボードでも到達できる全文確認経路を示す。幅不足は上下配置・別画面等を比較し、比率固定、均等幅、全画面中央寄せ、全要素11pt、余白率だけの評価で解決しない。

一覧と詳細では、選択対象、表示/編集対象、追加中の対象の関係を示す。親の識別番号・名称等はタブや明細の切替中にも判別できる位置へ置き、未選択・選択・新規/編集・参照の状態を区別する。対象切替、明細追加/変更/削除、画面離脱の各操作をイベントIDへ対応付け、対象取り違えと未保存内容の消失を防ぐ期待動作を具体化する。

保存契約には、方式・単位・確定時期・未保存範囲・取消範囲・失敗時の扱いを記す。「反映」と全体保存等が両方必要なら、ボタン名称と対象・結果・確定範囲を分け、未反映内容を残した保存/切替/離脱の結果も定める。明示保存では入力中の内容が黙って欠落しない期待結果、自動保存では保存中/済/失敗と取消可能範囲を示す。既存の方式を無断変更せず、新規の未確定契約はQAとし「保存・取消まで完成」と扱わない。連結/非連結、レコード移動・終了等のAccess特性に伴う確定経路は、詳細工程で確認すべき制約として引き継ぐ。

概要の埋込みHTML/CSSと項目IDを使い、対象環境と状態を明記したモックを作成する。通常だけでなく、対象機能に該当する未検索/0件/未選択/長い値/編集あり/入力エラー/処理中/保存失敗等を示し、対象外は理由を残す。初期フォーカス、Tab順、Enter/Esc、複数行入力、警告後の復帰は項目/イベント/MSGへ対応付ける。標準フォーム、タブ、サブフォーム、一覧内部まで必要な情報と主要操作に到達できるか確認し、最大化だけで配置を解決したことにしない。

設計レビューでは合理性・統一性・見やすさ・操作性から利用者タスクを確認し、次の9カテゴリを対象画面・状態へ対応付ける。確認表にはカテゴリごとの適用/対象外理由、要求ID・項目/イベントID、根拠版/位置、個別の合格条件、設計確認結果、下流の実画面検証方法を持たせる。単一のreadable=trueで代用せず、製品検査用JSONの作成は下流へ分ける。

| カテゴリ | 基本設計で具体化する条件 |
| --- | --- |
| identity | 画面名・対象識別・モードをどこで維持するか |
| layout | 画面タイプ別領域、列/行基準、共通トークン、一覧/詳細の配分と例外 |
| content | ラベル・長い識別値・長文の表示/全文確認経路と代表データ |
| selection | 選択方式、一覧/詳細の対象一致、未選択/対象切替時の扱い |
| saveCancel | 保存方式/単位/確定時期、反映との関係、取消範囲と失敗時の保持 |
| navigation | 戻る/閉じる/タブ/対象移動時の保持・離脱保護と移動先 |
| keyboard | 初期フォーカス・Tab・Enter/Esc・復帰と主要操作への到達 |
| states | 対象の初期/空/選択/編集/処理中/失敗等の区別と可能な操作 |
| viewport | 正式又は暫定の最小有効表示領域・倍率・単位と欠け/重なり/主要操作到達 |

完了時は設計適合、不適合、未検証、理由付き対象外を区別し、対象版・モック断片ハッシュ・確認環境・代表値・目視/計測結果を残す。重大な未決/不適合は影響と次の確認条件を明記する。詳細設計・実装へ、上記の画面/状態と条件、共通トークン、保存境界、確定/仮定/未決、根拠版・ハッシュを渡し、実部品の表示、キー操作、保存/破棄後のデータ再読込を未実施の検証として引き継ぐ。静的モックの適合を製品の適合・受入合格へ読み替えない。
