# 基本設計の処理手順

版1.3／2026-10-29。試験生成の分離・全件照合・Accessの9カテゴリを維持し、3分類のUIパターン/実行基盤別設計と検査・引継ぎを具体化する。

## 適用と入力

[契約](../AGENT.md)と[基本設計書作成ルール](../rules/基本設計書作成ルール.md)を読み、基本設計の新規作成・改善・レビューに適用する。文書形式・画面分類・配置・TABLEの共通規約は契約から参照する。専用工程の改訂はこのフォルダで行う。利用者要求、業務仕様、実装、過去の実施結果を工程規則へ埋め込まない。

Accessでは[Access画面品質規約](../../../../docs/Access画面品質規約.md)の適用版を固定し、基本設計への具体化は[専用規則の画面設計](../rules/基本設計書作成ルール.md#access画面の基本設計)に従う。段階横断の品質正本と基本設計専用の手順を分けて維持する。

3分類は[UIパターン規約](../../../../docs/UIパターン規約.md)と[WEB](../../../../docs/WEB画面品質規約.md)・[WinForms](../../../../docs/WinForms画面品質規約.md)・[Text](../../../../docs/Text画面品質規約.md)の該当規約を採用し、当工程の具体化は[専用規則](../rules/基本設計書作成ルール.md#3分類のuiパターン設計)に従う。参照資料の独立HTML正本・JSデモ・設定YAMLの複製を追加の必須成果物にしない。

## 基本設計の工程

1. **実行条件と要求の固定**

   1. 全体規則と当契約を読み、対象project・工程・方式・新規作成の許可、specRoot/sourceRoot、許可入力・出力、除外を固定する。利用者が指定した新project名を、将来予定の別projectへ読み替えない。試験生成の依頼ではgenerationModeとdraftOutputRootを固定し、採用前ドラフトと正式specRootを分けて正本を保全する。
   2. 選択specRootにある利用者確定前提・採用プロファイル・QAの決定を先に読み、根拠の版・SHA-256・適用範囲を保存する。新指定や矛盾がなければ継承し、旧案への復帰、同じ質問の反復、他方式前提の無断流用をしない。
   3. 要求を最小機能・利用者・入力/出力・対象外へ対応付ける。曖昧な用語は文脈から進められる解釈と根拠を設計判断へ残す。重要な未確定事項はQAとし、独立して進められる範囲を進める。
   4. 要件の利用者タスク・環境・保存単位・4観点の受入条件を取り込み、screenFamily/renderer・必要purposePatternIdsと理由を画面/状態・要求IDへ対応付ける。最小有効表示領域・倍率又は端末行桁、保存契約、変更範囲、UIパターン規約と該当分類規約の版/SHA-256、追加方式なら同specRootの規約/UIパターン.jsonの採用根拠を固定する。Access品質条件を維持し、正式条件と暫定モック条件を区別する。根拠が不足する動作や未決分類は画像から補わずQAへ残す。

2. **調査と設計の作成**

   1. 外部資料が求められた場合は実際に調べ、URLと確認日、採用する一般的な構成を記録する。公開様式の複写や推奨済み認定とせず、対象業務に合わせた独自様式を設計する。実データや秘密情報を試料へ混ぜない。
   2. AIがシステム概要、操作、画面、項目、イベント、テーブル、帳票、共通制約を執筆する。各イベントに「処理概要」「処理手順」「処理フロー」「SQL・テーブル関連（ER図）」「DB操作の詳細」「結果・例外時の扱い」の6下位見出しを置く。検索は単一表でもER図を必須とし、論理テーブル名・論理項目名、結合キー、多重度、マスタ分類の条件、FKと検索JOINの区別を示す。検索以外で単一表またはDBなしのためER図を省略する場合は理由を記す。更新は対象/操作、キー・WHERE相当の論理条件、項目別入力元・設定値・変換、非更新項目、期待件数、同時更新・コード有効性の確認時点、確定/取消、無変更・例外・競合時の結果まで具体化する。物理SQL・DDL・API・実装・実DB実行へ展開しない。
   3. **画面品質を具体化する**
      1. 分類/rendererと目的別画面タイプ・必要な主/補助パターンを分け、利用者タスク、画面/領域/遷移、主操作、必要状態を列挙する。役割別の字体/サイズ・間隔・部品高又は端末表示セル等の共通定義に単位・採用根拠・確定区分・例外を付け、方式内の共通UIへ一度定義する。全24パターンを生成しない。
      2. 方式標準部品又は固定行桁の静的HTML/CSSを概要GRID内のコードフェンス外に置き、CSSを画面root内へ限定して画面/項目/操作IDを対応付ける。Webは共通サイト枠・見出し・行リンク/操作・狭幅と一覧状態、WPFはDIP/ネイティブ移動、WinForms/Accessは標準部品/DPI/伸縮とスクロール、Textは行桁/DBCS/保護/カーソル/メッセージを具体化する。Accessの対象識別・一覧/詳細配分を維持し、JSデモや独立HTMLを正本へ追加しない。
      3. 検索/クリア・並び/取得・選択/ページ・出力範囲、対象/画面移動時の保持、保存/反映/取消/削除の対象と確定範囲、失敗/競合時の扱いをイベント/MSGへ対応付ける。Webの直接URL/戻る/再読込はBROWSERに限定し、WPF/WinFormsのネイティブキー/フォーカス、Textの機能キー/前後ページ/長文継続へ読み替える。既存認証・保存・字体・取得契約を継承し、Web20件等の提案値で他方式を変更しない。
      4. 合理性・統一性・見やすさ・操作性から分類別の個別合格条件をレビューし、画面/状態・要求/項目/イベント・根拠、適用/非適用理由を対応付ける。Accessは9カテゴリを維持する。必要状態と下流の実表示/キー/保存/状態復元の検査方法を示し、単一のreadable=trueや画像・参照資料の過去結果だけで適合を充足しない。
   4. 初期確認用データは[テストデータ整備規約](../../../../docs/テストデータ整備規約.md)に従い、必須マスタ、架空業務データ、隔離した異常fixtureの設計を区別する。件数・キー・時点・参照関係・再実行方針・想定操作を定義し、この工程で投入や実DB操作を行わない。

3. **検証と記録**

   1. 構造、リンク、要求対応、項目/イベント/CRUD/テーブル/帳票の意味整合を確認する。埋込み画面HTMLを.tmp/へ抽出して同じ断片を描画・目視し、対象版・断片ハッシュ・サイズ・倍率・状態・計測と目視結果を分けて残す。画面PNG・単独HTMLを仕様へ併置しない。
   2. 今回の入出力manifest、改訂、検査、未決・未実施を固定sourceRoot/build/spec-generation/へ更新する。方式を持たない共通記録はproject/build/basic-design/へ置く。作業中の入力変更を検出したら影響を確認し、版を混在させない。

処理手順が4項目以上になる場合は、意味のまとまりごとに大項目と小項目の入れ子番号リストへ階層化する。同じ階層は2～4項目を目安とし、必要な場合だけ3階層まで使う。3項目以下の短い手順は一段のままでよい。大項目は「受付・入力確認」「DB処理」「結果・復帰」等の短い目的を示し、小項目に具体的な動作・判定・分岐を置く。元の実行順・条件・判定ID・メッセージ・DB確定境界を維持し、項目数を減らすために処理を省かない。各階層の番号は1から連番とし、本文・チェック表・DB説明から参照する場合は「手順2.1」のように大項目からの経路で特定する。判定順や操作IDを手順番号と混同しない。

機能イベントの処理手順は番号付きで具体化し、一意の判定IDから対象項目・前提・成立/不成立・分岐先・MSG-IDまで追跡可能にする。入力、項目間、保存済みデータ、状態、認可、版、件数、更新前の再判定について、該当する条件と確認時点、複数違反時の優先順位を定義する。共通処理の名称だけで機能固有の引数・条件・結果分岐を省略しない。

DBの対象・条件・項目別設定・非更新項目・期待件数・トランザクション・確定/取消を手順と結ぶ。無変更0件、競合/消失0件、確定前失敗、保存結果不明を区別し、結果不明を成功や取消済みと断定しない。成立の確認、確認不能時の停止/照会、二重保存を防ぐ再操作可否を設計する。各結果はMSG-IDと日本語の実文言、差込値と取得元、表示位置、入力・選択の保持/破棄、フォーカス、再操作/再読込/取消の可否へ対応付ける。

Pilot検証設計には既存業務に必要な正常・境界・複合条件・競合・障害の代表ケースを置き、初期状態、操作、判定IDの組合せ、期待分岐・メッセージ、DB結果と復帰を追跡する。設計者の採用判断はQAへ未承認として記録し、既存の保存/出力条件や重複許容等を変えない。訓練のためだけの新機能や複雑化を促さず、11列の簡潔な項目表と処理本文の責務を分ける。

## 検査・描画・記録

1. **構造と対応の検査**

   1. 指定したspecRootの対象ファイルをrequiredDocuments/expectedFilesに索引・分冊・支援文書を含めて列挙し、文書ID・版・SHA-256とAgent契約・専用規則・工程の版とSHA-256を記録する。生成/改訂・既存採用・入力のみ・対象外を区分し、実出力の全ファイルと照合する。spec-meta.path、実見出しとsheets、LISTの矩形・列・キー、TABLEのfieldIds、相対リンクと方式内依存を照合し、採用前ドラフトのリンクも実出力先から解決する。正本にファイルが存在することだけで試験生成物の完全性を判定しない。
   2. 専用規則の項目一覧、既存ID、入力前と保存後の上限、必須条件、DB論理名・複数参照の組、候補元、非更新項目を確認する。TABLE正本との照合は基本設計の意味を確認する検査とし、実DBへの接続やSQL実行を伴わせない。
   3. 対象イベントの6下位見出し、処理手順の階層と番号、判定・分岐・MSGの定義先、更新条件・期待件数・確定/取消・復帰、Pilotの期待結果を照合する。機械で確認できない業務意味はAIの本文レビューと独立レビューで確認し、構造PASSだけで意味レビューを充足しない。

2. **図と画面の確認**

   1. 対象MDのMermaidを構文解析し、検索ERの主キー・論理名・結合・多重度・分類条件を対応付けて描画する。図の存在や描画成功だけでDB意味の整合を保証しない。
   2. 埋込み静的HTML/CSSと画面/項目/操作IDを同一断片のまま.tmp/へ抽出し、指定サイズ・倍率又は端末行桁・必要状態で描画する。抽出元MDと断片のハッシュ、描画環境、寸法/セル計測、目視状態、指摘と修正を記録する。共通枠・本文・必要状態が確認できるか分類別に照合し、独立HTMLの別正本やJSデモで代替しない。Textの半角/全角セル、ネイティブ基盤の単位差を記録し、ブラウザー描画をDBCS/IME/キー実動作の証明にしない。
   3. 参照・構造・描画・自己レビュー・独立レビューをそれぞれ記録する。Accessは対象Form/Page/Dialog・状態についてidentity/layout/content/selection/saveCancel/navigation/keyboard/states/viewportの個別条件と適用/対象外理由を照合し、不適合・未検証を合格へまとめない。暫定寸法/倍率を正式条件化していないこと、一覧/詳細と対象識別、反映/保存境界、必要な長い値/空/エラー等を確認する。静的モックとアプリ・端末・IME・帳票印刷の実行確認を分ける。
   4. 3分類のscreenFamily/renderer・必要purposePatternIds、共通枠/遷移/一覧状態・保存/キー操作・環境と個別条件を要求へ照合する。WPFへのURL/DOM/CSS/履歴、AccessへのWeb20件、TextへのGUIや可変行の強制、全パターン生成、数値例の無根拠な正式化を検査し、不足はQAと再開条件へ残す。

3. **最終記録と次工程**

   1. 指摘を直した後の対象版で必要な検査を行い、現在の出力ファイルとmanifestのSHA-256を照合する。入力が途中で変わった場合は影響を再確認し、旧版の結果と混在させない。
   2. 最終レポート、manifest、validation、描画・レビュー記録は契約の固定パスへ更新し、対象、検査範囲、根拠、未決・未実施を示す。過去の検査・生成結果は当時の証拠として保持し、別の工程の完了へ読み替えない。正式採点を依頼・実施していない場合はformalScore=nullとする。
   3. 文書ID・版・項目/イベントID・確定前提・QA決定に加え、Accessは利用者タスク・画面タイプ・対象Form/Page/Dialogと状態・共通トークン・保存/取消境界・9カテゴリの個別合格条件/対象外理由・根拠版/ハッシュ・仮定/未決を次工程へ引き継ぐ。実部品・キー操作・対象切替・保存/破棄後のデータ再読込など、未実施の検証方法を具体化し、製品検査JSONの作成は下流へ分ける。基本設計の完了を契機に詳細設計・アプリ・物理DB・実Excel帳票の生成を開始せず、その工程の実行要求で範囲を確定する。
   4. 3分類のscreenFamily・renderer・必要purposePatternIds・採用理由/差分、画面/領域/遷移・状態/環境・共通定義/単位と個別期待値、根拠版/ハッシュ・未決/非適用理由を次工程へ渡す。ブラウザー、WPF、WinForms、Access、端末で実施すべき表示・キー・保存/入力保持/状態復元の確認を具体化し、当工程からアプリ/DB実行へ展開しない。

## 配置と引継ぎ

基本設計専用のルールはrules/、執筆・検査・描画・記録の処理手順はworkflows/を正本とする。今後、再利用可能な基本設計専用の機械処理を追加する場合は当Agentのscripts/へ置き、業務値・方式数・project名・過去baselineを固定しない。スクリプトによる業務本文の生成は行わない。

project固有の仕様、確定前提、QAと採用済みの規約版は指定specRoot、方式別の最終記録はsourceRoot/build/spec-generation/に置く。方式を持たないAgent自体の検査記録は当Agentのbuild/、中間物は当Agentの.tmp/を使用する。一回用のproject改訂・改名・比較・描画スクリプトや過去の検査記録を、再利用可能な処理正本として移さない。

共通docsや他Agentに基本設計専用ルール・工程の別正本を作らず、このフォルダの正本を参照する。project内の採用済み規約は対象版の入力であり、Agent改訂だけで自動更新しない。次回の基本設計生成時に、利用者確定前提と今回適用する規則版の差を確認して必要範囲を更新する。
