# basic-design-agent

定義版1.10／2026-10-29。基本設計専用の正本を維持し、Access画面品質を設計・モック・状態/操作のレビューと下流への引継ぎへ接続する。

## 使い方

工程は[要件定義](../requirement-agent/README.md)・当Agentの基本設計・[詳細設計](../detail-design-agent/README.md)に分かれる。要件定義Agentは既存仕様から要件への逆生成も担当する。要件の新判断はQAと利用者の指示へ戻し、詳細設計への引継ぎは要求・ID・確定前提・QA・対象版を保持する。依頼されていない後工程を自動開始しない。

[AGENT.md](AGENT.md)が役割・入出力・工程の契約、[PROMPT.md](PROMPT.md)が起動指示と実行例である。CodexへPROMPT.mdと対象project・方式・基本設計の要求を渡す。基本設計専用Agentとして新規作成・改善・レビューを行う。専用のルールと処理はこのフォルダを正本とする。

専用規則は[rules/基本設計書作成ルール.md](rules/基本設計書作成ルール.md)、執筆・検査・描画・記録の工程は[workflows/基本設計.md](workflows/基本設計.md)へ保存する。共通docsと他Agentはこの正本を参照し、基本設計専用の別ルールを持たない。

Accessの段階横断UI品質は[Access画面品質規約](../../../docs/Access画面品質規約.md)を使用する。当工程は要件の利用者タスク・環境・保存単位・合理性/統一性/見やすさ/操作性の受入条件を読み、画面タイプ別構成、共通トークン、対象常時識別、実データ長に応じた一覧/詳細、保存/取消境界、状態とキー操作へ具体化する。

全体docsを読み、specRoot=project/spec/方式ID/とsourceRoot=project/srcs/方式ID/、許可入力・出力、除外、版・ハッシュを固定する。新projectは利用者の明示作成依頼があるときだけ作る。既存projectは許可された構造と書式を参照し、別題材の業務値や確定前提を転用しない。

選択specRootの利用者確定前提・採用プロファイル・QA決定を先に読み、変更指示や新たな矛盾がなければ次回も継承する。設計者の採用判断を利用者承認と呼ばず、方式固有の値を他方式へ無断展開しない。AIが業務本文を執筆し、機械処理は保存・検査・ハッシュ・描画に使う。

## 成果物

方式README、プロジェクト情報・前提、必要な共通設計、1機能1基本設計、テーブル索引・関係・1テーブル1分冊、必要な帳票設計、QA・出典を各specRoot内へ置く。ファイル名・文書ID・対象範囲は実行ごとにmanifestへ列挙する。複数方式の業務仕様は方式内で完結させ、project/spec/README.mdは配置索引に限定する。

機能設計は概要・項目一覧・イベント仕様・補足説明を主章とし、各イベントの6下位見出しに論理的な処理・DB操作・結果/例外を記す。テーブルはHEADERと9列LISTを同じシートに置く規約を適用する。画面はWEB系・WinForms系・Text系の分類と方式標準部品へ従い、概要内のHTML/CSSだけを正本とする。別HTMLや画面PNGを仕様へ併置しない。

11列の項目一覧、空欄/-/〇、条件必須、論理DB対応、検索ER、DB更新、階層化した処理手順、整合性チェック、日本語メッセージと復帰、Pilot代表ケースは専用規則に従う。帳票は元データから改ページ・長文・失敗/再出力まで基本設計で示す。Excel帳票の出力設計と、設計書のExcel変換や実帳票の生成は別の工程とする。

2026-10-27の初回対象はsample-project2、方式はAccessとCSharp_ASPNET、題材は社員経歴管理である。具体的な業務仕様は[方式索引](../../../sample-project2/spec/README.md)から選択し、このAgentへ埋め込まない。sample-project1は今回許可された構成・書式の参照先であり、社員業務の正解入力ではない。

## 確認と引継ぎ

生成確認では実行要求のgenerationModeとdraftOutputRootを固定し、既存正本を保全する。必要な索引・分冊・支援文書をexpectedFilesに列挙し、生成した文書と既存採用した文書を区別して、実出力から欠落・余分・参照切れを照合する。試験生成の完了を正本採用・業務受入れとは扱わない。

再利用可能な基本設計専用の機械処理を追加する場合はscripts/、Agent自体の最終検査記録はbuild/、中間物は.tmp/へ置く。project固有の一回用処理・過去の検査記録と、specRootの既存仕様・採用済み規約・QAは、それぞれの所有範囲で保持する。

要求・項目・イベント・CRUD・テーブル・帳票の意味を照合し、spec-meta、見出し、LIST/TABLE、ID、リンク、方式内依存を検査する。画面HTMLはsourceRoot/.tmp/へ同じ断片を抽出して描画・目視し、サイズ・倍率・状態・対象版・断片ハッシュ・計測/目視を記録する。静的モック、実Excelの印刷、製品実機の操作確認は別の状態である。

AccessではForm/Page/Dialogと状態を列挙し、identity/layout/content/selection/saveCancel/navigation/keyboard/states/viewportの9カテゴリに個別の合格条件、適用/対象外理由、根拠、設計確認結果、下流での実画面検証方法を対応付ける。4観点を単一のreadable=trueに集約せず、重要な未決・不適合・未検証があれば影響と次の確認条件を明記する。製品検査用JSONはこの工程では生成しない。

暫定の寸法/倍率を正式な対応環境へ自動昇格せず、画像から保存・取消・キー操作を確定しない。既存確定前提と変更範囲を守り、全画面中央寄せ・均等幅・全11pt・認証復活・自動保存への変更を画面品質の名目で強制しない。

イベントの品質確認では、具体手順・判定・分岐・更新前再判定・DB結果・メッセージと復帰・Pilotケースが対応しているかを確認する。定義のない参照や「検査する」「共通エラー」のみの説明を残さず、独立レビューとシナリオ設計/試験実施の状態を分けて記録する。

最終検査記録と入出力manifestは各sourceRoot/build/spec-generation/へ固定名で更新する。方式を持たない共通記録だけproject/build/basic-design/を使用する。中間生成・失敗試行は.tmp/へ置き、履歴はGitを使う。原入力・QA・正式試験コード・fixtureと対象外ローカル変更を保全する。

最終報告には入力/出力の版・ファイル・SHA-256、検査範囲、設計判断、未決・未実施を含める。構造・意味レビュー・描画/目視・実Excel・実装・ビルド・DB/実機・正式採点を分け、未採点ならformalScore=null。基本設計の存在を実装着手可能な詳細仕様の完成や受入合格と扱わない。次工程へは文書ID・版、機能/項目/イベントID、確定前提・QA決定を引き継ぐ。

対象projectの方式はその索引から選ぶ。sample-project1はフル方式パターン（登録方式を将来追加可）、sample-project2はAccess・CSharp_ASPNETの2方式パターン。前者の仕様適用では既存業務の条件を保持し、方式固有の認証・DB・ページ操作を他方式の値へ置換しない。
