# 要件定義の処理手順

版0.3／2026-10-29。要求起点と仕様からの逆生成・Access品質条件を維持し、3分類のUIパターンと実行基盤別の要件整理・検査・引継ぎを接続する。

## 適用と境界

[契約](../AGENT.md)、[実行指示](../PROMPT.md)、[専用規則](../rules/要件定義書作成ルール.md)を使用。projectと方式を実行要求と索引で固定する。仕様逆生成はspecRootが主入力で、コードからの逆仕様評価と混用しない。spec/全体・spec-eval・対象外方式・実装資源を読まない。

業務本文はAIが根拠を読んで執筆する。機械処理は保存・目録・ハッシュ・構造/参照検査に限定し、業務文のテンプレート置換で代用しない。

Accessは[Access画面品質規約](../../../../docs/Access画面品質規約.md)と[専用規則の画面品質要件](../rules/要件定義書作成ルール.md#access画面品質の要件)を使用する。当工程は要求と受入条件までとし、画面モック・詳細設計・実機確認の工程へ広げない。

3分類は[UIパターン規約](../../../../docs/UIパターン規約.md)と分類別の[WEB](../../../../docs/WEB画面品質規約.md)・[WinForms](../../../../docs/WinForms画面品質規約.md)・[Text](../../../../docs/Text画面品質規約.md)を参照し、具体的な要件整理は[専用規則](../rules/要件定義書作成ルール.md#3分類のui要件)へ従う。

## 入力と執筆

1. **実行条件を固定する**
   1. projectId、stage=requirement-definition、generationMode、方式一覧、specRoot/sourceRoot、出力、固定reportRoot、許可/除外を記録。コミットと未コミット差分を区別する。
   2. 選択specRootの確定前提・採用プロファイル・QAを先に読み、資料ID・版・SHA-256・適用範囲を固定。新指定・矛盾がなければ既回答を継承する。
   3. UIパターン規約と選択分類の品質規約、Accessでは追加のAccess画面品質規約の適用版・SHA-256をruleSetへ含める。screenFamily/rendererと採用根拠、変更範囲、利用環境・入力方法・保存契約の確認済み/仮定/未確認を固定する。既存規約との矛盾はQAで対応付け、未確認の数値を正式条件として補わない。

2. **資料を要求へ整理する**
   1. 要求起点では利用者資料、逆生成では共通・基本・詳細・DB・規約から、目的、範囲、利用者、入力/結果、例外、データ制約、運用条件を読む。旧案と採用版を区別する。
   2. 設計の重複を要求単位へ整理し、既存ID・適用条件・未決を保持。不足はQAとし、別方式で補完せず技術詳細を新たに設計しない。
   3. Accessでは利用者の作業順と対象識別、最小有効表示領域・倍率、保存方式/単位/確定時期/取消範囲を整理する。画像の配置と実動作の証拠を区別し、認証や保存方式等の既存決定をレイアウト改善の都合で変更しない。
   4. 利用者タスクから必要な主/補助purposePatternIdsを選び、移動・検索取得/表示・選択/出力・保存・キー操作・必要状態を分類とrendererに応じて整理する。WPFのネイティブ制約、WinForms/AccessのDPI・確定経路、Textの固定行桁/DBCS/保護/機能キー/ページ入力保持を落とさず、Web専用条件を横展開しない。

3. **要件定義書を作成する**
   1. 専用規則の章立てで要件ID・確定区分・根拠・受入条件を記す。承認と試験の状態を分ける。
   2. 3分類の利用者タスクに合理性・統一性・見やすさ・操作性の受入条件を対応付け、操作/前提・期待結果・確認方法・要求ID・根拠・適用/非適用理由を付ける。Accessは既知の画面・状態と9カテゴリの個別合格条件も整理する。未確定はQAで示し、単一のreadable=trueで4観点を充足しない。製品検査JSONや別HTMLの正本は作成しない。
   3. 方式READMEと既存一覧に入口を追加。入口自体が根拠なら更新後のハッシュを採り、要件ハッシュを入口へ埋め込む等の相互依存を作らない。

## 検査と記録

1. **構造と追跡性を検査する**
   1. spec-meta.path/ID/版、実見出しとsheets、シート名、LISTの矩形・表一つ・列数・キー一意性を検査。相対リンクの実在と業務依存が同一specRoot内に閉じることを確認する。
   2. 要求の根拠、受入条件の要求ID、未確定のQA、資料ID/版/SHA-256を照合。元業務仕様の保全と入口以外への意図しない書込みがないことを確認する。

2. **意味をレビューする**
   1. 範囲・権限・検索/保存・整合・取消/競合・非機能・QAを原文と照合。決定と提案の区分、方式固有差分、未記載事項の創作がないことを確認する。
   2. Accessでは利用者タスク・環境・保存単位・4観点の受入条件から根拠へ追跡し、欠落はQAで特定する。暫定寸法/倍率の正式条件化、認証復活、全画面中央寄せ・均等幅・全11ptや無断の保存方式変更を要求していないか照合する。
   3. 3分類とrendererの組合せ、必要パターン/採用理由、Webだけのサイト移動/ページング、Textの行桁/入力保持等が個別受入条件に対応するか照合する。全24パターン、Web20件やrem/pxを全方式へ強制せず、WPFへURL/DOM/ブラウザー履歴を要求していないか確認する。
   4. 自己/独立レビュー担当、対象版・ハッシュ、所見を記録。未確認は未確認とし、構造PASSだけで業務承認を完了にしない。

3. **最終記録を更新する**
   1. manifest.jsonへAgent/規則版・ハッシュ、入力/出力のファイル・ID・版・ハッシュ、前提・範囲を保存。validation.jsonへ検査結果と未実施、report.mdへ判断・未決・制限を保存する。
   2. 方式別はsourceRoot/build/spec-generation/requirement-definition/、方式なし全体記録はproject/build/requirement-definition/へ固定。別工程の既存記録は上書きしない。中間は.tmp/、run/attempt別履歴は累積しない。

## 完了と引継ぎ

出力数・方式、版、検査範囲、未解決QA・未実施を報告。作成、本文レビュー、利用者承認、受入試験を分ける。正式採点未実施ならformalScore=null。

Accessの要件整理完了は、利用者タスク・環境・保存単位・4観点の受入条件と、既知の画面/状態・9カテゴリの適用/対象外理由・個別合格条件が、要求ID・根拠・確認方法又は理由付きQAへ対応していることを確認して判定する。重要な未決は影響・後続で決める内容を明示し、画面操作や保存/取消が完成・合格したとは報告しない。

3分類ではscreenFamily・renderer・必要purposePatternIdsと採用理由、分類別の環境/操作/状態の受入条件、採用差分と非適用理由を確認して要件整理の完了を判定する。未決分類や不足条件はQAで特定し、基本設計へ要求ID・根拠版/ハッシュ・未実施の確認方法とともに渡す。参照HTMLのデモ保存・過去の適合件数を当工程の実行結果へ転記しない。

要求ID・確定前提・プロファイル・QA・根拠・既存設計IDに加え、Accessでは利用者タスク・環境の確定状態・保存/取消要求・4観点の受入条件と未実施の検証を基本設計へ渡す。既存設計との矛盾はQAを介して改訂工程へ渡し、逆生成の都合で元仕様を書き換えない。後続設計・実装・実DB・実Excelは別指示で確定する。
