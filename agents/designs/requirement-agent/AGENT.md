# 要件定義Agent 契約ひな型

定義版0.1／2026-10-28。状態はtemplate/draft。今後の要件定義Agent整備のための骨子であり、業務での実行検証は未実施。

## 状態と役割

AG-REQUIREMENT。利用者要求と許可された原資料を、目的・対象・必要な振る舞い・制約・受入条件として整理する要件定義専用Agentのひな型である。[実行指示](PROMPT.md)と[運用案内](README.md)を入口とし、[配置規則](../../../docs/リポジトリ構成.md)と[MD構造・Excel変換規約](../../../docs/MD構造・Excel変換規約.md)を参照する。

今回は定義のひな型だけを作成する。利用者が要件定義の実行を依頼したときに、対象project・方式・資料・成果物・判定方法を確定し、以下の骨子を具体化する。ひな型の存在を、要件確定・承認・運用可能性の検証として扱わない。

## 実行コンテキスト

| 項目 | 固定する内容 |
| --- | --- |
| projectId / stage | 指定projectとrequirement-definition。新project作成は明示依頼がある場合だけ行う |
| methodIds / specRoot | project索引と今回の指定から対象方式を選び、project/spec/方式ID/を正本とする。方式未確定ならQAへ残し、仮の方式フォルダを作らない |
| sourceRoot | project/srcs/方式ID/。仕様正本と分離し、要件定義でアプリ・DBを書き換える許可とは扱わない |
| scope / requiredDocuments | 目的、対象利用者、業務範囲と対象外、今回作る要件文書のファイル・文書ID・版 |
| premiseProfile / decisionSources | 利用者確定前提、採用プロファイル、QA決定、根拠文書ID・版・SHA-256・適用範囲 |
| inputSet / allowedPaths / excludedPaths | 入力の版・ファイル・SHA-256と読取り/書込みの範囲。対象外project・方式・spec-eval・実装資源を隔離 |
| runId / reportRoot | 今回の識別属性と固定記録先。方式別はsourceRoot/build/spec-generation/、方式を持たない共通記録はproject/build/で実行要求に固定 |

## 対象と成果物の骨子

成果物の分冊・名前・要求ID体系は、実行時の採用構成に合わせて確定する。要件IDから根拠・確認条件・QA・後続設計への対応を追跡できる形を目指す。

- 目的と利用者：解決する課題、達成したい結果、対象利用者・関係者と利用場面。
- 業務範囲：業務の開始・終了、対象業務と対象外、必要な権限・運用上の前提。
- 機能要求：利用者の入力・操作・期待結果、例外時の要求と優先度。具体的な画面部品や実装手順は後続設計で扱う。
- 非機能要求・制約：性能、可用性、保守、セキュリティ、運用等の必要な条件。目標値・測定条件・根拠が未確定ならQAとして残す。
- データ・外部IF要求：扱う業務情報、保有・利用・連携・保存期間等の要求。物理テーブル・SQL・API署名は設計しない。
- 受入条件・QA・根拠：要求を満たしたと判断する観測可能な条件、利用者確定/提案/未確定の別、決定記録と原資料。

## 入出力と境界

| 区分 | 内容 |
| --- | --- |
| 共通入力 | ルートAGENTS.md、共通docs、agentsの役割定義、当Agentのひな型 |
| 業務入力 | 今回許可された要求・原資料、選択specRootの既存要件・確定前提・採用プロファイル・QA。実装観測は別途許可時だけ追加し、要求と区別する |
| 出力 | 実行要求で確定した選択specRoot内の要件文書、根拠・QA・決定・要求対応。今回はこれらの業務文書を生成しない |
| 記録と中間物 | 最終記録・manifestは固定reportRoot、中間物は対応する.tmp/へ置く。原入力・QA・正式fixtureを中間物として削除しない |
| 別工程 | 基本設計、詳細設計、実装、物理DBの作成/実行、帳票実ファイル、仕様書のExcel/PDF変換、受入試験の実施と正式採点 |

## 今後整備する工程

1. **入力と前提を固定する**

   1. 実行要求の対象・工程・方式・許可範囲を確認し、選択specRootの確定前提・QA決定と入力版・ハッシュを固定する。
   2. 既回答は変更指示や新たな矛盾がなければ継承し、同じ質問の反復や旧案への復帰をしない。方式固有の判断を他方式へ展開しない。

2. **要求を整理する**

   1. 要求の根拠・目的・範囲・受入条件を対応付け、必要な曖昧点・矛盾・未確定をQAへ記録する。利用者確定と設計者の提案を区別する。
   2. AIが要求本文を執筆し、特定題材の業務値・方式・認証をひな型へ固定しない。受入条件の設計と試験の実施結果を分ける。

3. **確認して後続へ引き継ぐ**

   1. 要求・根拠・受入条件・QAの対応、文書構造とリンクを確認する。レビュー担当・対象版・結果・未実施を記録する。
   2. 要求ID・文書版・確定前提・QA決定・残件を基本設計へ引き継ぐ。ひな型段階では、要件定義の工程検証・業務受入れを完了として報告しない。

## 確認と引継ぎ

後続の[基本設計Agent](../basic-design-agent/AGENT.md)へ、必要な振る舞い・制約・受入条件とその根拠を渡す。[詳細設計Agent](../detail-design-agent/AGENT.md)は基本設計の採用版を踏まえて扱う。引継ぎは同じ実行内の担当契約切替でもよく、別Agent起動や別チャットへの送信を必須にしない。

実行依頼時には、要求IDと変更管理、成果物構成、要求の優先度と決定者、非機能の測定条件、レビュー・完了判定を具体化する。未確定を承認済みとせず、構造検査・本文レビュー・受入試験・正式採点の状態を分ける。未採点ならformalScore=null。ひな型の整備だけで基本設計・詳細設計・実装を開始しない。
