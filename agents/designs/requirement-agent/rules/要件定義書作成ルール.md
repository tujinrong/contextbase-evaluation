# 要件定義書作成ルール

版0.1／2026-10-28。requirement-agent専用の本文規則。共通のMD/Excel・配置規則は[契約](../AGENT.md)から参照する。

## 適用と根拠

利用者・業務確認者が、何をどこまで満たす必要があるかを判断できる粒度とする。要件は期待する振る舞い・業務情報・制約で記載し、実装クラス・関数・SQL・物理列一覧・HTMLを要求の代わりにしない。採用技術は既存の制約として記載できる。

タイトル直下に版・作成日・projectId・methodId・stage・generationMode・specRoot/sourceRoot・作成根拠・承認状態を置く。逆生成は「既存仕様から再構成、今回の利用者承認未実施」と明記。根拠のない業務目的等を推測した場合は設計者判断とする。

## 文書構成

| 章 | 種別 | 記載する内容 |
| --- | --- | --- |
| 概要 | GRID | 対象版、生成モード、前提と資料の適用順、作成と承認/実行の区別 |
| 目的と業務範囲 | GRID | 目的、開始・終了、対象/対象外、既存決定の継承範囲 |
| 利用者と権限 | LIST | 主体/役割ID、利用者、許可操作、信頼境界、確定区分、根拠 |
| 機能要件 | LIST | 要件ID、要件名、必要な振る舞い、確定区分、既存対応ID、根拠 |
| データ要件 | LIST | 要件ID、業務情報、保有・入力・整合・保存上の要求、確定区分、根拠 |
| 非機能要件・制約 | LIST | 要件ID、分類、要求/適用条件、確定区分、根拠。未確定値はQA対応 |
| 受入条件 | LIST | 受入ID、対応要件ID、条件・操作、期待結果、実施状態、根拠 |
| 未確定事項・引継ぎ | LIST | QA-ID、事項、現在の状態と根拠、影響する要求、後続への引継ぎ |
| 根拠資料 | LIST | 資料ID、方式内相対リンク、文書ID、版、SHA-256、適用範囲 |

## 要求と受入条件

要件IDは方式の文書内で一意とし、継続改訂で意味を変えない。既存要求IDは再利用又は対応欄へ保持し、機能/項目/イベント/CHK/QAのIDを黙って置換しない。方式・projectを跨ぐ同じ番号は別の要求である。

各要件に資料の章・既存IDなどから原文へ到達できる根拠を付ける。複数資料は適用範囲を示す。数値・条件・対象外・権限・確認理由・確定/取消・競合時保護を失わず、設計の重複を要求単位へ整理する。

受入条件は対応要件IDと観測可能な期待結果を持つ。正常に加え、必要な未入力・境界・権限差・重複・競合・失敗・取消を記述する。既存試験ID・CHK-IDがあれば対応を残す。「正常であること」だけの循環した条件にしない。今回実行していない試験は未実施とする。

LIST章は表一つだけとし説明段落を混ぜない。空値に未確定・非適用・参照なしを兼ねさせず状態を明記。表紙を独立主章にせず、spec-meta.sheetsと見出しを一致させる。

## 逆生成時の判定

既存仕様は要求承認の証拠とは限らない。利用者決定が明記された箇所だけを「利用者確定（継承）」、通常は「既存仕様から再構成」、設計案は「設計判断・提案」、不足は「未確定（QA-ID）」とする。新指定・確定前提・旧案の関係を読み、日付だけで決定権を推測しない。

認証なしサンプルと本番認証未選定、独立DBと共有プロファイル、スクロールとページング、業務文字数と物理容量、日付入力と保存値、初期確認データと異常fixtureを区別する。保持期間・性能/可用性目標・承認者・優先度・実件数を資料なしに補完しない。採用済み事項を未決へ戻さず、未指定の追加条件をQAにする。

移行方針等の薄い資料だけの場合は確認できる範囲へ限定する。引用先ソースや別方式を自動取得せず「引用記載として継承、今回原本未確認」とする。原資料の過去の検証成功を今回の検査済み表示へ転記しない。
