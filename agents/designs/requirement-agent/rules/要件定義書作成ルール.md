# 要件定義書作成ルール

版0.2／2026-10-29。requirement-agent専用の本文規則。Accessの利用者タスク・利用環境・保存単位と4観点の受入条件を定め、共通のMD/Excel・配置規則は[契約](../AGENT.md)から参照する。

## 適用と根拠

利用者・業務確認者が、何をどこまで満たす必要があるかを判断できる粒度とする。要件は期待する振る舞い・業務情報・制約で記載し、実装クラス・関数・SQL・物理列一覧・HTMLを要求の代わりにしない。採用技術は既存の制約として記載できる。

タイトル直下に版・作成日・projectId・methodId・stage・generationMode・specRoot/sourceRoot・作成根拠・承認状態を置く。逆生成は「既存仕様から再構成、今回の利用者承認未実施」と明記。根拠のない業務目的等を推測した場合は設計者判断とする。

## 文書構成

| 章 | 種別 | 記載する内容 |
| --- | --- | --- |
| 概要 | GRID | 対象版、生成モード、前提と資料の適用順、作成と承認/実行の区別 |
| 目的と業務範囲 | GRID | 目的、開始・終了、対象/対象外、既存決定の継承範囲 |
| 利用者と権限 | LIST | 主体/役割ID、利用者、許可操作、信頼境界、確定区分、根拠 |
| 機能要件 | LIST | 要件ID、要件名、必要な振る舞い、確定区分、既存対応ID、根拠 |
| データ要件 | LIST | 要件ID、業務情報、保有・入力・整合・保存上の要求、確定区分、根拠 |
| 非機能要件・制約 | LIST | 要件ID、分類、要求/適用条件、確定区分、根拠。未確定値はQA対応 |
| 受入条件 | LIST | 受入ID、対応要件ID、条件・操作、期待結果、実施状態、根拠 |

## 要求と受入条件

要件IDは方式の文書内で一意とし、継続改訂で意味を変えない。既存要求IDは再利用又は対応欄へ保持し、機能/項目/イベント/CHK/QAのIDを黙って置換しない。方式・projectを跨ぐ同じ番号は別の要求である。

各要件に資料の章・既存IDなどから原文へ到達できる根拠を付ける。複数資料は適用範囲を示す。数値・条件・対象外・権限・確認理由・確定/取消・競合時保護を失わず、設計の重複を要求単位へ整理する。

受入条件は対応要件IDと観測可能な期待結果を持つ。正常に加え、必要な未入力・境界・権限差・重複・競合・失敗・取消を記述する。既存試験ID・CHK-IDがあれば対応を残す。「正常であること」だけの循環した条件にしない。今回実行していない試験は未実施とする。

LIST章は表一つだけとし説明段落を混ぜない。空値に未確定・非適用・参照なしを兼ねさせず状態を明記。表紙を独立主章にせず、spec-meta.sheetsと見出しを一致させる。

## 逆生成時の判定

既存仕様は要求承認の証拠とは限らない。利用者決定が明記された箇所だけを「利用者確定（継承）」、通常は「既存仕様から再構成」、設計案は「設計判断・提案」、不足は「未確定（QA-ID）」とする。新指定・確定前提・旧案の関係を読み、日付だけで決定権を推測しない。

認証なしサンプルと本番認証未選定、独立DBと共有プロファイル、スクロールとページング、業務文字数と物理容量、日付入力と保存値、初期確認データと異常fixtureを区別する。保持期間・性能/可用性目標・承認者・優先度・実件数を資料なしに補完しない。採用済み事項を未決へ戻さず、未指定の追加条件をQAにする。

移行方針等の薄い資料だけの場合は確認できる範囲へ限定する。引用先ソースや別方式を自動取得せず「引用記載として継承、今回原本未確認」とする。原資料の過去の検証成功を今回の検査済み表示へ転記しない。

## Access画面品質の要件

Accessの段階横断UI品質は[Access画面品質規約](../../../../docs/Access画面品質規約.md)を正本とし、当工程では次の内容を既存の機能要件・データ要件・非機能要件・受入条件・QAの章へ整理する。画面タイプ別の領域構成、寸法トークン、モックを要件本文へ重複して設計しない。

| 整理する内容 | 要求として残す情報 | 不足時の扱い |
| --- | --- | --- |
| 利用者タスクと対象 | 利用者、目的、開始条件、探す/選ぶ/確認する/編集する/確定する流れ、対象識別情報と取り違え防止 | 確認できる範囲を記し、未確認の利用手順は根拠とQAを付ける |
| 利用環境 | 最小有効表示領域、モニター解像度との区別、表示倍率、利用する入力方法と主要なキーボード操作 | 候補・仮定と正式条件を区別。対象未確定をQAとし、暫定値を対応保証にしない |
| 保存と取消 | 保存方式、保存単位、確定時期、追加/変更/削除の未保存範囲、取消範囲、対象切替・離脱・失敗時に保持する内容 | 既存契約を根拠付きで継承。新規で保存方式が未確定なら未確定とし、画像やAccess既定から決めない |
| 変更範囲 | レイアウト限定、操作変更、データ処理変更の許可範囲と対象外 | 既存修正で未指定ならレイアウト限定とし、動作変更の提案を分ける |

受入条件は利用者の作業に対して次の4観点を対応付ける。必要な条件を要件ID・受入ID・根拠・確認方法へ結び、不要な条件は理由付き対象外とする。画面ごとの固定得点や余白率で置き換えない。

| 観点 | 観測可能な受入条件の内容 |
| --- | --- |
| 合理性 | 作業順と情報のまとまりが合い、対象の識別・必要情報の確認・主要操作に支障がない |
| 統一性 | 同じ意味の名称・表示形式・操作結果が揃い、画面タイプや用途による差には理由がある |
| 見やすさ | 画面と対象が分かり、重要な識別値・長い値を確認でき、欠け・重なり・小さすぎる文字で作業を妨げない |
| 操作性 | 選択対象と操作対象が一致し、保存/取消/離脱/失敗後の結果を予測でき、必要なキー操作と復帰が行える |

静止画像がある場合は、見えている配置上の事実・利用者への影響・確認が必要な動作を分ける。保存・取消・権限・Tab順が画像から正常と分かったことにしない。認証なしの採用範囲をAUTH画面の分類例で変更せず、全画面中央寄せ、全項目の均等幅、全要素11pt、自動保存への変更を要求として強制しない。

基本設計への引継ぎには要求ID、利用者タスク、環境の確定状態、対象識別と保存/取消の要求、4観点の受入条件、根拠版・ハッシュ、未解決QAを含める。既知の画面・状態にidentity/layout/content/selection/saveCancel/navigation/keyboard/states/viewportの9カテゴリの適用/対象外理由と個別の合格条件を対応付け、具体化が必要な箇所はQAで特定する。4観点を単一のreadable=trueで代用しない。Form/Page/Dialogへの具体化と製品検査用JSONの作成を当工程へ繰り上げず、受入条件が定義できた状態と、実機で適合を確認した状態を分ける。
