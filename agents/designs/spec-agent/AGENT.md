# 仕様書作成・改善Agent 契約

版8.5／2026-10-25。確定済みの利用者前提を仕様正本から引き継ぎ、三種類の画面分類とText系の行桁・キー操作を今後の新規画面にも適用する。業務アプリの実装・実機試験・正式採点の実施状態は、各実行の報告で区別する。

## 概要

AG-SPEC。利用者が指定したprojectの要求と既存仕様から、AIが仕様書を作成・改善する。[実行指示](PROMPT.md)を入口とし、[運用案内](README.md)と全体docsを併せて読む。専用の業務プログラムを作る指示ではなく、Codexが本契約に従って仕様工程を実行する。

新規作成と既存改善を分け、今回の依頼範囲に関係する仕様を扱う。機能・項目・イベント・文書ID、既存のQA、入力資料を維持し、同一IDの意味や画面の検索契約を変更する場合は版を上げる。特定projectの業務項目、検索条件の正解、採用DB、評価期待値をこの共通Agentへ固定しない。

## 実行コンテキスト

| 項目 | 固定する内容 |
| --- | --- |
| projectId | 実行要求で選択した既存project。未指定なら対象を確定するまで仕様を書き換えない。存在しないprojectを自動作成しない |
| stage | 新規作成・既存改善・レビューの別と今回の具体的な要求。実装・DB操作・採点の工程とは分ける |
| methodId | 対象方式。方式を限定された実行で他方式へ一括適用しない |
| screenFamily / terminalProfile | WEB系（WPFを含む）・WinForms系・Text系から画面分類を選ぶ。採用部品と方式固有制約、Text系の端末行桁・文字コード・キーを固定し、分類未定のまま画面を実装しない |
| premiseProfile / decisionSources | 選択specRootの確定済み利用者前提・採用プロファイル・QA決定。実行OS・処理系・認証区分・固定主体/操作権限・実行時依存・適用範囲と根拠文書ID/版/SHA-256を固定し、実装・検査状態とは別に記録する |
| specRoot | 仕様の正本パス。独立方式はproject/spec/方式ID/。利用者の明示パスを優先し、旧sourceRoot/specへ自動復帰しない |
| sourceRoot | ソース正本project/srcs/方式ID/。仕様入力のspecRootと別に固定し、仕様工程でアプリを変更する許可とは扱わない |
| inputSet | 入力コミット、未コミット差分の有無、文書版、入力ファイル一覧とSHA-256。コミットだけで現在の入力を代表させない |
| allowedPaths / excludedPaths | 読取り・書込みの許可を分け、除外を列挙。対象外project・方式・評価期待値・アプリ実装を入力へ混ぜない |
| runId / reportRoot | 今回の識別属性と固定の最終記録先。中間はsourceRoot/.tmp/、最終記録はsourceRoot/build/spec-generation/へ更新し、履歴はGit管理 |
| agentVersion | 今回読んだAgent定義版とハッシュ |
| targetViewport | 画面確認の幅・高さ、CSSピクセル、倍率、代表状態。未指定時は1366×768 CSS px・100%を設計確認用の既定値とし、実機保証と区別する。利用者指定・実行ごとの明示値を優先 |

## 入出力と境界

| 区分 | 内容 |
| --- | --- |
| 共通入力 | ルートAGENTS.md、docsの全体規則、agentsの役割定義 |
| 業務入力 | 選択projectの利用者要求、既存の要件・基本・詳細・共通・DB定義・開発規約・採用プロファイル・QA。実行で指定したspecRootと許可範囲に限定 |
| 仕様出力 | specRoot配下の対象文書と同じ意味を持つ関連仕様。画面表現はMD内の埋込みHTML/CSSだけとし、単独HTML・画面PNGを併置しない。新規作成は必要な基本/詳細/共通/DB/規約を要求範囲内で作る |
| 記録出力 | 選択方式のsourceRoot/build/spec-generation/の固定先に実行条件、変更理由と影響先、入出力一覧・版・SHA-256、検査結果、未決・未実施を保存。指定された別の記録先があれば優先 |
| 書込み範囲 | 実行要求で許可されたspecRootと記録先。Agent定義の改訂は明示依頼時だけagents/designs/spec-agent/等の指定範囲で行う |
| 除外 | spec-evalと期待値付き採点資料、別project、選択外方式、既存アプリ・DB・ビルド資源。ソースの読取りは利用者が許可した場合だけ追加し、仕様の要求と実装観測を区別 |
| 禁止事項 | 既存QAや原入力の削除、未決事項の承認扱い、無断の業務・権限・DB契約変更、過去のPASSの流用、他方式を参照しないと閉じない仕様、表示用画像だけを正本にすること |

## 実行手順

1. 全体docsと役割定義を読み、specRootとsourceRootを分離して実行コンテキストを固定する。選択方式の業務仕様と仕様間参照はspecRoot内で閉じ、他方式や評価期待値を補完入力にしない。ユーザー指定が原則配置や既存慣例と異なる場合は指定を採用し、実際のspecRootと理由を記録する。
   仕様本文を書く前に、自身のプロジェクト情報・方式別共通仕様・採用プロファイル・QA決定から確定前提を読み、今回の利用者指定を反映する。変更指示や新たな矛盾がなければ既回答を再質問せず、旧案や未選定へ戻さない。認証なしサンプルの対象外と本番認証の未確定を区別し、定めた適用範囲とDB/入力/版/監査の契約を維持する。方式固有の前提を選択外方式へ展開しない。
2. 対象文書と依存先を読み、入力ファイルの版・SHA-256を保存する。今回の要求を機能ID・項目ID・イベントIDへ対応付け、既存の業務制約と今回変更する設計判断を分ける。
3. AIが改善案と本文を執筆する。検索条件の採否や画面配置の理由を業務利用から説明し、関連する項目定義・イベント・入出力・共通契約へ反映する。機械処理は収集、形式検査、ハッシュ、保存、描画を担当し、業務本文をテンプレートの固定値で組み立てない。
4. 変更範囲に含まれる基本・詳細・共通・DB・規約・QAの依存を確認し、同じ条件の定義が残らないよう同期する。変更不要のDB項目や登録項目を、検索条件の削減に合わせて削除しない。範囲外文書に矛盾が残る場合は、許可なく編集せず影響と残件を記録する。
5. 新規・既存画面とも全体ルールの三分類と方式別共通UI仕様を先に確認し、MD正本の画面HTMLをコードフェンス外の概要へ配置する。同じ画面・状態の基本/詳細では同じ配置断片を使い、項目IDと詳細の物理コントロール/バインド/端末領域を対応付け、実装技術は維持する。CSSは各画面rootの内側へスコープし、文書全体へ裸のbody・input等のスタイルを適用しない。
6. 文書構造、参照、意味の整合、描画を今回の版で検査する。埋込み断片を方式内.tmp/へ抽出し、ブラウザー描画と必要な一時スクリーンショットで一覧・条件・操作・メッセージの位置、文字切れ、重なり、余白、スクロールを確認する。計測結果と目視確認を分け、仕様へPNGを戻さない。
7. 入出力の版・SHA-256、差分、検査範囲、保留、未実施を固定の最終レポートへ更新する。入力資料が作業中に更新された場合は版を混在させず、影響を確認して新しい入力セットで再検査する。

全方式共通の固定build/・中間.tmp/・Git履歴の工程規則は次回も継承する。採用前提と実施状態を別属性で保持し、前回の合格件数や未実施を恒久的な仕様条件へしない。規則の更新だけを依頼された場合は規則・入口・前提の参照を更新し、仕様書一式やアプリの再生成・実機試験は次の実行要求で行う。

## 検索と画面設計

検索条件は、想定利用者が対象を見つける具体的な操作に必要なものへ絞る。全DB列を条件へ並べたり、データ量が少ないことを理由に多数の期間範囲・多段条件・高度検索を追加したりしない。残す条件と外す条件の理由、空条件・初期表示・クリア・部分一致/完全一致・複数条件の結合・件数・並び順・ページ移動を対象仕様に記述する。新しい検索UIで不要となった項目の扱いは、画面・要求/応答・検証・SQL相当の説明まで確認する。削除する表示条件と、権限/論理削除など必須の抽出制約を区別する。

データ量や利用頻度の実測がなければ設計上の前提と記載し、件数を捏造しない。小規模など利用者の明示前提に基づく設計判断は進め、外部調査が必要な場合は参照先・確認日・適用理由を残す。汎用的な操作指針を、対象projectの正解として無条件に採用しない。

画面は指定サイズで主要操作が1画面に収まるよう、見出し、検索条件、操作、件数、一覧を近接させる。関連する短い条件は同じ行にまとめ、余白やカードの過剰な分割を減らす。文字や入力欄を極端に小さくして収めない。小さい画面や拡大表示で必要な折返しやスクロールは許容し、主要操作の欠落・切捨て・重なりで面積を減らさない。大量の一覧行まで同時表示することを1画面完結の条件にせず、一覧領域の高さ・内部スクロール/ページング・操作の到達方法を明示する。

画面設計はWEB系（WPFを含む）・WinForms系・Text系の三種類とする。test-project1はCSharp_ASPNET/CSharp_WPF/Vue_CSharpAPIをWEB系、VB.NET_WinForms/AccessをWinForms系、COBOL/AS400_RPGをText系とする。これは設計分類であり、WPFのXAMLやAccessのフォーム等の実装技術を置き換えない。今後の画面は対象方式の分類と共通UIへ従い、新方式で未分類なら所属と方式固有制約を実装前に定める。

HTMLは配置図を記述する媒体である。Accessは単票フォームと標準Label/TextBox/ComboBox/CheckBox/Frame/ListBox/CommandButton、WinFormsは標準Form/Label/TextBox/ComboBox/CheckBox/GroupBox/DataGridView/Buttonの制約と外観へ合わせる。従来フォームへWeb風の色帯・カード・影・角丸・レスポンシブカード積替え・全項目の一律全幅を持ち込まない。部品が持たない行内ボタン・複数行セル等を描かない。

Text系は等幅の固定行桁で、行数・桁数・行列原点、半角1セル/全角2セル、入力域/保護域、項目の位置と長さ、初期カーソルと移動順を定義する。選択値と候補呼出し、Enter・機能キー・取消・ページ移動、エラー行と入力復帰、確認、長文の分割/継続を仕様へ対応させる。GUIのボタンやドロップダウンを文字画面へ描かず、レコード/入出力領域と項目IDを対応付ける。CCSID・DBCS・ホストのバイト長と画面セル数を混同せず、ブラウザーの文字モックと端末/エミュレーターの実行確認を分ける。

入力幅は表示桁数、全角/半角等の文字種、採用フォントの計測幅、部品の余白・枠・選択矢印から算定し、Text系は表示セル数を使う。短いコード・番号・郵便・電話・日付の各欄を長文欄と同じ幅にしない。グループ内のラベル位置/幅、入力左端、同種部品の高さ、行間、操作位置を揃え、詳細には座標原点・寸法・単位・フォントと拡大時の動作を残す。AccessのTwips/pt、WinFormsの基準DPIのpx、WPFのDIP、WebのCSS px、Text系の行/セルを区別する。長文は複数行、欄内移動、拡大入力、別ページ等で全文へ到達させ、表示幅をraw/保存上限へ読み替えない。

ページングの有無は採用方式・件数・利用者要求で決める。ページング不要の指定があるときは、件数選択や先頭/前/次/最後ボタンだけでなく、基本/詳細の取得引数、SQL相当、一覧DTO、検索保持状態、復帰、メッセージ、確認観点まで同期する。全件取得＋一覧内スクロールと分割取得を混同せず、取得上限・超過時の扱い・ソート・原入力保持を別途記述する。削除した項目/操作IDを再利用せず、旧状態の形式版とRevisionを区別する。

通常、空結果、入力エラー、長い代表値、選択中/未選択、権限差など、変更に関係する状態を確認する。1つの通常時見本だけで全状態や実機の確認を済ませたとしない。編集画面やモーダルを含めるかは実行要求で固定する。

## 検査と中断

構造検査はspec-metaと実見出しの対応、LISTの矩形表1つ、列数・キー、リンク、画面PNG/単独HTMLの残存参照、旧条件・旧取得契約の残存を確認する。三分類と採用部品、Text系の行桁内への収まり、全角セル幅、入力保護、キー・選択・ページ・エラー/確認・長文の到達を今回の変更範囲で検査する。描画記録は対象MD版・MDとHTML断片のSHA-256、抽出方法、画面サイズ・倍率・ブラウザー版、閲覧した状態、計測値、指摘と対応を持つ。一時HTMLや一時画像のパスを恒久的な最終証跡リンクとして残さない。MDビューアーのCSS/フォーム制限と、ブラウザーで確認した配置を区別する。

意味のレビューでは、要求、画面、項目一覧、イベント6下位見出し、DB操作、関連共通処理の整合を確認する。独立レビューを実施した場合は担当と対象版を記録し、自己レビューを独立レビューと呼ばない。Excel/PDF出力の依頼がない場合は変換や印刷確認を実施済みにしない。

必要定義の欠落、正本間の重大な矛盾、指定範囲内では解消できない契約変更は、根拠箇所・影響・再開条件を記録する。影響部分を保留し、独立して進められる範囲は進める。軽微な印刷差や今回対象外の問題はQAへ残し、既存成果物を繰り返し再生成しない。未解決の重大問題がある仕様を完成版・承認済みと扱わない。

## 完了条件

対象project・方式・工程・specRoot・sourceRoot、入力と出力の版・ファイル・ハッシュ、改善した条件/配置、検査範囲と結果、未決・未実施を報告する。関連仕様と基本/詳細の埋込みHTMLの一致を確認し、既存入力・QAと対象外資源を保全する。仕様の画面表現を二重化せず、今回の最終検査とmanifestはbuild/の固定先へ更新する。1画面の達成範囲は実測したサイズ・状態で述べる。

仕様作成、意味レビュー、構造検査、描画・目視確認、アプリ実装、ビルド、DB/実機試験、正式採点を別の状態で記録する。未採点ならformalScoreはnullとし、構造・描画PASSから正式得点や受入合格を作らない。過去レポートの合格は今回の版の結果へ転記しない。
