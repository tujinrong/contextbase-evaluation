# ソース事実索引とモデル利用の契約

版0.3／2026-10-27。contextbase-source-facts/1の機械観測、検索、モデル利用、独立検証を定める。分類判断は[機能分類境界](機能分類境界.md)、導入・実施状態は[実装ガイド](../../../reverse-agent/docs/ContextBase初期実装.md)を参照する。現行Dのcatalog採用・正式export、後続層の未完了、過去の拒否と再検証を区別し、回帰・時間・入力境界の確定範囲は実装ガイドへ集約する。

## 1. 事実と解釈の境界

Tree-sitterが返すsymbol／call／entry／importを、封印原文へ結び付けた構文観測として保存する。モデルはこれを索引として実際に使い、業務目的・主子帰属・共通責務は原文から解釈する。索引の存在や機械検査passだけで、業務機能の完全性・正確性を認定しない。

callはresolution=unresolvedであり、callee名の一致は参照先symbolの確定ではない。callerIdは包含する宣言を指し、lambdaは包含宣言のcaller文脈を保つ。callerContext、呼出種別、receiver原文、arity、byte範囲と原文行を併記する。型束縛、Roslyn、データフローは提供しない。

C#のentry候補はmvc-action／minimal-route／program-main／top-level-programを区別する。属性・登録形状の観測であり、配備時の到達可能性や独立した業務機能の証明ではない。引数selector、MapGroup、継承routeの解釈は未実装である。非対応・部分解析ファイルも台帳に残し、factゼロを「対象なし」の証明にしない。

## 2. 封印とキャッシュ

索引はsnapshotIdとextractorSha256に束縛する。extractor指紋はfacts／adapter実装ソースとTree-sitter binding・grammar版を含む。封印材料または抽出器が変われば別索引となり、旧キャッシュをそのまま正本へ流用しない。

全manifestファイルをfiles台帳へ含め、各観測は安定ID、kind、path、data、原文evidenceを持つ。モデルへ送る前に索引全体を検査する。

| 機械検査 | 確認する条件 |
| --- | --- |
| 入力と抽出器 | schema、snapshot、抽出器指紋、内容digestの整合 |
| 全inventory | manifestの全ファイルと台帳の一致。非対応・partialを含む |
| 位置と同一性 | fact ID重複なし、許可kind、原文path・hash・行範囲 |
| 呼出元 | callerが同一ファイルのsymbolとして存在し、call範囲を包含 |
| 入口 | symbolIdを持つentryの宣言symbolが同一ファイルに存在 |
| 能力表明 | callが意味解決済みを主張しない |

この検査は登録候補の実行到達性や、parserが業務上の全要素を抽出したことまで保証しない。検査失敗はモデル呼出し前に明示失敗として扱う。

## 3. モデルなしの操作

既存indexの出力形状を維持し、queryで用途別に事実を検索する。validate-indexは完全inventory・内容・参照を機械検査する。いずれもモデルを起動せず、封印原文から必要な索引を作成又は読み込む。

```text
contextbase-discovery index --work WORK
contextbase-discovery validate-index --work WORK
contextbase-discovery query --work WORK --kind call --callee Search
contextbase-discovery query --work WORK --kind call --caller SERVICE_OR_SYMBOL_ID
contextbase-discovery query --work WORK --kind entry --route ROUTE
contextbase-discovery query --work WORK --path RELATIVE_PATH --text TERM --limit 20
```

queryはtext／path／kind／caller／callee／routeを組み合わせる。kindはsymbol／call／entry／import。path・callee・routeは正確一致、textは大文字小文字を区別しない部分一致、callerはID・宣言名・修飾名との一致である。callee検索は未解決の呼出名検索であり、意味参照検索へ読み替えない。

limitは明示した正の整数だけを使い、matchedCount／returnedCount／truncatedを返す。省略時は全一致を返す。truncated=trueの検索結果を完全被覆として報告しない。モデルへ渡す全索引の代わりに、検索結果だけを暗黙使用しない。設定を使う場合は--workを--config CONFIGへ置き換え、必要なら--profile NAMEを指定する。

## 4. 文脈投影と作者の利用証跡

作者と独立検証者の双方に、全files台帳と完全なsymbol／call／entry／importの簡潔な表を渡す。表の列名・file番号と全行を保持し、重複キー表現を減らす。原文は内容を保持したsourceTextの単一表現を使い、numberedTextとassignment内の重複structureを送信しない。検証投影ではcandidate.answer.recordsとcurrentRecordsも重複送信せず、完全なrecordsはverificationView.recordsに一度だけ置く。answerのfactUsage／coverage／unknowns／followupsは保持し、recordsLocationで所在を示す。保存candidate・hashは変更しない。原文の切捨て、未知領域の省略、根拠版の変更で文脈を縮めない。

D taskはホスト固定sourceFactsSha256を持ち、返答も同値を返す。作者のtop-level factUsageは、全proposed recordを一度ずつrecordKeyで覆い、factIdsとreasonを返す。ホストは次を検査する。

1. 使用索引のSHAがtaskと同一で、factUsageのrecordKey集合とrecord集合が正確に一致する。
2. 各factIdは実在し、そのfactのpath・原文行が同じrecord.evidenceと重なる。跨ファイルのcall等を使うときは、その位置・hashをrecord.evidenceにも正確に列挙する。本文の説明や別recordの根拠で代用しない。
3. そのrecord evidenceに索引factがある場合、factIdsを空にしない。
4. 対応factがない非対応材料等では空配列を許すが、作者が理由を示す。

task.recordKindsは実行Agentの許可kind集合で、作者schemaのenumも同集合へ制限する。Dの目録判断は許可された目録recordと説明へ記録し、独立fact等の層外recordを返さない。裸Sessionや外部検証の互換経路をDの権限制限の回避に使わない。

IDや行が一致することと、そのfactが業務主張を裏付けることは別である。宣言symbol一件だけで複数段の業務動作全体を証明したと扱わず、関連するentry・callと原文の意味を調べる。factUsageはcandidate監査に保持し、portable record形状へ追加しない。

## 5. 独立検証と採用条件

独立検証者は作者のfactIdsだけに限定せず、全索引・全inventory・原文から誤利用と未使用の重要根拠を確認する。sourceFactsSha256を回示し、factUsageCheckとしてstatus／reason／原文evidenceを返す。ホスト採用はfactUsageCheck=passを追加条件とする。

この検査は分類用classificationChecks／scopeChecksやunknown／followup gateを置き換えない。構文事実の利用がpassでも、誤った主子区分・被覆不足・阻害unknownがあれば採用しない。共通runtimeの構造検査、作者の利用説明、別文脈の原文検証、人手レビューを分けて報告する。

正式な索引・機械検査・候補・独立検証とfact利用レビューは[プロジェクト成果案内](../../../../test-project1/spec-reverse/discovery-agent/README.md)を参照する。実モデルのfact利用検査はpassだが、分類27対象のうち3件がunknownで、catalog採用と業務人手受入れは未完了である。原仕様・spec-evalを読まず、原アプリ・SQL・DBを実行しない。R／Bのモデル処理を起動しない。

## 7. 一括証拠検査と短縮伝送

検査の重複除去と--compactのtask内表現は[短縮伝送と証拠一括検査](短縮伝送と証拠一括検査.md)を正本とする。可逆aliasをcanonicalへ展開した後も、本書のfact実在・同record原文交差・索引版・独立利用検査をすべて適用する。原文全量と全索引を渡すため、queryを使った原文のオンデマンド調査が実装済みとは扱わない。

本書§6の220件と69候補未採用は前改訂の実績。compactの2回の新規抽出はhost拒否となり、fresh work .tmp/contextbase/csharp_aspnet-compact-repairの明示repairで候補化・独立検証を完了した。fact利用とconsumer修復は支持されたが、catalog未解決で未採用である。関連回帰と時間の確定範囲は実装ガイドを参照する。

## 8. 構成材料の取得と影響判定

source-onlyのテキスト取得は.slnxと.mjsも対象とする。discoveryの材料台帳では.slnxを構成、.mjsをprogramとして認識し、構成参照の存在を原文で確認する。schemaは変更せず、対応parserがない形式はunsupportedを明示する。テキストを取得できること、構文factsを抽出できること、実行できることを区別する。

spec・private・tests・build等の既定除外条件は維持し、構成ファイル中の参照を辿って許可外specへ読取り範囲を広げない。スクリプト・アプリ・SQLは実行しない。productionの参照と未取得対象を照合し、不足が現行の対象・数量・被覆を変えるかは[分類境界§12](機能分類境界.md)の基準で独立確認する。

0 callsは未接続・到達不能の証明ではない。未観測consumer、退役route、コメント構成、実登録を分け、全inventoryと原文の逆参照・構成確認を使う。業務の一覧や必要被覆へ影響しないと証明できる技術事項は根拠付きsupport又は非阻害unknownにできるが、現productionの不足は阻害として残す。tests／buildの除外妥当性もフォルダ名ではなくproject設定で確認する。

本改訂は新しい取得材料と判定根拠を追加するもので、索引・factUsage・unknown・独立検証・採用gateを緩和しない。本改訂の関連回帰255件と、有効な独立検証によるfact利用・catalog採用を確認した。詳細は実装ガイドに集約する。入力境界の実施上の制約は実装ガイドに開示し、全調査が一度も許可外へ触れていないという保証へ読み替えない。

新しい75ファイルの封印入力で全原文・1747 factsを提供し、factUsageは76 recordを覆った。ホストが初回検証のrecord版hash不一致を拒否し、raw・エンジンを変更せず、通常verifyの新しい独立実行からcatalog採用・正式exportへ進んだ。長いhashの転記誤りは残る機構上の制約で、索引利用や検証の安定性を過大評価しない。後続層の未知と全目標未完了を維持する。

調査全体が一度も許可外材料へ触れなかったとは保証しない。誤走査報告の破棄と明示ソースからの再確認を実装ガイドで開示し、新しい抽出・検証モデルには封印済みソースだけを渡して当該報告を渡していない、という範囲で説明する。
