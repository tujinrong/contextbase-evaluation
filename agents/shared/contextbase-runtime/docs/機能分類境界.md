# 主機能・子操作・共通能力の分類境界

版0.5／2026-10-27。ContextBaseの目録分類・集計・独立検証に適用する契約。[語彙の正本](../../../GLOSSARY.md)とD07を具体化し、discoveryの新分類モードに反映する実装契約を定める。本版の回帰・D実モデル結果は実装ガイドに記録し、人手受入れと区別する。

## 1. 分類の目的

主機能一覧は、独立した利用者目的と結果のまとまりを同じ粒度で示す。業務機能と、ログイン等のシステム利用機能の双方を含む。ソース上に処理が存在することと、その処理を独立した主機能として数えることを区別する。

「8件は多い」というレビュー意見は境界を再確認する契機であり、2件又は4件へ調整する件数目標ではない。機能数を先に決めず、対象範囲、利用者目的、結果、帰属と原文根拠から結果を導く。

## 2. 三つの軸を分ける

| 軸 | 決めること | 例・注意 |
| --- | --- | --- |
| 意味上の分類 | 主機能、子操作、共通能力、技術入口、資料、外部依存、運用支援、分類保留のどれか | すべてを主・子・共通の3種類へ押し込まない |
| 対象領域・集計範囲 | どの利用者目的の範囲として一覧へ含めるか | 学生業務、マスタ保守、システム利用・運用等。管理者が使うことだけで領域を決めない |
| 入口形態 | どこから起動・利用されるか | 画面、API、CLI、バッチ、ジョブ、メッセージ等。CLIだから非業務、画面だから主機能とはしない |

取得範囲と集計範囲も分ける。プロジェクト全体を読んでも、Web業務だけを集計する承認が得られたことにはならない。対象領域が未確定なら、領域ごとの候補を示し、合計を確定しない。

## 3. 三者の判断基準

| 分類 | 判断に必要な説明 | 計上と関係 |
| --- | --- | --- |
| 主機能 | 誰が、何を対象に、何のために開始し、どの成果で完了するかを説明できる。指定した粒度で独立した利用者目的・結果を持ち、業務機能とシステム利用機能の両方を対象にする | 現在の集計範囲に含まれる主機能だけを主機能数へ計上する。入口・操作・共通能力を関連付ける |
| 子操作 | ある主機能の利用者目的を実現する手順、モード、補助動作として説明できる | 利用文脈ごとに主帰属を示す。主機能へ独立計上しない |
| 共通能力 | 再利用する技術処理・業務規則又は集中して担う責務と、どの機能・操作から何のために使うかを説明できる | 利用関係として結ぶ。共通一覧と主機能一覧の数へ同じ対象を二重計上しない |

主機能の「独立」は、前置条件が不要という意味ではない。認証、別の業務成果、定期的な起動契機が必要でも、独立した利用者目的を持つことがある。

主機能は単なる分野名でもない。「学生管理」のような広い名称に異なる目的をまとめただけでは、独立した利用者目的と結果を説明したことにならない。反対に、HTTP操作や一つの成功応答を持つだけでは、主機能への昇格理由にならない。

### 判断だけでは足りない手掛かり

| 手掛かり | 単独では決められない理由 |
| --- | --- |
| 画面・URL・クラス・メソッド | 一つの業務を複数の入口で実現し、同じ実装を複数の利用者目的から利用することがある |
| 権限・利用者の違い | 同じ業務の操作可否の違いか、別の利用者目的かを追加確認する必要がある |
| テーブル・トランザクション | データ配置・確定境界と、業務上の粒度は一致するとは限らない |
| common等の名前・呼出回数 | 共有責務の根拠ではない。現在の利用先が一つでも集中責務を持つ候補はある |
| CRUD、検索等の動詞 | 利用者目的によって主機能にも子操作にもなる |

## 4. 分類手順

1. **範囲を固定する。** 取得元と、集計する業務領域・目的・粒度を別に記録する。期待件数から範囲を逆算しない。
2. **目的と成果を記述する。** 主機能候補ごとに利用主体、対象、開始理由、完了結果を原文の登録点・利用箇所・処理から説明する。名前だけで分類しない。
3. **子操作へ帰属させる。** 候補の違いが同一目的の手順・モード・補助動作だけなら、その主機能の操作として整理する。帰属先が不明なら保留する。
4. **共有責務を分ける。** 認証サービス、Cookie、共有レイアウト、入力正規化、日付、排他、共有業務規則等は、共有又は集中責務と利用関係を確認する。独立した利用者向けログイン機能等を共通実装で置き換えない。資料やライブラリそのものは別に記録する。
5. **逆の仮説を試す。** 分け過ぎとまとめ過ぎを両方点検する。分割・帰属・統合の理由と、判断を変える反例を残す。
6. **範囲と粒度がそろったものだけを数える。** 未確認候補、範囲外候補、子操作、共通能力、入口を別欄で示す。

### 分割・統合の確認

- 分割した候補の説明が同じ目的の手順やモードの言い換えだけなら、子操作への帰属を検討する。
- 統合した候補の説明に複数の独立した利用者目的・結果を並べなければならないなら、主機能の分割を検討する。
- 同じ画面や実装だから統合、別の入口だから分割、という決め方をしない。
- 同じ実装でも、純粋な詳細照会と編集準備の読込は異なる利用文脈を持つ。それぞれの操作の主帰属を示し、技術入口は共有できる。

## 5. 境界を確かめる反例

| 候補 | この文脈での分類 | 別の分類になり得る条件 |
| --- | --- | --- |
| 学生検索 | 利用者が情報を得る独立照会なら主機能候補 | 編集対象の選択用検索なら保守の子操作 |
| 新規登録・更新・削除 | 同じ情報保守の閉環内なら子操作候補 | 退学承認、法定記録廃棄等、独立した利用者目的と結果・手続の根拠があれば主機能候補 |
| 詳細表示 | 独立照会の詳細操作、又は編集準備の読込操作 | 別の利用目的・成果が確認できれば独立した主機能を検討 |
| 独立したログイン画面 | 入力・認証・成功失敗のフィードバックで独立した利用者目的を完結するなら主機能候補 | 認証サービス・Cookie・共有UIは別の共通能力として関連付ける。アカウント管理システムであることは要件ではない |
| メニュー | 共有nav断片、共通レイアウト、汎用の共通メニュー画面なら共通能力候補 | 顧客専用の完全画面、役割別選択、ワークスペース等が独立した利用者目的を持てば主機能候補。選択・移動だけでもDB更新は要件ではない |
| クラス・コードを変更するCLI | 業務マスタを管理する目的なら管理業務の主機能候補 | 学生業務を補助する配布・コンパイル・環境設定なら運用支援。運用管理自体が対象業務の場合は、その目的・成果で再判定 |
| 日付・正規化処理 | 共有又は集中した責務と利用関係があれば共通能力候補 | 単一の業務手順の局所処理にすぎなければ、その操作の内部処理 |
| 説明文書・外部ライブラリ | 資料・外部依存として別記 | 自作の共有ラッパー等の責務が確認できた場合、その実装を別の共通能力候補にできる |

### 新しい利用者目的基準の反例

- 独立ログイン画面の入力・認証・成功失敗が完結するのに、common又はentryだけへ隠すと、利用者が行う機能を欠落させる。共通認証実装との関連を別に保つ。
- 顧客専用の完全メニューや役割別選択・ワークスペースを「ナビゲーションだから全部共通」とするのは不適切。選択という目的と結果を確認する。一方、完全画面として表示しても、責務が共有ナビゲーション基盤で独立した顧客・利用者タスクを持たない汎用の共通メニュー画面は、共通能力又は技術ナビゲーションとして扱える。ブランド・タイトル・URLだけの変更は独立機能の根拠にならない。
- 各screenをすべて主機能へ数えるのも不適切。詳細・確認・popup・編集モードは親タスクの目的に従って子操作を判定する。独立画面は強い手掛かりだが十分条件ではなく、画面のないAPI／CLIにも独立主機能はあり得る。

## 7. 独立検証で確認すること

| 点検 | 合格に必要な説明 |
| --- | --- |
| 主機能の根拠 | 主体・対象・利用者目的・結果・範囲が説明され、入口の存在確認だけになっていない |
| 子操作の帰属 | どの主機能に対する何の操作かを、利用文脈ごとに説明できる |
| 共通能力の根拠 | 共有又は集中する責務と利用関係を説明でき、資料や外部依存と混同していない |
| 過度な分割 | 同じ目的の手順やモードを、根拠なく主機能として複数計上していない |
| 過度な統合 | 名前や画面の共用だけで、異なる独立目的を一つに隠していない |
| 多重計上と欠落 | 主機能・操作・入口を混ぜて数えず、保留や範囲外を黙って消していない |
| 反例と代替案 | 統合・分割を変える条件と、保留の理由が原文根拠付きで残っている |
| 集計 | 主機能、操作、共通、入口、未確認を別に示し、同範囲・同粒度の件数である |

主機能数を変える層の混在・重複・根拠不足は、分類を求める当該義務の阻害指摘として扱う。名称だけの改善と同じminorへ落とさない。部分成果を許す要求でも、分類不明を確定件数へ読み替えず、元目標の未完了と理由を保持する。

## 8. 新discovery分類モードの契約

新しいdiscovery taskは、ホストが固定するcatalogPolicy=contextbase-catalog/1を持つ。作者が任意に外したり、返却した内容だけで別policyへ切り替えたりしない。解析requestの識別や抽出／検証のtask.operationとは別の、目録分類の実行条件である。

### kindとtyped classification

| record.kind | classification.category／意味 | classificationの必要情報 |
| --- | --- | --- |
| function | main／主機能 | scope、area、actors、businessObject、purpose、trigger、outcome、rationale、alternative、entryRefs |
| operation | operation／子操作 | scope、parent、purpose、useContext、outcome、rationale、alternative、entryRefs |
| common | common／共通能力 | scope、responsibility、consumers、rationale、alternative |
| unclassified | pending／分類保留 | scope、tentativeKind、impact、reason、unknownIds |

保留のimpactはcount-or-coverage又はoutside-obligationを区別する。主機能数又は今回必要な被覆へ影響する保留は、全検査がpassでも採用しない。保留は実際のunknownへ結び付ける。unknownIdsはホストがrecordを物化する前にauthorTaskId:localIdの大域IDへ固定し、その値をrecord.versionへ含める。export／importでも大域IDを厳密に保持し、unknown本文の元local idは保持する。同名の未知を曖昧一致させない。資料・第三者依存・対象業務でない運用支援はsupport／material／dependency等の別分類として残し、主・子・共通へ押し込まない。この4意味分類以外のclassificationはnullとする。

これは新モードの出力契約である。既存のclassificationなし記録へnullを自動補完してhashを変えず、legacy記録のkind=functionを新基準の主機能へ読み替えない。

### 意味参照と依存

parentは分類済み主機能、entryRefsはentry、consumersはfunction／operation／entry／commonのキーを参照し、自己consumerを認めない。いずれも参照先が存在し、同scopeであることを確認する。技術入口は複数の主機能・子操作から共有できる。使用文脈の帰属と実装の共有を分離する。

意味参照はownerを跨ぐ失効判定へ含めるが、すべてをrecordの版依存DAGへ強制変換しない。子操作と主帰属、共通と利用先等の意味関係から不必要な循環を作らず、意味整合と版依存を区別する。

## 9. 独立検証と追加採用gate

- classificationChecksは主・子・共通・保留の全対象recordのkeyと版hashへ正確に束縛し、各分類の根拠・帰属・反例を別task・文脈で確認する。
- scopeChecksは元要求の全scopeを対象とし、recordがゼロのscopeも省略しない。
- scope検査はentry／data／support／material／dependency等の非意味分類を含む全viewをレビューする。過分割と過統合に加え、support／material／dependencyへ誤って落とした業務候補を探す。CLIやactor roleだけで候補を排除しない。
- ホストは全classificationChecks／scopeChecksのpassを追加の採用条件とする。count-or-coverageの保留が残る場合は検査passだけで採用しない。
- outside-obligationの保留でも理由・実unknown・範囲の妥当性を確認し、作者の自己申告だけで除外しない。

正本の意味定義をschema検査だけで証明することはできない。型・参照・scope・版束縛・保留のgateを機械で検査し、利用者目的や適切な粒度は独立原文検証と人手確認へ残す。件数2又は4へ合わせる採用条件は設けない。

## 10. legacyと分類導入時の実施範囲

新discoveryモードではtyped metadataを必須にする。contextbase-handoff/2は任意catalogPolicyフィールドを持つ互換拡張だが、新独立Agentの受信では正しいcontextbase-catalog/1を必須とする。discoveryはレコード0件でもホストがpolicyをexportし、relationship／behaviorはincomingの明示値を継承する。typed成果のflag欠落・不正値を拒否し、古いhandoffを自動的に新規則へ格上げせずdiscoveryを再抽出する。

legacy互換は裸のSessionにおける旧v2タスクに限定する。その通過を新分類基準へ合格したとは扱わず、旧記録へclassification=nullを自動補完して内容hashを変更しない。

今回の実施対象は分類基準の実装とdiscovery単独の再解析であり、relationship／behaviorを実行しない。既定ASP.NETの新しいworkは.tmp/contextbase/csharp_aspnet-classified-v2を使い、source・request・固定outputは維持する。旧workと旧結果は、新候補が独立検証・採用されるまで保持する。原稿の比較材料は旧work／.tmpに置き、正式なarchiveディレクトリを新設しない。

新しい構造・合成回帰は確認済みで、件数と範囲は実装ガイドに記録する。新workのdiscovery候補70レコードは独立検証を実施したが、未解決事項により未採用である。今回のDのみ再実行を実システムの完全理解や人手P0／P8の受入れへ読み替えない。原プログラム・SQL・DBは実行せず、原仕様spec/全体とspec-evalも解析入力にしない。

分類名や候補数は正解の先取りではない。第6節は旧8候補を再検討する例示として残し、実出力の結果と人手レビューの判断を別々に報告する。

## 11. 構文事実との接続

symbol／call／entryの観測、検索結果の限界、モデルによる利用証跡と別文脈の検査は[ソース事実索引契約](ソース事実索引.md)を参照する。分類の意味判断は本書を正本とし、構文索引のpassを主子帰属や業務被覆の合格へ変換しない。前改訂の70候補未採用と、新機構の実施結果を区別する。

## 12. 未接続・退役・不足材料の影響判定

作者と独立検証者は、技術上の未確認が現在のdiscoveryの対象・主機能数・必要な被覆へ影響するかを原文から判定する。すべての技術疑問を一律にblockingとせず、次の観測を区別する。

| 観測 | 確認する根拠と扱い |
| --- | --- |
| 静的consumerが観測されない宣言 | 呼出名だけでなく、参照元、実登録、構成、反射・動的利用の可能性を確認する。0 callsを実行不能の証明にしない |
| 退役したroute又は未接続の補助宣言 | 現行登録と利用側を逆参照し、退役・未接続という根拠と適用範囲を記録する。現在のAPIや架空の共通consumerへ変換しない |
| コメントにだけ存在する構成 | 記述資料と実際の登録・include・import・設定を分ける。コメント上の入口を稼働入口へ昇格しない |
| 実際に登録されたproduction対象 | 当該登録が必要とする対象・条件・include／import・生成物が欠けるなら、現在の被覆へ影響する不足としてblockingを維持する |
| tests／buildとされる材料 | ディレクトリ名だけで判定せず、csprojのcompile除外と明示的なtest／build設定からproductionとの関係を確認する |

原文の逆参照と構成確認により、本層の対象・数量・必要被覆を変えないと示せる場合は、根拠付きsupport又は非阻害unknownとして記録できる。理由・原文証拠・関連義務・適用範囲を明示し、独立検証者がその判断を確認する。共通として必要なconsumerを捏造したり、分類保留を名前だけsupportへ変更して通過したりしない。

productionのinclude／import、条件登録、対象の同一性・存在が未確認で、正しい一覧や範囲判断を変え得る場合はblockingである。「呼出ゼロ」「testsという名前」「資料に記載」の単一根拠で非阻害にしない。現行のcount-or-coverage保留gate、unknownの束縛、独立verify、ホスト採用条件は変更しない。妥当な不足が残る場合は未採用を正しい結果として保持し、合格を目標件数にしない。

本判定基準の追加と、実際の候補が基準を満たすことは別である。新しい全回帰・実D結果は実装ガイドで確認し、前改訂の合格を流用しない。

### 旧規則時点のvalidation修正実績

当時の規則を適用したDは、有効な独立検証でcatalog／scope／fact利用と全29分類のpassを確認し、ホストがcatalogを採用して正式exportした。採用はこのD義務に限定する。後続relationship／behaviorは未実行で、後層を阻害する未知と業務人手受入れは残る。初回の検証版hash誤記をホストが拒否し、新しい独立検証で通過した経緯・根拠版・時間・調査境界の制約は[実装ガイド](../../../reverse-agent/docs/ContextBase初期実装.md)を参照する。分類判断が常に安定する保証や、目標全体の完了へ広げない。

## 13. 利用者目的基準への改訂と再検証

schema／kindの形状とcatalogPolicy=contextbase-catalog/1は維持する。同policyの1は形式版であり、内容規則のhash変更を同一の意味基準として無視しない。新規則はfresh Dで原文から再検証する必要がある。今回は規則と合成試験のみで、新モデルを実行していない。本改訂の合成契約16件は成功し、構造の表現可能性とホストgate維持を確認した。実LLMの再分類結果ではなく、詳細は実装ガイドへ集約する。

規則変更後の実行はfresh workで行い、過去のpassを新規則の証明へ流用しない。利用者の指示により旧成果と旧実行記録を削除して新規則で再実行を開始した。削除を、旧判定を手作業でfailへ書換えた操作と混同しない。source・設定・正式テスト・target所有保護を保持し、新しい候補と独立検証が通常gateを通過した範囲だけ採用する。最新の状態・件数・合成確認と実モデル検証の範囲は実装ガイドへ集約する。
