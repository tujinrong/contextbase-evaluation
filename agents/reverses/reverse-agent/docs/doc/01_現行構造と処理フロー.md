# 1. 現行構造と処理フロー

対象版は[案内](README.md)参照。この文書は現在の実装を説明する。「推奨変更」は[汎用化設計](04_汎用化と動的Python生成.md)に分ける。

## 1.1 全体は三つの経路を持つ

| 経路 | 起点 | 入力 | 主な出力・変更範囲 |
| --- | --- | --- | --- |
| 全体を新しい原本から再生成 | `python -m contextbase rebuild` | 原本・設定・選択された解析器 | 検証後にoutput/report/pilot/解析状態を置換 |
| 社員マスタのDB仕様だけ更新 | `python -m mcterpgen.employee_db` | 承認済みMD・関連原本・固定したDB仕様資産 | 社員MD/HTMLと専用共通DB仕様MD/HTMLの4ファイル |
| MDを編集して閲覧HTMLを更新 | `python -m contextbase build` | `output/md` | `output/html`と変換記録。原本解析なし |

`check`は検査であり再生成ではない。`probe`は形式調査・プロファイル照合であり、高精度の業務仕様化ではない。社員だけの改善で全体再生成を使うと変更範囲が広がるので、入口を混同しない。

## 1.2 フォルダの実際の責務

```text
input/                  読み取る業務原本。生成器・AIの命令ではない
config/project.toml     案件ID、入力位置、解析器の選択方法
src/contextbase/        共通CLI、形式調査、解析器選択、実行・公開管理
src/specgen/            初期の基礎解析器・旧形式出力
src/docsite/            MD、埋込画面HTML、図、リンクの変換・検査
src-dynamic/mcterp/     MCTERP用解析と社員Pilotの個別定義
src-dynamic/tkl/        以前のTKL/VB.NET/WPF用解析・比較試験
.specgen-state/         ハッシュ、解析キャッシュ、索引、骨子、出力所有情報
.contextbase-work/     空から作る検証領域、失敗記録、以前の生成物
output/md/              文書原本。機能一覧、基本設計書、共通文書
output/html/            MDから作る閲覧版
report/                 対象範囲、未確認事項、テスト・比較・変換記録
```

`src`は再利用基盤だが、全言語の完全解析が既に入っている意味ではない。`src-dynamic`には解析拡張、辞書、文章、検査、旧案件の比較プログラムまで混在している。

根拠：[共通CLI](../../src/contextbase/__main__.py)、[案件選択](../../src/contextbase/registry.py)、[実行管理](../../src/contextbase/pipeline.py)。

## 1.3 全体再生成の流れ

```text
CLIの引数受付
 → 設定の検査・原本位置の確認
 → manifestの照合で案件別解析器を選択
 → ロック・入力と生成器のハッシュ取得
 → 原本と実装だけを空の作業領域へコピー
 → システム調査・関係するテスト実行
 → 選択経路の初回解析（キャッシュなし）
 → 同じ入力を再解析（キャッシュ利用）して生成内容比較
 → MDからHTMLへ変換・内容とリンク検査
 → 指定時にブラウザー描画検査
 → 入力・生成器の変更がないことを再確認
 → 合格後に生成物を公開領域へ入替
```

失敗時は公開済み成果物を維持し、作業領域に失敗の内容を残す。これは単一プロセス内の入替・復旧処理であり、OSの完全な隔離環境を作る仕組みではない。[pipeline.py](../../src/contextbase/pipeline.py)

### 解析器選択の注意

`registry.resolve_profile()`は、`src-dynamic/*/manifest.json`の指定原本とSHA-256を照合する。`trust=repository-reviewed`という文字列と形式を検査するが、第三者署名の検証ではない。

`profile=auto`で一致しなければ汎用の限定解析へ移る。特定プロファイルを指定して不一致なら停止する。依存定義などのアンカーファイルが変更されただけでも一致しなくなるため、選ばれたプロファイルと解析範囲を必ず確認する。

`process_env()`は選んだディレクトリを`PYTHONPATH`へ追加し、現在の環境変数を子処理へ引き継ぐ。**これだけでは動的コードのサンドボックスにはならない。** 将来自動生成したPythonをこの入口へ直接載せる場合、別途OS権限・通信・秘密情報の分離が必要である。[registry.py](../../src/contextbase/registry.py)

### 三つの解析分岐

| 分岐 | 実際に行う処理 | 保証しないこと |
| --- | --- | --- |
| MCTERPのcanonical経路 | `mcterpgen --cold`→通常実行→MD同一性→docsite | TKLと同じ精度、実DB・実API同等性、社員の完全再実装 |
| TKLの既存経路 | overviewgen→qualitygen→定義比較→指定時にnative比較 | MCTERPにも同じ比較が実施されたという解釈 |
| 未照合のgeneric経路 | 基礎宣言・限定項目抽出→暫定機能MD→HTML | 自動で社員Pilotと同じ詳細仕様になること |

MCTERPでは`--native`を付けても、現行のcanonical分岐は実言語Pilotを実行せず、その旨を記録する。オプション名だけで実行済みと判断してはいけない。[pipeline.py](../../src/contextbase/pipeline.py)

## 1.4 MCTERP内部の流れ

| 段階 | 主担当 | 処理 |
| --- | --- | --- |
| 原本を一覧化 | `model.collect` | 全通常ファイルのハッシュ、対象・除外・構造読取等の状態を記録 |
| ファイルを抽出 | `scan.py` | コメント・文字列・括弧を区別し関数、呼出表記、Vue項目・イベントを取得。コンパイラの完全型解析ではない |
| DB情報取得 | `scan.archive_schema`、`model.schema` | 保存ダンプの定義文字列、SQL宣言、生成済み型情報を区別 |
| 関係付け | `model.py` | Vueのimport→サービス・処理名→C#メソッド→DB/SQL関数を、対象の構成規約で対応付ける |
| 機能境界 | `model.py` | Serviceの名前空間、フォルダ、画面配置でまとめる。MCTERPの規約に依存する |
| UI役割補正 | `ui_state.separate` | visible/open/loading等を業務入力項目と混同しない |
| 通常文書 | `render.feature`、`contracts.shared` | 骨子から本文、共通説明、DB文書を作る |
| 社員だけの分岐 | `employee_external.generate` | 原本配置とレビュー済み外部契約で作り、DB補強を適用 |
| 保存・検査 | `__main__.run/validate` | 文書・項目・イベント・旧案件混入などを確認し、骨子と索引を保存 |

根拠：[model.py](../../src-dynamic/mcterp/mcterpgen/model.py)、[生成入口](../../src-dynamic/mcterp/mcterpgen/__main__.py)、[社員生成](../../src-dynamic/mcterp/mcterpgen/employee_external.py)。

### キャッシュは何を再利用するか

MCTERPのファイル解析キャッシュは、同じパッケージ直下のPython全体の内容、原本内容、パスをキーにする。したがって文章化を担うPythonの修正でも解析キャッシュ全体が無効になり得る。一方、`employee_db_assets/events.md`などはこのPython集合とは別である。

現状は「ファイル解析キャッシュがある」段階であり、意味解析・章・影響先だけを再実行する全面的な増分エンジンではない。最適化設計書に書かれた全機能が実装済みとは読まない。[model.py](../../src-dynamic/mcterp/mcterpgen/model.py#L51-L91)

## 1.5 社員Pilot限定更新の流れ

```text
社員MD/HTMLの所有ハッシュを確認
 → 関連29原本とレビュー版のハッシュを確認
 → 固定したAPI・共通DB対応を原本の宣言・関数と照合
 → SQL原本11引数と保存ダンプ6引数を別版として記録
 → 既存MDの第1章・第2章・8レイアウト断片を保持
 → 第3章をレビュー済みDBイベント資産で置換
 → 専用の共通DB仕様を追加
 → 2文書だけHTML化・ER図検査
 → 公開前に原本再確認
 → 許可した4出力だけを保存・所有情報更新
```

**重要：この経路は未知の業務を毎回ゼロから自動解釈しているのではない。** `employee_db.py`の`PATHS`、`API`、`COMMON_SYMBOLS`、`TABLES`と、`employee_db_assets/events.md/common.md`にレビュー済みの対応・説明が入っている。`refined()`はその文章を挿入し、`audit_document()`は資産との一致等を検査する。[employee_db.py](../../src-dynamic/mcterp/mcterpgen/employee_db.py)

原本の存在・版・一部の処理特性も別にテストしているので単なるコピーではないが、文章と期待値の元が同じ部分については、独立した業務正誤判定にはならない。

## 1.6 MDからHTMLだけを作る場合

`contextbase build`→`docsite.publish.build()`→各MDのリンク変換、埋込HTML処理、見出し・目次・表・コード・図の変換→HTML保存。

`diagram.py`はフローチャート又はER図を`dot`でSVG化する。DBからERを推定する処理そのものではない。`check()`は本文・表・図・リンク等の変換整合性を検査し、`browser_check.py`は外部通信を遮断して描画を確認する。実アプリや実DBの同等性検査とは別である。[publish.py](../../src/docsite/publish.py)、[diagram.py](../../src/docsite/diagram.py)

## 1.7 現在のコマンドと実行時の注意

```powershell
# リポジトリルート。初回のみ。
python -m pip install -e .
python -m contextbase probe

# 今回の説明資料作成では実行していない。生成物を置換する操作。
python -m contextbase rebuild --replace-output --browser

# MDだけを編集した場合
python -m contextbase build
python -m contextbase check

# 社員DB仕様だけの限定更新。原本・Graphviz等が必要。
$env:PYTHONPATH = "src;src-dynamic/mcterp"
python -m mcterpgen.employee_db --browser
```

原本保護・許可出力の制約を先に確認し、対象別入口を混ぜない。現在の限定更新ワークフローはコミット文字列`[employee-db-pilot]`で全体再生成を抑える設計であり、これは宣言的な機能依存スケジューラの実装ではない。[全体workflow](../../.github/workflows/pipeline.yml)、[限定workflow](../../.github/workflows/employee-db-pilot.yml)
