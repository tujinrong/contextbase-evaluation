# ２段階解析：実装・運用・検証範囲

## 独立プログラム

|工程|実行|入力|出力|
|---|---|---|---|
|P1 基盤解析|python -m contextbase.foundation|input、設定、案件別辞書|ContextBase/01-foundation|
|P2 詳細解析|python -m contextbase.detail|P1、関連ソース、レビュー材料|ContextBase/02-detailed|
|P3 文書生成|python -m contextbase.specification|P2のresolvedと封印済み素材のみ|output/md|
|P4 形式変換|python -m contextbase build --pdf --excel|MD、素材、既存テンプレート|HTML・PDF・Excel|

統括 `rebuild` は独立プロセスでP1/P2/P3を実行し、既存P4を呼ぶ。現行generic経路に適用した。旧MCTERP/TKL経路は変更せず、２段階移行済みとは扱わない。

P1/P2のJSON、参照、スキーマ、ハッシュを検査する。P3はinput・src-dynamic・P1なしのコピー環境でも同じMDと素材を出力することを独立プロセスのopen監査で確認する。

## ContextBaseの内容

P1：system、catalogs、glossary、feature-skeletons、source-index、relations、database。画面とPageModelを統合し、C#プライマリーコンストラクターを画面処理メソッドと混同しない。

P2：functions/{ID}/feature・items・layout・events・data-relations・scenarios・explanation、common/methods、table-usage、interfaces、messages、decisions、resolved。条件付きフローを木構造と順序リストで保持し、単純な早期return後の否定条件を後続処理へ引き継ぐ。関連メソッドは候補を追跡し、曖昧な同名呼出は未解決としてreportへ残す。

P3にはContextBase1の必要情報を解決した公開用データを渡す。保存済みの完成MDをコピーするだけの方式ではなく、項目・イベント・結果・シナリオと文書ブロックを組み立てる。案件固有の承認済み説明は原本ハッシュと別解析したメソッドの一致時だけ採用する。

## srcとsrc-dynamic

srcは再利用可能な解析器・情報モデル・工程管理・検証・文書変換。C#/Javaの静的構文解析もsrcに置く。

src-dynamicは案件固有辞書、レビューJSON、追加PY。職員番号入力の画面再構成と固有QAはjsbrms-pilot/adaptersへ分離した。extension.jsonに適用原本とコードのハッシュを持ち、未承認またはハッシュ不一致の追加コードを実行しない。

旧pilot.pyとgeneric.generateは過去互換用に残すが、現行２段階再生成では完成MD差替えを使用しない。構造化されたreviewed/100008.jsonを適用する。

## 保存・再開

独立P1/P2はキャッシュの内容ハッシュ・依存先・解析器の版が一致した場合に再利用する。P2はソースを読み直してP1の世代と照合する。キャッシュは機能ごとに保存し、失敗後の再実行で一致する完了結果を再利用できる。

P1/P2/P3は作業ディレクトリで生成後に入れ替える。全体rebuildではContextBase・output・report・QAを同じ公開処理で入れ替える。元inputはハッシュ比較で非変更を検証する。

P2の--featureは同じP1世代の既存結果だけを引き継ぐ。P1世代が異なる場合は、指定外の結果を最新として流用しない。P3の部分更新は管理済みMDだけを対象とし、手編集があれば中止する。

## QA採用

自由記述answerは保持するが自動で解析事実へ変換しない。必要な場合は該当QAへadoptionを追加する。status=approved、value、source_hashes（当該機能のdependenciesと完全一致）を検査し、推定欄だけへ「採用判断」として反映する。依存先が変化した場合はrecheckへ戻す。

## 今回の実装限界

- C#/Javaの解析は静的・構文ベース。完全な型解決、オーバーロード解決、反射、例外伝播、全経路の実行検証ではない。
- 他言語は既存の限定抽出を利用する。すべての言語を同精度へ拡張したものではない。
- DDL/ORMの明示定義とSQL参照の基礎照合は実装。ALTERの適用順、DB実機照合、Excel等のテーブル定義書の汎用自動採用は未実装。矛盾・資料未解析はreport/incompleteへ出力する。
- DTO・画面モデル・メモリー上のコレクションは物理DB表に変換しない。現行inputで物理DDLが見つからない場合は、その事実とデータ構造の定義を分けて出力する。
- 帳票・バッチ・API・コード一覧の完全な業務境界確定、全画面の共有レイアウト合成は未完成。空の一覧は「不存在」でなく未解決として保存する。
- Pilotの静的構造・期待仕様の検証は実行するが、本番DB／実アプリ同等性、全環境の画面・印刷再現は保証しない。
- P2からP1への提案保存場所は用意したが、共有定義を自動承認して訂正する仕組みは実装しない。

未完成でも可能な結果はoutputへ出力し、仮定はQA番号と区別する。未完成報告はreportへ保存する。
