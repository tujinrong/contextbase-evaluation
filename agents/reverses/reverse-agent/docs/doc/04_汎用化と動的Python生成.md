# 4. 汎用化と動的Python生成

**本書は提案であり、実装済みではない。** 現在の`src-dynamic`は保存済み解析器の置き場。[現行フロー](01_現行構造と処理フロー.md)と混同しない。

## 4.1 動的にPythonを作れば汎用性を保証できるか

**生成できることと、正しく解析できることは別である。** 動的生成は、未知の構造へ適応する手段として有用だが、誤った解釈・安全性・再現性・評価の独立性を自動的には解決しない。

適応が必要なのは、プログラミング言語だけではない。言語、画面方式、API通信方式、DBアクセス方式、保存形式、案件独自規約、業務の意味を分ける。同じVueでも部品の使い方が違い、同じC#でも呼出し・DBアクセスの仕組みが違う。案件ごとに一式のPythonを生成すると、その組合せごとのコピーが増え、肥大化を再現しやすい。

目指す保証は「将来のあらゆる入力に完全対応」ではなく、**宣言した対応範囲では検証でき、範囲外なら黙って誤った成果物を出さないこと**である。

## 4.2 固定するもの・生成するもの

| 区分 | 固定して再利用 | AIが生成・補足してよい |
| --- | --- | --- |
| 実行 | 原本保護、権限、成果物公開、所有台帳、予算、ログ | 実行計画の候補 |
| 中間データ | 機能・項目・イベント・データ・根拠・未知の共通形式 | 実際の抽出結果、案件対応表 |
| 言語・方式 | 再利用できる構文読取、共通部品・通信・DBの解釈 | 未対応の小さい変換アダプター |
| 案件情報 | ID安定化、出典と版の規則 | 日本語論理名候補、業務説明、部品対応、レビュー済み例外 |
| 文書 | 外部仕様章立て、HTML・ERの描画 | 根拠付きの説明文、例、未解決事項 |
| 評価 | 不変条件、固定ベンチマーク、公開条件 | 新しい再現ケースの候補。ただし承認済み期待値の自動緩和は禁止 |

**最初にJSON/TOML等の宣言データで表せないか検討し、足りない場合だけPythonを作る。** 社員名・項目名・説明文を新しい`*_fix.py`へ毎回埋め込むのではなく、根拠と適用範囲を持つデータとして保存する。

## 4.3 最小の推奨構成

以下は役割を示す案であり、すべてのフォルダを先に新設する指示ではない。

```text
固定カーネル
 ├─ 入力・権限・実行・公開の管理
 ├─ 共通データ形式と整合性検査
 └─ MD/HTML/ERの表示

再利用するアダプター
 ├─ 言語の構文抽出
 ├─ 画面・通信・DB方式の解釈
 └─ 共通形式への変換

案件プロファイル
 ├─ 対象構成・部品・APIの対応
 ├─ 論理名、業務用語、レビュー済み補足
 └─ 適用する能力・版・不足情報

AIの適応作業
 └─ 不足部分を調査し、候補データ又は小さなアダプターを提案
```

新案件で一式をコピーするより、「既存のVue抽出＋当該通信方式の解釈＋DBアクセス方式＋案件用語」を組み合わせる。新しい言語の対応まで社員固有ファイルへ追加しない。

## 4.4 中間データに持たせる情報

| 要素 | 必須情報 |
| --- | --- |
| Evidence | 原本パス、位置、内容ハッシュ、版、採取方法 |
| Field | 識別子、表示名、入力／表示／操作、状態条件、順序、長さと単位、根拠 |
| Event | 契機、前提、入力、分岐、処理順、取消・異常、結果、根拠 |
| DataAccess | 対象、操作、引数と値の由来、抽出／更新条件、キー、取引境界、根拠 |
| Relation | SQLの結合、後段の対応付け、物理FK、推定関係を区別した種別 |
| SharedContract | 共通処理ID、入力・出力、副作用、呼出元、版、未解決依存 |
| Unresolved | 未取得・未対応・動的・矛盾の理由、影響する主張、次に必要な証拠 |

「根拠で観測」「推定」「レビュー済み」「顧客承認」「実行確認」を一つの確度に潰さない。AIの自己申告確率だけで公開を許可しない。

例：検索SQLにJOINがないが検索後に名称マスタを読む場合、`relation_kind=post_lookup`を記録する。原本にない`sql_join`や`foreign_key`へ変換してはならない。これは社員Pilotで得た教訓を汎用ルールにする例である。[現在の社員DB資産](../../src-dynamic/mcterp/mcterpgen/employee_db_assets/events.md)

## 4.5 動的Pythonを使う際の制御フロー

1. 固定の調査器が、必要能力と現在不足する能力を列挙する。
2. 再利用できるアダプターと宣言設定を先に探す。既にある処理を複製しない。
3. AIは不足部分だけの候補コード、入出力仕様、テスト、根拠、制限を作る。
4. 候補を隔離して構文・依存・セキュリティ・出力形式を検査する。構文検査だけで実行許可しない。
5. 原本を読み取り専用、出力を一時領域、通信を原則禁止、秘密情報なし、時間・メモリ・プロセス数を制限して実行する。
6. 独立した原本照合・固定ケース・既存案件回帰で品質を評価する。生成器が評価条件を勝手に変更できないようにする。
7. 合格候補をレビューして版固定し、アダプターとして登録する。未知入力の自動importはしない。
8. 再実行は承認済みコードと設定を再利用する。毎回AIで生成し直さない。

`src-dynamic`のフォルダ分離、`trust`文字列、別プロセス化、AST検査はそれぞれ役に立つが、単独では安全な実行境界にならない。AI開発用のAPI鍵・GitHub書込権限を解析アダプターの実行プロセスへ渡さない。入力内のコメントやREADMEは解析データであり、ツール実行指示へ昇格させない。権限制限の考え方は[Codex Windowsの公式説明](https://developers.openai.com/codex/windows)も参照。

## 4.6 Pythonを生成しない方がよい例

| 要望 | 推奨する置き場所 |
| --- | --- |
| 社員番号の論理名を修正 | 根拠付き辞書・補足データ |
| DBアクセスのメソッド名が案件で違う | 宣言的な呼出→操作対応表。条件解釈が異なる場合のみアダプター |
| 新しい共通入力部品を認識 | 再利用可能な部品契約・UIアダプター |
| C#とは別の言語構文が必要 | 方式別解析器、共通データ形式への変換 |
| 一回だけのCSVデータ整形 | 一時的補助処理。製品解析器へ自動追加しない |
| 不足文書を自然な日本語にする | 根拠からの文章化。存在しない業務値は創作しない |

## 4.7 肥大化を防ぐ運用

新規ファイルを増やす前に、問題が「抽出」「方式解釈」「案件データ」「文書表示」「評価」のどこにあるか分類する。同じ責務の既存モジュールへ最小の変更を行う。案件名のif分岐を共通層へ増やさない。共通化は最低二つの異なる利用例で確認してから行う。

巨大な中心ファイルを多数のファイルへ機械的に割るだけでは依存関係は減らない。入出力、所有者、変更方向を先に決める。旧CLI・移行コード・一時パッチには終了条件を持たせ、無期限に新旧を積み重ねない。

文書・画像・キャッシュ・過去結果が増えることと、実装の分岐が増えることは別の問題である。原本・証拠は保存要件に従って保護し、再生成可能な巨大キャッシュ等の保存場所・保持期間は別に決める。

## 4.8 次に実施する評価実験

まず社員Pilotを固定し、現在の品質を変更しない。その上で別の読み取り専用の最小評価対象を許可範囲に選び、同じ言語・違う構造、その後に違う言語・方式で試す。本件で直ちに他88機能を修正する提案ではない。

測定するのは、重要項目・イベント・DB処理の正誤、未知の明示、原本・他機能不変、アダプター再利用、案件追加ごとの共通コード変更量、調査から修正・検証までの総時間である。キャッシュの1工程だけを速くして全体改善と呼ばない。

合格条件は対象に即して先に決める。案件名・ファイル名の変更で抽出が壊れない検査、未対応構造を追加して不足として報告する検査、明示SQL結合あり／なし、共通ラッパー、失敗経路も含める。固定標本が全件一致しても、未知の全入力に100%を保証したとは表現しない。
