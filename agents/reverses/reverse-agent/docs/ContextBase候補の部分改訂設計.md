# ContextBase 候補の部分改訂設計

版：設計 v0.3／2026-11-01。§1～11のDiscovery incremental v1を維持し、§12にnative joint v2を追加した。未信頼seed、CAS差分、指摘別処置、完全候補の新しい独立検証を共通の合成moduleで扱う。合成検査と実案件の採用・性能は区別する。

[段階的抽出・検証フロー](ContextBase段階的抽出・検証フロー.md)の独立Agent経路と、全義務を一つの作者会話で調査するnative経路の双方で、未採用の凍結候補を部分改訂する。nativeは3 Agentの固定起動を要求しない。本書を追加設計の正本とし、既存runtimeの操作説明と区別する。

## 1. 対象と優先順位

対象は、同じ許可ソース・request・担当義務について、旧候補を保ちながら指摘対象の記録を追加・置換し、新しい完全候補を検証する流れである。主機能の再分類やrecord追加はモデルの根拠付き提出と明示した変更範囲に従う。

最初の実装検証はdiscovery-agentに限定する。共通Moduleは言語非依存とし、relationship-agentとbehavior-agentの独立性を維持する。未対応の操作を他Agentの自動起動で代替しない。採用済み義務の撤回と下流失効は既存の`revise`の責務であり、本書の未採用候補の部分改訂とは別である。

仕様書生成、全案件の再解析、Graphiti・OpenViking・Lettaの実依存追加、一般的な跨snapshot再利用、レビュー合格の最小再利用は対象に含めない。知識の検索・失効管理については§10の後続課題とする。

## 2. 今回の観測と現行Interfaceの不足

実行状態の正本は[sample-project1の成果索引](../../../../sample-project1/spec-reverse/README.md)である。以下は設計の動機であり、人手正解表ではない。

| 観測 | 設計への要求 |
| --- | --- |
| 最初の113記録候補の独立審査で、配備状態の説明とルートREADMEのmaterial登録不足を指摘 | 指摘を識別し、処置を確認できる形で次の作業へ渡す |
| 通常retryで119記録・主機能6件の新候補ができたが、READMEの登録不足が残った | 未変更記録を再出力させるだけでなく、指定指摘への処置を必須にする |
| 新候補の審査は1組・6記録passまでで運用者が中止 | 途中passを新候補全体の合格や正式な不合格へ変換しない |
| 取得済み78ファイル・構文Fact 1,883件の索引再構築・検査は約6.2秒 | 静的索引を作り直す高速化より、不要な再調査・再送・復旧の拡大を先に減らす |
| 検索結果の数行だけから連続区間を引用して交付検査で停止し、容量故障でも未完了組を再実行した | 原文交付、候補修訂、provider故障を別の状態として扱う |

[agent.py](../../shared/contextbase-runtime/src/contextbase_runtime/agent.py)の`retry`はfeedback付きの再抽出・独立検証を行う。[incremental.py](../../shared/contextbase-runtime/src/contextbase_runtime/incremental.py)は旧候補・検証を参照用feedbackへ載せるが、findingごとの処置を要求しない。現行の正規契約に「旧findingは必ず正しい」という条件はない。

[repair.py](../../shared/contextbase-runtime/src/contextbase_runtime/repair.py)は、まだ候補にならなかった拒否草稿をfresh workで回復する限定機能である。凍結候補の部分改訂やrecord追加へ流用しない。現在の119記録は新しい正式検証failを受けた状態ではなく、原修訂項目の未処置を確認して審査を中止した状態である。

## 3. 知識と作業状態の分離

現行にもsnapshot、構文索引、草稿、候補、採用版が存在する。追加するのは、それらを目的別に参照し、改訂の責任と有効性を追える契約である。同名のデータベースや新しい親Agentを増設する意味ではない。

| 論理情報 | 扱いと信頼 |
| --- | --- |
| 封印原文・構文Fact | 許可範囲、snapshot、parser／規則版、位置・hashに束縛する。構文検査passを業務意味の正しさへ読み替えない |
| 未採用seed・候補 | 根拠付きでも未検証の主張。元候補、提出元、正確な記録版を保持する |
| 指摘と処置 | 何を調べ直すかを示す。作者の処置宣言と、独立検証による確認を分ける |
| 検証・採用版 | 対象view、記録・未知・指摘のhash、実行由来と適用条件に束縛する |
| 調査・交付状態 | 完了した作業、未処置事項、交付済み区間、失敗と再開条件を保持する。長いworkingNotesを唯一の状態にしない |

タスク用の知識ビューには、対象の指摘・記録・関連依存とその版、必要な原文への参照を渡す。全seedを毎回promptへ複製しない。必須指摘の本文を単に検索可能な場所へ置くだけで済ませず、分割した場合も全指摘の受領・処置集合を照合する。全候補・全許可inventoryへの検索可能性は維持する。

要約・地図は調査先を選ぶために使う。原文根拠は対象taskへ交付したsourceTextと区間・内容hashで確認する。旧候補の引用、検索ヒット、索引の位置があることは、今回の文脈で連続した原文区間を受け取ったことを意味しない。

## 4. 明示的な改訂要求

公開Interfaceは`AnalysisAgent.amend_candidate`／CLIの`amend-candidate`とする。初版はfreshなDiscovery incremental work専用で、R／Bは未対応を明示拒否する。通常`retry`、採用済み義務の`revise`、拒否草稿の`repair`を暗黙に別機能へ変えない。呼出側は基準候補、処置対象、変更範囲、作業先を指定し、hash照合・原文取得・合成・検証・公開の実装は共通Moduleへ集約する。

task.operationの`extract`／`verify`を維持し、`amendmentPolicy=contextbase-candidate-amendment/1`の明示サブモードで識別する。seedとspecのhashをtaskへ固定し、verifyには`amendmentIssueBindings`、結果には`amendmentIssueChecks`を要求する。通常taskの契約へ空の改訂欄を補わない。

| 束縛 | 必須内容 |
| --- | --- |
| 基準候補 | 元workの所有・由来、candidate SHA、完全view SHA、recordのkey・identity・版、元requestと担当義務 |
| 入力 | project/profile、許可・除外、snapshot、Fact indexと抽出規則版。初版は同一入力版に限定する |
| 指摘元 | 元candidate、元verification、finding IDと内容hash、担当requirement、元の根拠と関連記録 |
| 適用先 | 今回改訂する候補、調査対象scope、現在の採用を阻害する義務と将来義務の区別 |
| 変更範囲 | 置換可能な既存key・期待版、新規追加可能なkind／owner、必要な依存修正範囲 |

今回の119記録候補には完了済みの独立検証がない。113記録版のfindingを扱う場合は、同じsource/request/scopeと明示したfeedback由来を照合し、119記録版への調査事項として指定する。113記録版の判定を119記録版の正式な検証結果と表示しない。任意の古いverificationや別案件の会話を根拠として混入させない。

## 5. 指摘ごとの処置

選択された各findingを漏れ・重複なく一度ずつ処置する。処置とrecord差分は別に検査し、変更不要という結論のために架空の差分を作らせない。

| 作者の処置 | 必須の裏付け | 独立検証での確認 |
| --- | --- | --- |
| 今回変更した（changed） | 差分のkey、期待版、新しい記録と原文根拠 | 変更内容が指摘に応え、別の誤りを生んでいないか |
| 既に反映されている（already-addressed） | 現基準候補の該当key・版、指摘元からの変更由来、現在の原文根拠 | 旧指摘が現候補に残っていないか |
| 根拠付きで異議を示す（source-refuted） | 指摘に対する説明、現在の記録と反証原文 | 作者の反論を独立に採否判定する |
| 未解決（unresolved） | 残る問い、関連義務、阻害義務、追加調査の必要範囲 | 現在の採用を阻害するか、将来層への質問か |

作者の処置宣言だけで指摘を閉じない。旧findingも自動的な正解ではない。現在の採用に必要な問題が未処置・阻害状態なら、成果と理由を保存して完全審査・公開へ進めない。明示的に将来R/Bへ属する未知までDの一律阻害に変えず、現行の関連義務／阻害義務の区別を維持する。

## 6. 基準候補と差分の合成

初版は追加と全record置換に限定し、暗黙削除を認めない。新しいscopeや許可外の修正が必要なら、現在の範囲で未解決として返す。

| 不変条件 | hostの確認 |
| --- | --- |
| 基準候補は不変 | 入力candidate/view/seedのSHAを照合し、新しい候補を別SHAで作る |
| 未変更記録を保つ | key・identity・kind・ownerと提出本文を保持する。依存が不変なら記録版も同一。依存先が変わる場合の参照版と派生hashは完全viewの組立で再計算し、本文の再生成と区別する。モデルへ全記録の再出力を要求しない |
| 置換はCAS | keyと期待版が一致する時だけ適用する。key/kind/ownerのすり替えを拒否する |
| 新規追加は元義務内 | 既存keyとの衝突、許可kind、owner、scope、分類参照、依存を検査する |
| 未知・followupを落とさない | seedの完全viewに保持された未知と未閉鎖followupを含める。最新answerの空unknownだけで置き換えない |
| factUsageを保つ | 未変更記録の対応は同一hashで保持し、変更・追加分の参照を完全索引へ照合する |
| coverageを自動承認しない | 基準coverageは未検証の主張として扱う。record所属に基づくkey集合を整合させ、status・根拠・残課題は作者が改めて明示する |

未知の追加や処置の説明は根拠付きのモデル提出とする。既存unknownの内容・IDを勝手に上書きせず、解決の判定は新しい独立検証へ渡す。全体viewとownerの内容hash、依存参照は新候補について再計算する。未変更記録の保持と、全体viewのhashが変わることを区別する。

## 7. 原文交付とprovenance

合成候補の由来は「旧未採用候補＋今回モデルが提出した改訂」である。119記録すべてが新taskのモデル原回答だったように保存しない。

seedには元候補、元request、完全view、保持未知・followup・factUsage、元提出と原文交付を照合するための由来を含める。旧入力の原文交付鎖を読取り専用の検査で照合できない場合は拒否する。旧source hashがあるだけで当時の作者への交付済みと見なさない。これは入力としての由来検査であり、旧Sessionの受入れやengine互換を承認する操作ではない。

seedとstoreはhost管理領域とする。hashは内容整合・版束縛の検査であり、署名や作成者認証の代わりではない。

未変更フィールドは検査したseedの提出元へ、変更・追加フィールドと処置説明は今回のtaskへ結び付ける。今回モデルが変更・反証に使う原文は、そのtaskに正確な範囲を実際に交付する。hostは原文の補充や業務判断を捏造しない。候補全体の位置・hash・fact・参照は新入力上で機械検査し、完全な新viewは新しい検証者が原文から確認する。

原文不足は、file/pathだけでなく不足区間と関連する提出を識別できる診断とする。連続区間の一部の検索ヒットしかない場合は合格させない。既存の交付receiptやrejectionを手書きして通す復旧を認めない。自動補査・同一対話での回復は後続の明示実装まで未提供とする。

## 8. 新runtimeと作業領域

現行workは複数候補と旧検証を持ち、現在のcheckpoint upgradeの限定条件には適合しない。engine fingerprintを手書きで置き換えず、新runtimeのfresh workへ未信頼seedとして明示導入する。原workと既存正式成果は保持する。

| 保存対象 | 方針 |
| --- | --- |
| seed入力 | 選択操作が所有する不変の入力束。hashで識別し、launcherの`current`清掃対象から分離する |
| 改訂work | 新engineの独立workspace。旧採用状態、receipt、途中passを輸入しない |
| 操作descriptor | 操作種別・対象Agent、seed、request/source/index、engine・規則版、対象義務、owned workを束縛する。採用権限は持たない |
| 正式出力 | 現行profileの固定slotを維持し、新候補の独立検証・採用後だけ原子的に更新する |

ワンクリック入口は、明示した改訂操作のdescriptorから作業先を決定的に選び、同じ改訂を再開する。完了後も旧engineのworkへ戻って再調査しない。所有・パス・scope・版を検査し、任意workの移動、暗黙fresh、操作キュー、旧workの一般移行へ広げない。通常の抽出と改訂の選択が曖昧なら保存して停止する。

入力・parser・規則・上流版が変わった場合は同一版の改訂を拒否する。跨snapshotの影響解析・再利用は既存P6で扱う。入力seed・QA・正式fixtureを中間生成物として清掃しない。

## 9. 新候補の独立検証と公開

1. hostがseed、指摘集合、差分、原文交付と完全候補の機械検査を完了する。
2. 現在の義務を阻害する未処置・未解決があれば、診断と未採用候補を保存して停止する。
3. 新しいtask/contextで完全viewを固定し、全record・分類・scope・factUsage・保持未知を独立検証する。
4. 選択した各findingと作者処置を新版viewへ束縛し、処置検査の全件対応を要求する。作者の「反映済み」「異議」も反証対象に含める。
5. hostが通常の全gateと処置検査、候補・view・由来の一致を採用時に再照合する。
6. Dの正式採用・公開後だけ、Rが正確なhandoffを受け、自身の原文で前提を独立再検証する。Bは自動起動しない。

改訂サブモードと処置検査には明示したpolicy/schema版を束縛する。新しい検証集合では処置検査の全件対応も必須とし、旧verifyの欠落欄へ空集合や既定値を補って対応済みと見なさない。通常taskと追加契約の対応・拒否条件をCA0で固定する。

旧119記録候補で途中passだった6記録も新候補の検証済みとは扱わない。局所審査の省略や新旧view間のpass再利用は今回の設計に含めない。record修正だけを検証し、他の記録や全体漏れ検査を飛ばす方式にしない。

## 10. 後続の改善と参考実装

[参考実装ノート](ContextBase調査フローの参考実装.md)から、OpenVikingの階層的な検索・原文取得、Graphitiの由来・有効性管理、Lettaの経験・判断記録の分離を参考にする。検索のL0/L1/L2は取得粒度であり、D05が採用しなかった全件固定の「索引・概要・詳細」生成段階を導入しない。由来・時刻が保存されることだけで業務事実の真偽を確定しない。

本設計の閉じた部分改訂を先に成立させ、原文不足への応答回復、組内のround単位再開、関連証拠による検査単位の編成、交付・完全性検査のoperation内一括化を後続の別変更として測る。通常プログラムが扱える版照合・失効判定を、毎回モデルへ再判断させない。

2026-10-29の追加提案も、調査状態、静的観測、作者の主張、独立判定、有効な版を分離する方針へ反映する。将来の関係グラフは検索を助ける派生索引とし、辺の存在だけで業務上の調査完了を認定しない。既知の未調査点・未解決はプログラムで列挙・保持し、source変更時は旧結論の自動継承を拒否する。今回追加するDB依存はない。別プロジェクトの監査比率や仮定の削減率を本案件の実測値へ転記しない。

単一削除経路での原文調査・固定packet対照、同題再利用・失効、CallSite→宣言の小型試作の実績は[実装計画§13.10](ContextBase実装計画.md#1310-単一経路と呼出し解析の先行実験)へ分離した。呼出し解析の試作は実被覆条件を満たさず正式採用していない。合成試験の通過から有効な意味接続や費用改善を推定せず、現在は全体D→Rを保留する。

依存辺の閉包だけで業務上の影響を完全検出できるとはしない。動的呼出し、設定・登録、SQL、未対応構文や不明な依存では再確認範囲を広げる。summaryは参照したsource/Fact/候補版と新鮮度を保持し、過時なら判断根拠にしない。

## 11. 実装と確認範囲

契約と決定的mergeは[candidate_amendment.py](../../shared/contextbase-runtime/src/contextbase_runtime/candidate_amendment.py)、読取り専用の由来検査とfresh workへの導入は[amendment_seed.py](../../shared/contextbase-runtime/src/contextbase_runtime/amendment_seed.py)、task・差分・新候補の由来は[amendment_runtime.py](../../shared/contextbase-runtime/src/contextbase_runtime/amendment_runtime.py)へ置く。実行は既存controller／incremental、独立処置検査はcontracts／review_setへ接続し、新親Agentを追加しない。

[CA0～CA6](ContextBase実装計画.md#13-未採用候補の部分改訂を閉じる実装計画)で、正式な合成fixtureとproviderで候補保持、新しい全量・指摘別レビュー、未解決時の事前停止、検証中断からの再開を確認する。CLI／ワンクリックの操作は[Discoveryの案内](../../discovery-agent/README.md)を参照する。実モデル・人手の業務受入れ、D→R完了、速度改善を合成合格だけで認定しない。119件・主機能6件は保持した候補の内訳であり、正解件数へ固定しない。

## 12. native joint候補の限定改訂v2

nativeは役割ごとに一つの継続Codex会話を起動する。取証の順序・再読取り・判断はCodexへ任せ、宿主が封印入力、決定的索引、候補版、差分合成と採用を管理する。目録・関係・振舞いは成果の責務であり、3 Agentの固定起動数ではない。作者と独立検証者の基礎指示・モデル設定は別に固定する。

`analyze amend-candidate`に`--from-work`、`--candidate`、`--verification`、`--finding`、`--replace-key`を指定し、同一source/request/raw indexのfresh native workへ取り込む。`native_amendment.py`が元候補・view・参照・依存・unknown/followupの整合を検査し、seed/specを不変保存する。旧engine・役割・意味索引hashは由来、現行engine・役割・意味索引hashは今回の実行束縛として分離する。異なるengineの旧Sessionを再開せず、旧コードも実行しない。

v1の旧交付鎖検査と異なり、v2は旧候補を静的検査済みの未信頼主張として導入する。旧pass・交付ledger・採用権を継承しない。作者には選択指摘、対象原記録、凍結viewの正確なCAS版を先に提示し、全seedは必要時の限定ページ読取りに置く。作者の`submit_amendment`は許可された置換と指摘別処置、全元義務の新しいclosureを提出する。`candidate_amendment.py`の既存合成を使い、未変更記録・factUsage・未知ID・followupを保持する。変更記録、新しい未知・followup、処置説明、closureの根拠とFactは今回の作者へ実交付する。

完全合成候補を新しい独立検証へ渡し、全記録・全義務・未知と指摘別処置を検査する。未選択の旧指摘も参照入力へ保持する。選択指摘が未解決なら高価な全量検証の前で停止し、別の既存記録の問題が見つかった場合も通常どおり採用・exportを拒否する。旧reviewのpassは再利用しない。native transcriptには差分、closure、完全合成answerを束縛し、採用時に同じ合成と順序付き交付を再現する。

現v2の範囲は原始native候補の指定既存keyの置換である。新規追加、削除、identity/kind/owner変更、改訂済み候補を起点にした連続改訂は拒否する。導入元の未採用状態は読取り時点のsnapshotであり、導入完了まで元workをロックしない。同時に元workで採用されても、その採用状態や権限を今回へ持ち込まない。

取証回放は操作内で固定source textを共用し、入口・出口の完全性検査と各取得の取消確認を行う。元の呼出順でだけ交付権を増やし、後続readによる先行提出の救済を許さない。ライブ取証の検査とモデルの調査方法は維持する。実例の時間・候補・採用結果は[sample-project1の成果索引](../../../../sample-project1/spec-reverse/README.md)へ分離する。
