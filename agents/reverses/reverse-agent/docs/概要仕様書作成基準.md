# 概要仕様書作成基準

対象：output/機能一覧.md に掲載する各機能。文書は顧客が業務の流れ・操作・入力条件・結果を確認できる表現とし、プログラミング言語や実装クラスの知識を前提としない。

## 1. 必須の章立て

```text
1. システム概要
   1.1 概要説明・対象範囲
   1.2 画面レイアウト
   1.3 入出力（IO）
   1.4 関連図（本機能、入力・出力、データ／ファイル、外部との関係）
   1.5 画面・処理の遷移図
2. 項目一覧
   項目名／タイプ／DB関連／必須／長さ／概要説明
3. イベント仕様
   操作と契機、前提、処理内容、条件分岐、結果、例外・中止、データ例
   文章・箇条書き・Mermaid図・データ例を組み合わせる
4. 補足説明
   共通仕様、注意事項、その他・確認事項
```

## 2. 表現

- 本文は「何を入力し、どの条件で、何が起こり、何が残るか」を記載する。クラス名、メソッド名、イベントハンドラー名、言語固有の型、コード断片、解析器の都合は本文に持ち込まない。
- DB関連は顧客の照合に必要なため、確認できたテーブル／ビュー名と列名を記載する。物理定義がない場合に型・桁数・NULL制約・参照整合性を推測しない。
- 「呼出」「値セット」「グリッド更新」だけで終わらせず、「選択した顧客の名称と住所を表示する」「検索条件に一致する明細を一覧へ表示する」のように対象と結果を明記する。
- 機能ごとの業務説明を優先する。一般的なコンピューター操作や、すべての機能に同じ注意書きを繰り返すことは避ける。
- 実装上の問題と望ましい仕様は分ける。現行の動作を無断で改善済みとして記述しない。

## 3. 項目一覧

入力・選択・表示項目、一覧の列、引継ぎ項目、処理結果、帳票／ファイル出力の設定を対象とする。非表示の管理項目は画面入力と区別する。ボタンはイベント仕様と照合する。

「タイプ」は文字、整数、金額、率、日付、年月、選択、真偽、一覧等の業務上の形式で表す。「長さ」は画面入力の上限とDB定義の桁数を区別する。指定のない長さを無制限と断定しない。「必須」は新規／修正／削除、選択区分、状態による条件を併記する。

## 4. イベント仕様

起動、検索、選択、入力変更、フォーカス移動、追加、修正、削除、保存、確定、取消、終了、印刷、ファイル出力、外部処理を対象に、存在するイベントを漏れなく対応付ける。

イベントごとに前提、対象データ、入力チェック、計算・初期値・補完、分岐、更新範囲、正常終了、失敗／取消時の結果を確認する。明細の一時保存とDBへの確定、一覧再表示とDB更新、帳票作成と印刷成功を混同しない。

金額・数量・期間・丸め・符号・課税・計上条件は、確認できる範囲で式と具体値を使って説明する。データ例は架空であることを示し、実テスト結果と混同しない。採番結果、外部処理結果、未確認の計算値を創作しない。

## 5. 図

MermaidはMarkdown内のコードブロックとして記載する。レイアウトは画面構成の説明図とし、実画面の寸法再現ではないことを明示する。関連図には実際に利用する入出力・データ・ファイル・外部処理のみを載せる。存在しない外部連携を図の体裁のために追加しない。

遷移図は呼出元・遷移先・モーダル画面からの戻りを区別する。イベント図は正常系だけでなく、確認の否定・入力不備・対象なしなど、確認できる主要分岐を表す。

## 6. 網羅性と根拠の管理

顧客向け本文と調査証跡を分離する。証跡はreport以下に置き、項目・イベント・主要処理と根拠ファイル／行の対応、入力ハッシュ、文書リンク、Mermaid検査結果、未確認事項を管理する。

全画面・全項目・全イベントの対応件数を照合する。処理を確認できなかった箇所は黙って落とさず、確認事項として残す。対応件数の一致だけを業務仕様の完全性の証明としない。外部DB関数、DDL、設定、依存製品、実行時の挙動など原本だけで確定できない範囲は区別する。

受入条件は、4章の存在、項目の6列、IO・関連図・遷移図、イベントの文章／箇条書き／Mermaid／データ例、原本との対応、未確定事項の明示、本文からの言語依存表記の除去とする。
