# ホスト取証モード

版0.3／2026-10-28。ContextBase改善の第1段階として、封印原文・構文事実の検索と取得を3独立Agentへ接続する。取得済み一覧内のディレクトリ検索と、要求エラーの型付き返答を追加する。最終canonical結果、完全viewの独立検証、host採用を維持し、選択前提有効化、局所レビュー合成、作業単位ごとの部分採用は含めない。

## 有効化と互換性

新しいworkを作るinit時に明示的に選ぶ。既定は従来のfullモードで、run時の切替や既存workの自動移行は行わない。

```text
contextbase-discovery init --source SOURCE --request REQUEST.json --work NEW_WORK --evidence
contextbase-discovery run --work NEW_WORK
```

relationship／behaviorも同じinitオプションを使い、従来どおり必要なportable handoffを受け取る。前層を自動起動せず、受信側が自分の原文から全受領前提を独立に再検証する。

設定モードではprofileへcontext_modeを指定する。相対pathの基準、source-only、request・入力版・出力所有の束縛は変わらない。

```toml
[profiles.example]
source = "srcs/EXAMPLE"
request = "contextbase-request.json"
output = "spec-reverse"
work = ".tmp/contextbase/evidence-example"
context_mode = "evidence"
```

full／evidence以外の値、設定とworkのモード不一致を拒否する。full設定をinit --evidenceだけで上書きしない。evidenceモードでは--inline-sources、--compact、拒否草稿repairを併用せず、別方式として扱う。discoveryの一括起動も選択profileのモードに従う。

## 取証Interface

evidence.pyのEvidenceAccessが、入力プログラムを実行せず、hostから封印原文と索引を読む。

| operation | 内容 | ページの扱い |
| --- | --- | --- |
| inventory | 取得済み／除外材料とparser能力 | offset／limit、全件数、次の位置を返す |
| query | symbol／call／entry／importの構文事実 | 条件、offset／limit、全一致件数、次の位置を返す |
| search | 原文のリテラル文字列検索 | 一致した完全なLF行と証拠をページで返す |
| read | 指定pathと行範囲の原文 | 完全な行だけを返し、残りはnextLineで明示する |

要求schemaはcontextbase-evidence/1に対応するstrictな型を用い、nullableな検索条件のnullは条件指定なしを意味する。正のlimitは最大100件。各返答はJSON表現で32,768文字以内とし、単一の行・要素が入らなければoversized-itemを返す。原文を途中で切って完全な証拠と表示しない。CRLF、Unicode区切り文字、原文内容を保持する。

返答にはtaskId、contextId、snapshotId、indexSha256、要求・結果・返答のdigestを付ける。許可外path、不正範囲、型違反、source／index変更を拒否する。採用前には同じ封印原文から返答を再生成して照合する。batch内だけの読取り共有を使い、操作間で古い原文検査を流用しない。

query／searchのpathは、nullなら取得済み全体、取得ファイル名なら完全一致、末尾`/`なら正規化済みのディレクトリ接頭辞とする。例：`deployment/`はその配下の取得ファイルだけを検索し、`deployment-other/`へ広げない。実ファイルシステムの再列挙は行わず、封印manifestから選択する。`..`、絶対path、重複した区切りなどの別名表記を拒否する。readは引き続き完全一致するファイルと行範囲を要求する。空のprefix結果はディレクトリの実在や、除外資料に対象がないことの証明ではない。prefix返答は対象ファイルとparser能力、残るページを明示する。既存の完全一致／null要求の正常返答は従来の形を保持する。

修正可能な要求の不正はEvidenceRequestErrorとし、error_replyで`status=invalid-request`の返答へ変換できる。要求・task・context・source・indexに束縛し、result.errorにcode・message・correctionを記録する。原文・fact・検索一致や進展を付与しない。incremental対話は同じbatchの正常な要求を保持して次の呼出しへ返し、不正な要求だけを修正させる。source／indexの指紋不一致、版・権限束縛の破損、I/O故障を要求エラーとして握り潰さない。旧evidence対話全体の回復方式を変更した実績としては扱わない。

queryは構文上の候補を返す。callの参照先確定、登録候補の実機到達性、SQL対象の意味的同一性を保証しない。未対応・partial、ゼロ一致、切詰めを区別する。

## モデルとの往復

evidence_dialog.pyはcontextbase-evidence-dialog/1を使う。各応答はprotocol、taskId、action、requests、answer、workingNotesを持つ。

1. hostは元要求、全inventory、能力情報、保持record又は完全verificationView、未知・前提を渡す。初期文脈へ全原文と全fact表を複製しない。
2. モデルがaction=requestsで検索／読取りを要求する。hostが型、権限、snapshotを検査して返す。モデル側のshell起動を通常の取証経路にしない。
3. 次の呼出しは直近の原文返答、容量制限内の既取得材料、以前の要求とページ状態を示す台帳、置換型の暫定notesを受け取る。原文を無制限に累積せず、見えていない材料は再要求できる。
4. action=finishは完全なcanonical結果を返す。patch、要約、取証台帳を最終結果の代用にしない。

一度の要求は最大8件、notesは最大12,000文字。これらは単操作の形状・容量で、総round数や総token予算ではない。新しい原文行範囲、fact ID、材料台帳項目の交付を進展として扱い、連続3roundで新しい交付がなければ停止する。検索文字やpage位置だけを変えた空結果、既読範囲、供給不能結果は進展にしない。各呼出し・原文取得の前後で取消し、epoch、基準版を照合し、遅れて戻った応答を採用しない。

作業窓はcontextbase-evidence-window/1としてtask／setupへ固定する。元のcontextbase-evidence-dialog/1の要求・終了envelopeは維持する。直近の返答を優先し、以前の原文・fact・材料を最近の交付から決定的に選ぶ。保持上限は524,288文字で、完全な基礎文脈、指令、schemaと余裕を除いた実際の残容量も上限とする。直近の材料だけで超限なら技術失敗とし、未知や完全viewを削らない。

保持できるのは同一taskが実際に受け取った材料だけで、作者と検証者は別々の窓を持つ。原文はpath・source hash・行範囲、factはID、材料は種別・pathで重複を除く。同じ文字列でも別の出所を同一視しない。直近の返答と重なる原文を二重配置せず、可視・逐出済みの範囲を明示する。notesを原文へ格上げしない。

各roundで実際に送った作業窓を保存し、採用時にはrequest／reply鎖から同じ窓を再構成して照合する。再読や窓の再配置は新しい交付ではないため、無進展回数をリセットしない。必要材料を同時に収められない場合は、容量又は調査単位の制限として報告する。

単操作の入力容量はprovider指示・schema等の余裕も含めて事前確認する。上限時は記録を保持して技術失敗を返し、goal、record、未知を黙って切り捨てない。provider単体でも保存した完全promptの文字数を確認し、現在のCLI上限を超えればCLIを起動しない。

## 独立性と採用

作者と検証者は別task／contextで、それぞれ独立に原文を取得する。検証者へ作者の取証台帳を引き継いで原文確認の代用にしない。完全なcandidate・保持view、全担当義務、unknown／followup、classificationChecks／scopeChecksの検査は維持する。

最終結果のすべての原文引用は、そのtaskのread／searchが返した原文範囲で覆う必要がある。queryが示す証拠位置だけでは原文を取得したことにならない。DのfactUsageはそのtaskのqueryで返ったfact IDだけを使う。実在・原文交差・索引版・独立factUsageCheckの通常検査も行う。

取証台帳は「何を供給したか」を示し、業務上の正しさや調査範囲の充足を承認しない。全体の漏れ、逆利用、登録点、未対応材料からの反証を確認する責任は残る。

複数のprovider呼出しは、各raw応答を保存した実行鎖として扱う。hostが組み立てる最終transportにはresponseOrigin=host-assembled-evidence-dialogを明示し、一回のモデル原回答と偽らない。provenanceのtransportはcodex-ephemeral-evidence-dialogとし、採用と外部前提有効化の双方で鎖・返答・最終canonical内容を再生検査する。注入runnerは従来どおり信頼しない試験伝送で、通常採用できない。

## 保存と制限

生のprovider呼出しはwork/tasks/ID/provider/round-NNNN、取証要求・応答・鎖・失敗はwork/tasks/ID/evidenceに保存する。workは対象project又はAgentの.tmpへ置き、正式成果へround別ファイルを増やさない。portableの形状と公開先は従来どおりである。

この実装は、元の独立3Agentと原文参照権限を維持する。OS全体の読取り隔離やモデルの全tool動作を監査できたという保証は追加しない。静的意味束縛、完全な領域task分解、選択前提有効化、局所検証の合成、cross-snapshot再利用、実モデルの速度・品質、人手受入れは残作業である。
