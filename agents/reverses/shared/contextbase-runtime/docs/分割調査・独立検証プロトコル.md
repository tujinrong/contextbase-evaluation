# 分割調査・独立検証プロトコル

版0.5／2026-10-28。`contextbase-incremental/1`、`contextbase-drafts/1`、`contextbase-review-set/1`の実装範囲を示す。続行状態・公平な巡回・候補材料窓・要求回復に加え、作者の収束と独立検証の責務、検証対象の版束縛を明示する。同一形式版でも規則指紋を固定し、旧workを自動移行しない。3Agentは自層だけを実行する。

## 明示的な有効化

既定はfullのままとする。従来のfull／evidenceを残し、既存workを自動移行しない。incrementalは新しいworkのinit時に選び、run時には切り替えられない。`--evidence`との同時指定、profileと異なるflag、inline／compact／旧拒否草稿repairとの併用を拒否する。

```text
contextbase-discovery init --source SOURCE --request REQUEST.json --work NEW_WORK --incremental
contextbase-discovery run --work NEW_WORK
contextbase-discovery status --work NEW_WORK
```

設定利用時は次のように明示する。パスは設定ファイル基準で解決する。これは汎用例であり、既存案件のprofileを変更した実績ではない。

```toml
schema = "contextbase-project/1"
default_profile = "example"
[profiles.example]
source = "srcs/example"
request = "contextbase-request.json"
output = "spec-reverse"
work = ".tmp/contextbase/example-incremental"
context_mode = "incremental"
```

relationship／behaviorも独立CLIのinitで同じモードを選べる。前提handoffは受信側自身が封印原文から独立再検証し、外部passだけでは有効化しない。前提不足で前層を自動起動しない。

## 調査・統合・採用

| 工程 | 実装と保持する条件 |
| --- | --- |
| plan | 原義務に結び付く対象・質問・取得pathから内部unitを作る。unitは新しいscopeや採用義務ではない。各原義務に作業を割り当て、追加unitも同じ条件で検査する |
| draft／checkpoint | 型付きrecord、根拠、fact利用、残質問を保存する。completeは「現権限・入力での調査作業を終了」を意味し、blocking unknownがあっても終了できる。remainingQuestionsは現条件で実行可能な次の調査だけを記す。変更／削除は現record内容hashによるCASを必要とする |
| unknown／followup | 単位の局所unknownを名前空間化する。既知の正確な全体IDは参照できるが、コロンを含むだけでは全体IDと認めない。recordの削除や後続草稿の省略で既存質問を消さない |
| closure | 保存済み調査の収束包から、作者が原義務ごとの対象範囲・既知の不足をsupported／unresolved／not-applicable、理由と自分で取得した原文根拠で声明する。逐recordの全面再審査を繰り返さず、hostも終了単位数からsupportedを推測しない |
| 完全候補 | 全計画unitの終了と残質問、衝突を確認し、hostが提出内容を決定的に組み立てる。最後に全目録をモデルへ再出力させない。引用・参照・分類・依存・未知の通常検査を通す |
| 独立検証 | hostが全record・分類・unknown／followupを分割配賦する。別task／文脈が各自で原文を取得する。別途、原義務・ゼロ件scope・候補外の漏れ・跨単位矛盾をglobal検査する |
| 採用 | 完全view、全検証集合、原文取得と実行由来を再生照合し、従来の意味・分類・fact利用・未知・scopeのgateへ接続する。局所passの数だけでは採用しない |

最終候補の機械的な参照・整合エラーは、対象義務内の小さなrepair unitへ戻してモデルに修訂させる。hostは意味を補完しない。同じエラーで構造的前進がない反復は停止し、全件再生成で隠さない。独立レビューの意味指摘は候補修訂と再検証の対象である。

## 原文取得と候補の閲覧

原文側のinventory／query／search／readと、候補側のlisting／materialを区別する。後者はrecords、unknowns、factUsage、units、feedback、checkpointsの一覧・内容をページで返し、原文証拠ではない。feedbackには旧候補・検証・handoff質問・拒否応答が入り、巨大な旧候補をpromptへ重複配置しない。

同じ子taskで取得した候補ページはretainedMaterialsへ、原文・factはretainedEvidenceへ分ける。両方で一つの容量上限を共有し、実交付の新しい順に保持する。候補はcollection・object ID・版・文字区間と原返答へ束縛し、重複区間を除き、旧object版を捨てる。候補窓は原文deliveryや新規進捗に数えず、採用時にも同じ選択を再生する。

引用は当該子taskのread／searchで実際に供給した原文範囲、fact IDは自身のqueryで供給したものに限定する。queryが返す位置だけで原文確認済みにしない。呼出siteは構文観測であり、参照先や実行時到達性を確定しない。未対応・切詰め・ゼロ一致は不存在の証明ではない。

対話envelopeはrequests／checkpoint／finishを使う。checkpointはdraftだけで使い、完了宣言と採用を分離する。取得と草稿の構造的変化を別に観測し、同じ材料・文言・完了宣言だけの反復では進捗を作らない。無進捗の検出は意味上の改善の証明ではなく、固定総時間・総token予算も設けない。

query／searchは完全一致のファイルと末尾`/`のディレクトリ接頭辞を受け、readは取得済みファイルだけを読む。対象は封印manifest内に固定する。要求のpath・行範囲・材料キー等に誤りがある場合は、専用の要求例外だけを`invalid-request`返答へ変換し、同batchの正常返答と一緒にモデルへ戻す。エラーは要求・task・source・版に束縛して再生検査するが、原文引用、fact、候補材料、進展へ数えない。連続無進展の停止規則を維持する。source・index・版の破損やI/O故障を修正可能な質問へ変換しない。

## 実行由来と再開

集約結果は`host-composed`、transportは`codex-ephemeral-incremental`、responseOriginは`host-assembled-incremental`として記録する。単一モデル呼出しの`host-executed`回答とは扱わない。子task／context、原応答、取得返答、割当て、結果を残し、採用と受信前提の有効化の双方でcompositeを再生する。注入テストrunnerは通常採用できない。

継続basisにはrequest・snapshot・索引・規則・元義務・基準版・候補・feedback等を固定する。新しいroot task／epochは、同basisで完全性を再確認できる旧子成果を参照できるが、旧子taskのIDや実行時点を書き換えない。現在のepochで取消し・遅延返却を拒否する。

単位の続行にはcontextbase-unit-continuation/1を渡す。直前のモデル回答hash、残る実行可能な質問、累積提出record／unknown ID、現在の合併版hashを明示する。recordBindings.sha256は現在の正規化bodyのCAS版、submittedSha256は当unitの前回提出内容であり、両者を混同しない。全文はcheckpoints材料で参照できる。計画の責務地図も小さく示し、毎回原問題を最初から調べ直さない。

調査は実行回数の少ない未終了unitから決定的に選び、まず各unitに一巡の機会を与える。未終了の同義調査に構造的成果がなければ、unitが変わっても空転回数を解除しない。完了した有限の空調査と、新IDの空unitを無限追加する行為を区別する。終了宣言は未知の解決ではなく、入力不足はtyped unknown／followupに残して原義務closureと独立レビューへ渡す。現に未解決の阻碍があるclosureをsupportedにせず、hostも未知を勝手に消さない。

schema、引用、CAS、単位判断等で拒否した返答はraw診断に残し、再利用可能なtraceへcommitしない。構造化返答の後段検査で拒否した単位は、エラーと未信頼回答を再調査用feedbackにも残す。完了済みの有効な単位だけを復元する。作者完了後に検証が故障した場合は凍結候補を保持して検証集合から再開する。候補viewを変えたら旧局所レビューを別viewへ流用しない。

| 状態 | 続行方法と意味 |
| --- | --- |
| active | runで保存済みの有効工程から続行する。completedDraftUnitsは現入力での調査終了で、未知解決や受入れを意味しない。unitCompletionMeaningで表示意味を明示する |
| stopped／cancelled | 同一requestでresume後、runする。封印snapshot・規則・現在の実行世代を照合する |
| needs-investigation | 意味上の不足・採用拒否を保持する。同条件のrunを無限反復せず、必要なら候補IDを指定したretryで明示再調査する |
| 当層完了 | 当Agentの必要義務を採用済み。元goalの後続義務まで完了したとは表示しない |

```text
contextbase-discovery resume --work NEW_WORK --request REQUEST.json
contextbase-discovery run --work NEW_WORK
```

Discoveryの一括起動はincrementalの場合、同じowned current/workを既定で継続する。activeはrun、stopped／cancelledはresumeしてrun、当層採用済みならモデルを起動せず現在版を再配布する。継続前に現在sourceを同じ取得規則で再取得し、追加・削除・内容・omittedを含む完全manifestを比較する。

```text
python -m contextbase_discovery.launch --config contextbase.toml
python -m contextbase_discovery.launch --config contextbase.toml --fresh
```

--freshは同一ownerの許可範囲で明示的に作業を作り直す。別targetや所有不明のworkは削除しない。request／profile／source／規則が変わった旧checkpointは保持して拒否し、必要に応じて別workを選ぶ。full／evidenceの従来の新規起動動作は変えない。公開ロック・所有marker・rollback条件も維持する。

### 原義務の収束包

closureの入力は、原義務、各調査単位の質問・終了状態・原回答hash・産出keyと現在の材料hash、目録の階層索引と根拠位置、unknown、全followup、factUsageの宣言数と版、取得範囲と省略メタデータを決定的に束縛する。これらは作者の提出内容であり、検証合格や実行成功の証明ではない。future stage向けfollowupも省略せず、unknown配列が空であることを未決なしへ読み替えない。

収束包は既存feedbackの材料としてページ取得できる。十分小さい包はclosure文脈へ直接配置し、大きい場合は総数・hash・取得先を示す。見えていない部分を黙って捨てない。plan／draft／reviewの既存schema・通常文脈は変えず、保存済み草稿の原呼出しを再生できるようにする。

作者は原義務の範囲がどのように覆われ、どの不足が残るかを声明する。必要な登録点・範囲境界の原文は自分で取得し、収束包の引用位置だけを交付済み証拠へ格上げしない。真の矛盾・不足があればunresolvedを残す。終了単位やrecordの件数だけでsupportedにせず、収束のために未知を削除しない。

各recordの正確性、分類とconsumer、factUsage、全体の漏れと反例は、後段の完全な独立review集合が原文から検査する。作者の収束声明はその代用ではない。作業窓や空転判定を緩めず、収束を二度目の逐項全件審査へ広げない。

### 停止済み草稿の限定的な互換移行

通常のrun／resumeはengine指紋の不一致を引き続き拒否する。`checkpoint_upgrade.py`の明示保守操作は、指定された旧engineと審査済み新engineの正確な組合せ、停止済み・version 0・候補／検証／採用なし・実行中taskなしのDiscoveryに限定する。現在の対象は要求回復後のengineから収束包修正への移行で、推論規則の変更をincremental.pyだけに制限する。以前実施したdirectory-query／request-recovery移行の原監査・tool・journalを保持し、その処理を再実行しない。将来の未知の新engineは同じファイルだけの変更でも対象にしない。

```text
python -m contextbase_runtime.checkpoint_upgrade --work WORK --previous-runtime PREVIOUS_RUNTIME --request REQUEST.json --previous-audit PREVIOUS_AUDIT_SHA --dry-run
python -m contextbase_runtime.checkpoint_upgrade --work WORK --previous-runtime PREVIOUS_RUNTIME --request REQUEST.json --previous-audit PREVIOUS_AUDIT_SHA
```

最初に隔離したworkコピーで確認し、問題がなければ元workへ適用する。元request、取得規則による現在source全manifest、索引、Agent実装、保存済みplan／draft全呼出しを検査する。旧instruction・schema・prompt・原返答・正常query replyを完全一致で再生し、同じ草稿・unknown・followupの帰着を確認する。モデルは起動しない。未終了の子呼出しは診断として保存し、その単位から新しい呼出しで続ける。終了済みの単位を再抽出しない。

既存のruntimeUpgradeがあるworkでは--previous-auditを省略できない。旧configと監査ID、原旧新engine、完了markerのsession／state束縛を確認し、前回監査を新configの履歴へつなぐ。移行監査は旧session／state、旧新engine、互換検査と草稿hash、原呼出しファイルhash、保守tool hashを記録する。新configに監査IDを束縛し、epochを増やす。旧呼出しのID・context・原実行記録は変更せず、候補や採用receiptを作らない。今回のclosure-pending journalは過去のjournalと分けて保持する。config／stateの切替中に停止した場合は通常起動を拒否し、同じ保守操作で正確な旧／新組合せだけを回復できる。未知の変更を上書きしない。適用後も状態はstoppedのままで、通常のresume／run又は既存一括起動が保存済みworkflowを継続する。

### 凍結候補の検証のみを継続する移行

検証の`recordSha256`は記録bodyの`version`、`unknownSha256`はunknownの束縛版を指す。取得材料JSON全体の`materialSha256`とは別である。review文脈と大きい対象の参照には両方を明示し、返答schemaはkey／IDと期待版を対のconst分岐として制限する。他の対象の正しい版や、材料全体のhashを返しても合格しない。hostの全件集合・版一致検査も維持する。status・reason・evidenceは引き続き独立モデルが判断し、hostが値を補正して合格させない。

この修正には、収束包版engineから検証版束縛修正版engineへの別の限定移行を設ける。`--frozen-candidate CANDIDATE_SHA`と収束包移行の`--previous-audit AUDIT_SHA`を明示する。停止／取消し済み・version 0・未採用候補1件・集約検証なし・実行中taskなし・成功review断片なしだけを許可する。変更可能な推論ファイルはincremental.pyとreview_set.pyに限り、旧新engineの正確な組合せを固定する。

原候補のバイト列とview、原作者のplan／draft／closure全compositeを再生し、原返答・prompt・schemaと決定的な最終回答の一致を確認する。失敗した旧reviewは診断として保存し、その判断を新schemaの検証結果へ流用しない。検査はモデルを起動せず、隔離コピーを先に確認する。監査には候補・view・全作者trace・原ファイルhashを束縛し、review-pending journalを旧journalと分ける。適用後は通常の起動が凍結候補を再利用し、再抽出・再収束せず独立reviewだけを行う。

これらは任意版の自動移行、source変更後の再利用、検証済み成果の格上げではない。最終候補は通常の完全検査と独立検証・採用を必要とする。

## 保存・実装範囲

workはproject又はAgentの.tmp配下に置き、workflow state、calls、取証窓、拒否返答、失敗試行をそのwork内へ保存する。正式な公開先は既存の固定ContextBase・review・検証資料を使い、中間unit別ファイルを正式rootへ増やさない。新採用が成立するまで旧正式版を保持し、最新失敗と旧版を混同しない。

実装は[investigation.py](../src/contextbase_runtime/investigation.py)、[review_set.py](../src/contextbase_runtime/review_set.py)、[incremental.py](../src/contextbase_runtime/incremental.py)、[材料窓](../src/contextbase_runtime/material_window.py)、[controller.py](../src/contextbase_runtime/controller.py)、[独立Agent接続](../src/contextbase_runtime/agent.py)、[Discovery一括起動](../../../discovery-agent/src/contextbase_discovery/launch.py)を参照する。

確認済みは合成provider・fixtureによる契約、拒否、続行、独立検証・採用経路である。実Dの最新状態は案件成果案内を参照し、業務品質の人手受入れ・性能改善と区別する。D03の領域子集交接、cross-snapshot再利用、候補を跨ぐ局所レビューの最小失効、R／B専用typed relation、新しい包括的静的意味解析は未実装。既存全体catalogの内部unitだけでRを解禁しない。
