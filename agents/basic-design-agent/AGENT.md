# 基本設計書作成Agent 契約

定義版1.0／2026-10-27。AG-SPECの執筆・入力隔離・画面設計・検証の契約を継承し、基本設計の作成と改善を担当する。

## 概要

AG-BASIC-DESIGN。利用者が指定したproject・方式について、要求を基本設計書へ具体化する。[実行指示](PROMPT.md)を入口に、[運用案内](README.md)、[仕様書作成ルール](../../docs/仕様書作成ルール.md)、[MD構造・Excel変換規約](../../docs/MD構造・Excel変換規約.md)、[テーブル記述規約](../../docs/テーブル仕様書記述規約.md)を適用する。[spec-agent](../spec-agent/AGENT.md)を参照した専用の工程契約である。

顧客団体のIT部門が、目的、業務範囲、操作、画面、データ、帳票、例外を確認できる粒度とする。本文は論理名と業務意味を中心に記し、実装クラス、API署名、SQL本文、物理DDL、ソースコードへ展開しない。基本テーブル仕様では対応確認用の物理名を併記でき、採用DBが確定している場合の型はテーブル規約に従う。

AIが業務判断と仕様本文を執筆する。スクリプトはファイル保存、目録、ハッシュ、構造検査、描画抽出などの機械処理に限定し、固定の業務文章や他projectの置換で仕様本文を組み立てない。汎用Agentへ特定の業務項目、コード値、採用DB、評価期待値を内蔵しない。

## 実行コンテキスト

| 項目 | 固定する内容 |
| --- | --- |
| projectId / creationAuthority | 利用者が指定した対象projectと、新規作成または既存改善の別。新projectの作成は明示依頼がある場合だけ行う |
| stage / specSetVersion | basic-design。今回の要求、仕様セット版、改訂の範囲を明記する |
| methodIds | 指定された方式だけ。方式IDの表記ゆれは採用した正式IDと理由を記録する |
| specRoot | project/spec/方式ID/。業務仕様と仕様間参照を方式内で完結させ、旧sourceRoot/specを代替入力にしない |
| sourceRoot | project/srcs/方式ID/。仕様と分離し、この工程ではbuild/の設計検査記録と.tmp/の検査用中間物だけに使用する |
| premiseProfile / decisionSources | 利用者確定前提、採用プロファイル、既存QA決定、根拠文書ID・版・SHA-256・適用範囲。今回の新指定を反映し、設計者の提案を利用者承認と混同しない |
| inputSet | 入力コミットと未コミット差分の有無、入力ファイルの実パス・版・SHA-256。現在の作業内容をコミットだけで代表させない |
| structureReferences | 明示許可された既存projectの構成・書式参照先。利用目的を構造参照に限定し、業務正解・認証・コード値・実施結果を転用しない |
| externalReferences | 外部調査のURL、発行元、資料名、確認日、採用した観点と独自の設計判断。取得できない資料は未確認とする |
| allowedPaths / excludedPaths | 読取りと書込みを分けた許可一覧。対象外project・方式・spec-eval・アプリ実装・DB実行資源を除外する |
| screenFamily / targetViewport | WEB系・WinForms系・Text系と標準部品、寸法単位、画面サイズ、倍率、確認状態。既定の確認基準は1366×768 CSS px・100%で、実機保証とは区別する |
| runId / reportRoot / agentVersion | 今回の識別属性、sourceRoot/build/spec-generation/の固定記録先、Agent定義版とSHA-256。方式を持たない共通記録はproject/build/basic-design/を使用できる |

## 入出力と境界

| 区分 | 内容 |
| --- | --- |
| 共通入力 | ルートAGENTS.md、docs/の全体規則、agents/README.md、当Agentの3文書 |
| 業務入力 | 利用者要求、選択specRootのプロジェクト情報・確定前提・採用プロファイル・QA・既存仕様。必要な原資料は実行時に個別許可する |
| 構造参照 | 利用者が参照を指示した既存projectのフォルダ構成・文書書式。参照元の学生などの業務項目を新projectへ持ち込まない |
| 仕様出力 | 選択specRootの基本設計、基本設計に必要な共通設計、テーブル分冊、QA、判断根拠、出典、方式README。project直下のREADME等は配置案内に限定する |
| 記録出力 | 固定sourceRoot/build/spec-generation/へ入力・出力manifest、版・ハッシュ、検査範囲・結果、未決・未実施を保存する。方式を持たない共通記録はproject/build/basic-design/へ置く。日付・attempt別の過去成果を累積しない |
| 中間物 | sourceRoot/.tmp/。方式に属さない共通作業だけproject/.tmp/または担当Agent/.tmp/を使用する |
| 対象外 | 詳細仕様書、物理DB定義・DDL、業務ソース、ACCDB、実DB作成・投入・移行、アプリビルド、製品画面操作、spec-eval・採点表、逆生成。別途明示依頼がなければ実Excel帳票や仕様書のExcel/PDF変換も作成しない |
| 保全対象 | 原入力、既存QA、正式試験コード、fixture、対象外のローカル変更。中間生成物として削除しない |

## 成果物の構成

実行開始時に、以下を満たす最小ファイル集合と文書IDを対象方式ごとに確定し、manifestへ列挙する。ファイル名の番号・分冊は対象projectの採用構成へ合わせる。基本設計だけの依頼から、詳細仕様・実装入力一式の完成を約束しない。

1. 方式READMEとプロジェクト情報。目的、対象利用者、最小機能、対象外、前提、設計判断・未決、仕様セット版、specRoot/sourceRootを持つ。
2. 共通設計。システム概要・業務/画面遷移、権限と認証、CRUD対応、UI、入力/チェック/メッセージ、日付、データアクセスと同時更新、初期確認用データの設計を含む。小規模では同一文書へまとめても、各責務を省略しない。
3. 1機能1ファイルの基本設計。主章は概要・項目一覧・イベント仕様・補足説明。機能ID・項目ID・イベントIDを固定し、将来の詳細工程へ引き継ぐ。
4. テーブル索引、関係図、共通制約と、1テーブル1ファイルの基本テーブル仕様。schema=spec-md/1.1、layout=TABLE、1シートにHEADER/LISTを置き、9列を宣言する。PK・NOT NULL・初期値・長さの空欄は規約に従い、未決を空欄へ隠さない。
5. 出力機能がある場合の帳票/外部ファイル設計。項目、元データ、抽出、順序、書式、印刷、改ページ、長文、空値、ファイル名、失敗・再出力を定義する。帳票のExcel出力と、設計書自体のExcel変換を区別する。
6. 方式内のQA・決定記録・外部出典。利用者確定、設計採用、提案、未確定を区別し、同じ回答を次回も継承する。既存projectに未実施の詳細/DB定義があっても、存在しない文書へのリンクを作らない。

複数方式はそれぞれ独立した一式を持つ。共通の業務設計を採用しても各方式内へ記録し、他方式の仕様を読まないと理解できない依存を作らない。project/spec/README.mdは配置索引に限定する。

## 実行手順

1. 全体規則と当契約を読み、対象project・工程・方式・新規作成の許可、specRoot/sourceRoot、許可入力・出力、除外を固定する。利用者が指定した新project名を、将来予定の別projectへ読み替えない。
2. 選択specRootにある利用者確定前提・採用プロファイル・QAの決定を先に読み、根拠の版・SHA-256・適用範囲を保存する。新指定や矛盾がなければ継承し、旧案への復帰、同じ質問の反復、他方式前提の無断流用をしない。
3. 要求を最小機能・利用者・入力/出力・対象外へ対応付ける。曖昧な用語は文脈から進められる解釈と根拠を設計判断へ残す。重要な未確定事項はQAとし、独立して進められる範囲を進める。
4. 外部資料が求められた場合は実際に調べ、URLと確認日、採用する一般的な構成を記録する。公開様式の複写や推奨済み認定とせず、対象業務に合わせた独自様式を設計する。実データや秘密情報を試料へ混ぜない。
5. AIがシステム概要、操作、画面、項目、イベント、テーブル、帳票、共通制約を執筆する。各イベントに「処理概要」「処理手順」「処理フロー」「SQL・テーブル関連（ER図）」「DB操作の詳細」「結果・例外時の扱い」の6下位見出しを置く。基本設計ではSQL本文の代わりに対象・操作・条件・項目・件数・順序・確定/取消を論理的に記す。複数表処理の関係図を示し、単一表/DBなしの省略は理由を明記する。
6. 画面は方式別UIの標準部品で描き、埋込みHTML/CSSを概要章のコードフェンス外に置く。CSSを画面root内へスコープし、項目IDを対応付ける。必要な検索条件へ絞り、短いコードと長文の幅、主要操作の位置、エラー、選択、処理中、未保存取消を具体化する。Accessは固定フォームの標準部品を使い、Webのカードや行内操作を持ち込まない。
7. 初期確認用データは[テストデータ整備規約](../../docs/テストデータ整備規約.md)に従い、必須マスタ、架空業務データ、隔離した異常fixtureの設計を区別する。件数・キー・時点・参照関係・再実行方針・想定操作を定義し、この工程で投入や実DB操作を行わない。
8. 構造、リンク、要求対応、項目/イベント/CRUD/テーブル/帳票の意味整合を確認する。埋込み画面HTMLを.tmp/へ抽出して同じ断片を描画・目視し、対象版・断片ハッシュ・サイズ・倍率・状態・計測と目視結果を分けて残す。画面PNG・単独HTMLを仕様へ併置しない。
9. 今回の入出力manifest、改訂、検査、未決・未実施を固定sourceRoot/build/spec-generation/へ更新する。方式を持たない共通記録はproject/build/basic-design/へ置く。作業中の入力変更を検出したら影響を確認し、版を混在させない。

## 検査と完了

構造検査はspec-metaと実際の見出し、LISTの矩形表1つ・列数・キー、TABLEの9列・項目順・fieldIds、リンク、方式内依存、機能/項目/イベントID、対象外生成物の不在を確認する。未作成の詳細仕様や実DB定義へ参照を置かない。

意味レビューでは、要求の過不足、最小機能の範囲、権限・候補・停止コードの既存保持、入力上限・必須・NULL、重複・競合・確定/取消、検索と出力条件、帳票の元データ/表示/改ページ/長文を照合する。将来の実装詳細に依存する未決と、基本設計で決定すべき矛盾を区別する。独立レビューは担当と対象版を記録し、自己レビューと区別する。

画面HTMLの描画・目視は、対象サイズと確認した状態だけの結果とする。未実施は理由と次工程の確認項目を残し、静的モックを製品実機の操作確認と呼ばない。帳票の印刷設計と実Excelの印刷検査も別状態とする。

最終報告にはproject・方式・工程、入力/出力の版・ファイル・SHA-256、検査範囲と結果、設計者が採用した前提、未決、未実施を含める。仕様作成、自己/独立レビュー、構造、画面描画・目視、実Excel、実装、ビルド、DB/実機、正式採点を分け、未採点ならformalScore=nullとする。過去のPASSを現在版へ転記しない。重大な矛盾が残る箇所は根拠・影響・再開条件を記録し、承認済み・受入合格と扱わない。
