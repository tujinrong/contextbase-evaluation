# AccessからWebアプリへの再構築方針

版0.5／2026-10-28。利用者の追加指示「CSharp_ASPNETのソースを参照して、Accessから忠実に変換するわけではなく、WEBらしいアプリ」を現行方針とする。

## 目的

Accessの画面、物理コントロール、イベント順序、ダイアログをそのまま移植することを目的としない。Accessから業務データ・制約・処理目的を読み取り、指定されたWeb参照実装の構成と操作を使って、Webとして利用しやすいアプリを作る。業務仕様の保持と画面操作の同形再現を分ける。

## 根拠の役割

| 根拠 | 採用する内容 | 境界 |
| --- | --- | --- |
| 指定Access本体 | 業務データ、制約、保存・取消の意味、権限・競合・監査 | コントロール配置やデスクトップ固有イベントをWebの必須形にしない |
| 利用者指定CSharp_ASPNETソース | 検索・一覧・編集の構成、ページング、検証表示、状態管理、二重送信防止、MVCの責務分担 | 読取り専用の参照。必要なコードを対象方式内へ適応し、外部ProjectReferenceや実行時ファイル共用を作らない |
| 対象方式の移行設計・確定判断 | 採用するWeb操作、原本との差、適用範囲 | 他方式の認証・DB構造・コード値を比較せず自動採用しない |
| 今回の検査記録 | 新しい版の動作・構造・描画の証拠 | 過去の訓練PASSを新版へ転記しない。原仕様・spec-evalの期待値は入力にしない |

## Webの設計

検索は必要な条件を少数に絞り、条件・件数・一覧・主要操作を近くに置く。一覧は見出し固定、並び替え、ページ移動、選択から参照・編集までの経路を設け、操作対象を明確にする。画面幅に応じて再配置し、狭い画面でも切捨てや重なりを避ける。

編集は情報のまとまり、入力補助、項目ごとのエラー、保存・取消、処理中の表示をWebの部品で構成する。利用者が2026-10-27～28に確定したAR028～032を、今後のAccess→Web再構築へ適用する。

### 有効スペースの節約（AR028）

条件・一覧・入力・主要操作を近接させ、余白、見出しの高さ、繰返し説明、入力欄の幅を必要量に抑える。入力幅は内容・桁数・日本語表示に合わせ、短いコードや日付へ一律の全幅を割り当てない。補助説明は短くし、詳細は必要時に参照できるようにする。検索条件は業務に必要なものだけに絞る。

PC向けの対象表示領域を設計時に固定し、主要項目と主要操作がなるべく同一画面に収まる配置を目指す。文字の過度な縮小、項目やエラーの隠蔽、無断の業務項目削除で収めない。狭幅・拡大時は自然な折返しと縦スクロールを許容する。

### 見出し左・項目右の表形式（AR029）

PC向けの検索条件・編集・参照項目は、各行の左に見出し、右に対応する入力欄または表示値を置く。見出し列と項目列の開始位置を揃え、同じグループ内の列幅・行間を統一する。横幅に余裕があれば「見出し／項目」の組を複数列に並べ、住所や備考等は必要な幅を確保する。各項目の上に見出しを積むカード配置をPC画面の既定にしない。

表形式は見た目と対応関係の規則であり、HTMLのレイアウト用tableを必須としない。CSS Grid等で実現し、labelと入力の関連付け、グループの意味、自然なTab順、入力欄とエラーの対応を維持する。狭幅では見出しと項目の組を保って1組ずつ折り返し、必要時は見出しを上へ移せる。

### 日付・和暦のカレンダー入力（AR030）

日付は、ブラウザー標準または採用済みのカレンダーコントロールによるコンパクトな1入力を原則とする。和暦を扱う場合も、選択日と同期した短い和暦表示を同じ行または近接位置へ置き、元号・年・月・日の4欄を常設する配置を既定にしない。和暦表示・入力契約と保存用日付を境界で明示変換し、利用者の確定値を保つ。コントロールが和暦を直接表示できるとは仮定しない。

カレンダーはマウスとキーボードで使用でき、生年月日等の過去日も年月へ直接移動または入力できるようにする。未設定・クリア、必須／任意、最小最大、不正日、閏日、元号境界を扱い、日付だけの値を時差で別日にしない。日付以外の年度・年月・期間を無断で完全な日付へ変更しない。既存の直接和暦入力が明示要件なら、コンパクトな補助操作として設計し、採用理由を記録する。入力補助とは別にサーバーで業務制約を検証する。

### グループの上方見出し（AR031）

グループ名は内容領域の上方へ独立した見出しとして置き、太字で階層とまとまりを示す。番号を使う場合は「01 基本情報」のように番号と名称を一続きに読み取れる形とする。番号・名称は対象業務で決め、汎用Agentへ固定しない。

Accessのグループボックスのように、枠線を切り欠いて見出しを境界へ重ねる表示をWebの標準にしない。内容を囲む場合も見出しと内容領域の境界を明確にする。表示を変えても、グループの意味、入力との関連付け、参照時の無効化、ラベルとTab順を維持する。

### 左サイドメニュー（AR032）

主要なWebメニューは画面左の縦サイドメニューへ配置する。現在位置を視覚表示とアクセシビリティ上の状態で識別でき、キーボードで各項目へ移動・実行できるようにする。本文へのスキップリンク、見出しと本文の読み順を整える。メニュー項目は対象機能と既存権限に合わせ、無権限の機能を表示や直URLだけで利用できる状態にしない。

PC向けの対象表示領域でサイドメニューと本文が重ならず、必要な入力幅・一覧幅・主要操作を確保する。メニューの幅、間隔、補助表示を必要量に抑え、省スペースと可読性を両立する。既存の主体・認証・権限・未保存変更の扱いを保持し、見た目の変更を理由に新しい認証方式や業務機能を必須化しない。対象プロファイルでスマートフォン対応が不要と確定した場合は、PC向けの設計・検証に限定する。

### Webの状態と通信

年度・学年・在籍状態による候補変更はローカル絞込みまたは認証付きJSONで更新し、ページ全体のPOSTを必須にしない。候補はサーバーでも再検証する。通信中・失敗・古い応答の扱いを明記し、入力済み内容・フォーカス・未保存状態を守る。

成功後はPRG等で再送信を避ける。二重送信防止、CSRF、認証・権限、編集と確認の所有束縛、期限、競合、古い確認の失効を保つ。これらの目的を満たす限り、Accessと同じボタン数やイベント順を受入条件にしない。

## 検証と履歴

業務の回帰とWeb操作の検証を分ける。現行ブラウザーで検索・候補変更・保存・ページ移動・エラー・取消・画面幅変化・キーボード操作を確認し、候補更新が全画面POSTへ戻らないことも検査する。採用した参照ファイルとhash、原本から変えたUI判断を今回のmanifestへ残す。

AR028～032の実装検証では、対象viewport・拡大率を記録して主要項目と操作の配置、左見出し／右項目の列揃え、文字切れ・重なり・不要な横スクロールを画面で確認する。カレンダーの選択・直接入力・クリア・再表示・エラー後保持と和暦／保存値の対応を実操作で検証する。ルール採用だけを画面実装済み・操作PASSとしない。これらは確定した設計条件であり、各規則を適用した版の実装・操作検証は今回の記録で確認する。

グループ見出しが内容の上に独立し、枠線や入力と重ならず太字で読めることを確認する。左サイドメニューの位置・現在表示・Tab順・本文へのスキップ・権限別の項目表示と直接アクセスを検査し、本文の幅と主要操作の到達性も確認する。

最初の訓練2回は完了台帳として維持する。今回の変更は、その後の利用者が明示したWeb化改訂であり、第3回の訓練として台帳を再開・初期化しない。実装を行うWeb化改訂では、結果を対象sourceRoot/build/test-results/web-modernization.jsonへ固定保存し、配布物と入出力manifestを現行版へ更新する。ルールのみの更新ではAgentのbuild/へ今回の文書検査を記録し、アプリ配布物や実行結果を更新しない。
