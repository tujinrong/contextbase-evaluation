# 抽出からC#／Webへの実装

実施指示とrequestのproject・対象ファイル・許可を確認し、prepareとbegin-iterationを実行する。台帳が上限なら新しい候補を作らない。

業務の根拠は同一hashのACCDB/MDBから取得した目録・DAO構造・原文とする。利用者が許可したWebソースも読み、一覧・編集・検証・状態管理・HTTP境界の設計に活かす。参照元と適用範囲をhash付きで記録する。未取得と不存在を区別し、評価期待値を入力にしない。

Codexが業務目的を理解して対象方式のCore/Web/SQLを作成する。Accessのコントロールやイベントの同形変換を求めず、Webとして自然な入力補助・ページ移動・非同期候補更新・エラー表示を設計する。C#はsrc/、構造とSQLはdatabase/、正式試験はtests/に置き、実在プロジェクトを.slnxへ登録する。重要な未対応とUI変更判断を独立比較へ渡す。

[Web再構築方針](../docs/Web再構築方針.md)のAR028～030を適用する。Web画面は有効スペースを節約し、PCでは左見出し・右項目の列を揃えた表形式を標準とする。日付・和暦はコンパクトなカレンダー入力と同期した和暦表示を使う（AR028～030）。元号等4欄の常設や上ラベルのカード配置へ無条件に戻さない。業務制約・ラベル関連付け・Tab順を保持し、狭幅・拡大時に切れない配置を設計する。

AR031・AR032も適用する。グループ見出しは内容領域の上方に独立した太字で置き、Access風の枠線切欠き表示を既定にしない。主要なWebメニューは左の縦サイドメニューに配置し、選択中・権限・キーボード操作と本文の有効幅を保持する（AR031・AR032）。枠線と見出しの重なりを避け、メニューによって本文・入力・主要操作が押し出されないPC配置を設計する。参照モードの無効化、主体・認証・権限、未保存変更の確認を保持する。

検査の失敗は取得・設計・コード・環境に分類し、同じ回の内部で必要な局所修正を行う。候補全体の検証とルールへの反映を記録してcomplete-iterationする。次の候補へ進む前に台帳上限を確認する。
