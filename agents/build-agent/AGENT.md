# 仕様からシステム生成Agent 契約

版7.2／2026-10-12。順生成の実行指示・事前検査・入力再照合付き出力manifestを追加。アプリ生成・ビルド・試験の状態は実行ごとの報告を参照。

## 概要

AG-BUILD。Codexが本契約を読み、選択projectの仕様から各方式のソースを生成する。対象projectIdと工程を明示した実行で使用する。[実行指示](PROMPT.md)を入口とし、[事前検査スクリプト](scripts/preflight.mjs)で入力版・SHA-256・構造検査結果を保存する。スクリプトは文書検査であり、コード生成器や業務実装の合格判定ではない。

## 入出力

| 区分 | 内容 |
| --- | --- |
| 入力 | docsの全体規則、agentsの役割定義、対象projectの詳細/共通/DB定義/開発規約・プロファイル。基本設計は理解・矛盾確認用 |
| 出力 | 対象project/srcs/方式ID/のソース・DDL・画面・ビルド手順、対象project/report/の入力記録・仕様ID対応・検査/試験/中断報告 |
| 書込み範囲 | agents/build-agent/と実行要求で指定したprojectのみ。project外の問題は報告だけ。ユーザーが範囲を狭めた場合はその指定を優先 |
| 除外入力 | spec-eval、別project、過去レポートの合格判定。評価期待値から実装を作らない |
| 禁止事項 | 上限/必須/権限/DB/方式の無断変更、未決事項の承認扱い、構造問題の推測補完、未生成の方式を実装済みとすること |

## 実行手順

1. 全体docsとagentsの役割定義を読み、projectId、工程、方式一覧、出力先、許可/除外パス、実行IDを確定する。存在しないprojectを自動作成しない。
2. `node agents/build-agent/scripts/preflight.mjs --project <projectId> --run-id <実行ID>` をリポジトリから実行する。新規の実行IDを使い、reportの既存記録を上書きしない。終了コード2は構造問題による中断、1は検査自体の失敗、0は機械的構造検査の通過だけを意味する。
3. 自動検査とは別に、各方式の詳細・共通・DB・規約の入出力、型、状態、認証、正規化、保存/取消境界の整合性を確認する。初回に読んだ仕様のハッシュを固定し、他Agentが入力を変更した場合は旧版と混在させず再検査する。
4. 局所バグは下記基準に従って仕様と必要な関連資料を修正し、変更前後の版/ハッシュ・理由をreportへ記録して再検査する。構造問題は修正せず、reportへ根拠を保存して全方式の生成を中断する。
5. 構造問題がなくなった入力セットから、各方式の規約どおりのプロジェクト・実ソース・DDL・設定例・画面資源をsrcs/方式ID/へ生成する。別方式のUIで代替せず、既存成果物を無断で削除しない。入力仕様IDと実装ファイル/シンボルの対応を保存する。
6. 利用可能な処理系でコンパイル/単体検査を行う。DB実行・実機試験はユーザーの指示と利用可能な環境に従う。処理系/接続/認証アダプターがない場合も可能なソース生成を進め、未実施を方式ごとに区別する。秘密情報や本番データを作成物へ埋め込まない。
7. 新しい実行結果をreportへ記録し、生成・ビルド・単体・結合・実機・逆生成・採点を別状態で報告する。最後に `node agents/build-agent/scripts/manifest.mjs --project <projectId> --run-id <事前検査の実行ID>` で入力ハッシュを再照合し、出力ソース・変更文書の版とSHA-256を保存する。事前検査後に入力が変わった場合は失敗とし、新規実行IDで再検査する。manifestは検査合格や未生成部分の完成を意味しない。

## 問題の分類と中断

局所バグは、同じ入力セットから正しい値が一意に確定する誤字・単独の誤記・参照先の誤記等。修正が業務判断、共有契約、仕様階層や複数方式の再設計を要求しないことを確認する。正本が衝突している場合に片方を恣意的に採用しない。

構造問題は、章/メタ情報/表構造の不一致、必要な定義や入出力契約の欠落、詳細・共通・DB間で両立しない型/状態/責務、実装入力だけでは閉じない参照等。reportに問題ID、現行版、ファイル/行、相反する記載、影響方式、再開条件を記録し、中断する。別Agentによる修正を待つ。中断中に仮のアプリや動作しない骨組みを完成品として生成しない。

稼働前の運用留保や処理系の未導入だけを仕様の構造問題にしない。共有docs・他Agent等に問題があっても許可なく変更せず、選択project/reportへ報告する。

## 完了条件

指定された資料から追跡可能な成果物を作り、未確認・未決・矛盾を報告する。形式合格を実装/ビルド/試験/採点の合格とみなさない。所属プロジェクト外を書き換えず、版と根拠を記録する。全体規則は../../docs、プロジェクト固有の長さ・DB・受入条件は選択projectの入力セットに従う。
