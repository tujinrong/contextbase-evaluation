# 業務Web画面設計ルール ― HTMLレイアウト設計書

版：1.0 / 日付：2026-10-29 / 工程：設計 / 規則ID：`D-*`

## 1. 適用範囲と責任の分離

**D-001 必須**：特定業務の項目・文言・固定座標を標準に含めない。共通ルール、画面パターン、プロジェクト差分で構成する。

**D-002 必須**：設計書の主成果物をHTMLとする。文章だけ、スクリーンショットだけ、画像を埋め込んだだけのHTMLでは不可。実際の見出し・表・入力欄・ボタン・ナビゲーションでレイアウトを再現する。

**D-003 必須**：設計工程では「何を、どこに、どの順序で、どう操作するか」を定義する。本番のDB/API、認証、フレームワーク、トランザクション実装とは分離する。デモの保存成功表示を本番機能の完成根拠にしない。

**D-004 必須**：セキュリティ・データ保全上の制約、確定業務要件、正式な既存規約を優先する。本標準の提案値と競合した場合は差分を記録する。既存修正で保存方式や削除範囲を無断変更しない。

規則の強さ：**必須**は未充足を報告、**標準**は理由付きで変更可能、**条件付き**は該当機能に適用する。未知事項を仮定と区別する。

## 2. 設計工程の成果物

| 成果物 | 必須内容 |
|---|---|
| サイトマップ | 機能グループ、メニュー名、画面ID、URL方針、利用権限 |
| 画面一覧 | 画面ID、目的、主要パターン、補助パターン、主操作、設計状態 |
| 遷移表 | 起点、操作、遷移先、持ち越す検索条件、未保存時の扱い |
| HTMLレイアウト | 本番に近い配置・文字・寸法、共通サイトメニュー、主要状態の表示 |
| 画面仕様 | 項目、一覧列、操作、状態、保存契約、例外、受入条件 |
| 差分・未決事項 | 版、変更点、仮定、確認が必要な事項 |

**D-005 必須**：各HTML画面に「設計注記」を用意し、業務UIと視覚的に分離する。注記は折りたたみ可能とし、本番のメニューや入力項目へ混ぜない。

**D-006 標準**：設計HTMLを`design/index.html`と画面別HTMLに分ける。小規模では1ファイル内のハッシュ遷移で代替してよい。ブラウザーで開くだけで確認できる方式を優先する。

**D-007 必須**：HTML内のリンク・操作について、`試作動作あり／状態表示のみ／対象外`を明記する。デモ対象のボタンは反応するようにする。業務処理の未実装を黙って成功表示しない。

## 3. 「Webらしい業務画面」の定義

**D-010 必須**：独立した「メニュー画面へ戻る」ことを操作の前提にしない。認証後は全ページ共通のサイトナビゲーションを提供する。ログイン等の公開画面は例外。

**D-011 標準**：基本構成は「共通ヘッダー＋左サイトメニュー＋本文」。機能数が少なく横幅に収まるサイトは上部メニューでもよい。全機能の上部メニューと同内容の左メニューを重複させない。

**D-012 必須**：メニューには現在位置を示す。利用者・組織・ログアウトはヘッダーの利用者領域へ配置する。サイトメニューには業務機能を、ページ内タブには同一対象の情報分類を配置する。

**D-013 標準**：ホームは未処理事項、最近利用した対象、業務状況等の入口にする。大きな遷移ボタンだけのメニューページを標準生成しない。ホームが不要なら主一覧を初期ページにする。

**D-014 必須**：移動はリンク、実行はボタンを基本とする。行の詳細・編集は名称リンクや行操作から直接開く。ラジオ選択＋離れた編集ボタンは、マスター選択等の必要性がある場合に限定する。

**D-015 必須**：詳細URLの直接表示、再読込、ブラウザーの戻る・進む、別タブ表示を設計に含める。画面遷移だけのために機密データや認証情報をURLへ入れない。

## 4. 領域、情報密度、レスポンシブ

**D-020 標準**：本文は「パンくず（必要時）→ページタイトル・主操作→条件／要約→主要情報→補助情報」の順とする。ページ内の主見出しは1つとする。

**D-021 必須**：読み取り、入力、一覧、確認等の目的で最大幅を変える。一覧は広く、編集は読みやすい幅に制限する。全画面を同一幅にせず、全項目を均等幅にしない。

**D-022 必須**：関連する入力と操作を近づける。固定座標、空白文字、改行、空の表セルで位置を合わせない。余白で情報を分類し、カードや枠の入れ子を増やしすぎない。

**D-023 標準**：フォームは1〜2列を基本とする。短い相互関連項目のみ3列以上を検討する。単に横幅が空いていることを理由に会社名・日付・人数等を不自然に離さない。

**D-024 必須**：狭い幅ではサイドメニューを折りたたみ、フォームを1列にし、操作列を折り返す。縦スクロールは許容する。全体の横スクロールや、文字の縮小で収めることを避ける。

**D-025 条件付き**：比較に必要な多列表は表領域内の横スクロールを許す。重要列を黙って非表示にしない。モバイル用カード表示を採用する場合も識別・状態・操作を維持する。

**D-026 必須**：固定ヘッダー／固定保存バーを使う場合、入力欄やフォーカスを隠さない。小さい高さ・ソフトキーボード表示時の配置を定義する。

**D-027 標準**：初期トークンは`06_ui_tokens.css`を使う。設計で寸法を変えたらトークンの変更案として記録し、画面単位の例外値を散在させない。

## 5. 検索・一覧・ページング

**D-030 必須**：一覧の設計に次を含める。

| 設計項目 | 標準方針 |
|---|---|
| 条件 | よく使う条件を前面、まれな条件を詳細検索へ |
| 実行 | 入力中条件と適用済み条件を区別。検索ボタン方式を初期値とする |
| クリア | 初期値に戻して1ページ目を再検索。例外は明記 |
| 新規作成 | 一覧ヘッダーの主操作 |
| 単一行操作 | 名称リンク／行末の参照・編集。ホバーしなくても分かる |
| 複数行操作 | 必要な場合だけチェックボックスと選択件数を表示 |
| 列 | 識別情報と状態を優先。日付・数値は必要幅、名称は可変幅 |
| 空結果 | 「該当なし」と条件解除等の次の操作を示す |

**D-031 必須**：増加する業務データの一覧にはページング方針を定義する。初期値は20件、選択肢20／50／100件。上限件数が小さい固定一覧は省略可。無限スクロールを標準にしない。

**D-032 必須**：件数が確定する一覧は「全157件中21〜40件」「2/8ページ」のように表示する。総件数不明時は件数・総ページ数を捏造せず、前後移動と既知の表示範囲を示す。

**D-033 必須**：検索条件、並び順、ページサイズ変更時は原則1ページ目へ戻す。ページ移動だけでは検索条件・並び順を保持する。削除でページが空になった場合は有効なページへ移る。

**D-034 必須**：先頭・末尾ページ、0件、1ページだけの場合を定義する。不要な番号の羅列を避け、多数ページは省略表示にする。ページャーは下部を基本とし、長い一覧では上部にも配置する。

**D-035 必須**：検索結果に適用した条件・件数・並び順を表示と一致させる。編集中の条件のまま旧結果が残る場合、「条件未適用」を示す。

**D-036 条件付き**：一括操作は「現在ページの選択」「ページをまたぐ選択」「検索結果全件」を区別する。デフォルトは現在ページ内選択。ページ変更で解除する旨を示す。

**D-037 条件付き**：出力範囲を「現在ページ／検索結果全件／選択行」として明示する。ページングを追加しても、仕様なしに出力対象を現在ページへ変えない。

## 6. 入力、保存、明細

**D-040 必須**：新規・編集・参照モードと対象識別情報を表示する。必須、形式、単位、空欄の意味を設計する。必須項目や業務上限を推測で追加しない。

**D-041 必須**：保存契約を先に決める。

| 契約 | 記載内容 |
|---|---|
| 保存方式 | 明示保存／自動保存／行単位／なし |
| 保存単位 | 項目、対象1件、親子全体、選択行等 |
| 確定時期 | 最終保存、行確定、段階確定等 |
| 破棄範囲 | 未保存の追加・更新・削除のどこまで戻すか |
| 失敗・競合 | 入力保持、部分成功、再試行、最新データとの差分 |
| 離脱 | サイトメニュー、タブ、対象切替、戻る、再読込、閉じる |

**D-042 標準**：明示保存の場合、現在入力中の明細も最終保存に含める。利用者が「反映」を押し忘れただけで内容が捨てられる二重確定を標準にしない。二段階確定が業務上必要なら、対象と未反映状態を明示する。

**D-043 必須**：「戻る」「変更を破棄」「条件クリア」「再読込」を区別する。保存失敗時は入力を保持し、そのまま離脱させない。変更がない移動には不要な確認を出さない。

**D-044 条件付き**：アプリ内の未保存離脱では「保存して移動／破棄して移動／編集を続ける」を設計する。ブラウザーを閉じる場面に同じ独自ダイアログが必ず出せると約束しない。実装上の制約は実装規約に従う。

**D-045 必須**：破壊的操作は対象・影響を説明する。確認ボタンを「削除する」等にし、通常の保存ボタンと見分ける。削除を初期フォーカスや既定Enter動作にしない。

## 7. 画面仕様とHTML注記の書式

**D-050 必須**：画面ごとに以下を記載する。

```yaml
screen_id: SCR-001
name: 対象一覧
pattern: P02_SEARCH_LIST
subpatterns: []
route: /records
purpose: 条件に合う対象を探し参照・編集する
primary_action: 新規作成
roles: [業務仕様で定義]
selection: none
pagination: {mode: numbered, page_size: 20}
save_contract: none
states: [initial, loading, ready, empty, error, forbidden]
fields: [F-001, F-002]
actions: [A-001, A-002]
acceptance_tests: [AT-001, AT-002]
open_questions: []
```

項目表：`項目ID／表示名／型／表示・入力形式／必須条件／上限／初期値／権限／エラー`。
列定義：`列ID／意味／書式／幅区分／整列／折り返し／並べ替え／リンク／機密区分`。
操作表：`操作ID／文言／対象／有効条件／結果／遷移／失敗／確認／キーボード`。

**D-051 必須**：画面要素に`data-screen-id`、`data-field-id`、`data-action-id`等を付け、設計とテストから照合できるようにする。命名自体はプロジェクト規約に統一してよい。

**D-052 必須**：主要画面は通常、長い値、0件、エラー、未保存を用意する。状態切替用ツールは「設計確認用」と明記する。

## 8. 設計レビューの合格条件

- **D-Q01**：どのページでも業務機能へ移動でき、現在位置が分かる。
- **D-Q02**：タイトル・対象・主操作が明確で、関連項目が近接している。
- **D-Q03**：検索、ページング、選択、並べ替え、出力の対象範囲が矛盾しない。
- **D-Q04**：入力、保存、取消、離脱、競合・通信失敗の扱いが定義されている。
- **D-Q05**：狭い幅・長い値でも主要操作に到達し、文字を縮小して無理に収めない。
- **D-Q06**：実装すべき動作と、設計HTMLのデモ動作・未実装を区別できる。
- **D-Q07**：設計ID、受入条件、未決事項があり、実装担当が推測せずに着手できる。

結果は「適合／不適合／未検証／対象外」で記録する。設計合意は本番動作検証やアクセシビリティ適合の証明ではない。

## 9. 他パターンへの展開

`03_pattern_catalog.md`から主パターンを選ぶ。承認、取込、帳票等を無理に検索一覧の型へ押し込まない。新パターンは目的、領域、主操作、状態、保存契約、狭幅対応、受入条件を同じ書式で追加する。
