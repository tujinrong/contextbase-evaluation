# AI向け業務画面作成・修正ルール

- バージョン：1.0
- 作成日：2026-10-29
- 対象：Accessを含むデスクトップ業務アプリ、およびWeb業務アプリ
- 目的：特定の画面や業務項目に依存せず、配置・操作・保存・完成判定を統一する。
- 位置付け：プロジェクト用の初期規約。記載の寸法は推奨初期値であり、公的規格や製品の必須仕様ではない。

> AIは「共通ルール」と「指定された画面タイプの追加ルール」を組み合わせて適用する。異なるタイプの画面を、無理に同じレイアウトにしない。

---

## 1. 適用方法と優先順位

### 1.1 依頼時に指定する情報

最低限、`platform`、`screen_type`、画面の目的を指定する。既存画面の修正では、変更可能な範囲も指定する。

```yaml
platform: Access                  # Access / Web / Desktop / Other
screen_type: SEARCH_LIST           # 画面タイプは第2章を参照
purpose: 対象データを検索し、選択したデータを参照・編集する
operation: modify                 # create / modify
change_scope: layout_only         # layout_only / ui_behavior / data_logic
traits: [export]                  # 必要な追加特性だけ指定する
selection_mode: single            # none / single / multiple
save_mode: none                   # none / explicit / automatic / per_item / undecided
save_unit: null                   # 保存対象の単位。不要ならnull
minimum_client_area: undecided    # 画面内の有効領域。モニター解像度とは区別する
display_scales: [100, 125, 150]    # 確認対象の表示倍率（%）
density: normal                   # normal / compact / touch
existing_standard: null           # 既存の規約・共通フォーム・部品がある場合に指定
business_constraints: []          # 必須項目・権限・保存方式など、確定済みの業務制約
```

`traits`の例：`editable_rows`（一覧内編集）、`bulk_action`（一括操作）、`import`、`export`、`long_running`（長時間処理）、`destructive`（削除等）、`sensitive_data`（機密情報）。

これは依頼用の記述形式であり、そのまま実行する設定ファイルではない。

### 1.2 規則の強さ

- **必須**：原則として省略不可。実装上の制約がある場合は、理由・代替策・未解決リスクを報告する。
- **標準**：初期値として適用する。明示要件や実データに合わない場合は、理由を記録して変更する。
- **条件付き**：該当する画面タイプ・機能・利用環境にだけ適用する。

優先順位は、セキュリティ・権限・データ保全上の制約、明示された業務要件と変更範囲、既存の正式規約、本ルール、AIの仮定の順とする。競合がある場合は、都合のよい解釈で黙って解消しない。

### 1.3 情報不足と変更範囲

**G-01［必須］** 不足情報は「確認済み」「仮定」「未確認」に分ける。画面画像から、保存処理・入力制約・権限・実際の動作を推測して確定しない。

**G-02［必須］** 既存画面の修正で範囲が未指定の場合は、`layout_only`として扱う。データ構造、保存時期、検索条件の意味、削除範囲、外部連携、権限を無断で変更しない。

**G-03［必須］** `layout_only`で操作上の問題を発見した場合は、レイアウトの修正と、別途必要な仕様変更の提案を分離する。ラベル変更によって実際とは異なる操作結果を約束しない。

**G-04［標準］** 未指定の見た目は「デスクトップ利用・通常密度・プラットフォーム標準テーマ」とする。表示領域が未指定の場合は、1280×720論理ピクセル相当の有効領域を暫定設計基準とし、対応保証には使わない。

**G-05［必須］** 新規の編集画面で保存方式が未確定の場合は、`undecided`とする。方式を提案しても、未確定のまま「保存・取消まで完成」と報告しない。軽微な配置の判断は仮定を明記して進めるが、データ消失につながる仕様を推測で補わない。

## 2. 画面タイプの指定

主となるタイプを一つ選び、追加機能は`traits`で指定する。複合画面では、領域ごとに補助タイプを指定してよい。

| タイプ | 用途 | 標準構成 |
|---|---|---|
| `AUTH` | ログイン・本人確認 | サービス識別 → 入力 → 主操作 → 補助操作 |
| `HOME` | メニュー・業務入口 | 画面識別 → 業務別の入口 → 補助情報 |
| `SEARCH_LIST` | 検索・一覧・対象選択 | 検索条件 → 件数・一覧 → 対象操作 |
| `DETAIL` | 読み取り専用の詳細 | 対象識別 → 情報グループ → 関連操作 |
| `EDIT_FORM` | 新規登録・編集 | 対象・モード → 入力グループ → 保存・戻る |
| `MASTER_DETAIL` | 一覧と選択対象の詳細を同時表示 | 対象識別 → 一覧＋詳細 → 全体操作 |
| `WIZARD` | 手順を分けた入力・設定 | 手順表示 → 現在の入力 → 戻る・次へ・確定 |
| `DASHBOARD_REPORT` | 集計・状況確認・帳票確認 | 条件・基準時点 → 指標・表・図 → 出力 |
| `SETTINGS` | システム・利用者設定 | 適用範囲 → 設定項目 → 適用・保存・戻る |
| `DIALOG` | 確認・簡易入力・警告 | 目的・対象 → 必要情報 → 選択肢 |

該当しない場合は独自タイプを定義し、目的、領域構成、主操作、離脱時の動作を明記する。無関係なタイプの要素を機械的に追加しない。

## 3. 共通の寸法・文字・色

### 3.1 設計トークン

**V-01［標準］** 次の初期値を共通定義として使用する。部品ごとに似た数値を個別に設定しない。WebとAccessの値は、それぞれの初期値であり、厳密な換算対応ではない。

| トークン | Web・論理ピクセルで設計する場合 | Accessの場合 |
|---|---:|---:|
| 基本間隔 `U` | 4 CSS px | 0.1 cm |
| コンテンツ外周余白 | 6U | 6U |
| ラベルと入力欄の間隔 | 2U | 2U |
| 同じ操作グループのボタン間隔 | 2U | 2U |
| 入力行の間隔 | 3U | 3U |
| 異なるグループ間の間隔 | 6U | 6U |
| 通常の一行入力欄の高さ | 8U | 8U |
| 通常ボタンの高さ | 9U | 9U |
| 本文文字サイズ | 16 CSS px | 11 pt |
| 画面タイトル文字サイズ | 24 CSS px | 16 pt |

その他のプラットフォームでは、標準部品と表示倍率を考慮して対応値を一度定義する。`compact`や`touch`では画面単位で値を変更し、部品ごとに密度を混在させない。

**V-02［必須］** 文字や部品が収まらない場合は、列構成、幅、折り返し、領域分割を見直す。文字を小さくして収めることを第一の解決策にしない。使用する日本語フォントで、文字欠けがないことを確認する。

**V-03［標準］** ボタンは「通常幅」「長いラベル用幅」などの共通サイズを定義し、同じ役割には同じサイズを使う。異なる長さの名称を同一幅に押し込まない。表内の小型操作などは、用途別の別サイズとして定義する。

**V-04［必須］** 色だけで必須、選択、エラー、警告を伝えない。文字、記号、状態ラベルなどを併用する。選択色は、背景色そのものではなく、文字と選択状態の判別可能性で評価する。

**V-05［標準］** 強調色は主操作、状態色は警告・エラー等に限定する。プラットフォーム標準のフォーカス、選択表示、ハイコントラスト設定を不必要に壊さない。

## 4. 共通の構成・整列・余白

**L-01［必須］** 画面名または目的が分かる見出しを設ける。親画面やウィンドウ枠で明確に示されている場合は、同じ大見出しを重複させる必要はない。

**L-02［必須］** 特定データを参照・編集する画面は、識別番号と名称など、取り違えを防ぐ情報を表示する。タブ切り替えや主要な編集操作の間も、対象が分かる状態を維持する。

**L-03［標準］** 「画面・対象の識別」「条件または入力」「結果または詳細」「操作」の領域を分ける。無関係な機能を空いている場所へ追加しない。

**L-04［必須］** 入力・結果と、それに作用するボタンを近接させる。条件操作は条件領域、選択対象の操作は一覧領域、画面全体の操作は共通フッター等に配置する。

**L-05［必須］** 共通の列境界と行基準を定義する。同じ列の左端、同じ行の上端または縦中心を揃える。意図のない微妙なずれを残さない。

**L-06［標準］** 同一グループ内の間隔は、異なるグループ間より狭くする。枠線を増やす前に、見出しと余白でグループを表現する。

**L-07［必須］** 画面内でラベル配置を統一する。上置き、左置きなどは領域単位で選択してよいが、同じ領域内では理由なく混在させない。

**L-08［必須］** 空白をなくす目的だけで入力欄を伸ばさない。一方、右側に余白があるのに重要な情報が切れる配置は見直す。余白の面積ではなく、識別・入力・操作への支障で評価する。

**L-09［標準］** コンパクトな単一目的画面は横中央にまとめる。多項目の業務画面は、左揃えのグリッドや最大幅付き領域を使用してよい。全タイプの中央寄せを強制しない。

## 5. 入力項目と表示内容

**F-01［必須］** 同じ用途・同じ想定桁数の入力欄は、原則として同じ幅とする。すべての入力欄を同じ幅にはしない。

**F-02［標準］** 項目を「短い固定長」「中程度の文字列」「長文」に分類する。番号、日付、数量には適切な固定幅を使い、名称、説明、備考には残りの幅を優先配分する。

**F-03［必須］** 長い入力値は、欄内スクロール、折り返し、詳細表示等により全文を確認・編集できるようにする。入力上限と表示幅を混同しない。

**F-04［必須］** ラベルは、入力する対象が分かる名称にする。形式、単位、基準日、空欄の意味が自明でない項目には補足を付ける。補足をプレースホルダーだけに依存させない。

**F-05［条件付き］** 必須項目、読み取り専用、権限による編集不可を判別できるようにする。必須条件や初期値は業務仕様に従い、推測で追加しない。

**F-06［必須］** 項目の性質に合う部品を選ぶ。相互排他的な少数選択、複数選択、自由記述、年月、数量を同じ部品で済ませない。ただし、レイアウト限定の修正では入力仕様を無断で変えない。

**F-07［条件付き］** 入力エラーは、対象項目、理由、直し方が分かる内容で表示する。入力済みの値を保持し、該当項目へ移動できるようにする。

**F-08［必須］** 値なし、ゼロ、未設定、該当なし、不明を混同しない。日付・数値・通貨・識別子の表示形式を統一し、必要な先頭ゼロを維持する。

## 6. 一覧とマスター・詳細

**T-01［必須］** 一覧の見出しとデータの列境界を合わせる。別々に描画する場合も、列幅の定義を共有する。

**T-02［必須］** 列幅は内容に応じて配分する。固定長列を必要以上に広くしない。名前や件名など、対象を識別する列を、装飾や余白のために圧迫しない。

**T-03［必須］** 重要な識別情報が省略される場合は、詳細領域、行展開等で全文を確認できるようにする。マウスホバーだけを唯一の確認手段にしない。

**T-04［標準］** 一覧の高さと周辺ボタンの位置は、検索件数だけで変えない。件数が少ないときも安定した配置を維持し、件数が多いときはスクロール・ページ切り替え等で対応する。

**T-05［必須］** 検索済み件数と、表示中の範囲を必要に応じて示す。「未検索」「0件」「取得失敗」を区別する。条件変更後の旧結果を残す場合は、未適用の条件であることを明示する。

**T-06［条件付き］** 単一選択・複数選択を明示する。複数選択では選択件数と、一括操作の対象範囲を表示する。ページをまたぐ選択や「全件選択」の意味を曖昧にしない。

**T-07［必須］** 対象未選択時は、選択を必要とする操作を無効化または適切に制限する。二重クリックや右クリックだけに重要操作を隠さない。

**T-08［条件付き］** マスター・詳細画面は、識別に必要な一覧幅と、入力に必要な詳細幅から配分を決める。一定の比率を全画面に強制しない。最小幅を両立できない場合は、上下配置や別画面遷移を検討する。

**T-09［必須］** 一覧の選択対象と、詳細の表示・編集対象を常に一致させる。選択切り替えで編集中の値が別対象へ反映されたり、黙って消えたりしないようにする。

## 7. 操作名称・保存・取消・削除

**A-01［必須］** ボタン名から、対象と結果を判断できるようにする。「実行」「処理」「反映」だけの名称は、周辺の文脈で対象と結果が明確な場合に限る。

**A-02［標準］** 同一操作領域の主操作は原則一つとし、補助操作と区別する。保存等の確定、戻る等の遷移、削除等の破壊的操作を区別して配置する。削除を既定のEnter操作にしない。

**A-03［必須］** 新規作成の前に、保存に関する次の契約を定義する。既存修正では、現行の契約を確認する。

| 定義項目 | 明確にする内容 |
|---|---|
| 保存方式 | 明示保存、自動保存、行・項目単位の保存、保存なし |
| 保存単位 | 単一項目、1レコード、親子データ全体など |
| 確定タイミング | ボタン、フォーカス移動、行移動、画面離脱など |
| 未保存の範囲 | 追加・変更・削除のどこまでを保持するか |
| 取消の範囲 | 直前入力、対象レコード、画面全体の変更など |
| 失敗時の扱い | 全体取消、部分成功、再試行、競合時の扱い |

**A-04［条件付き］** 明示保存方式では、入力中の項目を含めて保存対象に取り込む。中間の「反映」を押し忘れたために、最終保存で内容が黙って欠落する構成を避ける。

**A-05［条件付き］** 二段階の確定が必要な場合は、それぞれの対象と確定範囲を明示する。未反映の内容がある場合は、最終保存時に取り込み、確認、または明確なエラーを行う。

**A-06［条件付き］** 自動保存方式では、保存中・保存済み・失敗を表示する。「戻る」や「閉じる」が変更破棄を意味すると誤解させない。取り消せる範囲だけを約束する。

**A-07［必須］** 未保存の変更を失う可能性がある遷移で保護を行う。変更がない場合や変更を保持する遷移で、不要な確認を繰り返さない。

明示保存方式で画面を離れる場合の標準選択肢は、「保存して移動」「破棄して移動」「編集を続ける」とする。実装できない選択肢を表示しない。保存失敗時は移動せず、入力を保持する。

**A-08［条件付き］** 削除・上書き・一括更新は、対象と影響範囲を示す。復元困難または影響が大きい処理は実行前に確認する。低リスクで復元可能な処理は、仕様に応じて取り消し機能を使ってよい。

**A-09［必須］** 確認ボタンは「削除する」等、結果を示す名称にする。曖昧な「はい／いいえ」だけに依存しない。

**A-10［条件付き］** 二重送信・二重登録を防止する。処理中は状態を示し、必要な操作を制限する。キャンセルできない処理を、停止できるように見せない。

**A-11［条件付き］** 親子データや複数レコードの保存では、全体成功が必要か、部分成功を許すかを定義する。部分成功を全件成功として通知しない。

**A-12［必須］** 「条件クリア」「初期値に戻す」「変更を破棄する」「検索へ戻る」を混同しない。戻す対象、戻し先、再検索の有無を決め、名称と動作を一致させる。

## 8. 状態・キーボード・安全性

**I-01［条件付き］** 初期、処理中、正常、空結果、未選択、編集あり、入力エラー、処理失敗、権限不足など、実際に起こる状態を設計する。通常時の画像だけで完成判定しない。

**I-02［必須］** Tab順序を見た目の操作順序と一致させる。主要操作をキーボードで行え、フォーカス位置を判別できるようにする。読み取り専用情報の確認・コピーも不要に妨げない。

**I-03［必須］** Enter、Esc、ショートカットの動作を定義する。複数行入力の改行を妨げず、Escで無警告の変更破棄を行わない。ダイアログを閉じた後は、適切な元の位置へフォーカスを戻す。

**I-04［必須］** エラーや警告は、何が起きたか、何が保存されたか、次に何をするかが分かる内容にする。通常利用者向け画面へ秘密情報や不要な内部情報を表示しない。

**I-05［条件付き］** パスワード等は適切に伏字化し、画面・ログ・サンプルへ実際の認証情報を埋め込まない。ボタンの非表示・無効化だけを権限制御の代わりにしない。

**I-06［条件付き］** 一括処理、取込、出力、長時間処理では、対象範囲、実行状態、成功・失敗件数、結果の確認方法を示す。分からない進捗率や残り時間を架空の数値で表示しない。

## 9. サイズ変更とプラットフォーム適用

**R-01［必須］** モニターの物理解像度、Windows等の表示倍率、アプリの有効表示領域を区別する。タイトルバー、リボン、ブラウザー枠等を含む寸法だけで、フォームが収まると判断しない。

**R-02［必須］** 最小の対象環境で、文字欠け、重なり、操作不能を発生させない。フォーム全体の横スクロールは原則不要とする。多列データ表の局所的な横スクロールは、必要性を明示して許容する。

**R-03［標準］** 広い画面では一覧、長文、説明等を優先して伸ばす。番号、数量、日付まで無制限に引き伸ばさない。狭い画面では折り返しや縦配置へ切り替え、入力内容を消さない。

**R-04［必須］** 保存・戻る等の主要操作へ到達できるようにする。固定フッターで入力欄を隠さない。長いフォームでは縦スクロールを許容し、全項目を一画面に押し込まない。

**R-05［必須］** 対象環境で使う表示倍率を確認する。未確定の場合は100％・125％・150％を確認候補とする。確認していないサイズ・倍率まで対応済みと報告しない。

### Accessの場合の追加確認

**P-01［条件付き］** フォームの表示方式、フォーム幅、各セクションの高さ、スクロール設定、ポップアップ等の使用方針を明示する。最大化だけで配置調整を済ませたとみなさない。

**P-02［条件付き］** コントロールの位置・幅・高さと、アンカー・レイアウトによる伸縮を確認する。サブフォーム、タブ、一覧の内部も確認し、外側だけ整えて完了にしない。

**P-03［条件付き］** 連結・非連結などのフォーム構成に応じて、入力値がいつ確定するかを確認する。ボタン押下だけでなく、レコード移動、対象切り替え、フォーム終了等の経路も試験する。

**P-04［条件付き］** 「保存前は未確定」「取消で全体を破棄」などの要件は、ボタン名称ではなく実際のデータ状態で検証する。必要に応じて編集用データ、作業領域、トランザクション等を検討し、採用方式と取消可能範囲を記録する。

**P-05［条件付き］** レコードセレクター、移動ボタン、標準メニュー等を残す場合は、独自操作との整合性を確認する。非表示にする場合も、必要な機能への別の入口を確保する。

Web・その他のデスクトップ環境では、同じ目的を満たすレイアウト・フォーカス・保存方式へ読み替える。Access固有のプロパティ名を他環境にそのまま要求しない。

## 10. 画面タイプ別の追加ルール

### AUTH：ログイン・本人確認

- 入力と主操作を小さな一つの領域にまとめ、横中央を標準とする。
- 入力欄の幅は同一グループ内で揃え、操作までの距離を短くする。
- 終了、ヘルプ等の補助操作を主操作と区別する。
- 認証失敗、処理中、利用不可の表示を用意する。未指定の認証機能を勝手に追加しない。

### HOME：メニュー・業務入口

- 業務目的で分類し、似た操作名を無関係な位置に分散させない。
- 利用頻度と業務順序で入口を整理する。
- 権限による利用可否を反映し、利用できない理由の表示方針を統一する。
- 終了・ログアウトを、通常の業務開始操作と区別する。

### SEARCH_LIST：検索・一覧

- 検索条件、検索操作、検索結果、選択対象への操作を分離する。
- 条件初期値、検索実行のタイミング、条件クリア後の動作を定義する。
- 件数・選択状態を表示し、新規作成と選択データへの操作を区別する。
- 出力する場合は、全件、検索結果、選択行、現在ページのどれを対象にするか明示する。

### DETAIL：読み取り専用の詳細

- 編集画面と見分けられる表示にし、編集不能の入力欄を大量に並べる方式だけに頼らない。
- 対象識別情報と、関連情報への導線を明示する。
- 長文・識別子の確認やコピーを可能にする。
- 編集操作がある場合は、権限と対象が明確な入口を設ける。

### EDIT_FORM：新規登録・編集

- 新規・編集のモードと対象を表示する。
- 入力項目を業務上のまとまりで分類し、保存方式を定義する。
- 必須・任意・読み取り専用を区別する。
- 入力検証、保存失敗、未保存離脱を含めて設計する。

### MASTER_DETAIL：一覧＋詳細

- 一覧と詳細の選択対象を一致させる。
- 詳細を編集中に別行へ移動した場合の動作を定義する。
- 明細の追加・変更・削除と、全体保存の関係を明確にする。
- 幅不足の場合は、比率固定ではなく、上下配置や画面分離を検討する。

### WIZARD：段階的な入力

- 現在の手順、全体の手順、次の操作を表示する。
- 前の手順へ戻っても入力内容を保持する。
- 最終確定と手順移動を区別し、途中離脱時の保存範囲を定義する。
- 不可逆な処理の前に、必要な対象・結果を確認できるようにする。

### DASHBOARD_REPORT：集計・帳票確認

- 対象期間、フィルター、単位、集計の基準時点を表示する。
- ゼロ、データなし、未取得、取得失敗を区別する。
- 表や図の表示だけで重要情報を確認できるようにし、色やホバーのみに依存しない。
- 出力と画面表示の条件を一致させる。印刷専用レイアウトは操作画面と分けて定義する。

### SETTINGS：設定

- 個人設定、共有設定、全体設定などの適用範囲を明示する。
- 変更が即時反映か、保存後か、再起動後かを示す。
- 初期値への復元と、編集中の変更破棄を区別する。
- 広い範囲に影響する変更は、影響範囲と実行権限を明確にする。

### DIALOG：確認・簡易入力

- 一つの目的に限定し、対象と操作結果を簡潔に示す。
- ボタン名は、実行結果が分かる名称にする。
- 初期フォーカスと既定操作を決め、破壊的操作を不用意に既定にしない。
- 複雑な多項目入力や多段階の処理は、専用画面へ分離する。

## 11. 完成判定・テスト

### 11.1 合否基準

**Q-01［必須］** 次の表で、該当項目を「適合」「不適合」「未検証」「対象外」に分類する。「対象外」には理由を付ける。未検証を適合として扱わない。

| 確認項目 | 合格条件 |
|---|---|
| 画面・対象の識別 | 何の画面で、何を操作しているかを判別できる |
| 整列と寸法 | 共通トークンと列・行基準が使用され、意図しないずれがない |
| 文字と部品 | ラベル・操作名が欠けず、長い値は全文確認ができ、重なり・操作不能がない |
| 一覧の列と選択 | 見出しと列が一致し、対象を取り違えない |
| 操作名称 | ボタン名と実際の対象・結果が一致する |
| 保存と取消 | 定義した保存単位・確定時期・破棄範囲が実データと一致する |
| 画面離脱 | 未保存データを意図せず失わず、保存失敗時に誤って離脱しない |
| キーボード | Tab、Enter、Escと主要操作が仕様どおりに動作する |
| 状態表示 | 未検索、空結果、処理中、失敗等を区別できる |
| サイズ・倍率 | 対象の最小領域・表示倍率で主要操作に到達できる |
| 権限・機密情報 | 許可された操作だけが実行でき、秘密情報を不必要に表示しない |
| 変更範囲 | 許可された範囲外の業務仕様・データ処理を変更していない |

### 11.2 最低限の確認データと操作

**Q-02［必須］** 機能に応じて、次の境界状態を確認する。

- 一覧：未検索、0件、1件、表示可能行数を超える件数、未選択、対象削除後。
- 値：未入力、最大長付近の名称、複数行長文、ゼロ、負数、日付境界等のうち仕様上該当するもの。
- 編集：追加、変更、削除、別対象への切り替え、保存成功、入力エラー、保存失敗。
- 離脱：変更なし、変更あり、保存して戻る、破棄して戻る、編集継続、ウィンドウを閉じる。
- 再表示：保存または破棄の後、対象を再読込してデータが仕様どおりであること。
- 環境：対象サイズ・倍率、通常の入力方式、キーボード操作。

同時編集、通信切断、一括処理、取込・出力がある場合は、競合、途中失敗、再実行の扱いも確認する。

**Q-03［必須］** コード生成、ビルド成功、画像の目視確認、実機操作、データ再読込を区別して報告する。画像だけを見て「保存・取消・Tab順序も正常」と判断しない。

## 12. AIが提出する内容

**D-01［必須］** 作成・修正結果には、実施した範囲に応じて次の内容を含める。

1. **前提**：画面タイプ、目的、対象環境、変更範囲、確認済み事項と仮定。
2. **設計**：領域構成、共通トークン、主要な列幅・整列基準、主操作、サイズ変更方針。
3. **操作仕様**：対象選択、保存、取消、削除、未保存離脱、エラー時の動作。変更しない場合は現行仕様を維持すると記載する。
4. **成果物**：実装、設計仕様、変更差分など、依頼で求められたもの。
5. **検証結果**：適用ルールの適合状況、実施した試験、未検証項目、既知の問題。

**D-02［必須］** 問題報告は、次の形式を使用する。「バランスが悪い」「見づらい」だけで終わらせない。

```text
ルールID：
該当箇所：
確認した事実：
影響・リスク：
修正内容：
合格条件：
検証方法・結果：
```

**D-03［必須］** 未解決の重大問題がある場合は、部分完了として報告する。確認できていない事項を「問題なし」と表現しない。

## 13. 依頼に添える短い指示例

### 既存画面のレイアウトだけを修正する場合

```text
添付の「AI向け業務画面作成・修正ルール」に従って修正してください。

platform: Access
screen_type: SEARCH_LIST
operation: modify
change_scope: layout_only

既存の検索・保存・削除・権限の仕様は変更しないでください。
共通トークン、整列、列幅、関連操作の配置を見直してください。
操作仕様に問題がある場合は、レイアウト修正とは分けて提案してください。
実施した検証と未検証項目を報告してください。
```

### 新規の編集画面を作成する場合

```text
添付の「AI向け業務画面作成・修正ルール」に従って作成してください。

platform: Access
screen_type: MASTER_DETAIL
operation: create
change_scope: data_logic
save_mode: explicit
save_unit: 親データと、その配下の明細全体

項目定義、入力制約、権限は別途提示する業務仕様に従ってください。
保存までは画面内の変更を未確定として扱い、破棄で追加・変更・削除を戻せる方式を設計してください。
選択対象の切り替えと、未保存離脱時の動作を明確にしてください。
実装上の制約がある場合は、代替策と取消可能範囲を説明してください。
```

## 最終原則

**余白を減らすこと、部品を同じ幅にすること、すべてを一画面に収めることを目的にしない。利用者が対象を取り違えず、入力を失わず、操作結果を予測できることを優先する。**
